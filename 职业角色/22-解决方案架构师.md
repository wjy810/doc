# 解决方案架构师进阶全景手册

> 从回答客户“这个能不能做”，到设计出客户能落地、能负担、能长期运行的方案，再到让技术方案成为客户与团队共同的决策依据。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：需要面向客户设计与讲解技术方案的开发者、售前与交付团队中的技术负责人、准备转向解决方案架构岗位的工程师，以及希望系统提升的在职解决方案架构师。

解决方案架构师常见于云服务商、软件厂商、系统集成商与外包公司，也被称为售前架构师或解决方案工程师。他们理解客户的业务问题与现有环境，设计满足需求与约束的方案，用演示与概念验证证明关键部分可行，估算成本、工作量与风险，回答客户的技术与安全问题，并把方案交接给负责实施的团队。

解决方案架构师最大的考验，是同时对两方诚实：对客户，不为了赢得项目而夸大产品能力、低估成本与风险；对自己的团队，不把无法交付的承诺带回来。一个在售前阶段看起来漂亮、却在交付阶段处处碰壁的方案，代价最终由客户、交付团队和公司的信誉共同承担。

本手册先建立角色坐标，然后讲解需求发现、方案设计、非功能需求与架构评估、集成与迁移、演示与概念验证、成本与商业方案、方案呈现与决策；随后进入安全与合规、部署模式、可复用资产、AI 解决方案、交接与落地；最后说明与开发者的协作，并用连锁企业招聘管理系统的方案设计演示完整的过程。

主线是：**理解客户的业务问题与现状 → 澄清需求、约束与成功标准 → 设计并比较候选方案 → 验证关键假设 → 估算成本、工作量与风险 → 清楚地呈现并支持决策 → 交接给交付团队并跟踪落地。**

不同公司中，这些职责可能由解决方案架构师、售前工程师、技术顾问、客户架构师或交付团队的技术负责人承担，与销售、软件架构师、实施工程师的分工也各不相同。本手册描述解决方案架构的职责与方法；D1—D6 分级是学习组织方式，不对应任何职级体系或厂商认证。文中的数字均为示意。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 解决方案架构师负责什么

#### 01.1 在客户、售前与交付之间

| 阶段 | 解决方案架构师的工作 |
| --- | --- |
| 机会识别 | 判断客户的问题是否适合用我们的产品或服务解决 |
| 需求发现 | 调研业务问题、现有系统、约束与成功标准 |
| 方案设计 | 设计并比较候选方案，确定推荐方案 |
| 验证 | 演示、概念验证，回答技术与安全问题 |
| 商务支持 | 估算成本与工作量，支持报价与投标 |
| 交接 | 把方案、假设、承诺与风险完整地交给交付团队 |
| 落地跟踪 | 关注方案在交付中的偏差，把客户需求反馈给产品 |

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 需求发现记录 | 记录客户的问题、现状与约束 | 区分事实、假设与偏好 |
| 方案文档 | 说明推荐方案与理由 | 有候选方案的比较、关键决定与风险 |
| 架构图 | 让不同受众理解方案 | 层次清楚，标明边界与集成 |
| 概念验证报告 | 证明关键假设 | 事先定义的成功标准，结果可复现 |
| 成本与工作量估算 | 支持报价与客户的预算决策 | 有依据、有区间、包含长期成本 |
| 安全问卷应答 | 通过客户的安全审查 | 准确、可证明，不过度承诺 |
| 交接包 | 让交付团队接手 | 承诺、假设与风险完整 |

#### 01.3 职责边界与相邻角色

| 事项 | 解决方案架构师的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 商务关系与报价 | 提供技术依据 | 销售、客户经理 | 价格由商务负责 |
| 需求的详细分析 | 早期发现，之后交接 | 业务分析师 | 见[《业务分析师》](03-业务分析师.md) |
| 系统的长期架构 | 提供方案与约束 | 软件架构师、技术负责人 | 见[《软件架构师与技术负责人》](10-软件架构师与技术负责人.md) |
| 项目计划与交付 | 交接并支持 | 项目经理、交付经理 | 见[《项目经理与交付经理》](21-项目经理与交付经理.md) |
| 部署、配置与迁移 | 设计方案，支持实施 | 实施与交付工程师 | 见[《实施与交付工程师》](23-实施与交付工程师.md) |
| 上线后的价值实现 | 协作 | 客户成功 | 见[《客户成功与技术支持》](20-客户成功与技术支持.md) |
| 产品路线 | 提供客户需求与缺口 | 产品经理 | 不代替产品经理承诺路线 |

几组容易混淆的角色：

- **解决方案架构师与软件架构师**：软件架构师对一个系统的长期结构与演进负责；解决方案架构师面对多个客户与各自的现有环境，把产品与服务的能力与客户需求匹配起来，并对方案能否落地负责。
- **解决方案架构师与销售**：销售负责商务关系与成交；解决方案架构师负责方案在技术上的正确与可行。两者目标一致，但解决方案架构师需要在技术判断上保持独立。
- **解决方案架构师与实施工程师**：解决方案架构师设计方案；实施工程师在客户环境中部署、配置与迁移。很多小团队由同一人承担，但设计时要考虑实施的实际条件。

**本章练习**：回顾一个你参与过的客户项目，写出售前阶段的承诺与交付阶段的实际情况，列出两者的差异，并分析每一处差异是否可以在售前阶段发现。

<a id="ch02"></a>

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **业务理解**：客户的行业、业务流程、问题与成功标准。
2. **需求发现**：调研方法、现状分析、需求与约束的澄清。
3. **方案设计**：候选方案、取舍、标准化与定制的平衡。
4. **非功能与评估**：可用性、性能、安全、可运维与成本的设计与评估。
5. **集成与数据**：系统集成、身份集成、数据迁移。
6. **验证**：演示、概念验证与试点。
7. **商业方案**：总拥有成本、工作量估算、价值论证与投标。
8. **呈现与影响**：面向不同受众的沟通、评审与异议处理。
9. **安全与合规**：安全审查、问卷应答与合规要求。
10. **交接与资产**：交付交接、落地跟踪、参考架构与可复用资产。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 熟悉产品能力，协助演示与资料准备 | 演示环境、应答素材 |
| D2 独立完成 | 独立完成中小型客户的发现、方案与验证 | 方案文档、概念验证报告 |
| D3 负责结果 | 负责复杂客户或重要机会的方案，并对落地结果负责 | 方案落地记录、交接与复盘 |
| D4 系统与跨团队 | 设计跨多个产品与合作方的方案，协调多方 | 多方集成方案、合作方协作记录 |
| D5 方法与机制 | 建立组织的方案方法、参考架构与资产体系 | 参考架构库、方案评审机制 |
| D6 创新与影响 | 提出新的方案模式或行业方案并验证 | 行业方案、公开分享 |

#### 02.3 成长中的常见偏差

- 还没理解客户的问题，就开始介绍产品功能。
- 只设计一个方案，无法说明为什么它是最好的选择。
- 忽视非功能需求、集成与数据迁移，低估实施的难度。
- 为了赢得项目，承诺产品还不具备的能力。
- 估算只包含首年的费用，忽视长期运维与退出的成本。
- 交接时只给一份演示材料，关键假设与承诺没有记录。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 理解客户与发现需求

#### 03.1 业务问题先于技术

需求发现的第一个问题不是“需要什么功能”，而是“要解决什么业务问题”。常用的发现问题：

```text
现在遇到了什么问题？影响有多大？
如果问题解决了，会发生什么变化？怎样衡量？
为什么是现在？有没有时间节点？
现在是怎样处理的？尝试过哪些办法？
谁会使用？谁做决定？谁负责推动？
有哪些不能改变的约束（系统、预算、合规、组织）？
怎样判断这个项目成功了？
```

#### 03.2 现状调研

| 方面 | 调研内容 |
| --- | --- |
| 业务流程 | 现在的流程、参与的角色、痛点与例外情况 |
| 现有系统 | 系统清单、版本、负责人、接口能力 |
| 数据 | 数据在哪里、质量如何、量有多大、谁拥有 |
| 基础设施 | 云或自建机房、网络、安全策略、运维能力 |
| 组织 | 信息技术团队的能力、变更的接受程度 |
| 合规 | 适用的法规、行业要求、内部安全规定 |

#### 03.3 区分需求、约束、假设与偏好

| 类别 | 含义 | 示例 |
| --- | --- | --- |
| 需求 | 方案必须满足的 | 应聘者信息按门店隔离 |
| 约束 | 不能改变的条件 | 必须与现有人事系统对接 |
| 假设 | 当前相信为真、尚未验证的 | 人事系统提供可用的接口 |
| 偏好 | 客户希望但可以讨论的 | 希望使用某个云服务商 |

把假设明确写出来，并标出需要在什么时候验证。很多交付问题，来自售前阶段没有被验证的假设。

#### 03.4 识别决策流程

了解谁参与决策、按什么标准决策、决策的时间与流程。业务负责人关心价值与风险，信息技术负责人关心集成、安全与运维，采购关心成本与合同。方案需要回应每一方的关注。

**本章练习**：为一个客户机会完成需求发现记录，按需求、约束、假设与偏好分类，为每个假设写出验证方式与时间，并画出客户的决策流程。

<a id="ch04"></a>

### 04 方案设计

#### 04.1 从需求到关键质量属性

方案的结构往往由少数几个关键质量属性决定：可用性、性能、安全、可扩展、可运维、成本。识别它们，并尽量量化，例如“高峰期每天处理 2 万份申请”“门店店长在手机上 5 分钟内完成一批筛选”。质量属性的分类可参考 ISO/IEC 25010，见[《软件架构师与技术负责人》第 03 章](10-软件架构师与技术负责人.md#ch03)。

#### 04.2 设计并比较候选方案

至少准备两到三个候选方案，从同一组标准进行比较。下表是空白模板，17 章给出了填写示例：

| 标准 | 方案 A | 方案 B | 方案 C |
| --- | --- | --- | --- |
| 满足关键需求的程度 | | | |
| 实施时间与风险 | | | |
| 总拥有成本 | | | |
| 运维复杂度 | | | |
| 可扩展与演进 | | | |
| 对客户现有系统的影响 | | | |

比较的目的不是证明推荐方案完美，而是说明在客户的约束下，为什么它是更合适的取舍。

#### 04.3 标准化与定制化

尽量使用产品的标准能力与配置满足需求，定制开发只用于真正差异化的部分。每一项定制都会增加实施成本、升级难度与长期维护的负担。客户提出定制需求时，先了解背后的问题，看能否用标准能力或流程调整解决。

#### 04.4 方案文档与架构图

方案文档通常包括：背景与目标、需求与约束、候选方案的比较、推荐方案、架构图、集成、安全、部署与运维、实施计划、成本、风险与假设。架构图按受众分层：系统与外部的关系、主要组成部分、关键的集成流程。C4 模型提供了一套分层绘制架构图的方法。[B01](#ref-b01)

#### 04.5 记录关键决定

关键的方案决定用架构决定记录写下：背景、选项、决定与后果。[B02](#ref-b02) 这些记录在交接与之后的争议中都非常有用。

**本章验收**：为一个客户需求设计三个候选方案，按统一标准比较并给出推荐；完成方案文档与分层的架构图，记录至少三项关键决定，并请交付团队评审可落地性。

<a id="ch05"></a>

### 05 非功能需求与架构评估

#### 05.1 把非功能需求说清楚

| 方面 | 需要澄清的问题 | 量化示例 |
| --- | --- | --- |
| 可用性 | 允许多长的停机？哪些时段最关键？ | 工作时间可用性 99.9% |
| 性能 | 多少用户、多大的数据量、多快的响应？ | 高峰期第 95 百分位响应时间小于 1 秒 |
| 容量与增长 | 未来三年的增长预期？ | 门店从 120 家增长到 300 家 |
| 灾备 | 最多能丢失多少数据？多久必须恢复？ | 恢复点目标 15 分钟，恢复时间目标 4 小时 |
| 安全 | 数据敏感程度、访问控制、审计要求 | 按门店与角色隔离，操作全部留痕 |
| 运维 | 谁负责运维？运维团队的能力？ | 客户只负责账号管理，其余由交付方运维 |

恢复点目标指故障时最多可以接受丢失多长时间的数据；恢复时间目标指服务最多可以中断多长时间。两者越小，成本越高，需要与业务价值一起权衡。

#### 05.2 用架构框架做评估

主要的云服务商都发布了架构评估框架，可以作为检查方案的清单：

- AWS Well-Architected 框架包括卓越运营、安全、可靠性、性能效率、成本优化与可持续性六个支柱。[B03](#ref-b03)
- Azure Well-Architected 框架包括可靠性、安全、成本优化、卓越运营与性能效率五个支柱。[B04](#ref-b04)
- Google Cloud Well-Architected 框架同样按六个支柱组织建议，并提供面向特定行业与技术的视角。[B05](#ref-b05)

即使方案不部署在这些云上，这些框架中的问题也适用于大多数系统。

#### 05.3 容量估算

用简单的计算检验方案的可行性，例如（示意）：

```text
高峰期每日申请 20000 份，集中在 10 小时内
平均每秒约 0.6 份；按高峰系数 5 估算，峰值约每秒 3 份
每份简历的分析平均耗时 8 秒
峰值时需要同时处理约 24 份，加上余量，按 40 个并发能力设计
```

估算的意义在于发现数量级的问题，并写明假设，便于交付阶段复核。

**本章验收**：为一个方案写出量化的非功能需求，用一个架构框架逐项检查方案，记录发现的问题与处理方式，并完成一次容量估算。

<a id="ch06"></a>

### 06 集成、身份与数据迁移

#### 06.1 集成方式

| 方式 | 适合 | 注意事项 |
| --- | --- | --- |
| 接口调用 | 实时查询与操作 | 认证、限流、错误处理、版本 |
| 消息与事件 | 异步通知、解耦 | 顺序、重复、失败重试 |
| 文件交换 | 批量数据、对方能力有限 | 格式校验、完整性、时间窗口 |
| 集成平台 | 集成数量多、需要统一管理 | 平台本身的成本与运维 |
| 直连对方数据库 | 尽量避免 | 绕过业务规则，结构变化会导致故障 |

每一个集成都需要确认：对方的负责人、接口文档与测试环境、调用量的限制、失败时的处理方式与监控。

#### 06.2 身份集成

企业客户通常要求使用自己的身份系统登录。常见的方式包括基于 OpenID Connect 或 SAML 的单点登录，以及用 SCIM 等协议同步用户与组织。OpenID Connect 核心规范定义了在 OAuth 2.0 之上的身份认证。[B06](#ref-b06) SCIM 协议定义了跨系统管理用户身份的标准接口。[B07](#ref-b07) 方案中需要说明：用户的创建与停用怎样同步、角色与权限怎样映射、离职人员的访问怎样及时收回。

#### 06.3 数据迁移

数据迁移是交付风险最高的工作之一。方案中需要包括：迁移的范围与历史数据的时间跨度、数据的映射与清洗规则、试迁移与对账方法、切换方式与回退方案、迁移期间的业务安排。迁移的执行见[《实施与交付工程师》](23-实施与交付工程师.md)，数据管道的方法见[《数据工程师》](17-数据工程师.md)。

**本章练习**：为一个方案列出全部集成点，为每个集成点填写方式、负责人、文档与环境的状态、失败处理与监控；对其中风险最高的一个设计验证方法。

<a id="ch07"></a>

### 07 演示与概念验证

#### 07.1 三种验证方式

| 方式 | 目的 | 规模 |
| --- | --- | --- |
| 演示 | 让客户直观了解产品如何解决他们的问题 | 小时级，使用演示环境 |
| 概念验证 | 证明关键的技术假设或风险可以解决 | 数天到数周，范围有限 |
| 试点 | 在真实的业务中小范围使用 | 数周到数月，真实用户与数据 |

#### 07.2 演示

围绕客户的业务场景演示，使用客户能理解的数据与流程，而不是逐个展示功能。演示中不展示还不存在的功能，除非明确说明它是规划中的。

#### 07.3 概念验证

```text
要验证的假设：
范围（包含与不包含）：
成功标准（可衡量，双方事先确认）：
所需的环境、数据与客户方人员：
时间盒：
结果与结论：
```

概念验证的关键在于事先确定成功标准，并限定时间与范围。没有成功标准的概念验证，容易变成没有结论的长期免费咨询；只验证容易的部分，会让风险留到交付阶段。

#### 07.4 报告结果

如实报告结果：哪些假设得到验证，哪些没有，发现了哪些新的风险。概念验证中的临时做法不能直接当作生产方案。

**本章验收**：为一个关键假设设计概念验证，事先与客户确认成功标准与时间盒；完成后写出报告，说明验证的结论、新发现的风险与对方案的影响。

<a id="ch08"></a>

### 08 成本、工作量与价值论证

#### 08.1 总拥有成本

| 成本项 | 内容 |
| --- | --- |
| 许可或订阅 | 软件费用，按用户、用量或固定费用 |
| 基础设施 | 计算、存储、网络、备份 |
| 实施 | 配置、定制开发、集成、迁移、测试 |
| 培训与变革 | 用户培训、流程调整 |
| 运维与支持 | 日常运维、升级、技术支持 |
| 退出 | 将来更换系统时的数据导出与迁移 |

至少按三年估算总拥有成本，并说明主要的假设，例如用户数的增长与用量的变化。

#### 08.2 云成本

云的成本随用量变化，需要估算正常与高峰的用量，考虑预留与按需的组合，并在方案中说明成本的监控与优化方式。FinOps 基金会的框架把云成本管理分为了解、优化与运营三个阶段，强调工程、财务与业务的共同负责。[B08](#ref-b08)

#### 08.3 工作量估算

实施工作量的估算方法见[《项目经理与交付经理》第 05 章](21-项目经理与交付经理.md#ch05)。售前阶段的估算要给出区间，写明假设，并把不确定性最大的部分标出来。

#### 08.4 价值论证

把方案的成本与业务价值放在一起：节省的人力时间、缩短的业务周期、减少的错误与风险。价值的估算同样要写明假设，并尽量使用客户自己的数据。

#### 08.5 不为赢单而低估

压低估算可能赢得项目，但会把超支、延期与质量问题留给交付团队与客户。估算与报价是两回事：估算反映真实的判断，报价由商务在了解风险后决定。

**本章练习**：为一个方案编写三年的总拥有成本估算与价值论证，写明全部假设，并请交付团队与财务分别评审。

<a id="ch09"></a>

### 09 方案呈现与决策

#### 09.1 按受众组织内容

| 受众 | 关心的问题 | 呈现重点 |
| --- | --- | --- |
| 管理层 | 值不值得、风险多大、多少钱 | 价值、风险、成本、时间 |
| 信息技术团队 | 能不能集成、安全吗、谁来运维 | 架构、集成、安全、运维 |
| 业务使用者 | 好不好用、工作会怎样变化 | 业务流程与使用场景 |
| 采购 | 成本、合同、供应商的可靠性 | 报价构成、服务承诺、资质 |

#### 09.2 方案评审

正式提交前，在内部组织方案评审：交付团队评审可落地性，安全团队评审安全设计，产品团队确认产品能力的描述是否准确。外部评审时，记录客户的问题与意见，并在会后书面答复。

#### 09.3 处理异议与比较

客户提出疑虑时，先弄清背后的担心，再回答。与竞品比较时保持诚实：承认对方的优势，说明我们的方案在客户关心的方面为什么更合适，不贬低、不臆测竞品。

#### 09.4 招标与投标

应答招标文件时，逐条回应技术要求，对不满足或部分满足的条款如实说明，并在偏离表中列出。不要为了得分而声称满足无法满足的要求，投标文件中的承诺通常会成为合同的一部分。

**本章练习**：为同一个方案准备面向管理层与面向信息技术团队的两版呈现，分别请对应的同事模拟提问，记录没有答好的问题并补充材料。

### 10 安全审查与合规

#### 10.1 客户的安全审查

企业客户常要求供应商通过安全审查：填写安全问卷、提供渗透测试报告与认证证书、说明数据的存储位置与访问控制。云安全联盟的共识评估问卷（CAIQ）是常见的问卷形式之一，用于评估云服务提供商的安全控制，其第 4 版于 2021 年发布。[B09](#ref-b09) 具体以客户采用的问卷与最新版本为准。

#### 10.2 应答原则

- **准确**：只描述已经具备的能力，规划中的能力明确标注。
- **可证明**：能提供文档、配置或报告作为证据。
- **一致**：与合同、隐私政策与其他应答保持一致，建立统一的应答库。
- **不过度承诺**：不确定时向安全团队确认，而不是先答应。

#### 10.3 共享责任

使用云服务或第三方产品时，安全责任由多方共担：基础设施的安全由服务商负责，配置、账号、数据与应用的安全通常由使用者负责。方案中要明确每一方的责任，避免出现没有人负责的部分。

#### 10.4 国内的合规要求

国内项目常涉及网络安全等级保护制度，相关的国家标准包括 GB/T 22239-2019《信息安全技术　网络安全等级保护基本要求》；处理个人信息与重要数据时，还需要考虑个人信息保护与数据出境的相关规定。方案只描述技术措施，具体义务由客户与我方的法务和合规负责人确认。安全设计的方法见[《安全工程师》](12-安全工程师.md)。

**本章练习**：建立一份安全问卷应答库，覆盖最常见的 50 个问题，每个答案注明证据与负责人；用它完成一份客户问卷，并请安全团队审核。

<a id="ch11"></a>

### 11 云、混合与私有部署

#### 11.1 部署模式

| 模式 | 优点 | 代价 |
| --- | --- | --- |
| 公有云多租户服务 | 上线快，升级与运维由服务方负责 | 定制能力有限，数据驻留受服务方限制 |
| 公有云独立部署 | 隔离更强，可按客户要求配置 | 成本更高，需要按客户运维 |
| 私有部署 | 数据与环境由客户控制 | 版本分散、升级困难、运维依赖客户能力 |
| 混合 | 敏感数据留在客户环境，其余使用云 | 架构与运维更复杂 |

#### 11.2 私有部署的长期代价

私有部署的客户越多，产品需要同时支持的版本与环境就越多，升级与问题排查的成本随之上升。方案中需要说明升级的方式与频率、远程支持的条件、客户需要具备的运维能力。

#### 11.3 锁定与可移植性

评估方案对特定服务商或技术的依赖：数据能否完整导出？迁移到其他平台需要多少工作量？依赖本身不一定是问题，但客户应当在了解退出成本的情况下做决定。

**本章练习**：为同一需求比较多租户服务与私有部署两种模式，列出三年内的成本、运维责任与升级方式的差异，并说明推荐的理由。

<a id="ch12"></a>

### 12 参考架构与可复用资产

#### 12.1 参考架构

把多次验证过的方案整理成参考架构：适用的场景、架构图、关键决定、非功能的设计、已知的限制与常见问题。参考架构能加快方案设计，也让不同的人设计的方案保持一致的质量。

#### 12.2 可复用资产

- 演示环境与演示脚本。
- 方案文档与架构图的模板。
- 安全问卷应答库。
- 成本估算模型。
- 常见集成的说明与示例代码。
- 概念验证的计划模板与常用测试数据。

#### 12.3 从项目中提炼

每个项目结束后，回顾方案与实际交付的差异，把有效的做法加入参考架构，把发现的问题加入检查清单。行业知识的积累见[《领域专家》](04-领域专家.md)。

**本章练习**：从最近的三个项目中提炼一份参考架构，写出适用场景、关键决定与已知限制，并请另一位同事用它设计一个新方案，收集反馈。

### 13 AI 解决方案设计

#### 13.1 评估 AI 用例

| 问题 | 说明 |
| --- | --- |
| 价值 | 解决什么业务问题？成功怎样衡量？ |
| 数据 | 需要哪些数据？是否可用？质量如何？能否合规地使用？ |
| 错误的代价 | 模型出错会造成什么影响？谁来复核？ |
| 评测 | 怎样在上线前判断效果是否达标？ |
| 成本 | 调用量、单次成本、延迟要求 |

#### 13.2 架构选择

- **使用外部模型服务**：上线快，需要评估数据传输与驻留、服务的可用性与条款。
- **私有部署模型**：数据留在客户环境，需要算力、运维能力与模型更新的方案。
- **混合**：敏感数据在本地处理，其余使用外部服务。

检索增强生成的数据管道见[《数据工程师》第 14 章](17-数据工程师.md#ch14)，应用工程见[《算法与机器学习工程师》第 11 章](18-算法与机器学习工程师.md#ch11)。

#### 13.3 成本估算

按调用次数、每次的输入与输出长度和单价估算模型费用，再加上检索、存储与人工复核的成本。用量的不确定性较大时，给出区间，并设计用量与费用的监控和上限。

#### 13.4 设定正确的预期

在方案与合同中说明：AI 会出错；验收以评测集上的指标为准；出错时有人工复核与纠正的流程；模型或服务更换前需要重新评测。不要承诺“准确率 100%”这样的结果。评测方法见[《算法与机器学习工程师》第 12 章](18-算法与机器学习工程师.md#ch12)。

**本章练习**：为一个 AI 用例完成评估表、架构选择的比较与成本估算，写出基于评测集的验收标准与出错时的处理流程。

### 14 交接、落地与反馈

#### 14.1 交接包

```text
客户背景与业务目标：
成功标准与验收方式：
推荐方案与关键决定（含理由）：
对客户的全部承诺（功能、性能、时间、服务）：
假设与待验证事项：
风险与建议的应对：
客户方的关键人员与关系：
未解决的问题与客户的顾虑：
相关文档（方案、架构图、概念验证报告、问卷应答、估算）：
```

#### 14.2 交接会

与项目经理、技术负责人与实施团队一起召开交接会，逐项讲解承诺、假设与风险，回答问题，并约定交付初期的支持方式。售前承诺中交付团队无法接受的部分，在签约前解决，而不是留到交付阶段。

#### 14.3 跟踪落地

交付期间定期了解方案的执行情况，帮助处理与方案相关的问题；项目结束后比较方案与实际的差异，改进估算与参考架构。

#### 14.4 反馈到产品

把客户的需求与产品的缺口整理后交给产品经理：需求背后的问题、涉及的客户与收入、当前的替代方案。不要以产品经理的名义向客户承诺路线。

**本章练习**：为一个即将签约的项目准备交接包，召开交接会，记录交付团队提出的问题与对方案的修改。

### 15 与开发者的协作接口

#### 15.1 解决方案架构师需要开发者提供的内容

| 内容 | 作用 |
| --- | --- |
| 产品能力的准确边界 | 避免承诺不具备的能力 |
| 性能与容量数据 | 支持非功能需求的回答与估算 |
| 路线图的可靠程度 | 区分已承诺、计划中与探索中的功能 |
| 技术验证的支持 | 概念验证中解决难题 |
| 定制需求的工作量评估 | 支持估算与报价 |

#### 15.2 开发者需要解决方案架构师提供的内容

客户的真实环境与约束、需求背后的业务问题、已经对客户做出的承诺、定制需求的优先级与商业价值，以及从交付中获得的客户反馈。

#### 15.3 共同的做法

- 涉及定制开发或未发布功能的承诺，事先经过技术评审。
- 概念验证的代码与生产代码区分开，不直接上线。
- 交付中发现方案的问题时，及时反馈并共同调整。

<a id="ch16"></a>

### 16 开发者怎样借用解决方案架构方法

#### 16.1 外包与项目制团队的技术负责人

- 报价前先做需求发现，至少弄清业务问题、现有系统与约束。
- 写出两到三个方案并比较，而不是只给一个报价。
- 把假设写进方案，把最大的风险安排在签约后最早验证。
- 估算中包括集成、迁移、测试、培训与上线后的支持。

#### 16.2 自由职业者

用简短的方案文档说明你理解的问题、建议的做法、不包含的范围、假设与价格构成。它能帮助客户比较不同的报价，也能在之后减少争议。

#### 16.3 技术背景的常见偏差

- 方案中技术细节过多，没有回答客户关心的业务问题。
- 低估集成与数据迁移的难度。
- 忽视非功能需求，直到上线前才发现性能或安全问题。
- 被问到不确定的问题时当场答应，而不是确认后再答复。

<a id="ch17"></a>

### 17 贯穿实战：连锁企业招聘管理系统的方案设计

本章展示在签约之前的方案设计过程，签约后的交付见[《项目经理与交付经理》第 17 章](21-项目经理与交付经理.md#ch17)。客户、数字与费用均为示意。

#### 17.1 需求发现

一家拥有 120 家门店的连锁企业希望在招聘旺季前改进招聘管理。发现会议的要点：

- **业务问题**：门店平均招聘周期 20 天，旺季缺人影响营业；录用审批通过聊天记录进行，无法追溯。
- **成功标准**：旺季前上线；门店平均招聘周期缩短一半；审批全部留痕。
- **约束**：必须与现有人事系统对接；应聘者信息按门店与角色隔离；客户的信息技术团队只有 3 人。
- **假设**：人事系统提供可用的接口（当前只有文档，测试环境需在签约后提供）。

#### 17.2 候选方案

| 标准 | A：现成的招聘服务 | B：完全定制开发 | C：基于已有的招聘管理产品配置与扩展 |
| --- | --- | --- | --- |
| 满足关键需求 | 门店审批流程与人事系统集成不满足 | 全部满足 | 满足，少量需要扩展开发 |
| 实施时间 | 4 周 | 28 周以上 | 14—18 周 |
| 三年总拥有成本 | 低 | 高 | 中 |
| 运维要求 | 低 | 高，客户团队难以承担 | 中，由交付方运维 |
| 主要风险 | 流程需要迁就系统 | 无法在旺季前上线 | 人事系统接口 |

推荐方案 C：在旺季前上线的同时满足关键需求，运维由交付方承担，符合客户信息技术团队规模小的情况。

#### 17.3 验证

- **演示**：用门店店长的实际流程演示筛选、面试安排与审批。
- **概念验证**（两周，事先确认成功标准）：手机端完成一批 20 份申请的筛选不超过 5 分钟；模拟高峰期每日 2 万份申请的处理能力。两项均达到标准。
- **未能验证的假设**：人事系统接口没有测试环境。方案中把它列为最高的风险，建议签约后第 2 周完成接口技术验证，并在合同中约定客户提供接口与测试环境的时间。

#### 17.4 成本、安全与决策

- **成本**：给出三年总拥有成本的估算区间，包括订阅、扩展开发、集成、迁移、培训与运维，并写明门店数增长到 200 家的假设。
- **安全审查**：完成客户的安全问卷，说明按门店与角色的权限隔离、操作日志与数据存储位置；规划中的功能单独标注。
- **决策**：客户的业务负责人、信息技术负责人与采购参加方案评审，选择方案 C。“推荐人奖励”被列为二期的候选需求。

#### 17.5 交接

交接会上逐项说明：对客户的承诺（旺季前完成三批门店上线、手机端筛选的性能）、最高风险（人事系统接口）与建议的验证时间、客户方信息技术团队的规模限制、二期候选需求。交付团队据此制定了项目计划与风险登记。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 解决方案架构师的工作是介绍产品 | 核心是理解客户的问题，设计能落地的方案 |
| 方案越完整越好 | 方案要回应客户的关键问题，并说明取舍 |
| 能定制的都可以答应 | 每项定制都会增加实施与长期维护的成本 |
| 概念验证通过就可以直接上线 | 概念验证中的临时做法不能直接当作生产方案 |
| 只要首年费用低客户就会满意 | 客户需要了解多年的总拥有成本与退出成本 |
| 安全问卷尽量都答“满足” | 应答必须准确、可证明，规划中的能力要标注 |
| 投标时先答应，交付时再说 | 投标承诺通常会成为合同的一部分 |
| 售前结束后工作就完成了 | 交接与落地跟踪决定方案能否兑现 |
| AI 方案可以承诺准确率 | 需要以评测集上的指标为验收依据，并设计出错处理 |
