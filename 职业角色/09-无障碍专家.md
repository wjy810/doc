# 无障碍专家进阶全景手册

> 从找出并修复一个页面的无障碍问题，到让团队在设计和开发中默认做对，再到建立组织的无障碍治理与合规体系。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：希望掌握无障碍实践的前端开发者与设计师、负责产品质量与合规的测试工程师和产品经理，以及希望系统提升的在职无障碍专家。

无障碍专家要回答的核心问题是：不同能力和处境的人，能否感知、理解和操作这个产品。使用屏幕阅读器的盲人、依靠键盘操作的肢体障碍者、需要字幕的听障者、对复杂界面感到吃力的认知障碍者和年长者，以及在强光下、单手持手机、网络很慢时使用产品的普通人，都会受到无障碍质量的影响。

无障碍常被当作上线前的一次“合规检查”，但这样做成本最高、效果最差：很多障碍在设计阶段就已产生，修复需要回到设计和组件层面。无障碍专家的价值，在于让团队从需求、设计、开发到测试都默认考虑无障碍，并通过标准、组件、工具和培训让这件事可以持续。

本手册先建立角色坐标，然后讲解理解残障与辅助技术、标准与规范、设计阶段与开发阶段的无障碍、测试与评估、内容与多媒体、修复优先级；随后进入法律合规与采购、移动与新兴媒介、AI 与无障碍、组织治理；最后说明无障碍专家与开发者的协作，以及开发者应掌握的基本功。

主线是：**理解用户与辅助技术 → 掌握标准与原则 → 在设计中预防障碍 → 在开发中正确实现 → 用多种方法测试与评估 → 按用户影响修复并防止回退 → 建立组织的治理与合规体系。**

本手册描述无障碍的职责与方法，涉及法律法规的内容只说明工程与协作层面的做法，各地的具体义务、适用范围与期限由法务或合规负责人确认，并以官方最新版本为准。D1—D6 分级是学习组织方式，不对应任何职级体系。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 无障碍专家负责什么

#### 01.1 核心问题：让所有人都能使用

W3C 的无障碍倡议（WAI）把网页无障碍描述为：让残障人士能够感知、理解、导航、交互和贡献于网络；同时，无障碍也惠及老年人、临时受伤者、处于特殊环境中的人等更广泛的人群。[B01](#ref-b01) 无障碍专家负责识别产品中的障碍，指导团队预防和修复，并建立让无障碍持续的机制。

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 无障碍评估报告 | 了解产品的现状与问题 | 范围清楚、方法可复现、问题按用户影响分级 |
| 问题清单与修复建议 | 指导修复 | 每个问题有位置、复现步骤、影响、对应准则与修复方法 |
| 设计与组件规范 | 在源头预防问题 | 纳入设计系统，有正反示例 |
| 测试方案与自动化检查 | 防止回退 | 自动检查与人工检查结合，接入持续集成 |
| 培训材料 | 提升团队能力 | 按角色区分，配合实际练习 |
| 无障碍声明 | 向用户说明符合程度与反馈渠道 | 准确、可读、定期更新 |
| 符合性报告 | 用于采购与合规 | 依据明确的标准逐项说明 |
| 治理方案 | 让无障碍成为组织的常规工作 | 包含政策、职责、流程与度量 |

#### 01.3 职责边界与相邻角色

| 事项 | 无障碍专家的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 无障碍要求与标准解释 | 主导 | 产品经理、法务 | 法律义务由法务确认 |
| 设计中的无障碍 | 指导与评审 | 交互设计师、视觉设计师 | 设计师负责落实到设计中 |
| 组件与代码实现 | 指导与评审 | 前端开发者、设计系统团队 | 开发者负责实现 |
| 测试与评估 | 主导或指导 | 测试工程师 | 测试团队把无障碍纳入常规测试 |
| 内容与多媒体 | 指导 | 内容设计师、市场团队 | |
| 与残障用户一起研究 | 共同负责 | 用户研究员 | 见[《用户研究员》第 12 章](02-用户研究员.md#ch12) |
| 采购与供应商评估 | 提供评估 | 采购、法务 | |

无障碍专家通常不是一个人修复所有问题，而是让每个角色在自己的工作中做对：产品经理把无障碍写进需求，设计师在设计中预防，开发者正确实现，测试人员纳入测试，内容人员写出可访问的内容。

#### 01.4 不同组织中的形态

- **嵌入团队的无障碍工程师**：在一个产品团队中负责实现与评审。
- **集中的无障碍团队**：为多个产品提供评估、培训和组件支持。
- **设计系统中的无障碍负责人**：确保组件默认可访问。
- **无障碍咨询与测评机构**：为客户提供评估、认证和培训。
- **兼任者**：在小团队中由前端开发者或测试人员兼任。

**本章练习**：只用键盘完成一个你常用网站的核心任务，再打开操作系统自带的屏幕阅读器完成同一任务，记录所有无法完成或困难的地方。

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **用户与辅助技术**：理解不同残障类型、使用方式与辅助技术。
2. **标准与规范**：掌握 WCAG、WAI-ARIA 及相关规范。
3. **设计无障碍**：颜色、对比、焦点、结构、表单、动效与认知负担。
4. **开发无障碍**：语义化、键盘、焦点管理、ARIA 与动态内容。
5. **测试与评估**：自动化工具、人工检查、辅助技术测试与用户测试。
6. **内容与多媒体**：替代文本、字幕、文档与通俗语言。
7. **问题管理**：按影响分级、组件级修复与防止回退。
8. **法律与合规**：了解适用法规、符合性报告与无障碍声明。
9. **移动与新兴媒介**：原生应用、游戏、可视化、扩展现实。
10. **组织治理**：政策、职责、培训、采购与成熟度。

#### 02.2 六级纵向深度

| 深度 | 无障碍专家的能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 能使用工具发现常见问题，理解基本原则 | 自动检查报告、键盘测试记录 |
| D2 独立完成 | 独立评估一个功能并给出修复方法 | 评估报告、修复建议、验证记录 |
| D3 负责结果 | 负责一个产品的无障碍质量 | 产品评估、组件改进、问题趋势 |
| D4 系统与跨团队 | 协调多产品、设计系统与采购的无障碍 | 设计系统无障碍、跨团队规范 |
| D5 方法与机制 | 建立组织的无障碍治理、培训与度量 | 政策、培训体系、成熟度评估 |
| D6 创新与影响 | 推动标准、工具或研究的进步 | 标准贡献、开源工具、研究成果 |

#### 02.3 成长中的常见偏差

- 只依赖自动化工具的结果，认为“工具没报错就是无障碍”。
- 只关注视觉障碍，忽视听觉、运动和认知方面的障碍。
- 滥用 ARIA，给本来可用的原生元素添加错误的角色和属性。
- 在上线前才介入，问题已经难以修改。
- 只追求符合标准的条目，而不验证残障用户能否真正完成任务。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 理解残障、辅助技术与使用方式

#### 03.1 不同的障碍类型

| 类型 | 举例 | 常用的方式与辅助技术 |
| --- | --- | --- |
| 视觉 | 全盲、低视力、色觉差异 | 屏幕阅读器、屏幕放大、高对比模式、调大字号 |
| 听觉 | 聋、重听 | 字幕、文字记录、手语 |
| 运动 | 肢体障碍、震颤、无法使用鼠标 | 键盘、开关设备、语音控制、眼动设备 |
| 认知与学习 | 注意力、记忆、阅读障碍 | 简单清楚的内容、一致的导航、足够的时间 |
| 言语 | 无法或难以说话 | 文字输入替代语音 |

W3C 的“残障人士怎样使用网络”系列通过用户故事介绍不同的使用方式与辅助技术。[B02](#ref-b02)

#### 03.2 永久、临时与情境

微软的包容性设计方法提出，障碍可以是永久的（失去一只手臂）、临时的（手臂受伤）或情境性的（抱着婴儿只能单手操作）。[B03](#ref-b03) 这个视角说明：为残障用户设计的方案，往往能惠及更多人，例如字幕帮助在嘈杂环境中观看视频的人。

#### 03.3 亲自使用辅助技术

无障碍专家需要熟练使用常见的辅助技术，至少包括：桌面与移动端的屏幕阅读器、键盘操作、屏幕放大、系统的减少动态效果与高对比设置。但要注意：专家使用辅助技术的方式与日常依赖它的用户不同，不能代替与残障用户一起测试（见 07 章）。

**本章练习**：用桌面和手机上的屏幕阅读器各完成一个购物或报名流程，记录导航方式、遇到的问题，以及你需要学习的快捷操作。

<a id="ch04"></a>

### 04 标准与规范：WCAG 2.2 及相关规范

#### 04.1 WCAG 2.2

《Web 内容无障碍指南》（WCAG）是最广泛采用的网页无障碍标准。WCAG 2.2 于 2023 年成为 W3C 推荐标准，按四个原则组织：

- **可感知**：信息和界面必须以用户能够感知的方式呈现，例如为图片提供替代文本、为视频提供字幕。
- **可操作**：界面组件与导航必须可以操作，例如所有功能都能用键盘完成。
- **可理解**：信息和操作必须能被理解，例如清楚的错误提示、可预测的行为。
- **健壮**：内容必须能被各种用户代理（包括辅助技术）可靠地解释。

每条成功准则分为 A、AA、AAA 三个级别，大多数法规与政策引用的是 AA 级。[B04](#ref-b04)

#### 04.2 WCAG 2.2 的新增内容

与 2.1 相比，WCAG 2.2 新增了 9 条成功准则，包括焦点不被遮挡、拖拽操作的替代方式、目标尺寸（最低）、一致的帮助、避免重复输入、无障碍的身份验证等，并移除了已经过时的“解析”准则。[B05](#ref-b05) 其中“目标尺寸（最低）”要求可点击目标一般不小于 24×24 CSS 像素，或与相邻目标保持足够间距；“无障碍的身份验证”要求登录过程不依赖记忆密码或解谜等认知功能测试，或提供替代方式。

#### 04.3 WAI-ARIA 与使用原则

WAI-ARIA 为自定义的富交互组件提供角色、状态与属性，让辅助技术能够理解它们。使用 ARIA 的第一条原则是：如果能使用原生的 HTML 元素或属性实现所需的语义和行为，就使用原生元素，而不是给其他元素加上 ARIA。[B06](#ref-b06) 错误的 ARIA 比没有 ARIA 更糟糕，因为它会向辅助技术传达错误的信息。自定义组件的键盘交互模式可以参考 ARIA 创作实践指南。[B07](#ref-b07)

#### 04.4 其他相关规范

- **欧洲标准 EN 301 549**：信息通信技术产品与服务的无障碍要求，网页部分引用 WCAG，常用于欧盟的公共采购与法规符合性。[B08](#ref-b08)
- **中国国家标准 GB/T 37668-2019**：《信息技术　互联网内容无障碍可访问性技术要求与测试方法》，2020 年 3 月起实施，为推荐性标准，参考了 WCAG 2.0 与 2.1。[B09](#ref-b09)
- **WCAG 3**：W3C 正在制定的下一代指南，目前仍是工作草案，不能替代 WCAG 2.2。

**本章验收**：选择 WCAG 2.2 AA 级中的 10 条成功准则，为每条写出一个通过和一个不通过的示例，并说明怎样测试。

<a id="ch05"></a>

### 05 设计阶段的无障碍

#### 05.1 在设计中预防的常见问题

| 问题 | 设计阶段的做法 |
| --- | --- |
| 对比不足 | 文字至少 4.5:1，大字号文字与界面组件至少 3:1，在设计工具中检查 |
| 只用颜色表达信息 | 状态同时用图标、文字或形状表达 |
| 焦点不可见 | 设计清晰的焦点样式，并确保不被遮挡 |
| 点击目标过小 | 遵守目标尺寸要求，常用操作留出更大的区域 |
| 结构不清 | 标题层级清楚，地标区域明确，阅读顺序合理 |
| 表单问题 | 可见标签、清楚的说明、错误信息与字段关联 |
| 动效干扰 | 提供减少动态效果的版本，避免闪烁 |
| 时间限制 | 允许延长或关闭，或避免不必要的时间限制 |
| 认知负担 | 简单的语言、一致的导航、分步骤的复杂任务 |

#### 05.2 无障碍设计标注

设计交付时标注无障碍相关的信息：标题层级、地标区域、焦点顺序、图片的替代文本、图标按钮的名称、动态内容的提示方式。这些信息开发者从视觉稿上看不出来，需要设计师明确写出。设计与交互方面的展开见[《UX／交互设计师》第 11 章](05-UX交互设计师.md#ch11)和[《UI／视觉设计师》第 05 章](06-UI视觉设计师.md#ch05)。

**本章验收**：为一个页面的设计稿完成无障碍标注，包含标题层级、焦点顺序、替代文本和动态内容提示，并请开发者确认能据此实现。

<a id="ch06"></a>

### 06 开发阶段的无障碍

#### 06.1 语义化 HTML

正确使用原生元素能免费获得大量无障碍能力：按钮用 `button`，链接用 `a`，标题用 `h1` 到 `h6`，列表用 `ul`、`ol`，表单控件配合 `label`。用 `div` 加点击事件模拟按钮，需要额外实现焦点、键盘、角色和状态，容易遗漏。

#### 06.2 键盘与焦点

- 所有交互都能用键盘完成，焦点顺序与视觉顺序一致。
- 不移除焦点样式；自定义样式要清晰可见。
- 打开对话框时把焦点移入，关闭后把焦点还给触发它的元素；对话框打开期间，焦点不应跑到背后的页面。
- 单页应用切换页面后，把焦点移到新内容的开头，并让屏幕阅读器知道页面已变化。

#### 06.3 动态内容

加载完成、表单提交结果、实时更新的内容，需要让屏幕阅读器用户知道。可以使用实时区域（`aria-live`）播报重要的变化，但要克制：过多的播报会打断用户。AI 流式输出的内容尤其需要注意：逐字更新会造成大量播报，通常应在内容完成或分段完成时再提示。

#### 06.4 常见组件的实现要点

| 组件 | 要点 |
| --- | --- |
| 对话框 | 角色与名称、焦点移入与归还、焦点限制、Esc 关闭 |
| 菜单与下拉框 | 方向键导航、当前选项的状态、关闭后焦点位置 |
| 标签页 | 方向键切换、选中状态、标签与面板的关联 |
| 表格 | 表头单元格、标题、复杂表格的关联 |
| 表单 | 标签、必填与错误状态、错误信息与字段关联 |
| 图标按钮 | 可访问的名称 |
| 轮播与自动播放 | 暂停控制，不自动抢夺焦点 |

**本章验收**：实现一个可访问的对话框和一个标签页组件，用键盘和至少两种屏幕阅读器测试，并对照 ARIA 创作实践指南检查键盘交互。

<a id="ch07"></a>

### 07 测试与评估

#### 07.1 多种方法结合

| 方法 | 能发现的问题 | 局限 |
| --- | --- | --- |
| 自动化工具 | 对比不足、缺少替代文本、缺少标签、无效的 ARIA 等 | 只能发现一部分问题，无法判断替代文本是否恰当、焦点顺序是否合理 |
| 键盘测试 | 无法操作的控件、焦点丢失、焦点陷阱 | 不能发现屏幕阅读器特有的问题 |
| 屏幕阅读器测试 | 名称、角色、状态、阅读顺序、动态内容播报 | 不同屏幕阅读器与浏览器组合的表现不同 |
| 人工检查 | 对照成功准则逐项检查 | 需要经验，耗时 |
| 残障用户测试 | 真实使用中的障碍与优先级 | 需要招募与准备，样本有限 |

自动化工具（例如 axe-core）适合接入开发与持续集成流程，快速发现可自动检测的问题。[B10](#ref-b10) 但通过自动检查只说明没有这些可检测的错误，不说明产品无障碍。

#### 07.2 评估方法

W3C 的网站无障碍符合性评估方法（WCAG-EM）提供了一个结构化的过程：确定评估范围、探索网站、选择有代表性的样本、审核样本、报告结果。[B11](#ref-b11) 它的价值在于让评估结果可复现、可比较。

#### 07.3 与残障用户一起测试

邀请日常使用辅助技术的用户完成真实任务，能发现标准检查发现不了的问题，并帮助判断问题的严重程度。测试前确认参与者使用的辅助技术与设置，确保测试材料与会议工具本身可访问，安排足够的时间，并支付合理的报酬。

**本章验收**：对一个包含 5 个页面的样本完成评估：自动化扫描、键盘测试、两种屏幕阅读器测试和人工检查，输出按严重程度分级的问题清单。

<a id="ch08"></a>

### 08 内容与多媒体无障碍

#### 08.1 替代文本

替代文本描述图片传达的信息或功能，而不是外观：

- 传达信息的图片：描述其中的信息，例如图表的关键结论。
- 功能性图片（例如图标按钮）：描述它的功能，例如“搜索”。
- 装饰性图片：使用空的替代文本，让屏幕阅读器跳过。
- 复杂图表：简短的替代文本加上详细的文字说明或数据表。

#### 08.2 音视频

- 预录视频提供字幕；只有音频的内容提供文字记录。
- 视觉信息对理解很重要时，提供音频描述或包含视觉信息的文字记录。
- 直播内容提供实时字幕（适用的级别要求不同，以具体准则为准）。
- 播放器本身可以用键盘操作，控件有名称。

#### 08.3 文档与通俗语言

PDF、Word 等文档同样需要无障碍：标题结构、阅读顺序、表格表头、替代文本、文档语言。扫描的图片式 PDF 对屏幕阅读器用户几乎不可用。复杂的内容使用通俗语言，帮助有认知障碍和阅读困难的用户（见[《内容设计师》第 04 章](07-内容设计师.md#ch04)）。

**本章练习**：为一个包含图表、图标和产品截图的页面写出所有替代文本，并说明每张图片属于哪种类型、为什么这样写。

<a id="ch09"></a>

### 09 修复优先级与问题管理

#### 09.1 按用户影响分级

| 级别 | 判断依据 | 示例 |
| --- | --- | --- |
| 阻断 | 某类用户无法完成核心任务 | 提交按钮无法用键盘激活；验证码没有替代方式 |
| 严重 | 完成任务非常困难或容易出错 | 错误信息没有与字段关联；焦点在对话框关闭后丢失 |
| 中等 | 造成困扰但可以绕过 | 标题层级混乱；部分图标缺少名称 |
| 轻微 | 体验不佳但影响有限 | 装饰性图片被朗读 |

优先修复核心任务上的阻断与严重问题，而不是按准则编号或问题数量排序。

#### 09.2 在组件层面修复

很多问题在多个页面重复出现，根源是同一个组件。在组件库中修复一次，所有使用它的地方都会改善。修复后补充组件的无障碍测试与文档，防止问题再次出现。

#### 09.3 防止回退

- 在持续集成中运行自动化检查，新增错误时阻止合并。
- 为关键组件编写键盘与可访问名称的测试。
- 在代码评审和设计评审的检查清单中加入无障碍项。
- 定期对核心流程做人工检查。

**本章练习**：把一份评估报告中的问题归类到组件，计算在组件层面修复能解决的问题比例，制定修复计划。

### 10 法律、合规与采购

#### 10.1 常见的法规与标准

| 地区 | 法规或标准 | 要点 |
| --- | --- | --- |
| 中国 | 《无障碍环境建设法》 | 2023 年 9 月 1 日起施行，设有“无障碍信息交流”专章 [B12](#ref-b12) |
| 中国 | GB/T 37668-2019 | 互联网内容无障碍的推荐性国家标准 |
| 欧盟 | 《欧洲无障碍法案》（指令 2019/882） | 自 2025 年 6 月 28 日起适用于电子商务、银行、电子书等多类产品与服务 [B13](#ref-b13) |
| 欧盟 | 公共部门网站与应用无障碍指令（2016/2102） | 要求公共部门网站与应用无障碍，并发布无障碍声明 [B14](#ref-b14) |
| 欧盟 | EN 301 549 | 用于证明符合相关法规的协调标准 |
| 美国 | 《美国残疾人法》（ADA）与第 508 条款 | 司法部 2024 年发布规则，要求州和地方政府的网页与移动应用达到 WCAG 2.1 AA，其后调整过合规期限；第 508 条款适用于联邦政府的信息通信技术 |

法规的适用范围、例外与期限经常变化，表中只用于了解概况。具体义务由法务或合规负责人依据最新的官方文本确认。

#### 10.2 无障碍声明

无障碍声明向用户说明产品的符合程度、已知问题、替代访问方式和反馈渠道。欧盟公共部门的网站与应用需要发布声明；对其他组织来说，发布准确的声明也是对用户负责的做法。W3C 提供了编写无障碍声明的指南与生成工具。[B15](#ref-b15)

#### 10.3 采购中的无障碍

采购软件和服务时，把无障碍写入需求与合同：要求供应商提供依据明确标准的符合性报告（常用美国信息技术产业理事会的 VPAT 模板编写），在评估中实际测试，约定问题的修复期限。采购的产品不可访问，同样会让组织的员工和用户受到影响。

**本章练习**：为一个面向欧盟和中国用户的产品整理适用的无障碍要求清单，注明每项的来源与需要法务确认的问题。

<a id="ch11"></a>

### 11 移动应用与新兴媒介

#### 11.1 移动应用

iOS 和 Android 都提供了完整的无障碍接口与辅助技术（VoiceOver、TalkBack、开关控制、语音控制等）。原生应用需要为控件提供可访问的标签、正确的角色与状态，支持系统的字体放大，确保触摸目标足够大，并在屏幕阅读器下测试手势操作。

#### 11.2 数据可视化

图表对屏幕阅读器用户来说常常是空白。提供文字摘要与数据表，允许键盘浏览数据点，不只依靠颜色区分系列。

#### 11.3 游戏、扩展现实与其他媒介

游戏和扩展现实应用涉及更复杂的输入与感知方式：可重新映射的控制、字幕与声音的视觉提示、减少眩晕的设置、可调整的难度。这些领域的标准仍在发展，需要更多地依靠与残障用户一起测试。

**本章练习**：用 VoiceOver 或 TalkBack 完成一个移动应用的核心任务，记录无法识别的控件和手势问题。

<a id="ch12"></a>

### 12 AI 与无障碍

#### 12.1 AI 带来的帮助

AI 可以自动生成图片描述、实时字幕、文本摘要和简化表达，扩展了辅助技术的能力。这些能力对残障用户很有价值，但质量参差不齐。

#### 12.2 需要注意的风险

- **自动生成的替代文本**：可能不准确，或只描述外观而不说明信息；重要图片的替代文本仍需要人工撰写或审核。
- **自动字幕**：在专有名词、口音和噪音环境中容易出错；正式发布的视频需要人工校对。
- **AI 测试工具**：可以辅助发现问题，但会产生误报与漏报，结论需要人工确认。
- **AI 界面本身的无障碍**：对话界面、流式输出、富文本与代码块需要对屏幕阅读器友好；生成的内容（例如图表、表格）也要可访问。

#### 12.3 原则

把 AI 视为辅助，而不是无障碍的替代方案；不能因为“用户可以用 AI 描述图片”而省略替代文本。AI 生成的无障碍内容需要明确的质量检查流程。

**本章练习**：用 AI 工具为 20 张产品图片生成替代文本，人工评估准确性与有用性，统计需要修改的比例。

<a id="ch13"></a>

### 13 组织治理与成熟度

#### 13.1 治理的组成

- **政策**：组织的无障碍目标、适用标准与范围。
- **职责**：各角色在无障碍中的责任，以及最终负责人。
- **流程**：需求、设计、开发、测试、发布、采购各环节的无障碍检查点。
- **能力**：按角色的培训与认证、内部专家网络。
- **工具**：设计插件、自动化检查、组件库。
- **度量**：问题数量与趋势、核心流程的符合情况、用户反馈。

#### 13.2 成熟度模型

W3C 的无障碍成熟度模型为组织提供了评估与改进无障碍能力的结构，关注组织的流程能否持续地产出无障碍的产品，而不是某一次评估的结果。[B16](#ref-b16) 可以用它定期评估组织所处的阶段，并制定下一步的改进计划。

**本章练习**：用成熟度模型评估你所在团队的无障碍现状，选出三个最需要改进的方面，制定一个季度计划。

## 第四篇：协作、实战与成长

<a id="ch14"></a>

### 14 与开发者的协作接口

#### 14.1 无障碍专家应提供给开发者的内容

| 内容 | 最低要求 | 常见缺失 |
| --- | --- | --- |
| 问题描述 | 位置、复现步骤、使用的辅助技术与浏览器 | 只说“不符合 1.3.1” |
| 用户影响 | 哪些用户受影响、影响多大 | 没有说明为什么重要 |
| 修复方法 | 具体的代码或组件修改建议 | 只引用准则原文 |
| 验证方法 | 修复后怎样确认 | 修复后无人验证 |
| 组件规范 | 组件的无障碍要求与测试 | 每个页面单独修复 |

#### 14.2 开发者应反馈给无障碍专家的内容

框架或组件库的限制、第三方组件的问题、修复的成本与替代方案、需要澄清的准则解释。

#### 14.3 让无障碍成为日常

在需求评审中提出无障碍要求，在设计评审中检查标注，在代码评审中检查语义与键盘，在测试中包含辅助技术测试。无障碍专家的目标是让这些检查由团队自己完成，专家专注于复杂问题与机制建设。

<a id="ch15"></a>

### 15 开发者的无障碍基本功

#### 15.1 十条基本功

1. 优先使用语义化的原生元素。
2. 所有交互都能用键盘完成，焦点可见。
3. 每个表单控件都有关联的标签。
4. 图片有恰当的替代文本，装饰图片使用空替代文本。
5. 图标按钮有可访问的名称。
6. 页面有清楚的标题层级与语言声明。
7. 对话框正确管理焦点。
8. 错误信息与字段关联，并能被屏幕阅读器读到。
9. 尊重系统的减少动态效果与字体大小设置。
10. 在持续集成中运行自动化检查，并定期用屏幕阅读器手动检查。

#### 15.2 独立开发者与外包项目

独立开发者可以从选择无障碍质量好的组件库开始，并在每次发布前用键盘和屏幕阅读器走一遍核心流程。外包项目中，在合同和需求中明确无障碍标准（例如 WCAG 2.2 AA）与验收方式，避免交付后再争论。

<a id="ch16"></a>

### 16 贯穿实战：求职平台的无障碍改造

本章展示一次完整的无障碍改造过程。数字与问题都是示意。

#### 16.1 背景与范围

平台收到视障学生的反馈：无法独立完成简历上传和职位申请。团队决定以 WCAG 2.2 AA 为目标，对核心流程进行评估与改造。

| 范围 | 内容 |
| --- | --- |
| 样本页面 | 首页、登录、简历上传、分析结果、职位详情、申请表单 |
| 方法 | 自动化扫描、键盘测试、两种桌面屏幕阅读器与一种移动屏幕阅读器测试、人工检查、3 名视障用户参与测试 |
| 目标 | 核心流程中没有阻断与严重问题 |

#### 16.2 主要发现

| 问题 | 级别 | 根源 |
| --- | --- | --- |
| 上传区域只能拖拽，不能用键盘选择文件 | 阻断 | 上传组件的实现 |
| 登录使用图形验证码，没有替代方式 | 阻断 | 身份验证方案 |
| 分析进行中没有任何播报，用户不知道是否完成 | 严重 | 动态内容没有提示 |
| 申请表单的错误信息只用红色边框表示 | 严重 | 表单组件 |
| 建议卡片的展开按钮没有名称 | 中等 | 图标按钮 |
| 多处文字对比不足 | 中等 | 颜色令牌 |

#### 16.3 修复

1. 上传组件增加可用键盘操作的“选择文件”按钮，拖拽作为补充方式。
2. 登录改用不依赖认知测试的验证方式，并保留其他替代方式。
3. 分析完成时用实时区域提示“分析已完成，共 8 条建议”，分析过程中不逐步播报。
4. 表单组件把错误信息与字段关联，提交后把焦点移到错误汇总。
5. 图标按钮组件要求必须提供可访问名称，缺少时开发环境报错。
6. 调整颜色令牌，所有文字满足对比要求。

大部分问题通过修改 5 个组件解决，修复后在持续集成中加入自动化检查，并为这 5 个组件补充键盘与名称测试。

#### 16.4 验证与发布

修复后再次请 3 名视障用户测试，他们都能独立完成从上传简历到提交申请的流程。团队发布了无障碍声明，列出已知的剩余问题和反馈渠道，并承诺每季度复查一次核心流程。

#### 17.5 检查清单

- [ ] 需求中写明无障碍标准与级别。
- [ ] 设计稿包含无障碍标注：标题、焦点顺序、替代文本、动态提示。
- [ ] 对比、焦点、目标尺寸符合要求，信息不只依靠颜色。
- [ ] 优先使用语义化原生元素，ARIA 使用正确。
- [ ] 所有功能可用键盘完成，焦点管理正确。
- [ ] 表单标签与错误信息正确关联。
- [ ] 动态内容与 AI 输出有恰当的提示方式。
- [ ] 自动化检查接入持续集成，关键组件有无障碍测试。
- [ ] 核心流程经过屏幕阅读器测试与残障用户测试。
- [ ] 发布了准确的无障碍声明与反馈渠道。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 无障碍只是为盲人服务 | 涉及视觉、听觉、运动、认知等多种障碍，也惠及更多人 |
| 自动化工具没报错就是无障碍 | 工具只能发现部分问题，需要人工与辅助技术测试 |
| 加上 ARIA 就能解决问题 | 优先使用原生元素，错误的 ARIA 会带来新的问题 |
| 无障碍是上线前的合规检查 | 从需求和设计开始考虑，成本最低、效果最好 |
| 符合 WCAG 就一定好用 | 符合标准是基础，仍需验证残障用户能否完成任务 |
| 无障碍会让设计变丑 | 好的无障碍设计与好的视觉设计可以兼容 |
| AI 能自动解决无障碍 | AI 可以辅助，但需要人工审核与明确的质量流程 |
| 法规要求都一样 | 不同地区的法规、适用范围与期限不同，需要专门确认 |

### C.2 内容边界

本手册覆盖数字产品无障碍的职责与方法，不展开建筑与物理环境的无障碍，也不提供法律意见。各地法规的适用范围、例外与期限，由法务或合规负责人依据官方最新文本确认。
