# 运维工程师与 SRE 进阶全景手册

> 从让一个服务稳定运行，到用工程方法管理可靠性、容量与事故，再到建立组织的可靠性文化与运行平台。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：需要自己部署和运行服务的开发者、准备转向运维、SRE 或 DevOps 方向的工程师、负责上线后运行的外包团队，以及希望系统提升的在职运维工程师与 SRE。

运维工程师与站点可靠性工程师（SRE）要回答的核心问题是：服务能否在用户需要时可靠地工作，出问题时能否快速发现、止损和恢复，以及怎样用工程方法让运行工作越来越少依赖人工。系统上线只是开始：流量会增长，依赖会出故障，配置会被改错，磁盘会写满，证书会过期。运行质量决定了用户实际体验到的产品。

传统运维侧重于部署、监控、处理故障与维护基础设施。Google 提出的 SRE 用软件工程的方法处理运维问题：用服务等级目标与错误预算平衡可靠性与变更速度，用自动化消除重复劳动，用无责复盘从事故中学习。[B01](#ref-b01) DevOps 则是一种更广泛的文化与实践，强调开发与运维协作、共同对交付与运行负责。三者的关系常被概括为：DevOps 描述目标与文化，SRE 是实现它的一种具体工程方法。

本手册先建立角色坐标，然后讲解服务等级目标与错误预算、可观测性与告警、事故响应与值班、复盘、变更与发布、容量规划、消除重复劳动；随后进入基础设施与平台运维、备份与容灾、混沌工程、DevOps 文化与度量、AI 系统的运维；最后说明与开发者的协作，以及开发者怎样为运行负责。可观测性、容量、发布等技术机制，见[《后端进阶全景手册》第 14—16 章](../技术方向/后端进阶全景手册.md#ch14)。

主线是：**定义用户关心的可靠性 → 让系统可观测 → 快速发现并响应事故 → 从事故中学习 → 安全地变更 → 规划容量与成本 → 自动化重复劳动 → 建立可靠性文化与平台。**

不同组织中，这些职责可能由运维工程师、SRE、DevOps 工程师、平台工程师或开发团队自己承担，“DevOps 工程师”这一岗位的具体职责差异尤其大，可能侧重流水线、基础设施自动化或运行保障。本手册描述运行与可靠性的职责本身；D1—D6 分级是学习组织方式，不对应任何职级体系。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 运维工程师与 SRE 负责什么

#### 01.1 核心职责

Google 的《Site Reliability Engineering》一书把 SRE 团队负责的事项概括为：服务的可用性、延迟、性能、效率、变更管理、监控、应急响应与容量规划。[B01](#ref-b01) 书中还提出，SRE 的运维性工作应设置上限（Google 的做法是不超过约一半），其余时间用于通过工程手段减少未来的运维工作。

#### 01.2 运维、SRE、DevOps 与平台工程

| 方向 | 侧重点 | 常见工作 |
| --- | --- | --- |
| 运维 | 保障系统稳定运行 | 部署、监控、故障处理、基础设施维护、变更执行 |
| SRE | 用工程方法管理可靠性 | 服务等级目标、错误预算、自动化、事故管理、容量 |
| DevOps | 开发与运维协作的文化与实践 | 持续集成与交付、基础设施即代码、共同对运行负责 |
| 平台工程 | 为开发团队提供自助的平台与工具 | 内部开发者平台、标准化的环境与流水线 |

平台工程见[《平台工程师与研发效能》](14-平台工程师与研发效能.md)。

#### 01.3 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 服务等级目标与错误预算策略 | 平衡可靠性与变更速度 | 基于用户体验，口径清楚，有执行规则 |
| 监控看板与告警 | 发现问题 | 告警可执行，误报少，覆盖关键用户旅程 |
| 运行手册 | 指导处理常见问题 | 步骤可执行，经过演练，及时更新 |
| 事故记录与复盘 | 从事故中学习 | 时间线清楚，原因深入，改进措施有负责人 |
| 发布与变更流程 | 安全地变更 | 渐进、可观察、可回退 |
| 容量计划 | 提前准备资源 | 基于数据与预测，有触发条件 |
| 自动化工具 | 减少重复劳动 | 可靠、可审计、失败时安全 |
| 灾备方案与演练记录 | 证明能够恢复 | 恢复目标明确，演练结果真实 |

#### 01.4 职责边界与相邻角色

| 事项 | 运维／SRE 的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 可靠性目标 | 共同确定 | 产品经理、开发团队 | 可靠性是产品特性，需要业务参与 |
| 应用的可观测性 | 指导与共建 | 开发者 | 开发者在代码中埋点，SRE 提供标准与平台 |
| 事故响应 | 主导或共同负责 | 开发团队、客服 | 很多团队由开发者参与值班 |
| 发布 | 提供机制与把关 | 开发团队 | |
| 基础设施 | 主导 | 平台工程师 | |
| 安全运营 | 协作 | 安全工程师 | 见[《安全工程师》第 12 章](12-安全工程师.md#ch12) |
| 数据库运维 | 协作 | 数据库工程师 | 见[《数据库工程师 DBA》](15-数据库工程师DBA.md) |

**本章练习**：统计你所在团队上个月花在运维性工作（处理告警、手工部署、回答咨询、修复故障）上的时间，分析其中哪些可以通过自动化或改进设计消除。

<a id="ch02"></a>

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **可靠性目标**：服务等级指标、目标与错误预算。
2. **可观测性**：指标、日志、追踪、告警与看板。
3. **事故管理**：值班、响应、沟通与复盘。
4. **变更与发布**：渐进发布、回退与变更风险控制。
5. **容量与性能**：负载预测、压测、扩缩容与成本。
6. **自动化与工具**：消除重复劳动，建设运维工具。
7. **基础设施**：云、容器、网络、配置与基础设施即代码。
8. **数据与恢复**：备份、容灾与恢复演练。
9. **韧性工程**：故障注入、混沌实验与故障域分析。
10. **文化与协作**：无责文化、共同负责、度量与改进。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 能部署服务、查看监控、按运行手册处理问题 | 部署记录、按手册处理的事件 |
| D2 独立完成 | 独立负责一个服务的监控、告警、发布与常见故障 | 看板、告警规则、运行手册、事故处理 |
| D3 负责结果 | 对一组服务的可靠性目标负责 | 服务等级目标达成情况、复盘改进、容量计划 |
| D4 系统与跨团队 | 负责跨团队的事故管理、可观测性平台或基础设施 | 统一的事故流程、可观测性平台 |
| D5 方法与机制 | 建立组织的可靠性实践与度量 | 错误预算策略、上线评审、可靠性度量体系 |
| D6 创新与影响 | 提出新的可靠性方法或开源工具 | 公开的方法、广泛采用的工具 |

#### 02.3 成长中的常见偏差

- 追求 100% 可用：目标过高会让变更停滞，成本急剧上升。
- 告警越多越安心：大量不可执行的告警会让值班人员疲劳并忽略真正的问题。
- 事故后寻找责任人，而不是寻找系统性原因。
- 手工操作熟练后不再自动化，运维工作随规模线性增长。
- 只关注基础设施指标（CPU、内存），不关注用户体验到的结果。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 服务等级目标与错误预算

#### 03.1 指标、目标与协议

- **服务等级指标（SLI）**：衡量服务质量的具体指标，例如成功请求的比例、请求延迟低于某个阈值的比例。
- **服务等级目标（SLO）**：在一个时间窗口内对指标的目标，例如“30 天内 99.5% 的分析请求在 30 分钟内完成”。
- **服务等级协议（SLA）**：对外的承诺，通常包含未达到时的后果。SLA 的目标通常比内部的 SLO 宽松。[B02](#ref-b02)

#### 03.2 选择指标

指标应反映用户体验，而不是系统内部状态。从关键用户旅程出发：用户在做什么？什么情况下用户会认为服务“坏了”？例如简历分析需要分别衡量：请求是否被受理、任务是否在合理时间内完成、结果是否可以获取。只看接口的成功率，会遗漏后台积压与交付失败（见[《后端进阶全景手册》第 15 章](../技术方向/后端进阶全景手册.md#ch15)）。

#### 03.3 错误预算

错误预算等于 1 减去服务等级目标：如果目标是 99.5%，那么在一个窗口内允许 0.5% 的请求不符合要求。错误预算让可靠性与变更速度的讨论变得具体：预算充足时，可以更积极地发布新功能；预算消耗过快时，优先投入可靠性工作。错误预算策略需要事先与产品和开发团队约定，包括预算耗尽时具体做什么。[B03](#ref-b03)

**本章验收**：为一个服务定义 3 个服务等级指标与目标，写清分子、分母、时间窗口与数据来源，并与产品经理一起制定错误预算策略。

<a id="ch04"></a>

### 04 可观测性与告警

#### 04.1 三类信号

- **指标**：数值的时间序列，适合趋势、聚合与告警。
- **日志**：离散的事件记录，适合诊断具体问题。
- **追踪**：一次请求跨越多个组件的路径，适合定位延迟与失败的位置。

OpenTelemetry 提供了统一的信号采集标准与工具，避免被单一供应商绑定。[B04](#ref-b04)

#### 04.2 监控什么

Google 提出监控用户服务的四个黄金信号：延迟、流量、错误与饱和度。[B05](#ref-b05) 对于服务，可以使用请求率、错误率与耗时（RED 方法）；对于资源（CPU、内存、磁盘、连接池），可以使用使用率、饱和度与错误（USE 方法）。[B06](#ref-b06) 此外还要监控业务信号，例如任务积压、分析完成率、额度对账差异。

#### 04.3 好的告警

- **基于症状告警**：优先对用户受到的影响告警（错误率上升、延迟超标），而不是对每个可能的原因告警。
- **可执行**：每个告警都有明确的处理方式和运行手册链接。
- **分级**：需要立即处理的才在夜间呼叫值班人员，其他的进入工单。
- **基于错误预算消耗速度告警**：比固定阈值更能反映对目标的实际威胁。

Prometheus 的文档总结了告警的实践原则，例如保持告警简单、针对症状告警。[B07](#ref-b07) 定期审查告警：从未被处理或总是被忽略的告警，应修改或删除。

**本章验收**：为一个服务建立包含四个黄金信号与业务信号的看板，配置基于症状的告警，并为每个告警编写运行手册。

<a id="ch05"></a>

### 05 事故响应与值班

#### 05.1 事故响应的角色

较大的事故需要明确分工，避免多人同时操作、互相冲突。Google 的事故管理实践包括事故指挥、运维处理、对外沟通与规划等角色。[B08](#ref-b08)

| 角色 | 职责 |
| --- | --- |
| 事故指挥 | 掌握全局，分配任务，做出关键决定 |
| 运维处理 | 执行诊断与修复操作 |
| 沟通负责人 | 向内部相关方与用户通报进展 |
| 记录员 | 记录时间线与关键决定 |

小事故可以由一人承担多个角色，但仍要有人明确负责全局。

#### 05.2 响应的优先顺序

1. **判断影响**：哪些用户、哪些功能、是否仍在扩大。
2. **止损优先**：回退最近的变更、关闭功能开关、切换流量、限流，先恢复服务，再寻找根本原因。
3. **保留证据**：时间线、日志、指标截图、执行过的操作。
4. **持续沟通**：定期更新状态，即使没有新的进展。
5. **业务修复**：服务恢复后，核对卡住的任务、重复的扣费、遗漏的通知。

#### 05.3 值班

健康的值班制度需要：合理的轮换与交接，可执行的告警，完善的运行手册，值班后的补偿与休息，以及持续减少告警与事故的改进。PagerDuty 公开的事故响应文档提供了值班与响应流程的参考。[B09](#ref-b09)

**本章验收**：编写事故分级标准与响应流程，组织一次模拟事故演练，记录响应时间、沟通与操作中的问题。

<a id="ch06"></a>

### 06 复盘与持续改进

#### 06.1 无责复盘

复盘的目的是理解系统为什么允许事故发生，而不是找出犯错的人。人在当时的信息与压力下做出的决定通常是合理的；如果一个人的操作就能导致严重事故，说明系统缺少保护。Google 把无责的复盘文化作为 SRE 的核心实践之一。[B10](#ref-b10)

#### 06.2 复盘的内容

- 影响：受影响的用户、时长、业务损失。
- 时间线：何时发生、何时发现、何时止损、何时恢复。
- 原因：触发条件、扩大因素、检测与恢复中的障碍。
- 做得好的地方与运气好的地方。
- 改进措施：每项有负责人、优先级与验收标准。

#### 06.3 跟踪改进

复盘的价值取决于改进措施是否完成。把改进措施纳入团队的工作计划，定期检查进展。对于反复出现的问题类型，进行跨事故的分析。不要用“加强注意”代替机制上的改进，也不要让所有改进都变成无期限的大型重构。

**本章验收**：为一次真实或模拟的事故编写复盘报告，至少找出两个系统性原因，提出有负责人和验收标准的改进措施，并在一个月后检查完成情况。

<a id="ch07"></a>

### 07 变更与发布管理

#### 07.1 变更是事故的主要来源之一

很多事故由变更引起：代码发布、配置修改、基础设施调整、依赖升级。安全变更的原则：

- **渐进**：先在少量实例或用户上生效，观察后再扩大。
- **可观察**：每次变更都有明确的观察指标与观察窗口。
- **可回退**：能快速回到变更前的状态；对数据库等无法简单回退的变更，提前设计前向修复的方案。
- **小批量**：每次变更的范围小，问题容易定位。

#### 07.2 渐进交付

金丝雀发布、蓝绿部署、功能开关、按比例放量。发布系统应能自动比较新旧版本的关键指标，在指标异常时停止发布。发布机制的工程细节见[《后端进阶全景手册》第 14 章](../技术方向/后端进阶全景手册.md#ch14)。

#### 07.3 变更与错误预算

错误预算为变更提供了客观的依据：预算充足时可以更频繁地发布；预算不足时，放慢发布节奏，优先处理可靠性问题。这比主观的“稳定期冻结发布”更能平衡创新与稳定。

**本章练习**：为一个服务设计渐进发布流程：放量比例、观察指标、自动停止条件和回退步骤，执行一次发布并记录。

<a id="ch08"></a>

### 08 容量规划与性能

#### 08.1 容量规划

| 步骤 | 内容 |
| --- | --- |
| 了解需求 | 业务增长预测、活动与季节性高峰 |
| 了解供给 | 每个实例或资源能承受的负载 |
| 找到瓶颈 | 数据库、外部依赖、配额、网络 |
| 留出余量 | 应对故障与突发流量 |
| 规划与采购 | 考虑资源准备的提前时间 |
| 验证 | 压力测试与真实数据对比 |

#### 08.2 自动扩缩容

自动扩缩容能应对流量变化，但有局限：扩容需要时间，数据库等有状态组件难以快速扩展，外部依赖的配额不会随之增加。还要防止扩缩容策略之间相互影响导致振荡。

#### 08.3 成本

容量与成本直接相关。关注资源的利用率、闲置资源、日志与监控的成本，以及单位业务的成本。性能与容量的方法见[《后端进阶全景手册》第 16 章](../技术方向/后端进阶全景手册.md#ch16)。

**本章练习**：为一个服务做下一个季度的容量计划：预测负载、确定瓶颈、计算需要的资源与成本，并设定扩容的触发条件。

<a id="ch09"></a>

### 09 消除重复劳动与自动化

#### 09.1 什么是重复劳动

Google 把运维中的重复劳动（toil）描述为：人工的、重复的、可以自动化的、战术性的、没有长期价值的，并且随服务规模线性增长的工作。[B11](#ref-b11) 例如手工扩容、手工处理固定类型的告警、手工执行部署步骤、反复回答同样的问题。

#### 09.2 自动化的原则

- 先度量重复劳动：记录每类工作的频率与耗时，优先自动化收益最高的。
- 从运行手册开始：把稳定的手工步骤逐步写成脚本，再变成自动化的工具或自愈机制。
- 自动化也需要可靠：有输入校验、执行记录、失败时安全停止、可以人工接管。
- 更好的方法是消除需求：通过改进系统设计，让这类工作不再需要。

**本章练习**：列出团队的前 5 类重复劳动，估算每月耗时，选择一项完成自动化，记录前后的耗时变化。

## 第三篇：专项与进阶

<a id="ch10"></a>

### 10 基础设施与平台运维

#### 10.1 基础设施即代码

用代码描述基础设施（网络、服务器、数据库、权限），通过版本控制与评审管理变更。好处是可重复、可审计、可回退，环境之间的差异清楚可见。

#### 10.2 GitOps

GitOps 用版本控制系统中的声明式配置作为系统期望状态的来源，由自动化的代理持续把实际状态与期望状态对齐。OpenGitOps 总结了它的四项原则：声明式、版本化且不可变、自动拉取、持续对齐。[B12](#ref-b12)

#### 10.3 容器与编排

容器提供一致的运行环境，Kubernetes 等编排平台负责调度、扩缩容、服务发现与自愈。它们功能强大，也带来较高的学习与运维成本。对于小团队，托管的容器服务或更简单的部署方式可能更合适。

**本章练习**：把一个服务的部署环境用基础设施即代码描述，通过评审与自动化流程完成一次变更，并演练从代码恢复整个环境。

<a id="ch11"></a>

### 11 备份、容灾与恢复演练

#### 11.1 恢复目标

- **恢复点目标（RPO）**：可以接受丢失多长时间的数据。
- **恢复时间目标（RTO）**：需要在多长时间内恢复服务。

两个目标需要按业务与故障场景分别确定，并决定了备份频率、复制方式与灾备架构的选择。

#### 11.2 备份不等于能恢复

只有经过恢复演练，才能证明备份可用。演练要覆盖：从备份恢复数据库、恢复文件与配置、恢复密钥与凭证、核对数据完整性、记录实际恢复时间。多个系统恢复到不同时间点，可能产生新的不一致，需要核对（见[《后端进阶全景手册》第 24 章](../技术方向/后端进阶全景手册.md#ch24)）。

#### 11.3 容灾

根据业务需要选择单可用区、多可用区、跨地域主备或多活。更高的可用性意味着更高的成本与复杂度，切换本身也可能出错。明确故障域：两个部署位置可能依赖同一个身份服务、同一个配置中心或同一个证书，并不真正独立（见[《后端进阶全景手册》第 26 章](../技术方向/后端进阶全景手册.md#ch26)）。

**本章验收**：完成一次数据库的恢复演练，记录实际的恢复点与恢复时间，与目标比较，找出差距并制定改进计划。

<a id="ch12"></a>

### 12 混沌工程与韧性

#### 12.1 混沌工程的原则

混沌工程通过在系统中有控制地引入故障，验证系统在真实条件下的韧性。其原则包括：围绕稳态行为建立假设；模拟真实世界的事件；在接近生产的环境中实验；自动化并持续运行；尽量减小影响范围。[B13](#ref-b13)

#### 12.2 从演练开始

在开展自动化的混沌实验之前，可以先组织故障演练日：选择一个场景（例如某个依赖变慢、一个可用区不可用），提前写下预期，执行后比较实际表现，修复发现的问题。实验需要有明确的停止条件，并提前通知相关团队。

**本章练习**：为一个服务设计 3 个故障演练场景，写出稳态假设、注入方式、观察指标与停止条件，在测试环境中执行并记录发现。

<a id="ch13"></a>

### 13 DevOps：文化、实践与度量

#### 13.1 DevOps 是什么

DevOps 不是一个工具或一个岗位，而是开发与运维共同对软件的交付与运行负责的文化与实践：小批量频繁交付、自动化的构建测试与部署、基础设施即代码、监控与快速反馈、从失败中学习、团队对自己的服务负责。“DevOps 工程师”这一岗位名称在不同公司差异很大，求职与招聘时需要看具体职责。

#### 13.2 DORA 指标

DORA（DevOps Research and Assessment）长期研究软件交付表现。目前它用五项指标衡量软件交付表现，分为两组：吞吐（变更前置时间、部署频率、失败部署的恢复时间）与不稳定性（变更失败率、部署返工率）。[B14](#ref-b14) 研究表明，吞吐与稳定性并不必然冲突，表现好的团队往往两者兼顾。

使用这些指标时注意：它们用于团队自我改进，而不是考核个人或比较团队；单个指标容易被“优化”而失去意义，需要一起看。

**本章练习**：为你的团队计算五项交付指标，找出最大的瓶颈，提出一项改进实验并在一个季度后比较。

<a id="ch14"></a>

### 14 AI 服务的运维

#### 14.1 AI 服务的运行特点

- **外部模型服务**：有速率限制、配额与区域可用性，延迟波动大，可能部分失败或返回质量下降的结果。
- **自建推理服务**：需要 GPU 等专用资源，容量昂贵且难以快速扩展；需要关注显存、批处理与排队。
- **成本**：按调用量或资源计费，异常流量可能带来巨大的费用。
- **质量**：服务“可用”不等于结果“可用”，需要质量信号。

#### 14.2 运维要点

- 为模型调用设置超时、重试预算与熔断，提供降级方案（排队稍后处理、使用较小的模型、暂时关闭非核心功能）。
- 监控调用量、延迟、错误、速率限制、单位成本与质量抽检结果。
- 设置费用告警与硬上限。
- 记录模型与提示词的版本，变更像代码发布一样渐进放量。

AI 应用的工程细节见[《后端进阶全景手册》第 32 章](../技术方向/后端进阶全景手册.md#ch32)。

#### 14.3 用 AI 辅助运维

AI 可以协助分析告警、总结事故时间线、检索运行手册与生成诊断建议。需要注意：建议可能错误，执行影响生产的操作前必须由人确认；给 AI 工具的权限遵循最小权限原则；事故数据可能包含敏感信息。

**本章练习**：为一个调用外部模型的服务设计降级方案与费用保护，模拟模型服务变慢与限流，验证降级是否按预期生效。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与开发者的协作接口

#### 15.1 上线前的就绪评审

新服务或重大变更上线前，与开发团队一起检查：

| 方面 | 检查内容 |
| --- | --- |
| 可观测性 | 关键指标、日志、追踪与看板是否就绪 |
| 告警与手册 | 告警是否可执行，运行手册是否覆盖常见问题 |
| 容量 | 预期负载与压测结果 |
| 发布 | 渐进发布与回退方案 |
| 依赖 | 依赖的可靠性、超时与降级 |
| 数据 | 备份、恢复与迁移方案 |
| 安全 | 密钥、权限与网络配置 |
| 值班 | 谁负责、怎样升级 |

#### 15.2 共同负责

“谁构建，谁运行”的实践让开发团队参与自己服务的值班，能显著提高他们对可靠性的关注。SRE 的角色是提供平台、工具、标准与专业支持，并在复杂事故中协助，而不是替开发团队承担所有运行工作。

#### 15.3 开发者应提供给运维与 SRE 的内容

服务的架构与依赖、关键的业务指标、已知的风险与限制、发布中的特殊步骤（例如数据库迁移）、处理常见问题的方法。

<a id="ch16"></a>

### 16 开发者怎样为运行负责

#### 16.1 开发者的运行基本功

- 在代码中输出结构化日志、关键指标与追踪。
- 为所有外部调用设置超时，控制重试，避免重试风暴。
- 健康检查反映真实状态，区分存活与就绪。
- 优雅地处理关闭：停止接收新请求，完成或交还进行中的任务。
- 配置与密钥外置，不写在代码中。
- 每次发布都知道要观察什么、怎样回退。
- 参与值班，从事故中了解自己代码的真实表现。

#### 16.2 独立开发者与外包项目

独立开发者优先选择托管服务以减少运维负担，并至少做到：基本的监控与告警、定期备份与恢复测试、证书与域名到期提醒、费用告警。外包项目交付时，提供部署说明、运行手册、监控与告警配置、备份与恢复方案，并约定上线后的支持方式与责任边界（见[《实施与交付工程师》](23-实施与交付工程师.md)）。

<a id="ch17"></a>

### 17 贯穿实战：求职平台招聘季的可靠性

本章展示一个服务在业务高峰前后的可靠性工作。数字均为示意。

#### 17.1 服务等级目标

| 用户旅程 | 指标 | 目标（30 天窗口） |
| --- | --- | --- |
| 上传简历 | 上传请求成功且在 3 秒内完成的比例 | 99.5% |
| 简历分析 | 受理的分析在 30 分钟内完成的比例 | 99% |
| 查看结果 | 结果页请求成功的比例 | 99.9% |

错误预算策略：任何一项预算在 30 天窗口内消耗超过一半时，暂停非紧急的功能发布，优先处理可靠性问题。

#### 17.2 招聘季前的准备

1. **容量**：根据去年的数据预测高峰为平时的 5 倍。压测发现瓶颈在外部模型服务的速率限制与数据库连接池。与模型服务商确认提高配额，并增加第二个备用模型；调整连接池与查询。
2. **降级**：分析任务排队等待，向用户显示预计完成时间并在完成后通知；高峰时暂时关闭非核心的“修改前后对比”功能。
3. **告警**：新增任务积压时长、模型速率限制命中率、单位成本的告警。
4. **演练**：模拟模型服务限流，验证降级与通知是否生效。

#### 17.3 一次事故

招聘季第三天，模型服务商的一个区域出现故障，分析请求大量超时。告警在 5 分钟内触发；值班工程师作为事故指挥，切换到备用模型，同时开启排队降级；沟通负责人在站内发布公告。服务在 25 分钟后恢复，积压的任务在 1 小时内处理完毕。事后核对发现，部分任务在超时后被重试，导致重复消耗额度，团队按记录退回了额度。

#### 17.4 复盘与改进

- **原因**：依赖单一模型区域；超时后的重试没有使用幂等键，导致重复扣费。
- **做得好的地方**：降级方案提前演练过，切换迅速。
- **改进**：模型调用增加幂等与结果查询；额度扣减与任务状态的一致性检查纳入每日对账；增加跨区域的模型路由。每项都有负责人与完成日期，一个月后全部完成。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 可用性越高越好 | 目标应基于用户需要，过高的目标会阻碍变更并大幅增加成本 |
| 告警越多越安全 | 不可执行的告警会造成疲劳，让真正的问题被忽略 |
| 事故后要找到责任人 | 应寻找系统性原因，人的错误通常说明系统缺少保护 |
| DevOps 就是一个岗位或一套工具 | DevOps 是开发与运维共同负责的文化与实践 |
| 有备份就能恢复 | 只有经过恢复演练才能证明可以恢复 |
| 自动扩缩容能解决所有容量问题 | 有状态组件与外部依赖往往无法快速扩展 |
| 两个机房就是高可用 | 需要分析共同依赖，两个位置可能并不独立 |
| SRE 替开发团队运行服务 | SRE 提供平台、标准与支持，开发团队对自己的服务负责 |
| DORA 指标可以用来考核个人 | 它们用于团队自我改进，用于考核会被扭曲 |
