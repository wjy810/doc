# 客户成功与技术支持进阶全景手册

> 从解答一个用户的问题，到让客户持续获得产品的价值，再到把一线听到的声音变成产品与工程的改进。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：需要直接面对用户问题与客户反馈的开发者、准备转向技术支持或客户成功岗位的工程师，以及希望系统提升的在职支持工程师与客户成功经理。

技术支持帮助用户解决使用中遇到的问题：功能怎么用、为什么报错、数据为什么不对。客户成功则更进一步，面向企业客户，负责让客户真正用好产品、达成购买时期望的业务结果，并因此愿意续约和扩大使用。两者都站在客户与公司之间，是产品团队最直接的“客户之声”来源。

支持工作的价值常被低估为“回答问题”。实际上，一线团队最早知道哪里出了故障、哪些功能让用户困惑、哪些客户正在考虑离开。好的支持与客户成功团队不只是快速解决问题，还会把每一次解决沉淀为可复用的知识，把重复出现的问题推动到根本解决，并在客户遇到风险之前主动介入。

本手册先建立角色坐标，然后讲解支持体系与分级、问题处理与排查、升级与跨团队协作、知识管理、客户上手与价值实现、健康度与风险管理、客户之声；随后进入企业客户的复杂环境、服务度量、隐私与安全、AI 与客户服务、支持工程化；最后说明与开发者的协作，并用一个企业客户的案例演示从问题处理到续约风险管理的完整工作。

主线是：**理解客户要达成的结果 → 快速、准确地解决问题 → 把知识沉淀为可复用的内容 → 识别风险并主动介入 → 把客户的声音转化为改进 → 用度量持续改进服务。**

不同公司中，这些职责可能由客服、技术支持工程师、支持经理、客户成功经理、客户经理或售后服务团队承担，与销售、实施、运维的分工也各不相同。本手册描述客户成功与技术支持的职责与方法；D1—D6 分级是学习组织方式，不对应任何职级体系。文中的响应时间等数字均为示意。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 客户成功与技术支持负责什么

#### 01.1 两个角色

| 方面 | 技术支持 | 客户成功 |
| --- | --- | --- |
| 工作方式 | 以响应为主：用户提出问题，支持解决 | 以主动为主：在问题出现之前介入 |
| 关注对象 | 每一个问题 | 每一个客户的整体结果 |
| 核心目标 | 准确、快速地解决问题 | 客户达成业务目标，持续使用并续约 |
| 典型指标 | 首次响应时间、解决时间、一次解决率、满意度 | 上手完成时间、采用度、健康度、续约率 |
| 常见场景 | 个人用户与企业用户 | 主要是企业客户 |

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 工单处理与回复 | 解决用户的问题 | 准确、清楚，用户不需要反复追问 |
| 缺陷报告与升级单 | 让工程团队处理问题 | 能复现，影响范围清楚 |
| 知识文章 | 让用户与同事复用解决方案 | 准确、可搜索、持续更新 |
| 上手计划 | 帮助新客户用起来 | 目标、里程碑与成功标准明确 |
| 客户健康度与风险记录 | 提前发现续约风险 | 信号有依据，介入有记录 |
| 客户之声报告 | 推动产品改进 | 有频率、影响与证据 |

#### 01.3 职责边界与相邻角色

| 事项 | 支持与客户成功的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 缺陷修复 | 报告与跟进 | 开发者、测试工程师 | 见 05、15 章 |
| 线上故障处理 | 对外沟通，收集影响 | 运维工程师与 SRE | 见[《运维工程师与 SRE》](13-运维工程师与SRE.md) |
| 实施与上线 | 协作与交接 | 实施与交付工程师 | 见[《实施与交付工程师》](23-实施与交付工程师.md) |
| 合同、报价与续约谈判 | 提供客户使用情况 | 销售、客户经理 | 商务条款由销售负责 |
| 产品改进 | 提供客户之声 | 产品经理 | 见[《产品经理》](01-产品经理.md) |
| 帮助文档 | 提供问题与素材 | 技术写作者 | 见[《技术写作者与文档工程师》](24-技术写作者与文档工程师.md) |

几组容易混淆的角色：

- **技术支持与运维**：技术支持面向用户，处理“我遇到了问题”；运维与 SRE 面向系统，处理“系统出了问题”。重大故障时两者紧密协作。
- **客户成功与销售**：销售负责签下客户；客户成功负责客户签约后的使用效果。续约与扩展常由两者共同负责，但客户成功的建议应基于客户的真实需要。
- **客户成功与实施交付**：实施交付负责把系统部署、配置并上线；客户成功负责上线后的持续使用与价值实现。
- **客服与技术支持**：国内常把面向大量用户的一线服务称为客服，技术支持通常处理更需要技术排查的问题。

**本章练习**：统计最近一个月的工单，按“使用问题、缺陷、功能请求、账号与计费、其他”分类，计算各类占比，并为占比最高的一类提出减少它的办法。

<a id="ch02"></a>

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **产品与技术理解**：产品功能、配置、集成方式与常见故障。
2. **问题排查**：信息收集、复现、日志与对比分析。
3. **沟通与写作**：清楚的回复、困难对话、情绪处理。
4. **升级与协作**：缺陷报告、升级判断、跨团队跟进。
5. **知识管理**：知识文章、帮助中心与知识的持续改进。
6. **客户上手**：上手计划、培训、价值实现。
7. **客户健康与续约**：健康信号、风险介入、续约与扩展。
8. **客户之声**：反馈收集、整理与推动改进。
9. **服务运营**：度量、容量、排班、质量与流程。
10. **安全与合规**：身份核验、客户数据的访问与保护。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 按知识库处理常见问题，正确收集信息 | 工单记录、质量抽检结果 |
| D2 独立完成 | 独立排查复杂问题，写出可复现的缺陷报告 | 升级单、知识文章 |
| D3 负责结果 | 负责一组客户的使用效果，或一个支持领域的质量 | 健康度改进、续约记录、领域知识库 |
| D4 系统与跨团队 | 推动跨团队解决重复问题，建立升级与反馈机制 | 根本解决的问题清单、反馈机制 |
| D5 方法与机制 | 建立组织的支持体系、知识管理与客户成功方法 | 服务体系、度量体系、培训 |
| D6 创新与影响 | 提出新的服务模式或方法并验证 | 公开分享、方法推广 |

#### 02.3 成长中的常见偏差

- 追求关闭工单的速度，问题没有真正解决。
- 回复中充满术语，用户看不懂。
- 不记录、不沉淀，同一个问题每次都从头排查。
- 把所有问题都升级给工程团队，或者从不升级。
- 只在客户投诉时才联系客户。
- 对客户承诺产品路线或交付时间，却没有得到确认。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 支持体系与分级

#### 03.1 支持渠道

| 渠道 | 适合 | 注意事项 |
| --- | --- | --- |
| 帮助中心与自助 | 常见问题 | 内容要准确，并且能被搜索到 |
| 在线咨询 | 简单、需要即时回答的问题 | 复杂问题及时转为工单 |
| 工单 | 需要排查与跟进的问题 | 状态清楚，用户能看到进展 |
| 电话 | 紧急或复杂的问题 | 通话后留下书面记录 |
| 社区 | 用户之间的经验交流 | 官方回答要标明，错误信息要纠正 |

#### 03.2 分级

| 层级 | 负责 | 示例 |
| --- | --- | --- |
| 自助 | 用户通过帮助中心自行解决 | 如何修改简历的目标岗位 |
| 一线 | 常见问题的解答与信息收集 | 账号登录、功能使用 |
| 二线 | 需要技术排查的问题 | 上传失败、数据不一致 |
| 三线 | 需要修改代码或深入系统的问题 | 缺陷修复、性能问题 |

分级的目的是让问题在能解决它的最低层级被解决，同时让复杂问题快速到达合适的人。每一级都需要明确的升级条件。

#### 03.3 优先级与响应目标

| 优先级 | 判断标准（示例） | 首次响应目标（示意） |
| --- | --- | --- |
| 紧急 | 大量用户无法使用核心功能，或存在数据与安全风险 | 30 分钟 |
| 高 | 部分用户的核心功能受影响，没有替代方案 | 4 小时 |
| 中 | 功能受影响，有替代方案 | 1 个工作日 |
| 低 | 咨询、建议、轻微问题 | 3 个工作日 |

优先级根据影响范围与严重程度判断，而不是根据用户的语气。对企业客户，响应目标常写入服务水平协议，需要与合同保持一致。

#### 03.4 值班与交接

紧急问题需要有人值班；交接班时说明未完成的工单、正在跟进的事故与需要注意的客户。

**本章练习**：为一个产品设计支持体系：渠道、分级与各级的升级条件、优先级判断标准与响应目标，并用最近 20 个工单检验这些标准是否容易判断。

<a id="ch04"></a>

### 04 问题处理与排查

#### 04.1 收集信息

一次就收集完整的信息，可以避免反复追问。常见的信息清单：

```text
问题描述（期望发生什么，实际发生了什么）：
发生时间与频率：
影响范围（一个用户、一类用户、所有用户）：
操作步骤：
环境（设备、浏览器、应用版本、网络）：
错误提示（原文或截图）：
请求编号或订单号等标识：
是否有临时解决办法：
```

#### 04.2 排查方法

- **复现**：按用户的步骤在相同或相近的环境中复现。
- **缩小范围**：是所有用户还是部分用户？所有文件还是某种文件？最近才出现还是一直存在？
- **对比**：与正常的情况对比，找出差异。
- **查证据**：根据请求编号查询日志与记录，而不是只凭推测。
- **检查已知问题**：搜索知识库、已知问题列表与近期的发布记录。

#### 04.3 沟通

- 先确认收到问题，说明下一步与预计的时间。
- 排查时间较长时，定期告知进展，即使还没有结论。
- 给出结论时，说明原因、解决方法与预防方式。
- 不能解决时，诚实说明原因与替代方案。

#### 04.4 回复的写法

结论先行，步骤编号，避免术语，必要时附截图。回复之前从用户的角度读一遍：他能不能按照回复完成操作？

#### 04.5 安全

验证提问者的身份后再处理账号相关的问题；不向用户索要密码；不在工单中复制完整的身份证件号码、银行卡号等敏感信息。详见 12 章。

**本章验收**：独立处理 10 个复杂工单，每个工单记录收集的信息、排查步骤、证据与结论；请资深同事按准确性、完整性与清晰度抽检评分。

<a id="ch05"></a>

### 05 升级与跨团队协作

#### 05.1 何时升级

- 已确认是缺陷，或怀疑是缺陷但无法进一步排查。
- 影响范围扩大，可能是线上故障。
- 涉及数据损坏、安全或隐私风险。
- 超出权限范围的操作，例如修改数据、退款。

升级之前完成能做的排查，并把结果写进升级单。

#### 05.2 缺陷、功能请求与使用问题

| 类型 | 判断 | 处理 |
| --- | --- | --- |
| 缺陷 | 产品没有按设计工作 | 提交可复现的缺陷报告 |
| 功能请求 | 产品按设计工作，但不满足用户的需要 | 记录到客户之声，说明当前的替代方案 |
| 使用问题 | 产品按设计工作，用户不清楚如何使用 | 解答，并考虑改进文档或界面 |

不要把功能请求包装成缺陷来提高优先级，也不要把缺陷解释为“产品就是这样设计的”。

#### 05.3 重大事故中的支持角色

线上故障时，支持团队负责：收集用户报告并判断影响范围，及时向工程团队提供信息，统一对外的沟通口径，更新状态页面或公告，在恢复后通知受影响的用户。Google SRE 书中的事故管理一章说明了事故中的角色分工，其中包括专门负责沟通的角色。[B01](#ref-b01)

对外沟通的原则：及时承认问题，说明影响与正在采取的措施，告知下一次更新的时间；不猜测原因，不做没有把握的承诺。

**本章验收**：写出一份能让工程师直接开始处理的升级单；参与一次故障演练，负责对外沟通，按时发布至少三次进展更新。

<a id="ch06"></a>

### 06 知识管理

#### 06.1 在工作中沉淀知识

知识为中心的服务（KCS）是支持领域常用的知识管理方法。它的核心做法是：在解决问题的过程中记录知识，用一致的结构编写，每次使用时检查并改进，让知识库随工作持续生长。[B02](#ref-b02) 这套方法由服务创新联盟维护，2026 年起联盟将其名称改为“以知识为中心的成功”（Knowledge-Centered Success），强调它不只适用于支持团队。

#### 06.2 知识文章的结构

```text
标题（用用户的说法描述问题）：
适用范围（产品、版本、环境）：
现象（用户看到了什么）：
原因：
解决方法（编号步骤）：
预防方法：
相关文章：
最后核对日期：
```

#### 06.3 知识的生命周期

- 新问题解决后创建文章，或在已有文章中补充。
- 每次使用文章时，发现不准确的地方立即修正或标记。
- 产品更新后检查受影响的文章。
- 定期清理长期未使用或已过时的文章。

#### 06.4 自助的度量

关注搜索没有结果的关键词、文章的有用比例、阅读文章后仍然提交工单的比例。这些信号说明哪些内容缺失或写得不清楚。帮助文档的写作方法见[《技术写作者与文档工程师》](24-技术写作者与文档工程师.md)。

**本章练习**：选出最近一个月出现最多的 10 类问题，检查知识库是否有对应的文章；为缺失的问题编写文章，一个月后统计这些问题的工单数变化。

<a id="ch07"></a>

### 07 客户上手与价值实现

#### 07.1 从签约开始

企业客户购买产品，是为了达成某个业务结果，例如“缩短门店招聘的筛选时间”。客户成功的工作从了解这个结果开始：

- 客户为什么购买？期望的业务结果是什么？怎样衡量？
- 谁是决策者、谁是日常使用者、谁负责客户内部的推动？
- 客户内部有哪些限制：系统、流程、时间、人员？

#### 07.2 上手计划

| 内容 | 示例 |
| --- | --- |
| 业务目标 | 门店简历筛选时间从平均 3 天缩短到 1 天 |
| 成功标准 | 上线 60 天内，80% 的门店店长每周使用 |
| 里程碑 | 账号与权限配置、数据导入、培训、试点门店、全面推广 |
| 双方负责人 | 客户的项目负责人与客户成功经理 |
| 风险 | 门店店长时间紧张，培训难以集中 |

#### 07.3 价值实现时间

从签约到客户第一次获得业务价值的时间越短，客户越容易持续使用。缩短的方法：先在小范围试点，尽快达成第一个可见的结果，再逐步推广。

#### 07.4 培训与采用

培训针对不同的角色：管理员学习配置，日常使用者学习完成自己的任务。培训后观察实际的使用情况，而不只是统计参加培训的人数。

**本章验收**：为一个新客户制定上手计划，包括业务目标、成功标准、里程碑、双方负责人与风险，并在计划执行后对照成功标准评估结果。

<a id="ch08"></a>

### 08 客户健康度与风险管理

#### 08.1 健康信号

| 类别 | 信号示例 |
| --- | --- |
| 使用 | 活跃用户比例、核心功能使用频率、使用趋势 |
| 支持 | 工单数量、未解决的严重问题、满意度 |
| 关系 | 关键联系人是否变动、是否参加定期回顾 |
| 结果 | 客户的业务目标是否达成 |
| 商务 | 续约时间、付款情况 |

#### 08.2 健康分

把多个信号组合成健康分，便于快速发现风险客户。健康分需要验证：过去流失的客户在流失前的健康分是否明显偏低？不要把健康分当作不可解释的黑箱，每个客户的健康分都应能说明原因。

#### 08.3 风险介入

| 风险 | 介入方式 |
| --- | --- |
| 使用率下降 | 了解原因，提供培训或调整配置 |
| 关键联系人离职 | 尽快建立与新负责人的联系，重新确认目标 |
| 严重问题未解决 | 协调内部资源，定期向客户同步进展 |
| 业务目标未达成 | 与客户一起回顾目标，调整使用方式或计划 |

#### 08.4 续约与扩展

续约与扩展应建立在客户获得的价值之上。推荐客户扩大使用，前提是它确实能帮助客户达成目标；对客户不需要的功能或版本，不应强行推销。

#### 08.5 流失分析

客户流失后，了解真实的原因：产品没有满足需求、价值没有被实现、预算变化、被竞品替代。把原因分类统计，并反馈给产品与销售团队。

**本章练习**：用过去一年的客户数据验证一个健康分方案，比较续约客户与流失客户在续约前 90 天的健康分，并调整信号与权重。

<a id="ch09"></a>

### 09 客户之声

#### 09.1 收集

工单标签、客户访谈、定期回顾、满意度调查、社区讨论、流失访谈与销售反馈都是客户之声的来源。工单标签需要统一的分类体系，否则无法统计。

#### 09.2 常用的度量

| 度量 | 问题 | 用途与局限 |
| --- | --- | --- |
| 满意度 | 你对这次服务满意吗 | 适合评估单次服务，受当时情绪影响 |
| 客户费力度 | 解决这个问题有多容易 | 关注用户付出的努力 |
| 净推荐值 | 你有多大可能向朋友推荐 | 简单常用，但预测能力存在争议 |

Dixon 等人在《哈佛商业评论》的文章提出，减少客户解决问题时付出的努力，比追求“惊喜”更能提高忠诚度，并提出了客户费力度这一度量。[B03](#ref-b03) 净推荐值由 Reichheld 在 2003 年提出。[B04](#ref-b04) 后来的研究对它预测增长的能力提出了质疑。[B05](#ref-b05) 任何单一分数都不能代替对具体反馈内容的分析。

#### 09.3 整理与传递

- 按主题汇总，统计频率与影响（影响多少客户、涉及多少收入、是否阻碍关键任务）。
- 附上客户的原话与具体案例。
- 区分问题与客户提出的解决方案：客户说“需要一个导出按钮”，背后的问题可能是“需要把数据给上级汇报”。
- 定期与产品经理一起回顾。

#### 09.4 闭环

问题解决或功能上线后，告诉提出反馈的客户。不能实现的需求，也要说明原因。闭环让客户愿意继续提供反馈。

**本章验收**：完成一份季度客户之声报告，包括主题、频率、影响、客户原话与建议；与产品经理确认后续行动，并在问题解决后通知相关客户。

### 10 企业客户与复杂环境

#### 10.1 企业环境的常见问题

- **身份与权限**：单点登录配置、组织架构同步、角色与权限的设置。
- **数据导入与集成**：与客户现有系统对接，数据格式与映射。
- **网络与安全策略**：客户的防火墙、代理、白名单与安全审查。
- **私有部署**：客户自己的环境中的部署、升级与故障排查。
- **变更通知**：产品更新可能影响客户的流程与集成，需要提前通知。

#### 10.2 与客户技术团队协作

明确双方的责任边界：哪些由客户的信息技术团队负责，哪些由我们负责。远程排查时，事先确认客户允许访问的范围，所有操作留有记录。

解决方案设计见[《解决方案架构师》](22-解决方案架构师.md)，实施与部署见[《实施与交付工程师》](23-实施与交付工程师.md)。

**本章练习**：为一位企业客户整理环境说明：身份与权限配置、集成方式、网络限制、联系人与双方责任边界，并在下一次问题排查中使用它。

<a id="ch11"></a>

### 11 服务度量与运营

#### 11.1 常用指标

| 指标 | 含义 | 注意事项 |
| --- | --- | --- |
| 首次响应时间 | 从提交到第一次有效回复 | 自动回复不算有效回复 |
| 解决时间 | 从提交到问题解决 | 区分等待用户回复的时间 |
| 一次解决率 | 不需要再次联系即解决的比例 | 与重开率一起看 |
| 重开率 | 关闭后被重新打开的比例 | 说明问题没有真正解决 |
| 积压 | 未解决的工单数量与时长 | 关注长时间未解决的工单 |
| 满意度 | 用户对服务的评价 | 回复率低时代表性有限 |

#### 11.2 避免指标被扭曲

只考核关闭速度，会导致匆忙关闭未解决的问题；只考核满意度，可能导致回避困难的问题。用一组相互制衡的指标，并结合质量抽检。

#### 11.3 容量与排班

根据历史工单量、季节变化与产品发布计划预测工单量，安排人员与排班。招聘季、重大发布与活动期间提前增加人手。

#### 11.4 质量抽检

定期抽查工单，按准确性、完整性、清晰度与态度评分，把发现的问题用于培训与知识库改进。

**本章练习**：为支持团队建立一组相互制衡的指标与质量抽检表，统计一个月的结果，找出一个需要改进的环节并提出行动。

<a id="ch12"></a>

### 12 隐私、安全与客户数据

#### 12.1 身份核验与社会工程

攻击者可能冒充用户或客户管理员，要求重置密码、修改绑定手机或导出数据。处理账号相关的请求之前，按规定的方式核验身份；遇到催促、威胁或不寻常的请求时，按流程升级，而不是为了“服务好”而绕过核验。

#### 12.2 访问客户数据

- 支持人员只在处理问题需要时访问客户数据，并且只访问必要的部分。
- 访问需要有记录，敏感操作需要审批或客户授权。
- 内部工具默认对敏感字段脱敏显示。
- 排查结束后，不在本地保留客户的数据。

#### 12.3 用户的个人信息请求

用户可能要求查询、更正、删除个人信息或注销账号。我国《个人信息保护法》要求个人信息处理者建立便捷的个人行使权利的申请受理和处理机制，拒绝请求时应当说明理由。[B06](#ref-b06) 支持团队需要清楚的处理流程与负责人，具体义务由法务或隐私负责人确认。

安全事件的处理方法见[《安全工程师》](12-安全工程师.md)。

**本章练习**：审查支持团队处理账号请求的流程，列出可能被社会工程攻击利用的环节，并提出改进；检查支持工具对客户数据的访问是否有记录与脱敏。

<a id="ch13"></a>

### 13 AI 与客户服务

#### 13.1 AI 辅助支持人员

AI 可以帮助分类工单、总结长对话、推荐知识文章、起草回复。支持人员需要核对内容的准确性，尤其是涉及政策、价格、退款与安全的内容。

#### 13.2 面向用户的智能客服

- **回答依据**：智能客服的回答应基于准确、及时更新的知识库，并能说明来源。
- **转人工**：用户要求、问题复杂、情绪激动或涉及账号与资金时，及时转给人工，并把上下文一并转交。
- **不编造政策**：2024 年，加拿大不列颠哥伦比亚省民事解决仲裁庭在一起案件中裁定，航空公司需要对其网站聊天机器人提供的错误退款政策信息负责。[B07](#ref-b07) 企业对智能客服的回答承担责任，不能以“那是机器人说的”推脱。
- **标识**：让用户清楚自己在与 AI 对话。
- **评测**：用真实问题建立评测集，定期检查回答的准确率与转人工的比例。评测方法见[《算法与机器学习工程师》第 12 章](18-算法与机器学习工程师.md#ch12)。

#### 13.3 隐私

不要把客户数据发送给未经评估的外部服务；对话记录的保存与使用遵守隐私政策与适用的规定。

**本章练习**：用 50 个真实问题测试智能客服，按准确、部分准确、错误与应转人工四类统计结果，针对错误回答改进知识库或转人工规则。

<a id="ch14"></a>

### 14 支持工程化与工具

#### 14.1 工单系统的设计

- **字段**：产品模块、问题类型、优先级、客户、环境、关联的缺陷编号。
- **标签体系**：统一、互斥、数量适中，便于统计。
- **自动化**：按关键词与客户等级自动路由，超时自动提醒。
- **回复模板**：常见问题的模板，使用时根据具体情况修改。

#### 14.2 诊断工具

与开发者一起建设支持人员可用的诊断能力：按请求编号查询处理过程、查看用户的配置与状态（只读并脱敏）、检查常见的配置错误。诊断工具减少了对工程团队的打扰，也缩短了解决时间。

#### 14.3 支持工程师的技术能力

支持工程师可以编写脚本整理日志、批量检查配置、分析工单数据，也可以参与改进错误提示与诊断工具。这些工作需要遵守数据访问的规则。

**本章练习**：统计升级到工程团队的工单中，有多少只是需要查询信息；设计一个只读诊断工具，说明它能减少多少升级。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与开发者的协作接口

#### 15.1 支持团队需要开发者提供的内容

| 内容 | 作用 |
| --- | --- |
| 可读的错误信息与错误码 | 用户与支持人员能看懂问题，并能据此查找文章 |
| 请求编号 | 根据用户提供的编号查询日志 |
| 诊断工具 | 支持人员自行查询状态，减少升级 |
| 发布说明与已知问题 | 提前准备回答，判断问题是否与新版本有关 |
| 功能开关与配置说明 | 了解不同客户的配置差异 |

#### 15.2 开发者需要支持团队提供的内容

可复现的缺陷报告、影响范围与频率、受影响的客户、已尝试的排查步骤、客户之声的汇总。

#### 15.3 共同的机制

- 约定缺陷优先级的判断规则，以及各优先级的处理时限。
- 发布前向支持团队介绍变化，发布后关注相关的工单。
- 开发者定期轮流参与支持工作，直接了解用户遇到的问题。
- 重复出现的问题进入根本解决的清单，而不是一直由支持人员处理。

错误信息的设计见[《内容设计师》](07-内容设计师.md)，可观测性与日志见[《后端进阶全景手册》第 15 章](../技术方向/后端进阶全景手册.md#ch15)。

<a id="ch16"></a>

### 16 开发者怎样借用支持与客户成功方法

#### 16.1 独立开发者

- 自己回复早期用户的问题，这是了解产品的最好机会。
- 为每个用户问题记录类型与原因，每月统计一次。
- 把常见问题写成帮助文档，并在产品中相应的位置给出链接。
- 让错误信息包含用户可以提供给你的编号。
- 给出明确的反馈渠道与响应时间预期。

#### 16.2 外包与交付项目

在合同中约定维保期内的支持范围、响应时间、联系方式与升级路径；交付时提供运维手册、常见问题与联系人清单；维保结束前与客户确认后续的支持安排。

#### 16.3 技术背景的常见偏差

- 回复过于技术化，或者认为是用户“不会用”。
- 修复问题后不告诉用户。
- 没有日志与请求编号，无法排查用户的问题。
- 把支持工作视为打扰，而不是了解用户的机会。

### 17 贯穿实战：企业客户的问题处理与续约风险

本章以求职平台的企业版为例：一家连锁企业的 200 家门店使用平台筛选应聘者的简历，AI 生成的简历摘要帮助店长阅读，是否面试由店长决定。数字均为示意。

#### 17.1 一个支持问题

1. **报告**：多家门店反映部分简历上传失败，提示“处理失败，请重试”。
2. **一线**：收集门店、时间、文件类型与大小、请求编号，发现失败的文件都是扫描仪生成的大于 10 MB 的 PDF。
3. **二线**：用相似的文件复现，根据请求编号查询日志，确认文件在解析阶段超时。
4. **升级**：提交升级单，说明复现步骤、影响范围（约 30% 的门店、每天约 50 份简历）、临时办法（压缩后上传）。
5. **处理**：工程团队调整大文件的处理方式，并把错误提示改为说明原因与解决方法；支持团队编写知识文章，并通知受影响的门店。

#### 17.2 一个续约风险

1. **信号**：续约前 120 天，健康分下降，原因是 40% 的门店店长近一个月未使用。
2. **了解原因**：访谈门店店长，发现他们在门店高峰期没有时间登录电脑，而大部分简历是在手机上查看的，手机端的筛选操作不方便。
3. **介入**：与客户负责人确认目标；提供手机端的使用指南与简短培训；为门店配置每日简历汇总通知；把手机端批量筛选的需求整理为客户之声，附上店长的原话与使用数据。
4. **结果**：两个月后未使用的门店比例降到 15%；产品团队将手机端批量筛选列入计划；客户按期续约。

#### 17.3 复盘

- 文件上传问题加入发布前的测试样本，并在知识库中保留文章。
- 健康分中增加“按门店统计的使用比例”，比整体活跃人数更能反映连锁客户的风险。
- 客户之声报告中，手机端批量筛选的需求来自多家连锁客户，影响面比单个客户的反馈更大。

| C 领域负责 | 10—14 章 | 负责一个支持领域或一组重要客户 | 重复问题减少，客户之声推动了改进 |
| D 组织机制 | 11、15、18 章 | 建立支持体系、度量或客户成功方法 | 其他团队能借助你建立的机制稳定地服务客户 |

#### 18.3 工单回复模板

```text
问候与确认问题：

```

#### 18.4 升级单模板

```text
标题（现象＋范围）：
优先级与判断依据：
影响范围（客户、用户数、频率、是否有临时办法）：
复现步骤与环境：
期望结果与实际结果：
证据（请求编号、日志片段、截图）：
已完成的排查：

```

#### 18.5 检查清单

- [ ] 优先级根据影响范围与严重程度判断。
- [ ] 一次收集完整的信息，减少反复追问。
- [ ] 结论基于证据，例如日志与复现结果。
- [ ] 回复结论先行，用户能按步骤完成操作。
- [ ] 升级单包含复现步骤、影响范围与已完成的排查。
- [ ] 解决后编写或更新知识文章。
- [ ] 账号相关的请求先核验身份。
- [ ] 访问客户数据有必要的理由与记录。
- [ ] 重复出现的问题进入根本解决的清单。
- [ ] 客户之声附有频率、影响与原话，并在解决后闭环。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 支持就是回答问题 | 还包括沉淀知识、推动根本解决与传递客户之声 |
| 关闭工单越快越好 | 需要同时看一次解决率与重开率 |
| 客户成功就是续约销售 | 客户成功的核心是帮助客户达成业务结果 |
| 用户没有投诉就是满意 | 不满意的用户常常直接离开 |
| 净推荐值能预测增长 | 预测能力存在争议，需要结合具体反馈分析 |
| 所有缺陷都应立刻修复 | 按影响与严重程度排序处理 |
| 客户要什么功能就记录什么功能 | 要找到需求背后的问题 |
| 为了服务好可以跳过身份核验 | 核验是保护用户的必要步骤 |
| 智能客服的回答与公司无关 | 企业需对智能客服提供的信息负责 |

本手册覆盖客户成功与技术支持的职责与方法，不展开呼叫中心的运营细节与商务谈判方法。线上故障处理见[《运维工程师与 SRE》](13-运维工程师与SRE.md)，实施与部署见[《实施与交付工程师》](23-实施与交付工程师.md)，帮助文档见[《技术写作者与文档工程师》](24-技术写作者与文档工程师.md)。涉及法规的内容只描述做法，具体义务由法务与隐私负责人确认。
