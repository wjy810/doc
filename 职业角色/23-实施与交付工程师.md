# 实施与交付工程师进阶全景手册

> 从在客户环境中把系统装起来，到让系统在客户的业务中真正运转起来，再到让每一次实施都可重复、可验证、可交接。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：需要在客户环境中部署、配置与上线系统的开发者，软件厂商与外包公司的实施工程师和交付工程师，准备转向实施或交付岗位的工程师，以及希望系统提升的在职实施顾问。

实施与交付工程师负责把系统落地到客户的环境与业务中：调研客户环境，部署与配置系统，与客户的现有系统联调，迁移历史数据，培训使用者，按计划切换上线，在上线后的保障期内快速处理问题，最后把系统交接给运维与支持团队。在软件即服务的产品中，实施工作以配置、数据导入与培训为主；在私有部署的项目中，还包括基础设施的准备与长期的升级维护。

实施工作直接面对“真实世界”：客户的网络比文档里复杂，接口文档与实际行为不一致，历史数据充满重复和错误，使用者有自己的工作习惯，上线窗口只有一个周末。好的实施工程师不会把成功寄托在现场的随机应变上，而是事先调研、脚本化部署、反复演练迁移、准备回退方案，并把每一次实施的经验沉淀为下一次可以复用的方法。

本手册先建立角色坐标，然后讲解实施启动与环境调研、部署与配置管理、集成联调、数据迁移、培训与上线准备、切换与上线、上线后保障与交接；随后进入私有部署的长期运维、客户现场的安全、实施方法的标准化、变革管理、AI 系统的实施；最后说明与开发者的协作，并用连锁企业招聘管理系统的实施演示完整的过程。

主线是：**确认实施范围与客户环境 → 准备可重复的部署与配置 → 完成集成联调 → 迁移并核对数据 → 培训使用者 → 按计划切换上线 → 上线后保障并完成交接。**

不同公司中，这些职责可能由实施工程师、实施顾问、交付工程师、部署工程师、技术支持或项目团队的开发者承担，与项目经理、运维、客户成功的分工也各不相同。本手册描述实施与交付的职责与方法；D1—D6 分级是学习组织方式，不对应任何职级体系。文中的数字均为示意。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 实施与交付工程师负责什么

#### 01.1 实施的典型阶段

| 阶段 | 主要工作 | 关键产出 |
| --- | --- | --- |
| 启动 | 确认范围、交付物与客户方配合事项 | 实施计划、配合事项清单 |
| 环境准备 | 调研并准备服务器、网络、证书、账号 | 环境调研记录、环境验收记录 |
| 部署与配置 | 安装系统，按客户需求配置 | 部署记录、配置清单 |
| 联调 | 与客户现有系统对接与测试 | 联调记录 |
| 数据迁移 | 迁移并核对历史数据 | 映射规范、核对报告 |
| 培训 | 按角色培训使用者与管理员 | 培训材料、考核记录 |
| 切换上线 | 按计划切换到新系统 | 切换计划与执行记录 |
| 保障与交接 | 上线后快速处理问题，交接给运维与支持 | 问题记录、运维手册、交接清单 |

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 环境调研记录 | 发现环境中的限制与风险 | 覆盖网络、安全、依赖与访问方式 |
| 部署脚本与配置清单 | 可重复地部署 | 同一份脚本能部署测试与生产环境 |
| 联调记录 | 证明集成可用 | 覆盖正常与异常场景，双方确认 |
| 数据映射与核对报告 | 证明数据迁移正确 | 规则经客户确认，核对有数量与抽样 |
| 培训材料与记录 | 让使用者能完成工作 | 按角色组织，有实际操作的考核 |
| 切换计划 | 安全地上线 | 步骤、时间、负责人与回退条件清楚 |
| 交接材料 | 让运维与支持接手 | 完整、准确，接手的人能独立处理常见问题 |

#### 01.3 职责边界与相邻角色

| 事项 | 实施工程师的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 方案设计 | 接收方案，反馈可落地性 | 解决方案架构师 | 见[《解决方案架构师》](22-解决方案架构师.md) |
| 计划、风险与客户沟通 | 执行并反馈 | 项目经理 | 见[《项目经理与交付经理》](21-项目经理与交付经理.md) |
| 需求与流程 | 配置实现，反馈问题 | 业务分析师 | 见[《业务分析师》](03-业务分析师.md) |
| 定制开发与缺陷修复 | 提出需求，验证结果 | 开发者 | 见 15 章 |
| 长期运维 | 交接 | 运维工程师与 SRE | 见[《运维工程师与 SRE》](13-运维工程师与SRE.md) |
| 上线后的使用与续约 | 交接 | 客户成功与技术支持 | 见[《客户成功与技术支持》](20-客户成功与技术支持.md) |

几组容易混淆的角色：

- **实施工程师与运维工程师**：实施工程师负责把系统落地并上线；运维工程师负责系统上线后的长期稳定运行。私有部署项目中，实施工程师常常也承担一部分运维工作。
- **实施工程师与解决方案架构师**：解决方案架构师在签约前设计方案；实施工程师在签约后把方案落地，并发现方案中没有考虑到的现实问题。
- **实施工程师与前沿部署工程师**：前沿部署工程师深入客户的业务，通过编写代码解决客户的具体问题，并把通用的部分反馈给产品；实施工程师更侧重按照既定的方案部署、配置与上线。两者在很多公司有交叉，见[《前沿部署工程师》](26-前沿部署工程师FDE.md)。

**本章练习**：回顾一次实施或上线，按上表的阶段列出实际做了什么、花了多少时间、遇到了哪些问题，找出耗时最长或问题最多的阶段，并分析原因。

<a id="ch02"></a>

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **环境与基础设施**：服务器、操作系统、网络、证书、数据库与中间件。
2. **部署与配置**：脚本化部署、配置管理、离线与受限环境。
3. **集成联调**：接口对接、身份集成、问题定位。
4. **数据迁移**：映射、清洗、试迁移、核对与回退。
5. **业务配置**：把客户的流程与规则转化为系统配置。
6. **培训与采用**：培训设计、材料、考核与变革管理。
7. **切换与发布**：切换策略、切换计划、回退与发布纪律。
8. **保障与交接**：上线后保障、问题处理、运维手册与交接。
9. **安全与合规**：远程访问、客户数据、凭证与软件物料清单。
10. **方法与工具**：实施方法、模板、自动化工具与知识库。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 按手册完成部署、配置与培训的部分工作 | 部署记录、检查清单 |
| D2 独立完成 | 独立完成一个中小型客户的实施与上线 | 实施记录、核对报告、交接材料 |
| D3 负责结果 | 负责复杂客户的实施，对上线质量负责 | 一次上线成功、上线后问题数低 |
| D4 系统与跨团队 | 协调多个系统、多方团队的实施 | 多方联调与切换记录 |
| D5 方法与机制 | 建立组织的实施方法、工具与知识库 | 实施方法、自动化工具、培训体系 |
| D6 创新与影响 | 提出新的实施方式或工具并验证 | 工具推广、公开分享 |

#### 02.3 成长中的常见偏差

- 手工部署与修改配置，不同环境之间的差异无法追溯。
- 数据迁移只试一次，或者只核对总数。
- 培训只讲功能，不让使用者完成自己的实际任务。
- 没有回退方案，或者回退方案从未演练。
- 上线后立即撤离，问题集中爆发时无人处理。
- 交接只给一份安装文档，运维与支持无法独立工作。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 实施启动与环境调研

#### 03.1 确认范围与交付物

实施开始前，对照合同、方案与售前交接包，确认：实施的范围与不包含的内容、交付物清单、验收方式、上线的时间要求、客户方需要配合的事项。售前阶段的交接方法见[《解决方案架构师》第 14 章](22-解决方案架构师.md#ch14)。

#### 03.2 环境调研

```text
部署位置（公有云、私有云、客户机房）：
服务器与资源（数量、规格、操作系统与版本）：
网络（内外网访问、防火墙规则、代理、带宽、专线）：
域名与证书（域名、证书签发方式、到期时间）：
数据库与中间件（类型、版本、由谁提供与运维）：
外部系统与接口（清单、负责人、测试环境）：
身份与登录（单点登录方式、用户来源）：
安全策略（访问审批、堡垒机、软件准入、扫描要求）：
运维方式（谁负责、监控与备份工具）：
访问方式（远程或现场、可用的时间段）：
```

环境调研要尽早完成，并请客户方确认。很多实施延误来自调研阶段没有发现的限制，例如生产环境不能访问外网、软件需要经过安全扫描才能安装。

#### 03.3 客户方配合事项

| 事项 | 负责人 | 需要的时间 |
| --- | --- | --- |
| 提供服务器与账号 | 客户信息技术部门 | 第 1 周 |
| 开通网络与防火墙规则 | 客户信息技术部门 | 第 2 周 |
| 提供接口文档与测试环境 | 外部系统负责人 | 第 2 周 |
| 提供历史数据 | 业务部门 | 第 4 周 |
| 确认数据清洗规则 | 业务部门 | 第 5 周 |
| 安排培训对象与时间 | 业务部门 | 第 8 周 |

配合事项要写进计划并持续跟踪，延误时及时通过项目经理升级。

**本章练习**：为一个即将开始的实施编写环境调研记录与客户方配合事项清单，请客户确认，并记录调研中发现的风险及应对措施。

<a id="ch04"></a>

### 04 部署与配置管理

#### 04.1 可重复的部署

部署过程用脚本或自动化工具完成，而不是按文档一步步手工操作。同一套脚本用于测试、预生产与生产环境，只有配置不同。可重复的部署让问题容易复现，也让重新部署与灾难恢复成为可能。

#### 04.2 配置与代码分离

随环境变化的内容（数据库地址、外部服务的地址与凭证、功能开关）属于配置，应与程序分开管理，不写死在代码或安装包中。十二要素应用方法中的“配置”一节说明了这一原则。[B01](#ref-b01) 配置清单需要版本管理，每次修改都有记录；密码与密钥存放在专门的凭证管理工具中，而不是写在配置文件或文档里。

#### 04.3 环境的一致性

测试环境与生产环境的差异越大，测试的结论越不可靠。记录各环境的差异，并尽量缩小：相同的软件版本、相同的配置结构、相近的数据规模。

#### 04.4 离线与受限环境

部分客户的生产环境不能访问互联网。需要提前准备完整的安装包，包括全部依赖与镜像；为安装包提供校验值，客户可以确认文件没有被篡改；确认客户的软件准入与安全扫描流程，预留扫描的时间。

#### 04.5 部署记录

每次部署记录：时间、执行人、版本、配置的变化、执行结果与发现的问题。部署记录是排查问题与交接的重要依据。

**本章验收**：为一个系统编写部署脚本与配置清单，在两个环境中各部署一次，证明只需修改配置即可完成；在一个不能访问互联网的环境中完成一次离线部署。

<a id="ch05"></a>

### 05 集成联调

#### 05.1 联调计划

```text
接口清单（方向、方式、负责人）：
双方环境与访问方式：
测试数据（双方准备，避免使用真实个人信息）：
测试场景（正常、异常、边界、性能）：
时间安排与双方人员：
问题记录与处理方式：
完成标准：
```

#### 05.2 联调的顺序

1. **连通性**：网络是否可达，证书是否有效。
2. **认证**：凭证与签名是否正确。
3. **单个接口**：请求与响应的格式、字段含义。
4. **端到端流程**：完整的业务场景。
5. **异常情况**：超时、错误响应、重复调用、数据缺失。

按顺序推进，每一步通过后再进入下一步，可以快速定位问题出在哪一层。

#### 05.3 定位问题

保留每次请求与响应的证据：时间、请求编号、请求内容与响应内容（敏感字段脱敏）。双方对问题有分歧时，用证据而不是猜测讨论。接口文档与实际行为不一致时，记录差异，并请对方确认以哪一方为准。

#### 05.4 联调记录

联调完成后，双方确认联调记录：通过的场景、已知的限制与遗留问题。集成方式的设计见[《解决方案架构师》第 06 章](22-解决方案架构师.md#ch06)。

**本章验收**：为一个外部接口完成联调，覆盖正常与至少五种异常场景，保留每个场景的请求与响应证据，并由双方签字确认联调记录。

<a id="ch06"></a>

### 06 数据迁移

#### 06.1 迁移的步骤

1. **盘点**：有哪些数据、在哪里、数量多少、质量如何、需要迁移多长时间的历史。
2. **映射**：旧数据的字段怎样对应到新系统。
3. **清洗**：处理重复、缺失、格式错误与不一致的数据。
4. **试迁移**：在测试环境中完整执行，发现问题。
5. **核对**：数量、金额、抽样与关键业务场景。
6. **正式迁移**：在约定的时间窗口内执行。
7. **验证**：业务人员在新系统中确认数据。

#### 06.2 映射规范

| 来源字段 | 目标字段 | 转换规则 | 无法转换时的处理 | 确认人 |
| --- | --- | --- | --- | --- |
| 表格“门店” | 门店编号 | 按门店名称对照表转换 | 列入异常清单，由业务确认 | 人事专员 |
| 表格“电话” | 手机号 | 去除空格与横线，校验 11 位 | 列入异常清单 | 人事专员 |
| 表格“状态” | 申请状态 | 按状态对照表转换 | 默认“待筛选”，并列入清单 | 人事经理 |

#### 06.3 清洗规则需要客户确认

数据怎样清洗是业务决定，不是技术决定。例如两条记录的手机号相同、姓名不同，是同一个人还是录入错误？清洗规则与异常数据的处理方式都需要客户书面确认。

#### 06.4 核对

- **数量**：每类数据迁移前后的数量一致，差异有说明。
- **汇总值**：金额、状态分布等汇总结果一致。
- **抽样**：随机抽取记录，逐字段核对。
- **业务场景**：业务人员用新系统完成典型的业务操作。

#### 06.5 时间窗口与增量

迁移期间旧系统是否继续使用？如果继续使用，需要处理迁移开始后新增与修改的数据，或者设置冻结窗口，在窗口内停止使用旧系统。

#### 06.6 回退

正式迁移前确认回退条件与回退方法：迁移失败时，业务怎样继续进行？新系统中已经产生的数据怎样处理？数据管道与核对方法见[《数据工程师》](17-数据工程师.md)。

**本章验收**：为一次数据迁移编写映射规范与清洗规则并经客户确认，完成至少两次试迁移，按四种方式核对并输出报告，记录回退方案并演练一次。

<a id="ch07"></a>

### 07 培训与上线准备

#### 07.1 按角色培训

| 角色 | 培训内容 | 方式 |
| --- | --- | --- |
| 系统管理员 | 用户与权限、配置、常见问题处理 | 实操培训与管理员手册 |
| 日常使用者 | 完成自己的工作任务 | 场景化的实操与简短的操作指南 |
| 关键用户 | 深入的功能与常见问题，帮助同事 | 提前培训，参与测试 |
| 支持人员 | 常见问题、排查方法、升级路径 | 培训与知识文章 |

#### 07.2 培训材料

围绕使用者的实际任务编写，例如“怎样筛选今天收到的申请”，而不是按菜单逐个介绍功能。材料包括简短的操作指南、常见问题与短视频，培训后发给使用者，并放在容易找到的地方。

#### 07.3 培训效果

培训后让使用者独立完成典型的任务，记录完成情况与遇到的问题，而不只是统计签到人数。考核中发现的普遍问题，可能说明界面或流程需要改进。

#### 07.4 上线准备检查

- 账号与权限已按角色配置并抽查。
- 数据迁移完成并经业务确认。
- 配置与集成在预生产环境验证通过。
- 监控、告警与备份已就绪。
- 支持渠道、值守安排与应急联系人已公布。
- 使用者已完成培训与考核。

**本章练习**：为一个角色设计培训方案与操作指南，培训后用三个实际任务考核，统计完成率与问题，并据此修改材料。

<a id="ch08"></a>

### 08 切换与上线

#### 08.1 切换策略

| 策略 | 做法 | 适合的情况 |
| --- | --- | --- |
| 一次性切换 | 在约定时间全部切换到新系统 | 规模较小，或新旧系统无法同时运行 |
| 分批切换 | 按区域、部门或门店分批上线 | 规模较大，希望控制风险 |
| 并行运行 | 新旧系统同时运行一段时间 | 风险高、需要核对结果 |
| 蓝绿切换 | 准备两套环境，通过切换流量上线 | 需要快速回退的系统升级 |

蓝绿切换准备两套尽可能相同的生产环境，新版本在非活动的环境中部署与验证，再把流量切换过去；出现问题时切回原环境。[B02](#ref-b02)

#### 08.2 切换计划

```text
切换时间窗口：
参与人员与联系方式（双方）：
切换前检查：
切换步骤（时间点、操作、执行人、验证方式）：
回退条件（出现什么情况时回退）：
回退步骤与所需时间：
切换后验证（业务人员确认的关键场景）：
沟通（通知谁、何时、通过什么方式）：
```

切换步骤精确到每个时间点与执行人，并在切换前完整演练至少一次。上线决策会的组织方式见[《项目经理与交付经理》第 10 章](21-项目经理与交付经理.md#ch10)。

#### 08.3 发布纪律

只发布经过测试的版本，发布的内容与版本可以追溯，不在上线当天临时修改代码或配置。Google SRE 书中的发布工程一章强调了可重复、自动化的构建与发布。[B03](#ref-b03)

#### 08.4 不兼容的变更

升级涉及接口或数据结构的不兼容变更时，可以分为三步：先扩展，让新旧两种方式同时可用；再迁移，让使用方逐步转向新方式；最后收缩，移除旧的方式。这一做法常被称为并行变更，它把一次高风险的切换拆成几次低风险的步骤。[B04](#ref-b04)

**本章验收**：为一次上线编写切换计划，完整演练一次并记录各步骤的实际耗时；演练一次回退，确认在约定的时间内完成。

<a id="ch09"></a>

### 09 上线后保障与交接

#### 09.1 保障期

上线后的最初几天到几周，问题最集中。保障期内：

- 安排现场或远程值守，约定响应时间。
- 每天汇总问题，按类型与严重程度分类，跟踪处理。
- 与关键用户保持联系，及时了解使用情况。
- 根据问题补充培训与常见问题。

#### 09.2 问题分类

| 类型 | 处理方式 |
| --- | --- |
| 使用问题 | 解答，补充到常见问题与培训材料 |
| 配置问题 | 修正配置并记录 |
| 数据问题 | 核实来源，按约定的规则修正，并检查是否影响其他数据 |
| 缺陷 | 提交给开发团队，说明影响与临时办法 |
| 需求变更 | 记录并按变更流程处理 |

#### 09.3 交接

交接给运维与支持团队的材料：

- 系统架构与部署说明。
- 配置清单与修改记录。
- 运维手册：启停、备份与恢复、监控与告警、常见故障的处理。
- 账号与权限清单（凭证通过安全的方式交接）。
- 已知问题与临时办法。
- 双方联系人与升级路径。

交接时，由接手的人在实施工程师的陪同下完成几项典型的运维与支持操作，确认能够独立处理。运维的方法见[《运维工程师与 SRE》](13-运维工程师与SRE.md)，支持的方法见[《客户成功与技术支持》](20-客户成功与技术支持.md)。

#### 09.4 验收与结项

按约定的验收标准完成验收，确认遗留问题的处理方式与期限，归档实施过程中的全部材料。

**本章验收**：完成一次上线后的保障，每天输出问题汇总；编写运维手册并完成交接，由接手的人独立完成三项典型操作。

## 第三篇：专项与进阶

<a id="ch10"></a>

### 10 私有部署的升级与长期维护

#### 10.1 升级

- **版本兼容**：维护版本兼容矩阵，说明支持的操作系统、数据库与中间件版本。
- **升级路径**：说明能否跨版本直接升级，还是需要逐个版本升级。
- **数据库变更**：数据库结构的变更以版本化的迁移脚本管理，随程序一起发布与执行。演进式数据库设计的做法是把数据库变更拆成小的、可组合的迁移，并与代码一起存放在版本库中。[B05](#ref-b05)
- **回退**：升级前备份，并确认回退的方法与所需时间。

#### 10.2 补丁与安全更新

建立安全更新的通知与发布机制：客户怎样得知需要更新、更新的紧急程度、更新的步骤。安全更新的发布不能等到下一个常规版本。

#### 10.3 多客户的版本管理

私有部署的客户越多，同时需要维护的版本就越多。尽量减少长期维护的版本数量，鼓励客户按计划升级，并记录每个客户的版本、配置与定制内容。

#### 10.4 备份与恢复演练

确认备份的范围、频率与保存位置，定期演练恢复，验证备份确实可用。

**本章练习**：为一个私有部署的系统编写升级说明，包括兼容矩阵、升级路径、数据库迁移、备份与回退；在测试环境中完成一次跨版本升级与回退演练。

<a id="ch11"></a>

### 11 客户环境中的安全

#### 11.1 访问客户环境

- 访问前获得客户的授权，按客户要求使用指定的访问方式，例如堡垒机。
- 使用个人账号而不是共享账号，权限仅限实施所需，实施结束后收回。
- 操作留有记录，重要操作事先告知客户。

#### 11.2 客户数据

- 不把客户的生产数据复制到自己的电脑或公司环境中。
- 测试与培训使用脱敏或虚构的数据。
- 需要用真实数据排查问题时，获得客户同意，在客户的环境中完成。

#### 11.3 凭证

凭证通过安全的方式传递与保管，不写在文档、聊天记录或配置文件里；实施结束后，提醒客户修改实施期间使用过的密码。

#### 11.4 软件物料清单

客户的安全审查可能要求提供软件物料清单，列出系统使用的全部组件与版本，便于评估漏洞的影响。SPDX 与 CycloneDX 是两种常用的物料清单格式。[B06](#ref-b06) [B07](#ref-b07) 国内项目还可能涉及网络安全等级保护的要求，具体由客户的安全与合规负责人确认。安全方法见[《安全工程师》](12-安全工程师.md)。

**本章练习**：审查一次实施中对客户环境的访问方式、账号、权限与数据处理，列出不符合上述原则的地方并提出改进；为系统生成一份软件物料清单。

<a id="ch12"></a>

### 12 实施方法的标准化

#### 12.1 实施手册

把实施的阶段、每个阶段的工作、检查清单、模板与常见问题整理成实施手册。新成员可以按手册完成工作，有经验的成员也能减少遗漏。

#### 12.2 工具化

把重复的工作变成工具：环境检查脚本、部署脚本、配置校验、数据核对脚本、健康检查。工具的价值在于把经验固化下来，减少人为的差错。

#### 12.3 度量

| 指标 | 含义 |
| --- | --- |
| 实施周期 | 从启动到上线的时间 |
| 一次上线成功率 | 不需要回退即上线成功的比例 |
| 上线后问题数 | 保障期内的问题数量与严重程度 |
| 客户方等待时间 | 因客户方配合事项而等待的时间 |
| 客户满意度 | 客户对实施过程的评价 |

#### 12.4 知识库

记录每个客户环境的特殊情况、遇到的问题与解决方法。跨项目汇总后，可以发现产品与实施方法中需要改进的地方。

**本章练习**：比较最近三次实施的周期与上线后问题数，找出耗时最多与问题最多的环节，为其中一个环节编写检查清单或工具。

<a id="ch13"></a>

### 13 变革管理与用户采用

#### 13.1 系统上线会改变人的工作方式

新系统意味着新的流程、新的习惯与新的责任分配。即使系统本身没有问题，使用者也可能因为不习惯、不信任或担心增加工作而抵触。

#### 13.2 做法

- **识别受影响的人**：谁的工作会改变？改变有多大？
- **说明原因**：让使用者了解为什么要换系统，对自己有什么好处。
- **关键用户**：在每个部门或区域培养熟悉系统的关键用户，帮助身边的同事。
- **听取反馈**：上线初期主动收集反馈，快速解决影响使用的问题。
- **关注采用**：统计实际的使用情况，对使用率低的部门或角色了解原因。

客户上手与采用的度量见[《客户成功与技术支持》第 07 章](20-客户成功与技术支持.md#ch07)。

**本章练习**：为一次上线列出受影响的角色、工作方式的变化与可能的抵触，设计关键用户的安排与上线初期的反馈收集方式。

<a id="ch14"></a>

### 14 AI 系统的实施

#### 14.1 实施中的特殊工作

- **知识与数据导入**：导入客户的文档与数据，确认解析质量，保留来源与权限信息。
- **权限**：检索与生成的结果遵守原文档的访问权限，不同部门的使用者只能看到自己有权查看的内容。
- **在客户数据上评测**：用客户的真实问题与数据建立评测集，上线前确认效果达到约定的标准。
- **配置与版本**：记录使用的模型、提示词与检索数据的版本，变更后重新评测。
- **数据驻留**：确认数据的处理与存储位置符合客户的要求与适用的规定。

#### 14.2 上线后

收集使用者对结果的反馈，定期抽查输出；客户文档中可能包含试图改变模型行为的文字，需要按方案中的防护措施处理。AI 方案的设计见[《解决方案架构师》第 13 章](22-解决方案架构师.md#ch13)，评测方法见[《算法与机器学习工程师》第 12 章](18-算法与机器学习工程师.md#ch12)。

**本章练习**：为一次 AI 功能的实施编写导入与评测计划，包括数据来源、权限映射、评测集与通过标准，并在上线前完成一次评测。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与开发者的协作接口

#### 15.1 实施工程师需要开发者提供的内容

| 内容 | 作用 |
| --- | --- |
| 安装包与部署脚本 | 可重复地部署，包括离线环境 |
| 配置说明 | 每个配置项的含义、取值与影响 |
| 升级说明与数据库迁移脚本 | 安全地升级与回退 |
| 版本兼容矩阵 | 判断客户环境是否满足要求 |
| 诊断与健康检查工具 | 现场快速判断系统状态 |
| 已知问题与临时办法 | 减少现场排查的时间 |

#### 15.2 开发者需要实施工程师提供的内容

客户环境的真实情况、现场问题的完整证据（日志、配置、步骤）、定制需求的真实业务场景、部署与升级过程中的困难。

#### 15.3 共同的做法

- 把可部署性与可运维性作为需求：安装、配置、升级、诊断都需要设计与测试。
- 开发团队定期参与或观察实施，了解真实环境中的问题。
- 现场的临时修改必须回到版本库，不能只存在于某个客户的环境中。

<a id="ch16"></a>

### 16 开发者怎样借用实施方法

#### 16.1 独立开发者为客户部署

- 把部署过程写成脚本，配置与代码分开。
- 交付时提供部署说明、配置清单、备份与恢复方法。
- 上线前准备回退方法；上线后约定一段保障期。
- 凭证通过安全的方式交给客户，并提醒客户修改。

#### 16.2 外包项目

不要低估实施阶段：环境准备、联调、迁移与培训往往占用大量时间，而且依赖客户方的配合。在计划中为这些工作留出时间，并把客户方的配合事项写进合同或计划。

#### 16.3 技术背景的常见偏差

- 在生产环境中手工修改配置，不留记录。
- 迁移脚本只在少量数据上测试过。
- 培训变成功能介绍，使用者仍不会完成自己的工作。
- 只考虑上线，不考虑回退。

<a id="ch17"></a>

### 17 贯穿实战：连锁企业招聘管理系统的实施

本章从实施的角度展示一个外包项目，方案设计见[《解决方案架构师》第 17 章](22-解决方案架构师.md#ch17)，项目管理见[《项目经理与交付经理》第 17 章](21-项目经理与交付经理.md#ch17)。客户、时间与数字均为示意。

#### 17.1 环境调研

- 招聘管理系统部署在公有云上，由交付方运维；客户的人事系统在自建机房，只能通过客户的接口网关访问。
- 门店店长主要使用手机；部分门店的网络较慢。
- 客户要求远程访问通过堡垒机进行，并在工作时间外操作需要提前申请。
- 风险：接口网关的白名单开通需要两周审批，列入客户方配合事项并提前申请。

#### 17.2 部署与联调

1. 用同一套部署脚本完成测试、预生产与生产环境的部署，环境差异全部记录在配置清单中。
2. 与人事系统联调时发现缺少门店编码字段（这一风险在方案阶段已被列为最高风险）。客户补充字段前，先用门店名称对照表完成开发与测试，字段补充后切换为正式的编码。
3. 联调覆盖了正常流程与超时、重复推送、门店不存在等异常场景，双方签字确认联调记录。

#### 17.3 数据迁移

- **范围**：各门店表格中的在途应聘者约 3000 条。
- **清洗**：发现约 8% 的记录存在问题：同一手机号的重复申请、手机号格式错误、门店名称写法不一致。清洗规则经人事经理书面确认：同一手机号、同一门店的申请合并为一条，保留最新状态。
- **试迁移**：完成两次试迁移，第二次的数量、状态分布与抽样核对全部通过。
- **正式迁移**：每一批门店上线前的周末执行，迁移开始后门店暂停在表格中登记新的申请。

#### 17.4 培训与切换

- 每个区域先培训两名关键用户，再由实施工程师与关键用户一起培训店长；培训以“筛选今天的申请”“安排面试”“提交录用审批”三个任务进行实际操作考核。
- 第一批 20 家试点门店在周一上午上线，避开周末的招聘高峰；回退条件为“店长无法查看或筛选申请超过 2 小时”。上线顺利，没有触发回退。
- 其余门店按区域分两批上线，每批前一周完成培训，旧表格并行使用两周后停用。

#### 17.5 保障与交接

- 每批上线后安排两周保障期，每天汇总问题。最常见的问题是手机端填写面试评价不便，记录为二期需求；配置问题当天修正。
- 交接材料包括部署说明、配置清单、运维手册、已知问题与联系人；运维团队在实施工程师陪同下完成了重启、备份恢复与新增门店三项操作。
- 实施知识库中补充了接口网关白名单的审批周期与门店名称对照表的处理方法。

#### 18.5 检查清单

- [ ] 环境调研完成并经客户确认，客户方配合事项写进计划。

- [ ] 上线后有保障期，每天汇总问题。
- [ ] 交接材料完整，接手人能独立完成典型操作。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 实施就是安装软件 | 还包括配置、联调、迁移、培训、切换与交接 |
| 部署文档写清楚就够了 | 部署应当脚本化，才能可靠地重复 |
| 数据迁移只要总数对上就行 | 还需要核对汇总值、抽样与业务场景 |
| 清洗规则由技术人员决定 | 清洗是业务决定，需要客户确认 |
| 培训完成就是会用了 | 需要实际操作考核与上线后的跟进 |
| 有回退方案就安全了 | 回退方案需要演练，确认能在约定时间内完成 |
| 上线成功就可以离场 | 上线后的保障期问题最集中 |
| 现场改一下配置没关系 | 修改要有记录，并回到版本库 |
| 用客户的真实数据测试更方便 | 测试与培训应使用脱敏或虚构的数据 |

### C.2 内容边界
