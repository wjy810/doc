# 安全工程师／应用安全工程师进阶全景手册

> 从发现并修复一个漏洞，到让系统在设计上就难以被攻破，再到建立组织的安全开发、漏洞管理与事件响应体系。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：希望掌握安全开发实践的开发者与测试工程师、需要为自己的产品负责安全的独立开发者和外包团队，以及希望系统提升的在职应用安全工程师。

安全工程师要回答的核心问题是：谁可能以什么方式损害这个系统、它的数据和它的用户，损害会有多严重，以及怎样以合理的成本预防、发现和应对。应用安全工程师（AppSec）专注于软件本身：设计是否有缺陷、代码是否有漏洞、依赖是否可信、权限是否正确、敏感数据是否得到保护。

安全常被看作“上线前做一次扫描”或“出事后再处理”，这样做代价最高。安全工程师的价值在于让安全成为软件开发的一部分：在设计阶段识别威胁，在开发阶段提供安全的默认做法与工具，在发布前验证，在运行中检测与响应，并让团队能够自己做出安全的决定。

本手册先建立角色坐标，然后讲解威胁建模、安全设计原则与架构评审、身份与访问控制、安全编码与常见漏洞、安全测试与工具链、软件供应链、漏洞管理；随后进入数据保护、云与基础设施安全、安全运营与事件响应、AI 应用安全、安全治理与合规；最后说明安全工程师与开发者的协作，以及开发者应掌握的安全基本功。本手册以防御为目的，只讨论识别、预防、检测与修复，不提供攻击操作指导；任何安全测试都应在获得明确授权的范围内进行。

主线是：**识别资产与威胁 → 设计安全的架构 → 正确实现身份与权限 → 编写安全的代码 → 在流水线中持续验证 → 管理依赖与漏洞 → 检测与响应事件 → 建立组织的安全开发体系。**

不同组织中，安全职责可能由应用安全工程师、产品安全工程师、云安全工程师、安全运营工程师、渗透测试人员和治理合规人员分担，小团队中常由技术负责人兼任。本手册描述应用安全的职责与方法；D1—D6 分级是学习组织方式，不对应任何职级体系。涉及法律法规的内容，只说明工程层面的做法，具体义务由法务或合规负责人确认。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 安全工程师负责什么

#### 01.1 核心问题：保护什么、防范谁、做到什么程度

安全的基本目标常概括为保密性（信息不被未授权的人获取）、完整性（信息与系统不被未授权地修改）和可用性（授权的人能在需要时使用）。安全工作从三个问题开始：有哪些值得保护的资产（用户数据、资金、账号、业务能力、声誉）？可能的威胁来自谁、通过什么途径？在有限的资源下，把风险降低到什么程度是可以接受的？

安全不追求“绝对安全”，而是有意识地管理风险：识别最重要的风险，用合适的措施降低它，并能够发现和应对剩余风险的发生。

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 威胁模型 | 识别设计中的威胁与对策 | 基于数据流与信任边界，威胁有优先级与负责人 |
| 安全设计评审意见 | 在实现前修正设计缺陷 | 具体、可执行，说明风险与替代方案 |
| 安全需求与规范 | 让团队默认做对 | 按场景给出要求与示例，能自动检查的就自动检查 |
| 安全工具链 | 持续发现问题 | 集成在开发流程中，误报可控 |
| 漏洞报告与修复跟踪 | 管理已知风险 | 有严重程度、影响、修复期限与验证 |
| 事件响应预案与复盘 | 在事件中减少损失 | 角色清楚、步骤可执行、复盘有改进措施 |
| 安全培训与安全倡导者网络 | 提升团队能力 | 按角色与场景设计，配合实际练习 |
| 合规证据 | 满足审计与客户要求 | 与实际控制措施一致，可追溯 |

#### 01.3 职责边界与相邻角色

| 事项 | 安全工程师的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 安全需求与风险判断 | 主导 | 产品经理、业务方 | 风险接受由业务负责人决定 |
| 威胁建模与设计评审 | 主导或指导 | 架构师、开发者 | 团队熟练后可以自主进行 |
| 安全编码 | 指导与评审 | 开发者负责实现 | |
| 安全测试 | 主导专项测试 | 测试工程师 | 常规安全检查纳入日常测试 |
| 基础设施与云安全 | 共同负责 | 平台工程师、SRE | |
| 安全监控与事件响应 | 共同负责 | 安全运营、SRE | |
| 隐私与数据保护 | 共同负责 | 法务、数据团队 | 法律义务由法务确认 |
| 合规审计 | 提供技术证据 | 合规负责人 | |

#### 01.4 不同组织中的形态

- **应用安全工程师**：关注软件的设计、代码与依赖。
- **产品安全工程师**：嵌入产品团队，覆盖产品的完整安全生命周期。
- **云与基础设施安全工程师**：关注云配置、身份、网络与平台。
- **安全运营工程师**：监控、检测与响应。
- **渗透测试与红队**：在授权范围内模拟攻击，检验防御。
- **治理、风险与合规**：政策、审计与认证。
- **兼任者**：小团队中由技术负责人或资深开发者兼任。

**本章练习**：为一个你熟悉的系统列出 5 项最重要的资产，以及每项资产被泄露、篡改或不可用时的后果，按严重程度排序。

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **威胁建模与风险分析**：识别资产、威胁、攻击面与对策。
2. **安全架构与设计**：信任边界、最小权限、纵深防御与安全默认值。
3. **身份与访问控制**：认证、会话、授权、服务间身份。
4. **安全编码**：常见漏洞的成因与预防。
5. **安全测试与工具**：静态、动态、依赖与密钥扫描，渗透测试协作。
6. **供应链安全**：依赖、构建、制品与来源。
7. **漏洞管理**：分级、修复、例外与度量。
8. **数据保护**：分类、加密、密钥、脱敏与隐私工程。
9. **检测与响应**：日志、告警、事件响应与复盘。
10. **治理与文化**：安全开发流程、合规、培训与安全倡导者。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 理解常见漏洞与原则，能运行工具并解读结果 | 扫描结果分析、修复记录 |
| D2 独立完成 | 独立完成一个功能的威胁建模与安全评审 | 威胁模型、评审意见、修复验证 |
| D3 负责结果 | 对一个产品的安全负责 | 安全路线图、漏洞趋势、事件处理 |
| D4 系统与跨团队 | 负责多产品的安全架构与工具链 | 统一的身份方案、安全平台、跨团队标准 |
| D5 方法与机制 | 建立组织的安全开发体系与成熟度评估 | 安全开发流程、度量、培训与倡导者网络 |
| D6 创新与影响 | 发现新的漏洞类型或防御方法，影响行业 | 公开研究、开源工具、标准贡献 |

#### 02.3 成长中的常见偏差

- 只依赖扫描工具，把工具报告当作安全评估。
- 用“绝对安全”的标准否决方案，而不提供可行的替代方案。
- 只关注技术漏洞，忽视业务逻辑与权限设计问题。
- 安全团队成为瓶颈，所有变更都要等待安全审批。
- 只在出事后介入，没有参与设计。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 威胁建模

#### 03.1 四个基本问题

《威胁建模宣言》把威胁建模概括为四个问题：我们在构建什么？可能出什么问题？我们打算怎样应对？我们做得够好吗？[B01](#ref-b01) 威胁建模不需要复杂的工具，关键是在设计阶段系统地思考，并让结果进入需求与测试。

#### 03.2 用数据流图描述系统

画出系统的数据流图：外部实体（用户、第三方服务）、处理过程（服务、任务）、数据存储（数据库、对象存储、缓存）、数据流，以及信任边界（数据从一个信任级别进入另一个级别的地方，例如从浏览器进入服务端、从业务系统调用外部模型）。大多数威胁出现在信任边界上。

#### 03.3 STRIDE

微软提出的 STRIDE 是常用的威胁分类方法，帮助系统地检查每个元素：[B02](#ref-b02)

| 类别 | 含义 | 对应的安全属性 | 示例 |
| --- | --- | --- | --- |
| 仿冒 | 冒充他人或其他系统 | 认证 | 盗用他人账号登录 |
| 篡改 | 未授权修改数据或代码 | 完整性 | 修改请求参数改变他人的数据 |
| 抵赖 | 否认做过某事 | 不可否认性 | 没有日志证明谁删除了数据 |
| 信息泄露 | 未授权获取信息 | 保密性 | 通过猜测编号访问他人简历 |
| 拒绝服务 | 使系统不可用 | 可用性 | 上传超大或特制文件耗尽资源 |
| 权限提升 | 获得不应有的权限 | 授权 | 普通用户调用管理接口 |

#### 03.4 排序与跟踪

为每个威胁评估可能性与影响，确定优先级、对策和负责人。威胁模型应随设计变化更新，高优先级威胁的对策要进入需求和测试，并在发布前验证。

**本章验收**：为一个功能绘制数据流图并标出信任边界，用 STRIDE 识别至少 10 个威胁，为前 5 个写出对策、负责人与验证方法。

<a id="ch04"></a>

### 04 安全设计原则与架构评审

#### 04.1 经典的设计原则

Saltzer 与 Schroeder 在 1975 年总结的信息保护设计原则至今仍有指导意义，包括：机制尽量简单；默认拒绝；对每次访问都进行检查；设计不依赖保密；权限分离；最小权限；尽量减少共享的机制；易于正确使用。[B03](#ref-b03) 在现代系统中，这些原则体现为：

| 原则 | 实践 |
| --- | --- |
| 最小权限 | 服务、用户、密钥只拥有完成任务所需的最小权限 |
| 默认拒绝 | 未明确允许的访问一律拒绝 |
| 完全检查 | 每个入口、每次访问都检查授权，包括内部接口与后台任务 |
| 纵深防御 | 多层措施，任何一层失效都不导致全部失守 |
| 安全默认值 | 默认配置就是安全的，不安全的选项需要明确开启 |
| 失败时安全 | 出错时拒绝访问，而不是放行 |
| 减少攻击面 | 关闭不需要的接口、端口、功能与调试入口 |

#### 04.2 零信任

零信任的核心思想是不因为网络位置而默认信任：每次访问都基于身份、设备状态与上下文进行验证和授权。美国国家标准与技术研究院的 SP 800-207 描述了零信任架构的原则与组成。[B04](#ref-b04) 对应用开发者来说，最直接的含义是：内部服务之间同样需要认证与授权，不能假设“内网的请求都是可信的”。

#### 04.3 安全架构评审

评审重点：信任边界与身份传递、授权检查的位置、敏感数据的存储与传输、密钥管理、外部输入的处理、第三方集成、日志与审计、失败时的行为。评审意见要具体，说明风险、影响与可行的替代方案，并区分必须修改与建议改进。

**本章练习**：用上面的原则检查一个系统的架构，找出至少 3 处违背最小权限或默认拒绝的设计，并提出改进方案。

<a id="ch05"></a>

### 05 身份、认证与授权

#### 05.1 认证

- **密码**：使用成熟的密码哈希算法存储；检查常见与已泄露的密码；不要强制定期更换或设置复杂但无效的组合规则。美国国家标准与技术研究院的数字身份指南 SP 800-63-4 于 2025 年发布，提供了认证方面的详细要求。[B05](#ref-b05)
- **多因素认证**：对重要账号与操作启用；优先使用抗钓鱼的方式。
- **通行密钥**：基于 WebAuthn 与 FIDO 标准，用设备上的密钥代替密码，具有抗钓鱼的特性。[B06](#ref-b06)
- **会话**：安全地生成与存储会话标识，设置合理的过期，登出与修改密码时使会话失效。

#### 05.2 OAuth 与 OpenID Connect

OAuth 2.0 用于授权第三方访问资源，OpenID Connect 在其上提供身份认证。IETF 在 2025 年发布的 RFC 9700 汇总了 OAuth 2.0 的安全最佳实践，并弃用了一些不安全的使用方式。[B07](#ref-b07) 实现时优先使用成熟的库与身份服务，而不是自己实现协议。

#### 05.3 授权

授权是应用安全中最常见、影响最大的问题之一。OWASP Top 10:2025 把“访问控制失效”列为第一位。[B08](#ref-b08) 常见问题包括：

- **对象级授权缺失**：只检查用户是否登录，不检查用户是否有权访问这个具体对象（例如通过修改编号访问他人的简历）。
- **功能级授权缺失**：普通用户可以调用管理功能。
- **字段级授权缺失**：用户可以修改不应由他修改的字段（例如自己的角色或所属组织）。
- **遗漏的入口**：界面上隐藏了按钮，但接口仍然可以调用；后台任务、导出、搜索绕过了授权检查。

授权检查应集中、一致地实施，并覆盖所有入口。授权模型与组织生命周期的工程设计见[《后端进阶全景手册》第 10 章](../技术方向/后端进阶全景手册.md#ch10)与[第 27 章](../技术方向/后端进阶全景手册.md#ch27)。

**本章验收**：为一个系统建立角色与对象的访问矩阵，编写自动化测试验证跨用户、跨组织访问被拒绝，覆盖接口、导出、搜索与后台任务。

<a id="ch06"></a>

### 06 安全编码与常见漏洞

#### 06.1 OWASP Top 10

OWASP Top 10 是最广为人知的 Web 应用安全风险清单。2025 版的十项是：访问控制失效、安全配置错误、软件供应链失效、加密失效、注入、不安全的设计、认证失效、软件或数据完整性失效、安全日志与告警失效、异常情况处理不当。[B08](#ref-b08) 与 2021 版相比，软件供应链与异常处理受到了更多关注。它是认识风险的入口，不是完整的检查清单。

#### 06.2 常见漏洞的预防原则

| 漏洞类型 | 成因 | 预防原则 |
| --- | --- | --- |
| 注入（SQL、命令等） | 把不可信数据当作代码执行 | 参数化查询，避免拼接命令，使用安全的 API |
| 跨站脚本 | 不可信数据未经编码输出到页面 | 按输出上下文编码，使用框架的自动转义，配置内容安全策略 |
| 服务端请求伪造 | 服务端按用户提供的地址发起请求 | 限制目标地址与协议，隔离出口网络 |
| 不安全的反序列化 | 反序列化不可信数据 | 避免反序列化不可信数据，使用安全的数据格式 |
| 路径遍历 | 用户输入用于文件路径 | 不直接使用用户输入构造路径，使用白名单 |
| 跨站请求伪造 | 浏览器自动携带凭证发起请求 | 使用框架的防护、合适的 Cookie 属性 |
| 不安全的文件上传 | 未校验文件类型、大小与内容 | 校验、隔离存储、限制解析资源、不直接执行 |
| 敏感信息泄露 | 在日志、错误信息中暴露 | 脱敏日志，统一错误处理 |

#### 06.3 验证标准

OWASP 应用安全验证标准（ASVS）把安全要求组织为可验证的条目，并按保证级别分层，2025 年发布了 5.0 版本。[B09](#ref-b09) 它适合用于制定安全需求、设计评审清单和测试范围。

**本章练习**：选择 OWASP Top 10:2025 中的 3 项，在你的代码库中查找可能的问题，写出修复方案与防止复发的自动检查。

<a id="ch07"></a>

### 07 安全测试与工具链

#### 07.1 工具类型

| 类型 | 做法 | 适合发现 | 局限 |
| --- | --- | --- | --- |
| 静态分析 | 分析源代码 | 注入、不安全的 API 使用 | 误报较多，难以发现业务逻辑问题 |
| 依赖扫描 | 检查依赖中的已知漏洞 | 有公开漏洞的组件 | 只能发现已知漏洞 |
| 密钥扫描 | 检查代码与历史中的凭证 | 泄露的密钥与令牌 | 需要配合密钥轮换 |
| 动态扫描 | 对运行中的应用发起测试 | 配置问题、部分注入 | 覆盖有限 |
| 基础设施即代码扫描 | 检查配置文件 | 不安全的云与容器配置 | 需要与实际环境核对 |
| 渗透测试 | 由专业人员在授权范围内模拟攻击 | 业务逻辑与组合漏洞 | 成本高，是某个时间点的快照 |

#### 07.2 集成到开发流程

把快速、误报少的检查放在开发者的本地与代码合并前；把耗时的扫描放在每日构建或发布前。对每类发现设定处理规则：哪些阻止合并，哪些创建工单。持续调整规则，减少误报，否则开发者会逐渐忽视结果。OWASP 的 Web 安全测试指南提供了系统的测试方法。[B10](#ref-b10)

#### 07.3 渗透测试与漏洞奖励

渗透测试与漏洞奖励计划都必须有明确的授权与范围。渗透测试的结果要进入漏洞管理流程，并分析为什么常规流程没有发现这些问题。

**本章验收**：为一个代码库配置依赖扫描、密钥扫描与静态分析，统计一个月的发现、误报率与修复时间，调整规则后再比较。

<a id="ch08"></a>

### 08 依赖与软件供应链

#### 08.1 依赖的风险

现代应用的大部分代码来自依赖。风险包括：依赖中的已知漏洞、被篡改或恶意的包、仿冒名称的包、维护停止的项目、许可证问题。OWASP Top 10:2025 把软件供应链失效列为第三位。[B08](#ref-b08)

#### 08.2 实践

- **软件物料清单**：记录产品包含的组件与版本，常用格式有 CycloneDX 与 SPDX。[B11](#ref-b11) 物料清单能帮助快速判断新漏洞是否影响产品，但它本身不证明组件安全。
- **依赖更新**：定期更新，使用自动化工具创建更新请求，并依靠测试保证更新安全。
- **锁定与来源**：锁定依赖版本，从可信的仓库获取，检查完整性。
- **构建与发布**：保护构建流程，记录制品的来源，对制品签名。SLSA 框架描述了供应链完整性的级别要求，[B12](#ref-b12) Sigstore 等工具让制品签名与验证更容易。[B13](#ref-b13)

更多工程实践见[《后端进阶全景手册》第 14 章](../技术方向/后端进阶全景手册.md#ch14)。

**本章练习**：为一个项目生成软件物料清单，检查其中有已知漏洞与停止维护的组件，制定更新计划。

<a id="ch09"></a>

### 09 漏洞管理

#### 09.1 漏洞的来源

扫描工具、渗透测试、漏洞奖励、外部报告、供应商公告、事件调查。所有来源的漏洞进入统一的流程：接收、确认、分级、分配、修复、验证、关闭。

#### 09.2 分级

通用漏洞评分系统（CVSS）用于描述漏洞的技术严重程度，当前版本是 4.0。[B14](#ref-b14) 实际的优先级还要考虑：漏洞是否在野外被利用（美国网络安全与基础设施安全局的已知被利用漏洞目录可以作为参考）、[B15](#ref-b15) 是否暴露在互联网上、影响的数据与业务、是否有缓解措施。不要只按 CVSS 分数排序。

#### 09.3 修复期限与例外

按严重程度约定修复期限。暂时无法修复的漏洞，需要记录风险接受的理由、缓解措施、负责人和重新评估的日期，由有权限的业务负责人批准。

#### 09.4 度量

| 指标 | 含义 |
| --- | --- |
| 按严重程度的修复时间 | 是否在约定期限内修复 |
| 超期漏洞数量 | 风险积压情况 |
| 重复出现的漏洞类型 | 需要从源头改进的地方 |
| 例外数量与期限 | 接受的风险是否被跟踪 |

**本章练习**：为团队制定漏洞分级与修复期限规则，统计现有漏洞的状态，找出超期与重复出现的类型。

## 第三篇：专项与进阶

<a id="ch10"></a>

### 10 数据保护与隐私工程

#### 10.1 数据分类

按敏感程度对数据分类，例如公开、内部、敏感、高度敏感（身份证号、财务信息、健康信息等）。不同级别对应不同的存储、访问、传输、日志与保留要求。

#### 10.2 保护措施

- **传输加密**：所有外部与内部通信使用安全的传输协议。
- **存储加密**：敏感数据加密存储；密钥与数据分开管理，定期轮换。
- **密钥管理**：使用专门的密钥管理服务，不在代码与配置中保存明文密钥。
- **脱敏与最小化**：日志、测试数据与分析数据中去除或替换敏感信息；只收集必要的数据。
- **访问审计**：记录对敏感数据的访问。

#### 10.3 法规要求

中国的《网络安全法》《数据安全法》《个人信息保护法》以及网络安全等级保护制度，对数据分类分级、个人信息处理、安全保护措施等作出要求；面向欧盟用户的产品还需要关注 GDPR。工程团队负责实现与证明控制措施，具体义务由法务与合规负责人确认。删除与保留的工程实现见[《后端进阶全景手册》第 23 章](../技术方向/后端进阶全景手册.md#ch23)。

**本章练习**：为一个系统的数据做分类，标出每类数据的存储位置、加密方式、访问权限与日志中的处理方式，找出不符合要求的地方。

<a id="ch11"></a>

### 11 云与基础设施安全

#### 11.1 责任共担

使用云服务时，云厂商负责底层设施的安全，客户负责自己的配置、身份、数据与应用。很多云上的安全事件源于客户的配置错误，例如公开的存储桶、过宽的访问权限。

#### 11.2 关键实践

- 身份与权限：最小权限，避免长期有效的访问密钥，定期审查权限。
- 网络：分段与隔离，只开放必要的入口。
- 密钥与凭证：使用托管的密钥服务与短期凭证。
- 配置基线：参考互联网安全中心（CIS）等发布的基准，[B16](#ref-b16) 用基础设施即代码管理配置并扫描。
- 日志与监控：开启云平台的审计日志，监控异常的权限变更与访问。

**本章练习**：审查一个云账号的权限、存储与网络配置，找出过宽的权限与公开的资源，制定整改计划。

<a id="ch12"></a>

### 12 安全运营与事件响应

#### 12.1 检测

安全检测依赖日志与告警：认证与授权的失败、权限变更、敏感数据的异常访问、异常的流量与错误模式。OWASP Top 10:2025 把安全日志与告警失效列为一项风险，因为没有记录与告警，攻击可能长期不被发现。[B08](#ref-b08)

#### 12.2 事件响应

美国国家标准与技术研究院在 2025 年发布了事件响应指南 SP 800-61 第 3 版，把事件响应纳入网络安全风险管理，并与网络安全框架 2.0 对应。[B17](#ref-b17) 事件响应的基本过程包括：准备、检测与分析、遏制、清除与恢复、事后总结。

| 阶段 | 关键工作 |
| --- | --- |
| 准备 | 预案、联系人、工具、日志保留、演练 |
| 检测与分析 | 确认事件、判断范围与影响、保存证据 |
| 遏制 | 阻止扩大：禁用账号、轮换密钥、隔离系统 |
| 清除与恢复 | 修复漏洞、清除恶意内容、恢复服务并验证 |
| 事后总结 | 复盘原因、改进措施、必要时依法报告与通知 |

涉及个人信息泄露等情况时，可能有法定的报告与通知义务，需要法务参与判断。事件响应与 SRE 的事故处理有相似的协作方式（见[《运维工程师与 SRE》](13-运维工程师与SRE.md)）。

**本章练习**：为“发现生产数据库的访问凭证泄露到公开代码仓库”编写响应预案，组织一次桌面演练，记录发现的不足。

<a id="ch13"></a>

### 13 AI 应用安全

#### 13.1 新的风险

大模型应用带来新的攻击面。OWASP 的大模型应用风险清单中，提示注入位于第一位：不可信的输入（包括用户上传的文档、网页内容）可能包含试图改变模型行为的指令，而检索增强与微调都不能完全消除这一风险。[B18](#ref-b18) 过度代理能力指模型被授予了超出需要的功能、权限或自主性，可能在被操纵时造成损害。[B19](#ref-b19)

#### 13.2 防护原则

- **把模型的输出当作不可信的输入**：在使用前校验与编码，不直接执行。
- **权限在模型之外实施**：模型可以建议操作，但实际执行时由业务系统按用户身份检查授权。
- **最小功能与最小权限**：只给模型完成任务所需的工具与数据。
- **高影响操作需要人工确认**。
- **隔离不可信内容**：区分系统指令与外部内容，限制外部内容能触发的能力。
- **防止数据泄露**：检索结果按用户权限过滤；不在提示中放入不必要的敏感信息；注意模型服务商的数据处理条款。
- **记录与监控**：记录模型调用、工具调用与异常，便于检测与调查。

MITRE ATLAS 整理了针对 AI 系统的攻击技术与案例，可用于威胁建模。[B20](#ref-b20)

**本章验收**：为 AI 简历分析做一次威胁建模，覆盖简历中的隐藏指令、越权的工具调用、敏感信息泄露与模型服务商的数据处理，写出对策并实现 10 个对抗测试。

<a id="ch14"></a>

### 14 安全治理、合规与组织

#### 14.1 安全开发生命周期

把安全活动嵌入开发的各个阶段：需求阶段的安全需求，设计阶段的威胁建模，开发阶段的安全编码与工具，测试阶段的安全验证，发布阶段的检查，运行阶段的监控与响应。美国国家标准与技术研究院的安全软件开发框架（SSDF）与 OWASP 软件保证成熟度模型（SAMM）都提供了组织安全开发实践的框架，可用于评估现状与规划改进。

#### 14.2 合规

常见的合规框架包括信息安全管理体系标准 ISO/IEC 27001、中国的网络安全等级保护制度，以及各行业的专门要求。合规是安全的底线之一，但不等于安全：通过审计的系统仍可能有严重漏洞。把合规要求映射到实际的控制措施，用同一套证据满足多个框架，避免为每个审计重复工作。

#### 14.3 安全倡导者与文化

安全团队的人数总是有限的。安全倡导者计划在每个开发团队中培养对安全感兴趣的成员，作为团队与安全团队之间的桥梁：参与威胁建模、推动安全实践、第一时间处理团队的安全问题。安全文化的目标是让开发者把安全当作质量的一部分，而不是外部的检查。

**本章练习**：用 SAMM 或类似框架评估团队的安全开发实践，选出三个最需要改进的方面，制定一个季度计划。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与开发者的协作接口

#### 15.1 安全工程师应提供给开发者的内容

| 内容 | 最低要求 | 常见缺失 |
| --- | --- | --- |
| 安全需求 | 按场景的具体要求 | 只说“要安全” |
| 安全的默认做法 | 可直接使用的库、模板与配置 | 开发者自己摸索 |
| 漏洞报告 | 位置、影响、复现条件、修复建议 | 只有工具输出 |
| 工具与规则 | 误报少、反馈快 | 大量误报，开发者忽视结果 |
| 及时的支持 | 设计阶段就能获得意见 | 只在发布前出现 |

#### 15.2 开发者应提供给安全工程师的内容

设计变更与新的外部集成、数据流与权限模型、使用的依赖与第三方服务、发现的可疑问题、事件中的系统信息。

#### 15.3 一起工作的方式

安全工程师参与设计评审，而不只是发布前审批；开发者在设计中主动考虑威胁，遇到不确定的问题及早询问。对于发现的问题，双方共同寻找能修复根本原因、又不过度影响交付的方案。

<a id="ch16"></a>

### 16 开发者的安全基本功

#### 16.1 十条基本功

1. 每个入口都检查授权，包括对象级、功能级与字段级。
2. 使用参数化查询，不拼接 SQL 与命令。
3. 输出到页面时按上下文编码，使用框架的自动转义。
4. 不在代码、配置与日志中保存明文密钥和敏感数据。
5. 使用成熟的库实现认证、加密与协议，不自己发明。
6. 校验文件上传的类型、大小与内容，限制解析资源，隔离存储。
7. 服务端按用户提供的地址发起请求时，限制目标与协议。
8. 依赖保持更新，开启依赖与密钥扫描。
9. 错误信息不暴露内部细节，日志记录关键的安全事件。
10. 设计新功能时问一句：“如果有人恶意使用这个功能，会发生什么？”

#### 16.2 独立开发者与外包项目

独立开发者应优先使用托管的身份服务、开启框架的安全默认配置、启用依赖与密钥扫描，并定期备份与检查权限。外包项目中，在合同中约定安全要求（例如依据 ASVS 的级别）、漏洞修复的责任与期限、源代码与密钥的交接方式；交付时提供依赖清单与安全测试结果。

<a id="ch17"></a>

### 17 贯穿实战：求职平台的威胁建模与安全设计

本章展示一次完整的威胁建模与安全设计。内容都是示意。

#### 17.1 数据流与信任边界

```mermaid
flowchart LR
    U[学生浏览器] -->|上传简历、查看结果| API[应用服务]
    API --> DB[(业务数据库)]
    API --> OS[(对象存储)]
    API --> Q[任务队列]
    Q --> W[分析工作进程]
    W --> OS
    W --> LLM[外部模型服务]
    W --> DB
    E[招聘方后台] -->|查看授权的申请| API
```

信任边界包括：浏览器与应用服务之间、招聘方后台与应用服务之间、分析进程与外部模型服务之间、应用与对象存储之间。上传的简历内容在整个流程中都是不可信数据。

#### 17.2 主要威胁与对策

| 威胁 | 类别 | 对策 | 验证 |
| --- | --- | --- | --- |
| 修改编号访问他人的简历或分析结果 | 信息泄露 | 所有查询按当前用户与组织检查对象归属 | 跨用户、跨组织的自动化测试 |
| 招聘方看到未授权的申请 | 信息泄露 | 招聘方只能访问投递给本组织的申请；授权撤销后立即失效 | 权限变化测试 |
| 特制文件耗尽解析资源 | 拒绝服务 | 限制大小、解压体积、解析时间与内存；隔离解析进程 | 模糊测试与资源上限测试 |
| 简历中隐藏的指令影响模型 | 篡改 | 区分系统指令与简历内容；模型不能调用工具修改数据；输出按格式校验 | 对抗测试 |
| 日志中记录了简历全文 | 信息泄露 | 日志只记录标识与摘要，敏感字段脱敏 | 日志审查 |
| 外部模型服务保留简历数据 | 信息泄露 | 选择符合数据处理要求的服务与配置；只发送必要内容 | 合同与配置审查 |
| 账号被盗用 | 仿冒 | 检查泄露密码，支持多因素认证与通行密钥，异常登录提醒 | 认证测试 |
| 依赖中的已知漏洞 | 多类 | 依赖扫描、物料清单、定期更新 | 每日扫描 |

#### 17.3 落实与验证

- 授权检查集中在服务层，用访问矩阵生成自动化测试。
- 文件解析放在独立的进程中运行，设置资源上限，失败时返回明确的错误而不是崩溃。
- 为 AI 分析建立对抗测试集，每次提示词或模型变更时运行。
- 在持续集成中运行依赖扫描、密钥扫描与静态分析，严重问题阻止合并。
- 每季度复查威胁模型，并在新增招聘方 API 时更新。

#### 17.4 一次事件演练

团队演练“对象存储的访问策略被误改为公开”：监控在几分钟内发现策略变更并告警，值班人员按预案恢复策略、轮换相关凭证、检查访问日志，确认在暴露期间没有异常访问。复盘后增加了基础设施即代码扫描，禁止存储桶的公开访问配置。

<a id="ch18"></a>

#### 18.5 检查清单

- [ ] 新功能完成了威胁建模，高优先级威胁有对策与验证。
- [ ] 所有入口实施对象级、功能级、字段级授权。
- [ ] 认证使用成熟的方案，支持多因素认证。
- [ ] 不可信输入经过校验，输出按上下文编码。
- [ ] 文件上传与解析有类型、大小、资源与隔离限制。
- [ ] 密钥不在代码与配置中，敏感数据加密并在日志中脱敏。
- [ ] 依赖、密钥与静态扫描集成在持续集成中。
- [ ] 漏洞按分级规则在期限内修复，例外有批准与复查。
- [ ] 安全事件有日志与告警，事件响应预案经过演练。
- [ ] AI 功能把模型输出视为不可信，权限在模型之外实施。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 扫描工具没报问题就是安全的 | 工具只能发现部分问题，业务逻辑与权限问题需要设计评审与测试 |
| 内网是安全的 | 内部服务之间同样需要认证与授权 |
| 隐藏按钮就能阻止操作 | 授权必须在服务端检查 |
| 通过合规审计就安全了 | 合规是底线之一，不等于没有漏洞 |
| 安全是安全团队的事 | 安全是每个角色的责任，安全团队提供专业支持 |
| 越复杂的安全措施越好 | 复杂的措施容易被误用，安全默认值与简单机制更可靠 |
| 只要 CVSS 分高就先修 | 还要考虑实际利用情况、暴露面与业务影响 |
| 模型能自己判断请求是否合法 | 权限必须在模型之外由业务系统实施 |
| 加密了就安全了 | 还需要正确的密钥管理与访问控制 |

### C.2 内容边界

本手册以防御为目的，覆盖应用安全的职责与方法，不提供攻击操作指导，也不展开密码学、恶意代码分析与网络攻防的专业细节。任何安全测试都必须在获得明确授权的范围内进行。涉及法律法规的内容只说明工程做法，具体义务由法务或合规负责人确认。

相邻角色的展开见本系列其他各册，总览见[《职业角色全景》](README.md)。
