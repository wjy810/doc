# 算法与机器学习工程师进阶全景手册

> 从训练出一个能用的模型，到让模型在生产环境中持续、可靠、负责任地创造价值，再到建立组织的机器学习与 AI 工程体系。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：希望在产品中使用机器学习或大模型的开发者、准备转向算法或机器学习工程的工程师，以及希望系统提升的在职算法工程师与机器学习工程师。

算法工程师用模型解决产品问题：推荐用户可能感兴趣的岗位、判断一份简历与岗位的匹配程度、识别异常的交易、为用户生成修改建议。机器学习工程师侧重让模型可靠地运行：训练流程、模型服务、监控与平台。两者在很多公司由同一个人承担，本手册统称为“算法工程师”。

模型在实验环境中的效果只是起点。真正的难点在于：问题是否值得用机器学习解决、离线指标能否代表真实效果、上线后数据变化怎么办、模型出错时用户会受到什么影响、成本是否可以承受。大模型普及之后，很多工作从“训练一个模型”转向“选择、组合、约束与评测模型”，但这些难点并没有消失，评测反而变得更加重要。

本手册先建立角色坐标，然后讲解问题定义、数据与标签、基线与迭代、离线评测、在线验证、部署与服务、监控与持续训练；随后进入推荐与排序、大模型应用工程、大模型评测、负责任的 AI、机器学习平台；最后说明算法工程师与开发者的协作，并用岗位匹配与简历建议演示一次完整的工作。

主线是：**判断问题是否需要机器学习 → 定义目标与评测方法 → 准备数据与标签 → 建立基线并迭代 → 离线与在线验证 → 可靠地部署与监控 → 持续改进并管理风险。**

不同公司中，这些职责可能由算法工程师、机器学习工程师、数据科学家、研究科学家或 AI 应用工程师承担。本手册描述把模型用于产品的职责与方法，不展开具体算法的数学推导；D1—D6 分级是学习组织方式，不对应任何职级体系。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 算法与机器学习工程师负责什么

#### 01.1 模型在产品中的常见形态

| 形态 | 示例 | 关键难点 |
| --- | --- | --- |
| 预测与分类 | 预测用户是否会流失，判断内容是否违规 | 标签质量、错误代价不对称 |
| 排序与推荐 | 岗位推荐、搜索结果排序 | 反馈循环、位置偏差、冷启动 |
| 匹配 | 简历与岗位的匹配程度 | 公平性、可解释性 |
| 生成 | 生成简历修改建议、回答用户问题 | 事实性、评测、成本 |
| 感知 | 识别证件、解析文档版面 | 输入质量的差异、边界情况 |
| 异常检测 | 识别异常登录与欺诈 | 正样本稀少、对手会适应 |

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 问题定义与评测方案 | 明确模型要优化什么、怎样判断好坏 | 与产品目标对应，评测集有代表性 |
| 模型与训练流程 | 产生可用的模型 | 可复现，有版本，有基线对比 |
| 评测报告 | 支持上线决策 | 含分群结果、不确定性与已知问题 |
| 模型服务 | 为产品提供预测 | 满足延迟与成本要求，有降级方案 |
| 监控与重训机制 | 保持模型持续有效 | 能发现漂移与效果下降 |
| 模型说明 | 让使用者了解模型的用途与局限 | 写明适用范围、评测结果与风险 |

#### 01.3 职责边界与相邻角色

| 事项 | 算法工程师的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 产品目标与体验 | 协作 | 产品经理、设计师 | 见[《产品经理》](01-产品经理.md) |
| 训练数据与特征管道 | 协作 | 数据工程师 | 见[《数据工程师》](17-数据工程师.md) |
| 实验设计与效果分析 | 协作 | 数据分析师 | 见[《数据分析师与产品分析师》](16-数据分析师与产品分析师.md) |
| 模型服务的集成 | 协作 | 后端开发者 | 接口契约见 15 章 |
| 训练与推理的基础设施 | 协作 | 平台工程师、运维工程师 | 见[《平台工程师与研发效能》](14-平台工程师与研发效能.md) |
| 安全与滥用防护 | 协作 | 安全工程师 | 见[《安全工程师》](12-安全工程师.md) |

几组容易混淆的角色：

- **算法工程师与研究科学家**：研究科学家提出新方法并发表研究；算法工程师把方法用于具体产品并对效果负责。
- **算法工程师与数据科学家**：数据科学家侧重分析、统计建模与决策支持；算法工程师侧重把模型部署到产品中。两者在很多公司重叠。
- **算法工程师与 AI 应用工程师**：AI 应用工程师侧重基于大模型构建应用，较少训练模型；评测、数据与风险控制的方法两者相通。

#### 01.4 什么时候不需要机器学习

先判断问题是否真的需要机器学习：规则能否解决大部分情况？有没有足够的数据与可靠的标签？错误的代价是否可以承受？Google 的机器学习工程规则的第一条就是：不要害怕在没有机器学习的情况下发布产品。[B01](#ref-b01) 用简单规则上线，还能积累数据并建立评测基线。

**本章练习**：列出所在产品中三个可能使用模型的地方，分别判断规则方案能解决多大比例的情况、数据与标签是否充足、错误会造成什么影响，给出是否使用机器学习的结论。

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **问题定义**：把产品目标转化为可学习、可评测的问题。
2. **数据与标签**：数据收集、标注规范、特征与数据泄漏。
3. **建模与迭代**：基线、模型选择、错误分析与可复现。
4. **评测**：离线指标、数据划分、分群评测与不确定性。
5. **在线验证**：实验、灰度、影子部署与回滚。
6. **部署与服务**：推理方式、延迟、成本与降级。
7. **监控与持续训练**：漂移、延迟标签、重训与反馈循环。
8. **大模型应用**：提示词、结构化输出、检索增强、工具调用与评测。
9. **负责任的 AI**：公平、可解释、隐私、安全与文档。
10. **平台与体系**：训练流水线、模型注册、评测服务与资源管理。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 能复现已有模型、运行训练与评测 | 实验记录、评测结果 |
| D2 独立完成 | 独立完成一个模型从问题定义到上线 | 评测报告、上线记录 |
| D3 负责结果 | 负责一个产品领域模型的长期效果 | 指标改进记录、监控与重训机制 |
| D4 系统与跨团队 | 设计多模型系统或跨团队的模型能力 | 系统架构、共享模型与接口 |
| D5 方法与机制 | 建立组织的机器学习平台、评测与治理机制 | 平台、评测规范、上线流程 |
| D6 创新与影响 | 提出新方法并在实践或研究中验证 | 论文、开源项目、方法推广 |

#### 02.3 成长中的常见偏差

- 先选模型，后想问题，追逐最新的模型而不是解决问题。
- 只看一个离线指标，不做分群评测与错误分析。
- 训练数据中混入了未来信息，离线效果虚高。
- 不建基线，无法说明复杂模型带来了多少提升。
- 只关心模型，不关心上线后的监控、成本与降级。
- 把公平、隐私与安全当作上线后的补充工作。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 问题定义与目标

#### 03.1 从产品目标到模型目标

| 层次 | 示例 |
| --- | --- |
| 产品目标 | 帮助学生找到合适的岗位并投递 |
| 可度量的结果 | 推荐岗位的投递率、投递后进入面试的比例 |
| 模型目标 | 预测学生对某个岗位投递的概率，并据此排序 |
| 训练标签 | 曝光后是否投递 |

模型优化的通常是一个代理目标。代理目标与真实目标不一致时，模型会“学会”错误的东西：只优化点击率可能推荐标题吸引人但并不合适的岗位。定义目标时，写明代理目标与真实目标的差距，以及用哪些护栏指标防止偏离。

#### 03.2 错误的代价

不同的错误代价不同。把合适的岗位漏掉，用户少了一个机会；把明显不合适的岗位排在前面，用户会失去信任。代价不对称时，应调整决策阈值或损失函数，而不是只追求整体准确率。

#### 03.3 约束条件

在定义问题时一并确认：延迟要求、单次预测的成本上限、是否需要解释、能使用哪些数据、哪些因素不能作为特征、模型出错时的降级方式。

**本章练习**：为一个模型需求写出产品目标、可度量的结果、模型目标、训练标签与护栏指标，并说明代理目标可能与真实目标产生偏离的情况。

<a id="ch04"></a>

### 04 数据、标签与特征

#### 04.1 标签

- **标签来源**：用户行为（点击、投递）、人工标注、业务结果（是否录用）。行为标签量大但有噪声，人工标注质量高但成本高，业务结果最接近目标但延迟长。
- **标注规范**：写清每个标签的定义、边界示例与难以判断时的处理方式。
- **一致性检查**：让多人标注同一批样本，计算一致程度；一致性低时，先改进规范，而不是增加标注量。

#### 04.2 数据泄漏

数据泄漏指训练时使用了预测时无法获得的信息，使离线效果虚高、上线后效果下降。常见形式：

- 特征中包含标签的信息，例如用“是否发出面试邀请”预测“是否通过初筛”。
- 用全部数据做标准化、特征选择等预处理后再划分训练集与测试集。
- 时间相关的数据随机划分，用未来的数据预测过去。
- 同一个用户的样本同时出现在训练集与测试集中。

scikit-learn 文档的“常见陷阱”一节演示了预处理导致泄漏的情况与正确做法：预处理只在训练数据上拟合，再应用到测试数据。[B02](#ref-b02)

#### 04.3 特征

- 特征要在预测时可以获得，并且与训练时的计算方式一致。
- 记录每个特征的来源、计算逻辑与更新频率。
- 构建训练样本时使用当时的特征值（时点正确），见[《数据工程师》第 14 章](17-数据工程师.md#ch14)。
- 某些因素不应作为特征，例如在招聘场景中可能导致歧视的个人属性；也要注意与它们高度相关的替代变量。

#### 04.4 数据文档

为训练数据集记录：收集动机、组成、收集过程、预处理、用途与限制。Gebru 等人提出的“数据集说明书”给出了一组系统的问题。[B03](#ref-b03)

**本章验收**：为一个模型整理训练数据：写出标签定义与标注规范，检查并说明已排除的泄漏风险，记录特征的来源与计算方式，完成一份数据集说明。

<a id="ch05"></a>

### 05 基线与模型迭代

#### 05.1 先建立基线

| 基线 | 示例 |
| --- | --- |
| 规则 | 按专业与岗位类别的匹配规则排序 |
| 统计 | 按岗位热度排序 |
| 简单模型 | 逻辑回归、梯度提升树 |
| 现成模型 | 通用的文本向量模型计算相似度 |

复杂模型需要证明比基线更好，并且提升值得它增加的成本与维护负担。

#### 05.2 错误分析

指标提升停滞时，抽取模型出错的样本人工查看，按错误原因分类统计：标签错误、特征缺失、样本稀少的群体、输入格式异常等。错误分析常常比调整模型结构更能指出改进方向。

#### 05.3 可复现

记录代码版本、数据版本、参数、随机种子与运行环境，使用实验记录工具保存每一次训练的配置与结果。不能复现的结果无法比较，也无法在出问题时回退。

#### 05.4 实验纪律

- 测试集只用于最终评估，调参使用验证集。
- 每次只改变一个主要因素，便于判断改进来自哪里。
- 记录失败的实验，避免重复尝试。

**本章练习**：为一个问题建立两个基线和一个模型，比较三者的效果与成本，完成一次错误分析，按原因列出错误的比例并提出下一步改进。

<a id="ch06"></a>

### 06 离线评测

#### 06.1 选择指标

| 任务 | 常用指标 | 注意事项 |
| --- | --- | --- |
| 分类 | 精确率、召回率、F1、AUC | 类别不平衡时准确率会误导 |
| 概率预测 | 对数损失、校准程度 | 概率用于决策时需要校准 |
| 排序与推荐 | NDCG、召回率@K、MRR | 与用户实际看到的位置数量对应 |
| 回归 | 平均绝对误差、均方根误差 | 对极端值的敏感程度不同 |
| 生成 | 人工评分、基于规则的检查、模型评分 | 见 12 章 |

#### 06.2 数据划分

- 有时间顺序的数据按时间划分，用过去的数据训练，用之后的数据测试。
- 同一用户、同一岗位的样本放在同一侧，避免信息在训练与测试之间泄漏。
- 测试集的分布应接近上线后的真实分布。

#### 06.3 分群评测

整体指标可能掩盖某些群体上的严重问题。按用户类型、地区、设备、新老用户、输入质量等维度分别评测，并关注样本少的群体。

#### 06.4 不确定性

测试集有限，指标存在波动。用自助法等方法估计置信区间，两个模型的差异小于波动范围时，不能断定哪一个更好。

#### 06.5 离线与在线的差距

离线评测基于历史数据，而历史数据是旧系统产生的：用户只能对旧系统展示过的内容做出反应。新模型推荐的内容如果从未被展示过，离线评测无法判断用户是否喜欢。因此离线评测用于筛选，上线效果需要在线验证。

**本章验收**：为一个模型制定离线评测方案：选择主要与次要指标、说明数据划分方式、列出需要分群评测的维度，报告结果的置信区间，并说明离线评测无法回答的问题。

<a id="ch07"></a>

### 07 在线验证与上线

#### 07.1 上线方式

| 方式 | 做法 | 用途 |
| --- | --- | --- |
| 影子部署 | 新模型接收真实请求但不影响用户 | 检查延迟、错误率与预测分布 |
| 灰度发布 | 少量用户使用新模型 | 发现严重问题，控制影响范围 |
| 对照实验 | 随机分组比较新旧模型 | 判断对产品指标的因果影响 |
| 交错评测 | 把两个排序结果交错展示给同一用户 | 用较少流量比较排序质量 |

对照实验的设计与分析方法见[《数据分析师与产品分析师》第 07 章](16-数据分析师与产品分析师.md#ch07)。

#### 07.2 护栏与回滚

上线前确定护栏指标（延迟、错误率、投诉、成本）与回滚条件。模型版本与特征版本一起管理，回滚时两者一致。

#### 07.3 上线决策

综合主要指标、护栏指标、分群结果、成本与风险做出决策，并记录依据。主要指标提升但某个群体明显变差时，需要先解决或明确接受这一代价。

**本章练习**：为一个模型的上线制定计划：影子部署的检查项、灰度比例与时长、实验的主要与护栏指标、回滚条件，以及每一步的负责人。

<a id="ch08"></a>

### 08 模型部署与服务

#### 08.1 推理方式

| 方式 | 适合 | 注意事项 |
| --- | --- | --- |
| 批量推理 | 结果可以提前计算，例如每日推荐列表 | 结果有延迟，新用户没有结果 |
| 在线推理 | 需要根据实时输入预测 | 延迟、可用性与成本 |
| 流式推理 | 根据事件流持续更新 | 状态管理与一致性 |
| 端侧推理 | 在用户设备上运行 | 模型大小、设备差异、更新方式 |

#### 08.2 训练与服务的一致性

训练与服务时特征计算方式不同，是模型上线后效果下降的常见原因。Google 的机器学习工程规则专门讨论了这种“训练与服务偏差”。[B01](#ref-b01) 常见做法：训练与服务共用同一份特征代码，记录服务时的特征值并用于后续训练，定期比较两侧的特征分布。

#### 08.3 延迟与成本

- 为每次预测设定延迟预算，并拆分到特征获取、模型计算与后处理。
- 降低成本的方法：模型压缩与量化、蒸馏为较小的模型、批量处理请求、缓存结果、按请求的难度选择不同大小的模型。
- 监控每次预测的成本，与产品价值对照。

#### 08.4 降级与失败处理

模型服务不可用或超时时，使用规则、缓存结果或热门内容作为降级方案。降级状态要能被监控与记录，避免长时间静默降级。

**本章验收**：部署一个模型服务，设定并验证延迟预算；实现训练与服务共用的特征代码；演练一次模型服务故障，确认降级方案生效并被监控记录。

<a id="ch09"></a>

### 09 监控与持续训练

#### 09.1 监控什么

| 层次 | 内容 |
| --- | --- |
| 服务 | 延迟、错误率、吞吐、成本 |
| 输入 | 特征的缺失率与分布变化 |
| 输出 | 预测分布、置信度分布、降级比例 |
| 效果 | 在线指标；标签到达后的离线指标 |
| 分群 | 关键群体上的效果差异 |

#### 09.2 漂移与延迟标签

- **数据漂移**：输入数据的分布发生变化，例如招聘季的岗位类型变化。
- **概念漂移**：输入与输出之间的关系发生变化，例如市场变化后同样的简历的匹配结果不同。
- **延迟标签**：真实结果需要很久才能知道，例如投递后是否被录用。标签到达前，用输入与输出的分布变化作为早期信号。

#### 09.3 重训

重训可以按固定周期、按监控信号或两者结合触发。重训后的模型同样需要通过评测与上线流程，不能自动替换线上模型而不经过检查。

#### 09.4 反馈循环与技术债

模型的输出会影响未来的训练数据：推荐系统只展示模型认为好的岗位，用户也只能对这些岗位做出反应，模型因此越来越确信自己的判断。Sculley 等人的论文系统讨论了机器学习系统特有的技术债，包括反馈循环、数据依赖与配置复杂度。[B04](#ref-b04) Breck 等人提出的测试与监控评分表，可以用来检查一个机器学习系统是否具备上线所需的测试与监控。[B05](#ref-b05)

**本章验收**：为线上模型建立覆盖上表五个层次的监控，设定告警条件；说明重训的触发方式与上线前的检查，并识别系统中至少一个反馈循环及其缓解方法。

### 10 推荐、搜索与排序

#### 10.1 多阶段架构

候选集很大时，通常分为几个阶段：召回从全部候选中快速选出几百到几千个；粗排用较简单的模型初步排序；精排用更复杂的模型精细排序；重排考虑多样性、业务规则与去重。每个阶段在效果与计算成本之间权衡。

#### 10.2 常见问题

- **位置偏差**：排在前面的内容更容易被点击，不完全因为它更好。训练与评测时需要考虑这种偏差。
- **冷启动**：新用户与新岗位缺少行为数据，需要使用内容特征或探索策略。
- **探索与利用**：只推荐模型最有把握的内容，会让系统失去了解新内容的机会。
- **多目标**：点击、投递、面试、用户满意度等目标需要权衡。
- **双边公平**：在招聘等双边市场中，既要考虑求职者的体验，也要考虑岗位与企业获得曝光的机会。

搜索系统的检索与评价方法可参考[《后端进阶全景手册》第 22 章](../技术方向/后端进阶全景手册.md#ch22)。

**本章练习**：画出一个推荐系统的多阶段架构，标出每个阶段的候选数量、延迟预算与优化目标，并说明系统如何处理新岗位的冷启动。

### 11 大模型应用工程

#### 11.1 选择方案

| 方案 | 适合 | 代价 |
| --- | --- | --- |
| 提示词 | 任务清楚，通用模型已具备能力 | 成本最低，效果受模型能力限制 |
| 检索增强生成 | 需要使用私有或最新的知识 | 需要建设与维护检索数据 |
| 微调 | 需要固定的格式、风格或特定领域能力 | 需要训练数据、评测与模型维护 |
| 工具调用与智能体 | 需要执行多步骤操作 | 风险与评测难度明显增加 |

通常从提示词开始，用评测集判断是否需要更复杂的方案。检索数据的准备见[《数据工程师》第 14 章](17-数据工程师.md#ch14)。

#### 11.2 工程要点

- **结构化输出**：要求模型按约定的结构输出，并在程序中校验，校验失败时重试或降级。
- **版本管理**：模型、提示词、检索数据与工具定义都纳入版本管理，任何一项变化都需要重新评测。
- **成本与延迟**：控制上下文长度，缓存可复用的结果，按任务难度选择模型。
- **失败处理**：超时、拒答、格式错误与内容不当都需要处理方式。

#### 11.3 安全风险

- **提示词注入**：用户输入或检索到的文档中可能包含试图改变模型行为的指令。OWASP 将其列为大模型应用的首要风险。[B06](#ref-b06) 不要让模型输出直接决定高风险操作，对外部内容与系统指令加以区分，并对输出做校验。
- **过度授权**：给模型的工具与权限超出任务所需，一旦被诱导就可能造成损害。[B07](#ref-b07) 工具按最小权限设计，高风险操作需要用户确认。
- **数据泄露**：系统提示词、其他用户的数据与内部文档可能通过输出泄露，检索时按用户权限过滤。

AI 应用的后端设计见[《后端进阶全景手册》第 32 章](../技术方向/后端进阶全景手册.md#ch32)，交互设计见[《前端与 UI／UX 设计进阶全景手册》第 17 章](../技术方向/前端与UIUX设计进阶全景手册.md#chapter-17)。

**本章练习**：为一个大模型功能写出方案选择的理由、结构化输出的格式与校验方式、版本管理的范围，以及针对提示词注入与过度授权的防护措施。

<a id="ch12"></a>

### 12 大模型应用的评测

#### 12.1 评测集

- **代表性样本**：来自真实使用场景，覆盖主要的用户类型与任务。
- **边界情况**：信息不足、格式异常、超出范围的请求。
- **对抗样本**：试图诱导模型输出不当内容或执行越权操作的输入。
- **回归样本**：曾经出现过问题的案例，防止问题再次出现。

评测集要有版本，并与线上真实输入定期对照，避免评测集与实际使用脱节。

#### 12.2 评分方式

| 方式 | 适合 | 局限 |
| --- | --- | --- |
| 规则检查 | 格式、长度、是否包含必要字段 | 无法判断内容质量 |
| 参考答案对比 | 有明确正确答案的任务 | 开放式任务难以准备参考答案 |
| 人工评分 | 开放式任务的质量判断 | 成本高，需要评分标准与一致性检查 |
| 模型评分 | 大规模的初步评估 | 存在偏差，需要用人工评分校准 |

使用模型作为评分者时，研究发现它存在偏好特定位置的答案、偏好更长的回答、偏好与自己相似的输出等偏差。[B08](#ref-b08) 常见的缓解方法：交换答案顺序重复评分、提供明确的评分标准、定期用人工评分检查一致程度。

#### 12.3 持续评测

每次修改模型、提示词或检索数据，都在评测集上运行回归评测，并与上一版本比较；上线后抽样检查真实输出，并把发现的问题加入评测集。AI 功能的线上度量见[《数据分析师与产品分析师》第 13 章](16-数据分析师与产品分析师.md#ch13)。

**本章验收**：为一个大模型功能建立包含四类样本的评测集与评分标准，比较人工评分与模型评分的一致程度，并把评测接入每次修改的检查流程。

<a id="ch13"></a>

### 13 负责任的 AI

#### 13.1 公平

在招聘、信贷、教育等对人有重大影响的场景，模型可能对某些群体产生不合理的区别对待。做法包括：按群体评测效果与结果分布、检查特征中的敏感属性及其替代变量、为不公平的结果设定改进目标。不同的公平定义之间可能相互冲突，选择哪一种需要与产品、法务一起决定。

#### 13.2 可解释与申诉

对用户有重要影响的结果，应能说明主要依据，并为用户提供纠正与申诉的途径。解释要准确：不能把事后编造的理由当作模型的真实依据。

#### 13.3 隐私与安全

训练数据的使用需要合法依据；模型可能记住并泄露训练数据中的个人信息；用户输入的数据是否用于训练，需要明确告知并遵守承诺。

#### 13.4 文档与风险管理

- **模型说明**：Mitchell 等人提出的“模型卡”记录模型的用途、适用范围、评测方法、分群结果与已知局限。[B09](#ref-b09)
- **风险管理框架**：美国国家标准与技术研究院的 AI 风险管理框架提供了治理、映射、度量与管理四项职能，可用于组织 AI 风险的识别与处理。[B10](#ref-b10)
- **国内规则**：《互联网信息服务算法推荐管理规定》自 2022 年 3 月 1 日起施行，《生成式人工智能服务管理暂行办法》自 2023 年 8 月 15 日起施行，《人工智能生成合成内容标识办法》自 2025 年 9 月 1 日起施行。具体义务由法务与合规负责人确认。

**本章练习**：为一个对用户有重要影响的模型完成分群公平性评测，写出发现的差异与改进计划，并完成一份模型说明。

### 14 机器学习平台与工程体系

#### 14.1 平台的组成

| 组成 | 作用 |
| --- | --- |
| 数据与特征管理 | 统一特征的定义、计算与服务，保证训练与服务一致 |
| 实验记录 | 保存每次训练的配置、数据版本与结果 |
| 训练流水线 | 自动化数据准备、训练、评测与注册 |
| 模型注册 | 管理模型版本、状态与上线记录 |
| 评测服务 | 统一的评测集与评测流程 |
| 推理服务 | 部署、扩缩容、灰度与监控 |
| 资源管理 | 训练与推理的算力分配与成本统计 |

#### 14.2 建设顺序

不要一开始就建设完整的平台。先把一两个重要模型的流程做扎实，把重复出现的工作抽象为平台能力。平台工程的通用方法见[《平台工程师与研发效能》](14-平台工程师与研发效能.md)，数据部分见[《数据工程师》](17-数据工程师.md)。

#### 14.3 算力与成本

训练与推理的算力成本可能很高。为团队与项目统计成本，评估模型改进带来的价值是否大于成本，避免闲置的算力资源。

**本章练习**：盘点团队当前模型从训练到上线的全部步骤，标出手工完成的步骤及其耗时，选择一项最值得自动化的步骤并说明理由。

### 16 开发者怎样借用算法工程方法

#### 16.1 独立开发者与小团队

- 先用规则或现成的模型接口验证需求，再考虑训练自己的模型。
- 在写第一行模型代码之前，先准备一个包含几十到几百个样本的评测集。
- 记录每次修改提示词或模型后的评测结果。
- 为模型输出设计校验与降级，不让模型的错误直接到达用户或数据库。
- 控制成本：设定单次调用与每日的成本上限，并进行监控。

#### 16.2 外包与交付项目

与客户约定模型的验收方式：使用哪个评测集、达到什么指标、在什么条件下测量。不要承诺无法保证的准确率；说明模型会犯错，以及出错时的处理流程。明确训练数据与模型的所有权、数据的使用范围，以及交付后谁负责监控与更新。

#### 16.3 技术背景的常见偏差

- 把模型当作确定性的函数，不处理错误与不确定性。
- 只用几个例子手工测试就上线。
- 忽视成本，上线后才发现费用超出预算。
- 把用户输入直接拼接进系统指令，产生注入风险。

### 17 贯穿实战：岗位匹配与简历建议

本章以求职平台为例，展示一次完整的算法工作。数字均为示意。

#### 17.1 问题定义

- **岗位匹配**：为学生推荐合适的岗位。模型目标是预测学生对岗位投递的概率，护栏指标包括投递后被企业标记为“明显不符合”的比例、各学历与地区群体的推荐质量差异。
- **简历建议**：根据目标岗位为简历生成修改建议。目标是用户采纳且修改后质量提升的建议比例，护栏包括错误建议率、编造经历的比例与单次成本。

#### 17.2 岗位匹配

1. **基线**：按专业与岗位类别规则匹配，再按发布时间排序。
2. **模型**：召回阶段使用文本向量相似度与规则；排序阶段使用梯度提升树，特征包括技能匹配度、地点偏好、历史投递行为。
3. **离线评测**：按时间划分数据，排序模型在召回率@20 上比基线高约 15%；按学历层次与地区分群评测，发现某些地区的样本少、效果较差，计划补充数据。
4. **在线实验**：投递率提升约 8%，“明显不符合”比例没有上升，上线。

#### 17.3 简历建议

1. **方案**：先用提示词加结构化输出，要求每条建议包含问题、原因与修改示例，并标注依据的简历原文位置。
2. **评测集**：300 份脱敏简历与目标岗位组合，其中包括信息不足、格式异常的简历，以及试图在简历中嵌入指令的对抗样本。
3. **评分**：规则检查结构完整性与原文引用；人工按评分标准评估建议的正确性与有用性；模型评分用于大规模回归，每月用人工评分校准一次。
4. **安全**：简历内容作为数据传入，不作为指令；建议只能引用简历中实际存在的内容，校验失败的建议不展示。
5. **结果**：错误建议率从初版的 9% 降到 3%；上线后的建议采纳率见[《数据分析师与产品分析师》第 17 章](16-数据分析师与产品分析师.md#ch17)的实验。

#### 17.4 持续改进

监控投递率、建议采纳率与分群差异；每月把线上发现的问题样本加入评测集；更换底层模型前，必须在完整评测集上通过回归评测。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 有数据就应该用机器学习 | 先判断规则能否解决、标签是否可靠、错误代价能否承受 |
| 离线指标高说明上线效果好 | 离线评测基于旧系统产生的数据，需要在线验证 |
| 准确率是最重要的指标 | 类别不平衡与错误代价不对称时，准确率会误导 |
| 模型越新越大越好 | 需要与基线比较，并考虑延迟、成本与维护负担 |
| 上线之后模型就完成了 | 数据会漂移，需要监控与重训 |
| 模型评分可以代替人工评估 | 模型评分存在偏差，需要用人工评分校准 |
| 去掉敏感属性模型就公平了 | 其他特征可能是敏感属性的替代变量，需要分群评测 |
| 大模型只要提示词写好就不会出错 | 仍需评测、输出校验、降级与安全防护 |
| 换一个更强的模型一定更好 | 需要在完整评测集上回归评测后再决定 |
