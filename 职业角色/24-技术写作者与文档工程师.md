# 技术写作者与文档工程师进阶全景手册

> 从写清楚一篇操作说明，到为产品建立读者找得到、看得懂、信得过的文档体系，再到让文档与产品一起被设计、测试和交付。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：需要编写技术文档的开发者、准备转向技术写作或文档工程的工程师，以及希望系统提升的在职技术写作者、开发者文档工程师与开发者关系从业者。

技术写作者为产品编写读者需要的文档：入门教程、操作指南、参考文档、概念说明、发布说明、接口文档，以及团队内部的设计文档与运维手册。文档工程师则用工程的方法支撑文档：把文档纳入版本管理与评审流程，自动生成接口参考，检查链接与示例代码，构建、发布并维护文档站点。两者在很多团队中由同一人承担。

文档常被当作“功能做完之后补上的说明”。实际上，文档是产品体验的一部分：开发者能不能在十分钟内完成第一次接口调用，管理员能不能独立完成配置，用户遇到错误时能不能找到解决办法，很大程度上取决于文档。好的技术写作者从读者要完成的任务出发组织内容，用准确、一致的语言写作，并像对待代码一样测试和维护文档。

本手册先建立角色坐标，然后讲解读者与任务、文档类型与信息架构、清楚准确的写作、接口与开发者文档、评审与测试、文档即代码、文档的维护；随后进入内部文档、本地化、可访问性、度量与反馈、AI 与文档；最后说明与开发者的协作，并用求职平台开放接口的开发者文档演示一次完整的文档工作。

主线是：**理解读者与任务 → 规划文档的类型与结构 → 用清楚准确的语言写作 → 与产品一起评审与测试 → 用工程方法发布与维护 → 用反馈与度量持续改进。**

不同公司中，这些职责可能由技术写作者、文档工程师、内容设计师、开发者关系工程师、支持团队或开发者自己承担。本手册描述技术文档的职责与方法；界面文字与内容策略见[《内容设计师》](07-内容设计师.md)。D1—D6 分级是学习组织方式，不对应任何职级体系。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 技术写作者与文档工程师负责什么

#### 01.1 文档的读者与类型

| 读者 | 常见文档 | 读者的目标 |
| --- | --- | --- |
| 最终用户 | 帮助中心、操作指南、常见问题 | 完成具体的任务，解决遇到的问题 |
| 管理员 | 安装、配置、权限与维护说明 | 正确地部署与管理系统 |
| 开发者 | 快速开始、接口参考、示例、软件开发工具包文档 | 集成产品，完成开发 |
| 运维与支持人员 | 运维手册、排查指南、已知问题 | 维护系统，处理故障 |
| 团队内部 | 设计文档、架构决定记录、新人入门文档 | 理解系统，做出决定，快速上手 |

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 文档计划 | 明确读者、任务与要写的内容 | 基于真实的读者需求，有优先级 |
| 教程与操作指南 | 帮助读者学习与完成任务 | 读者能按步骤完成，结果可预期 |
| 参考文档 | 提供完整、准确的事实 | 与产品一致，结构统一，便于查找 |
| 概念说明 | 帮助读者理解原理与设计 | 解释为什么，而不只是怎么做 |
| 发布说明与变更日志 | 告知变化与影响 | 说明对读者的影响与需要的操作 |
| 文档工具链 | 支撑写作、评审、构建与发布 | 自动检查，发布可靠，便于贡献 |

#### 01.3 职责边界与相邻角色

| 事项 | 技术写作者的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 界面文字与错误信息 | 协作 | 内容设计师 | 见[《内容设计师》](07-内容设计师.md) |
| 技术事实的准确性 | 组织评审 | 开发者 | 开发者是技术事实的主要来源 |
| 支持知识库 | 协作 | 技术支持 | 见[《客户成功与技术支持》](20-客户成功与技术支持.md) |
| 培训材料 | 协作 | 实施工程师、培训人员 | 见[《实施与交付工程师》](23-实施与交付工程师.md) |
| 翻译与本地化 | 为翻译而写，管理流程 | 翻译与本地化团队 | 见 11 章 |
| 文档站点与工具链 | 主导或协作 | 文档工程师、平台工程师 | 见 08 章 |

几组容易混淆的角色：

- **技术写作者与内容设计师**：内容设计师侧重产品界面中的文字与内容策略；技术写作者侧重产品之外、帮助读者学习与完成任务的文档。两者在错误信息与帮助内容上紧密协作。
- **技术写作者与文档工程师**：技术写作者关注内容；文档工程师关注支撑内容的系统与流程。
- **技术写作者与开发者关系**：开发者关系侧重与开发者社区的互动、示例项目与技术推广；开发者文档是两者共同的重点。

**本章练习**：盘点一个产品的现有文档，按读者与类型分类，标出每类文档最近的更新时间，找出读者需要却缺失或明显过时的部分。

<a id="ch02"></a>

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **读者研究**：读者画像、任务分析、信息需求的来源。
2. **信息架构**：文档类型、导航、页面结构与交叉链接。
3. **写作与编辑**：清楚、准确、一致的语言，中英文排版与风格指南。
4. **开发者文档**：接口参考、快速开始、示例代码、错误参考与变更日志。
5. **评审与测试**：技术评审、编辑评审、文档的可用性测试与自动检查。
6. **文档工程**：文档即代码、构建与发布、版本管理、站点与搜索。
7. **维护与治理**：所有权、审查周期、废弃与重定向、风格指南。
8. **本地化与可访问性**：为翻译而写、翻译流程、可访问的文档。
9. **度量与反馈**：指标、反馈渠道、与支持团队的合作。
10. **AI 与文档**：AI 辅助写作、面向 AI 检索的文档结构与风险控制。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 按模板与风格指南编写和修改文档 | 文档页面、修改记录 |
| D2 独立完成 | 独立负责一个功能的完整文档，从计划到发布 | 文档计划、评审记录、发布的文档 |
| D3 负责结果 | 负责一个产品的文档质量与读者体验 | 文档体系、度量与改进记录 |
| D4 系统与跨团队 | 协调多个团队的文档，建立统一的结构与流程 | 跨产品的信息架构、贡献流程 |
| D5 方法与机制 | 建立组织的文档标准、工具链与治理机制 | 风格指南、文档平台、培训 |
| D6 创新与影响 | 提出新的文档方法或工具并验证 | 开源工具、公开分享 |

#### 02.3 成长中的常见偏差

- 按产品的功能菜单组织文档，而不是按读者的任务。
- 教程、操作指南、参考与概念说明混写在一页里。
- 示例代码没有运行过，或者随着产品更新而失效。
- 只追求“写完”，不测试读者能否按文档完成任务。
- 文档没有负责人，过时的内容长期没人更新。
- 把实现细节当作用户需要的信息。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 读者、任务与信息需求

#### 03.1 了解读者

| 方面 | 需要了解的内容 |
| --- | --- |
| 角色 | 读者是谁：学生、店长、管理员、开发者 |
| 经验 | 对产品、领域与相关技术的熟悉程度 |
| 目标 | 读者打开文档时想完成什么 |
| 环境 | 在什么设备、什么情境下阅读，是否着急 |
| 语言 | 使用的语言与对术语的理解 |

同一份文档很难同时满足新手与专家。为主要读者写作，并为其他读者提供合适的入口与链接。

#### 03.2 任务分析

列出读者需要完成的任务，按重要程度与频率排序。每个重要的任务都应当有对应的文档，并且能从读者自然会去找的地方找到。

#### 03.3 信息需求的来源

- 支持工单与常见问题。
- 文档站点与产品内的搜索记录，尤其是没有结果的搜索。
- 社区与论坛中的提问。
- 用户访谈与可用性测试。
- 产品与开发团队对新功能的说明。

#### 03.4 文档计划

```text
功能或主题：
主要读者与次要读者：
读者要完成的任务：
需要的文档（类型、标题、优先级）：
信息来源与技术评审人：
完成标准（例如三位读者能按文档完成任务）：
发布时间（与功能发布对齐）：
维护负责人：
```

**本章练习**：为一个即将发布的功能编写文档计划，分析最近一个月与该功能相关的工单与搜索记录，说明计划中的每篇文档对应哪些读者需求。

<a id="ch04"></a>

### 04 文档类型与信息架构

#### 04.1 四类文档

Diátaxis 框架把技术文档分为四类，每一类服务于不同的读者需要。[B01](#ref-b01)

| 类型 | 读者的需要 | 写法 |
| --- | --- | --- |
| 教程 | 学习：第一次接触，跟着做一遍 | 带领读者完成一个完整、可靠的小项目，少讲原理 |
| 操作指南 | 完成任务：已经知道要做什么 | 针对一个具体的目标，给出步骤 |
| 参考 | 查找事实：参数、字段、错误码 | 完整、准确、结构统一，不夹带教学 |
| 概念说明 | 理解：为什么这样设计、怎样工作 | 解释背景、原理与取舍 |

#### 04.2 不要混写

在操作指南中插入大段原理，会打断正在完成任务的读者；在参考文档中加入教学内容，会让查找事实变得困难。需要时用链接连接不同类型的文档，而不是把它们写在同一页。

#### 04.3 信息架构

- **按任务组织导航**：例如“上传与解析简历”“查看分析结果”，而不是按内部模块命名。
- **每一页都可能是入口**：很多读者从搜索直接进入某一页，因此每页都要说明它适用于什么、需要什么前提，并链接到相关内容。
- **命名一致**：页面标题使用读者的说法，同一概念在各处使用同一个名称。
- **控制层级**：导航层级不宜过深，重要内容在两三次点击内可以到达。

#### 04.4 版本与产品变体

产品有多个版本或版本差异较大时，读者需要知道当前阅读的文档对应哪个版本。在页面上标明版本，并提供切换方式；不同版本的差异，在文档中明确标注。

**本章验收**：把一个功能的现有文档按四类重新组织，画出新的导航结构，并请三位读者分别完成一项查找任务，比较调整前后找到内容所需的时间。

<a id="ch05"></a>

### 05 清楚准确的写作

#### 05.1 先写结论

每篇文档、每一节的开头先说明它能帮助读者做什么，以及读者需要知道的最重要的信息。读者通常只读开头的几句话。

#### 05.2 句子与段落

- 一段只讲一个主题，先写主题句。
- 使用短句，一句话表达一个意思。
- 使用主动语态，明确谁做什么。
- 删除不承载信息的词语，例如“进行”“相关的”“一些”。

#### 05.3 步骤的写法

1. 开始之前，列出前提条件。
2. 用编号列出步骤，每一步只包含一个动作。
3. 条件写在动作之前，例如“如果需要分析多份简历，选择批量上传”。
4. 界面元素的名称与产品保持一致。
5. 在关键步骤之后说明读者应当看到的结果，便于确认是否成功。

#### 05.4 术语

为产品建立术语表，规定每个概念的标准名称、定义与不推荐的说法。同一概念在文档、界面与接口中使用同一个名称。

#### 05.5 中文排版

中文技术文档常用的规范包括：中文与英文、数字之间加空格；使用全角的中文标点；数字与单位之间按规范处理。阮一峰整理的《中文技术文档的写作规范》[B02](#ref-b02) 与《中文文案排版指北》[B03](#ref-b03) 是常用的参考。本仓库的[写作规范](../写作规范.md)也是一个例子，它把这些规则整理成了团队约定。

#### 05.6 英文风格指南

编写英文文档时，可以采用公开的风格指南作为团队的基础，例如 Google 的开发者文档风格指南 [B04](#ref-b04) 与微软的写作风格指南 [B05](#ref-b05)，再补充团队自己的约定。

#### 05.7 示例与代码

- 示例尽量真实，贴近读者的使用场景。
- 代码示例完整、最小、可以直接运行，并标明语言与版本。
- 不在示例中出现真实的密钥、个人信息或内部地址。
- 示例代码纳入自动测试，产品变化时能及时发现失效（见 07 章）。

#### 05.8 图示与截图

图示适合说明结构与流程；截图帮助读者确认界面，但界面变化后需要更新，维护成本较高。只在必要时使用截图，并为图片提供替代文字。

**本章练习**：选一篇现有的操作指南，按本章的原则改写，比较改写前后的字数与步骤数，并请一位新读者按改写后的版本完成任务。

<a id="ch06"></a>

### 06 接口与开发者文档

#### 06.1 开发者文档的组成

| 部分 | 内容 |
| --- | --- |
| 快速开始 | 从获取凭证到完成第一次调用的最短路径 |
| 认证与授权 | 获取与使用凭证的方式、权限范围、安全建议 |
| 概念说明 | 核心对象、状态、限制与设计原则 |
| 接口参考 | 每个接口的地址、参数、请求与响应、错误 |
| 示例与教程 | 常见场景的完整示例 |
| 软件开发工具包 | 安装、初始化与常用方法 |
| 错误参考 | 错误码、原因与解决方法 |
| 限制与配额 | 调用频率、数据大小等限制 |
| 变更日志 | 每个版本的变化，以及不兼容变更的迁移方法 |

#### 06.2 接口参考

接口参考最好从接口描述文件自动生成，避免与实际接口不一致。OpenAPI 规范是描述 HTTP 接口的常用标准。[B06](#ref-b06) 自动生成的参考只说明“有什么”，还需要人工编写的概念说明与示例来说明“怎样用”和“为什么”。

#### 06.3 快速开始

快速开始是开发者对产品的第一印象。衡量它的一个常用指标是首次成功所需的时间：新开发者从打开文档到完成第一次成功调用花了多长时间。删去所有非必要的步骤，提供可以直接复制运行的示例，并说明成功时会看到什么。

#### 06.4 错误参考

每个错误码说明：含义、常见原因、解决方法，以及是否可以重试。错误信息本身的设计见[《内容设计师》](07-内容设计师.md)，接口的错误契约见[《后端进阶全景手册》第 07 章](../技术方向/后端进阶全景手册.md#ch07)。

#### 06.5 变更与废弃

接口的变化记录在变更日志中。不兼容的变更需要提前通知，说明废弃的时间表与迁移方法，并在废弃的接口文档中明确标注。

**本章验收**：为一组接口编写快速开始、概念说明与错误参考，接口参考从接口描述文件生成；请两位未接触过该接口的开发者完成第一次调用，记录所需时间与遇到的问题。

<a id="ch07"></a>

### 07 评审、测试与质量

#### 07.1 三种评审

| 评审 | 评审人 | 关注点 |
| --- | --- | --- |
| 技术评审 | 开发者、领域专家 | 技术事实是否准确，步骤是否可行 |
| 编辑评审 | 其他写作者 | 结构、清晰度、一致性、风格 |
| 读者测试 | 目标读者 | 能否找到并按文档完成任务 |

请求技术评审时，提出具体的问题，例如“第 3 步的参数默认值是否正确”，比“请看一下”更容易得到有用的反馈。

#### 07.2 读者测试

请目标读者按文档完成真实的任务，观察他们在哪里停顿、误解或放弃。少量的读者测试往往就能发现大部分严重的问题。

#### 07.3 自动检查

- **链接检查**：发现失效的内部与外部链接。
- **拼写与风格检查**：Vale 等工具可以按风格指南中的规则检查文字。[B07](#ref-b07)
- **示例代码测试**：在持续集成中运行文档中的示例代码。
- **构建检查**：标记语法错误、缺失的图片、无效的锚点。

本仓库的 [`tools/check_docs.py`](../tools/check_docs.py) 是一个小型的例子：它检查粗体能否在 GitHub 上正确渲染、页内与跨文件的链接是否有效、表格的列数与参考资料的引用是否一致。

#### 07.4 质量清单

发布前检查：读者与目的明确；标题与开头说明了用途；步骤可以完成；术语与界面一致；示例经过测试；链接有效；图片有替代文字；已经过技术评审。

**本章验收**：为一组文档建立链接检查、风格检查与示例代码测试，接入持续集成；组织一次读者测试，按发现的问题修改文档。

<a id="ch08"></a>

### 08 文档即代码

#### 08.1 用开发的方式写文档

文档即代码指使用与开发相同的工具与流程管理文档：纯文本的标记语言、版本控制、问题跟踪、代码评审与自动测试。Write the Docs 社区的指南介绍了这种做法及其好处。[B08](#ref-b08)

#### 08.2 好处与条件

- 文档与代码的变化可以在同一次评审中检查。
- 开发者可以直接贡献与修改文档。
- 可以把“文档已更新”作为功能完成的条件之一。
- 自动检查与预览环境让问题在发布前被发现。

这种做法需要写作者熟悉版本控制与评审流程，也需要为不熟悉这些工具的贡献者提供简单的入口。

#### 08.3 构建与发布

文档通常由静态站点生成工具构建：每次合并后自动构建并发布，每个修改请求生成一个预览版本，便于评审。发布失败时可以回退到上一个版本。

#### 08.4 版本对应

文档的版本与产品的版本对应。产品发布时，对应版本的文档同时发布；旧版本的文档按支持策略保留。

**本章练习**：把一组文档迁移到版本控制中，设置修改请求的预览与合并后的自动发布，并在一次功能开发中让开发者与写作者在同一个修改请求中完成代码与文档。

<a id="ch09"></a>

### 09 文档的维护与生命周期

#### 09.1 文档也会过时

产品在变化，文档如果不随之更新，就会误导读者。过时的文档比没有文档更糟糕：读者按错误的步骤操作，失败后不再信任文档。

#### 09.2 所有权与审查

- 每一篇文档都有负责人。
- 页面上标注最后核对的日期。
- 按重要程度设定审查周期，例如快速开始每个版本检查一次，其他文档每半年检查一次。
- 产品发布时，检查受影响的文档清单。

#### 09.3 废弃与重定向

删除或合并文档时，设置重定向，避免读者与其他文档中的链接失效。废弃的功能，其文档标注废弃的状态与替代方案，而不是直接删除。

#### 09.4 发布说明

发布说明按读者关心的影响组织：新功能、改进、修复的问题、不兼容的变化与需要的操作。避免只列出内部的任务编号。

**本章练习**：为一个产品的文档建立负责人与审查周期，统计超过一年未核对的页面，选出其中最重要的十篇完成核对与更新。

## 第三篇：专项与进阶

<a id="ch10"></a>

### 10 内部文档与工程知识

#### 10.1 常见的内部文档

| 文档 | 用途 |
| --- | --- |
| 仓库说明 | 项目是什么、怎样运行与贡献 |
| 设计文档 | 在实现之前说明问题、方案与取舍 |
| 架构决定记录 | 记录重要决定的背景、选项与理由 |
| 运维手册 | 处理常见故障与日常运维 |
| 新人入门文档 | 帮助新成员快速上手 |

架构决定记录的写法见[《软件架构师与技术负责人》](10-软件架构师与技术负责人.md)，运维手册见[《运维工程师与 SRE》](13-运维工程师与SRE.md)。

#### 10.2 内部文档的读者也是用户

内部文档同样需要考虑读者、任务与维护。最常见的问题是：信息分散在聊天记录与个人笔记中，决定的原因没有被记录，文档写完后不再更新。

#### 10.3 记录决定与原因

代码说明系统现在是什么样，文档需要补充它为什么是这样。记录决定的背景与被放弃的选项，可以避免后来的人重复讨论或无意中破坏重要的设计。

**本章练习**：为一个项目补齐仓库说明与新人入门文档，请一位新成员按文档完成环境搭建与第一次修改，记录所需时间与遇到的问题。

<a id="ch11"></a>

### 11 本地化与国际化

#### 11.1 为翻译而写

- 使用短句与简单的句式。
- 避免俚语、双关语与只在某种文化中成立的比喻。
- 术语保持一致，便于建立术语库。
- 不把文字放在图片中。
- 日期、时间、数字与货币按地区格式处理。

#### 11.2 翻译流程

建立术语库与翻译记忆，由熟悉产品的译者翻译，并安排审校。机器翻译可以提高效率，但技术术语与关键步骤需要人工审校。

#### 11.3 同步

源语言的文档更新后，跟踪各语言版本的翻译状态。翻译滞后时，在页面上说明，并提供源语言版本的链接。

**本章练习**：为一组文档建立中英文术语表，检查现有的翻译是否一致，并为源语言更新后的翻译同步设计一个跟踪方式。

<a id="ch12"></a>

### 12 文档的可访问性

文档同样需要让使用辅助技术的读者能够阅读：

- 标题按层级使用，不跳级，便于屏幕阅读器导航。
- 链接文字说明目标，避免“点击这里”。
- 图片提供有意义的替代文字，装饰性图片除外。
- 表格有表头，不用表格做排版。
- 不只用颜色传达信息。
- 视频提供字幕，必要时提供文字稿。
- 代码块可以被复制，不把代码放在图片中。

无障碍的系统方法见[《无障碍专家》](09-无障碍专家.md)。

**本章练习**：用屏幕阅读器阅读一篇文档，记录无法理解或无法操作的地方，按本章的原则修改，并请另一位同事复查。

<a id="ch13"></a>

### 13 度量与反馈

#### 13.1 常用指标

| 指标 | 说明 | 局限 |
| --- | --- | --- |
| 页面浏览量 | 哪些内容被阅读 | 浏览量高可能是因为问题多，而不是文档好 |
| 搜索无结果 | 读者在找、但没有找到的内容 | 需要人工分析关键词 |
| 页面有用率 | 读者对页面的评价 | 回应率低，代表性有限 |
| 首次成功时间 | 新开发者完成第一次调用的时间 | 需要专门的测试或埋点 |
| 与文档相关的工单 | 文档缺失或不清楚导致的工单 | 需要支持团队统一标注 |

#### 13.2 反馈渠道

在页面上提供简单的反馈方式，并允许读者留下具体的意见；为开源或开发者文档提供问题跟踪的入口。收到的反馈要有人定期处理，并在修改后回复。

#### 13.3 与支持团队合作

支持团队最清楚读者在哪里遇到困难。定期与支持团队一起查看工单中与文档相关的问题，把支持人员写的解决方案整理为正式文档。知识管理的方法见[《客户成功与技术支持》第 06 章](20-客户成功与技术支持.md#ch06)。

**本章练习**：分析一个月的搜索记录与页面反馈，列出最需要补充或修改的五项内容，完成修改后再观察一个月，比较相关指标的变化。

<a id="ch14"></a>

### 14 AI 与文档

#### 14.1 AI 辅助写作

AI 工具可以帮助起草、改写、翻译、总结评审意见、检查术语是否一致。需要注意：AI 可能编造不存在的参数、接口或步骤，所有技术事实都需要与产品和开发者核对；不把未公开的产品信息发送给未经评估的外部服务。

#### 14.2 文档也被 AI 阅读

越来越多的读者通过 AI 助手获取文档中的信息，AI 助手也会检索与引用文档。对人清楚的文档，通常对 AI 也更容易使用：

- 每一页自成一体，说明适用范围与前提。
- 结构清楚，标题准确描述内容。
- 术语一致，同一概念不用多个名称。
- 示例代码完整，包含必要的上下文。
- 标明版本，避免旧版本的内容被当作当前的说明。

一些项目开始在站点根目录提供面向大模型的内容索引，例如 llms.txt 提案。[B09](#ref-b09) 它目前是社区提案，各类工具是否使用并不确定，是否采用可以根据读者的实际情况决定。

#### 14.3 风险

过时或错误的文档会被 AI 助手放大传播。及时更新与废弃旧内容，在重要的页面上标明最后核对的日期。

**本章练习**：用 AI 助手回答 20 个关于产品的真实问题，检查回答引用了哪些文档、哪些回答有误，分析错误是否与文档的结构、术语或过时内容有关，并修改相应的文档。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与开发者的协作接口

#### 15.1 技术写作者需要开发者提供的内容

| 内容 | 作用 |
| --- | --- |
| 功能说明与设计文档 | 了解功能的目的、行为与限制 |
| 可以试用的版本 | 亲自完成任务，发现问题 |
| 技术评审 | 确认文档中的技术事实 |
| 示例代码 | 提供真实、可运行的示例 |
| 变更通知 | 及时更新受影响的文档 |

#### 15.2 开发者需要技术写作者提供的内容

文档计划与发布时间、带具体问题的评审请求、术语与命名的建议、对错误信息与接口设计的反馈。写作者常常是第一个从读者角度使用新功能的人，他们发现的困惑往往也是产品本身的问题。

#### 15.3 共同的做法

- 文档纳入功能完成的定义。
- 写作者尽早参与功能的设计评审。
- 接口描述文件由开发者维护，文档从中生成参考。
- 示例代码与文档一起在持续集成中测试。

<a id="ch16"></a>

### 16 开发者怎样借用文档方法

#### 16.1 写好仓库说明

```text
项目是什么，解决什么问题：
快速开始（安装、运行、第一个示例）：
配置说明：
常见问题：
如何贡献：
许可证与联系方式：
```

#### 16.2 外包交付的文档

外包项目的交付物通常包括用户手册、管理员手册、运维手册与接口文档。按读者分别编写，在验收前请客户的使用者按文档完成典型任务，并把文档的更新纳入维保范围。

#### 16.3 技术背景的常见偏差

- 只写参考文档，没有教程与操作指南。
- 按代码的结构组织文档，而不是按读者的任务。
- 默认读者具备与自己相同的背景知识。
- 文档写完后不再更新。

<a id="ch17"></a>

### 17 贯穿实战：求职平台开放接口的开发者文档

本章以求职平台为例，展示一次完整的文档工作。数字均为示意。

#### 17.1 背景与读者

求职平台向合作学校的就业指导中心开放“简历分析”接口，学校的信息中心可以把它集成到自己的就业服务系统中。主要读者是学校信息中心的开发者：熟悉常见的编程语言与接口调用，但不熟悉平台的概念。

#### 17.2 文档计划

| 文档 | 类型 | 完成标准 |
| --- | --- | --- |
| 快速开始 | 教程 | 新开发者在 15 分钟内完成第一次分析调用 |
| 认证与签名 | 操作指南 | 按步骤完成签名，并能验证签名是否正确 |
| 分析任务的状态 | 概念说明 | 解释排队、处理中、完成、失败等状态与轮询方式 |
| 接口参考 | 参考 | 从接口描述文件生成，与实际接口一致 |
| 错误参考 | 参考 | 每个错误码有原因与解决方法 |
| 隐私与数据处理 | 概念说明 | 说明简历数据的用途、保存期限与删除方式 |
| 变更日志 | 参考 | 每个版本的变化与迁移方法 |

#### 17.3 读者测试与改进

邀请三位学校的开发者按快速开始操作：两位在签名步骤卡住，原因是示例中的时间戳格式没有说明；一位不清楚分析结果需要轮询获取。改进：在签名指南中给出完整的签名示例与验证工具；在快速开始中加入轮询的示例，并链接到状态说明。

#### 17.4 自动检查

- 快速开始与示例代码在持续集成中针对测试环境运行。
- 接口参考在每次接口描述文件变更时重新生成。
- 链接检查与风格检查在每个修改请求中运行。

#### 17.5 上线后的改进

上线一个月后，搜索记录中“回调”一词出现多次但没有结果，说明开发者希望在分析完成时收到通知，而不是轮询。写作者把这一需求反馈给产品团队；在回调功能上线前，先补充了“如何高效轮询”的操作指南。首次成功时间从首轮测试时的约 40 分钟降到约 12 分钟。

#### 18.2 学习路线

| 阶段 | 学习重点 | 实践目标 | 进入下一阶段的信号 |
| --- | --- | --- | --- |
| A 建立基础 | 01—05 章 | 独立完成一个功能的操作指南与参考 | 读者能按文档完成任务 |

#### 18.3 操作指南模板

```text
标题（以动词开头，描述读者要完成的任务）：

```

#### 18.4 发布说明模板

```text
版本与发布日期：
新功能（对读者的价值与入口）：
改进：
修复的问题：

```

#### 18.5 检查清单

- [ ] 文档计划基于真实的读者需求与任务。
- [ ] 每篇文档只属于一种类型，不同类型之间用链接连接。
- [ ] 标题与开头说明了读者能完成什么。
- [ ] 步骤编号清楚，一步一个动作，关键步骤后说明结果。
- [ ] 术语与界面、接口一致。
- [ ] 示例代码完整、可运行，并经过自动测试。

- [ ] 链接、风格与构建检查接入持续集成。
- [ ] 每篇文档有负责人与最后核对日期。
- [ ] 删除或合并文档时设置了重定向。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 文档是功能完成后的补充 | 文档是产品体验的一部分，应与功能一起设计与发布 |
| 文档越详细越好 | 文档要满足读者的任务，过多的信息会掩盖重点 |
| 一篇文档可以满足所有读者 | 为主要读者写作，为其他读者提供入口 |
| 自动生成的接口参考就是完整的文档 | 还需要快速开始、概念说明与示例 |
| 开发者写的文档一定准确 | 准确也需要评审与测试，并随产品更新 |
| 浏览量高说明文档好 | 浏览量高也可能是因为问题多 |
| 截图越多越清楚 | 截图维护成本高，只在必要时使用 |
| AI 可以直接写出正确的文档 | AI 可能编造技术细节，需要人工核对 |
| 过时的文档留着也无妨 | 过时的文档会误导读者，也会被 AI 助手放大 |
