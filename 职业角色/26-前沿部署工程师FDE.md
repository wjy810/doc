# 前沿部署工程师（FDE）进阶全景手册

> 从深入一个客户的现场解决真实问题，到把一次次定制的经验沉淀为产品能力，再到建立“前线发现问题、产品团队把方案产品化”的协作机制。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：希望在客户场景中用工程能力解决问题的开发者，做过外包或实施、想更深入业务的工程师，正在考虑 AI 应用落地岗位的工程师，以及希望系统了解这一交叉角色的产品与工程负责人。

前沿部署工程师（Forward Deployed Engineer，常缩写为 FDE）是一种处在客户与产品之间的工程角色：他们进入客户的真实业务，找到最有价值的问题，接入并理解客户的数据，用公司的产品平台加上必要的代码快速做出可用的解决方案，证明价值、推动采用，并把在现场发现的共性需求反馈给产品团队。

这个角色的价值来自两个方向。对客户，FDE 把通用的产品变成能解决他们具体问题的方案；对公司，FDE 是最接近真实问题的人，他们发现的产品缺口与解决模式，决定了产品下一步应该做什么。它的风险也来自同一处：如果每个方案都是一次性的定制，FDE 团队就会变成高成本的外包团队，产品也得不到改进。

本手册先建立角色坐标，然后讲解进入客户场景、数据的接入与理解、快速构建方案、在客户环境中保证工程质量、证明价值与推动采用、从现场到产品、沟通与现场工作方式；随后进入 AI 应用的现场落地、受监管的环境、赋能客户与交接、FDE 团队的组织与度量、职业发展；最后说明 FDE 与产品工程师的协作，并用一个连锁企业落地 AI 招聘助手的案例演示完整的过程。

主线是：**进入客户的真实场景 → 找到最有价值的问题 → 接入并理解数据 → 快速做出能用的方案 → 在客户环境中可靠地运行 → 证明价值并让客户团队接手 → 把共性需求反馈为产品能力。**

不同公司对这一角色的称呼与职责差异很大，常见的名称还有前沿部署软件工程师、客户工程师、部署工程师、应用 AI 工程师等，具体的编码、客户沟通与出差比例因公司和岗位而异。本手册描述这一角色的共同职责与方法；D1—D6 分级是学习组织方式，不对应任何职级体系。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 前沿部署工程师负责什么

#### 01.1 起源

这一角色因 Palantir 而广为人知。Palantir 的工程师主要分为两类：开发与工程化 Foundry、Gotham 等软件平台的软件工程师，内部称为 Dev；与客户一起工作的前沿部署软件工程师，内部称为 Delta。Palantir 的博客介绍了两类角色的区别与 Delta 的工作方式。[B01](#ref-b01) [B02](#ref-b02)

可以这样理解两者的差别：产品工程师为许多客户打造一种能力，前沿部署工程师为一个客户组合多种能力。两者互相依赖：没有好的平台，FDE 只能从零写定制系统；没有 FDE 带回的真实问题，平台很难知道该往哪里发展。

#### 01.2 在 AI 公司中的发展

2025 年前后，许多 AI 公司扩大了前沿部署工程师的招聘，让工程师深入企业客户，把模型落地到具体的业务流程中。行业报道认为，AI 产品能否在企业中成功，很大程度上取决于这些工程师能否又好又快地完成落地，而他们从客户那里获得的认识也会反过来改进产品。[B03](#ref-b03)

#### 01.3 典型的工作

| 工作 | 内容 |
| --- | --- |
| 发现问题 | 观察客户的实际工作，找到最有价值、可解决的问题 |
| 接入数据 | 连接客户的系统与数据，理解字段的业务含义 |
| 构建方案 | 在产品平台上搭建应用、工作流与集成，必要时编写代码 |
| 证明价值 | 用客户认可的指标说明方案带来的变化 |
| 推动采用 | 让方案进入客户的日常工作，培训客户的团队 |
| 反馈产品 | 记录产品缺口与共性需求，推动产品化 |

#### 01.4 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 问题发现记录 | 选择最有价值的问题 | 基于现场观察，有业务影响的估计 |
| 可用的方案 | 解决客户的具体问题 | 真实用户在日常工作中使用 |
| 数据接入与业务模型 | 让数据可用、可信 | 字段含义经业务确认，质量有检查 |
| 价值报告 | 证明方案的效果 | 有基线、有对比，口径经客户认可 |
| 产品缺口记录 | 改进产品 | 说明问题、频率、变通方式与建议 |
| 交接材料 | 让客户或其他团队接手 | 文档、负责人与运维方式完整 |

#### 01.5 职责边界与相邻角色

| 事项 | FDE 的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 售前方案 | 协作，提供可行性判断 | 解决方案架构师 | 见[《解决方案架构师》](22-解决方案架构师.md) |
| 按既定方案部署与上线 | 协作 | 实施与交付工程师 | 见[《实施与交付工程师》](23-实施与交付工程师.md) |
| 平台与产品能力 | 提出需求，参与产品化 | 产品工程师、产品经理 | 见 08、15 章 |
| 长期的使用与续约 | 交接 | 客户成功 | 见[《客户成功与技术支持》](20-客户成功与技术支持.md) |
| 业务知识 | 学习与核对 | 客户的业务专家、领域专家 | 见[《领域专家》](04-领域专家.md) |
| 数据管道 | 主导或协作 | 数据工程师 | 见[《数据工程师》](17-数据工程师.md) |

几组容易混淆的角色：

- **FDE 与实施工程师**：实施工程师按照既定的方案部署、配置与上线；FDE 在现场发现问题、设计并编写方案，方案本身常常在过程中改变。
- **FDE 与解决方案架构师**：解决方案架构师多在签约前设计方案；FDE 多在签约后进入现场，把方案真正做出来，并持续迭代。
- **FDE 与外包开发**：外包开发为客户建设归客户所有的系统；FDE 基于公司的产品平台工作，并把现场的经验转化为产品能力。
- **FDE 与产品工程师**：产品工程师深耕平台的某一部分，服务所有客户；FDE 横跨平台的多种能力，服务少数客户。

**本章练习**：选一个你参与过的客户项目，列出其中哪些工作属于“发现问题、接入数据、构建方案、证明价值、推动采用、反馈产品”，分别由谁完成，哪些环节缺失。

<a id="ch02"></a>

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **业务发现**：现场观察、问题选择、成功标准与决策者地图。
2. **数据接入与建模**：接入方式、字段理解、业务对象模型、质量与对账。
3. **方案构建**：在平台上搭建应用与工作流，编写集成与定制代码。
4. **快速迭代**：最小可用版本、每周交付、从原型到生产。
5. **工程质量**：版本控制、测试、安全、可运维与定制代码的维护。
6. **价值证明与采用**：基线与对比、关键用户、融入日常流程。
7. **产品反馈与产品化**：区分一次性与共性需求，推动并参与产品化。
8. **沟通与信任**：与一线用户、信息技术部门与管理层沟通，期望管理。
9. **AI 落地**：用例选择、构建、评测、人工复核与风险控制。
10. **现场工作与自我管理**：驻场与出差、多客户切换、边界与可持续。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 在资深 FDE 带领下完成数据接入与部分开发 | 代码提交、接入记录 |
| D2 独立完成 | 独立负责一个客户的一个用例，从发现到采用 | 可用的方案、价值报告 |
| D3 负责结果 | 负责一个重要客户的整体成果与关系 | 多个用例的采用、客户续约与扩展 |
| D4 系统与跨团队 | 协调多个客户的经验，推动产品化，带领小团队 | 被产品化的能力、跨客户的方案模式 |
| D5 方法与机制 | 建立 FDE 团队的方法、工具与产品反馈机制 | 方法手册、可复用资产、反馈流程 |
| D6 创新与影响 | 开创新的行业方案或交付模式 | 新的产品方向、公开分享 |

#### 02.3 成长中的常见偏差

- 客户说什么就做什么，没有找到真正的问题。
- 为了快而跳过版本控制、测试与权限设计，留下难以维护的系统。
- 每个客户都从零定制，从不产品化。
- 只与一线用户或只与管理层沟通，缺少另一方的支持。
- 演示效果很好，却没有进入客户的日常工作。
- 长期驻场与多客户切换导致倦怠。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 进入客户场景，找到最有价值的问题

#### 03.1 走到一线

阅读需求文档与参加会议之外，花时间观察一线人员的实际工作：他们每天做什么、用什么工具、在哪里等待、在哪里重复劳动、在哪里出错。很多真正的问题，只有在现场才能看到。观察与访谈的方法见[《用户研究员》](02-用户研究员.md)。

#### 03.2 选择问题

| 判断维度 | 需要回答的问题 |
| --- | --- |
| 价值 | 解决后能节省多少时间、减少多少错误、带来多少收入？ |
| 可行性 | 数据是否可得？平台能力是否足够？需要多长时间？ |
| 关注度 | 决策者是否关心这个问题？一线用户是否愿意改变？ |
| 可见性 | 结果能否在几周内被看到？ |
| 可扩展 | 方案能否推广到客户的其他部门或其他客户？ |

先选一个价值明确、几周内能见效的问题建立信任，再逐步扩展到更大的问题。

#### 03.3 用户与决策者地图

列出与问题相关的人：每天使用方案的一线用户、负责系统与数据的信息技术人员、关心结果的业务负责人、最终做决定的管理层。了解每个人的目标与顾虑，方案需要同时得到一线用户的认可与决策者的支持。

#### 03.4 定义成功

与客户一起确定成功的衡量方式，并在开始前记录基线，例如“店长每天处理候选人消息的时间”“从收到申请到安排面试的平均天数”。业务规则与流程的梳理见[《业务分析师》](03-业务分析师.md)。

#### 03.5 解决问题，而不只是实现需求

客户提出的需求是他们设想的解决办法。追问背后的问题：“如果有了这个功能，你的工作会有什么变化？”常常会发现更简单、更有效的方案。

**本章验收**：在一个客户现场完成至少两天的观察与访谈，列出发现的问题，按上表的维度评估并选择一个，写出成功标准与基线。

<a id="ch04"></a>

### 04 数据的接入、理解与建模

#### 04.1 盘点客户的数据

数据在哪些系统中？谁负责？能以什么方式访问？更新频率如何？质量怎样？是否包含个人信息或敏感数据？盘点结果决定了方案的可行性与工作量。

#### 04.2 接入与权限

按客户的要求申请访问权限，只接入方案需要的数据；记录每一个接入的来源、方式、负责人与更新频率；敏感数据按客户的安全要求处理。

#### 04.3 与业务一起理解数据

字段的名称往往不能说明它的真实含义。与业务人员一起核对：这个状态值代表什么？这个时间是提交时间还是审批时间？为什么有些记录是空的？把确认的结论记录为数据字典。

#### 04.4 把数据组织成业务对象

把来自多个系统的数据组织成业务人员能理解的对象与关系，例如“门店、岗位、候选人、面试、录用”，以及对象之间的关系与发生的事件。用业务对象而不是原始表来构建应用，方案更容易理解、复用与维护。

#### 04.5 质量与对账

为关键数据设置质量检查，并与客户的权威数据对账。数据有问题时，先让客户看到问题的证据，再一起决定处理方式。数据管道与质量方法见[《数据工程师》](17-数据工程师.md)。

**本章验收**：为一个用例完成数据盘点与接入，与业务人员一起编写数据字典，建立业务对象模型与质量检查，并完成一次与权威数据的对账。

<a id="ch05"></a>

### 05 快速构建可用的方案

#### 05.1 从最小可用的版本开始

选择一类用户、一个工作流，先做出能在真实工作中使用的最小版本。比起一次覆盖所有需求的大版本，小版本能更早得到真实的反馈，也更早建立信任。

#### 05.2 优先使用平台能力

| 方式 | 适合 | 代价 |
| --- | --- | --- |
| 使用产品的标准能力 | 大部分常见需求 | 可能需要调整客户的流程 |
| 在平台上配置与组合 | 需要组合多种能力的工作流 | 需要熟悉平台 |
| 编写定制代码 | 平台暂不支持、但价值明确的部分 | 需要长期维护，应考虑产品化 |

编写定制代码前先问：这是这个客户特有的需要，还是其他客户也会遇到的问题？后者应当记录为产品缺口（见 08 章）。

#### 05.3 迭代的节奏

每周让真实用户使用新的版本，观察他们怎样使用、在哪里卡住，并据此调整。演示中的好评不等于真实的使用：只有当用户在没有人陪同的情况下仍然使用，方案才算真正可用。

#### 05.4 从原型到生产

原型证明方向可行之后，在用户依赖它之前，补齐生产所需的部分：错误处理、权限、监控、性能、文档与负责人。原型中的临时做法要么替换，要么明确记录风险。

**本章验收**：为选定的问题在两周内交付最小可用的版本，让至少三位真实用户在日常工作中使用，记录反馈与修改；列出从原型到生产需要补齐的事项并完成。

<a id="ch06"></a>

### 06 在客户环境中保证工程质量

#### 06.1 快而不草率

- 所有代码与配置纳入版本控制，修改经过评审。
- 关键逻辑有自动化测试，尤其是数据转换与业务规则。
- 配置与代码分离，各环境的差异有记录。
- 部署可重复，出问题时能回退。部署的方法见[《实施与交付工程师》](23-实施与交付工程师.md)。

#### 06.2 安全与权限

只申请必要的权限；方案中的数据访问遵守客户的权限体系，不同角色只能看到自己有权查看的数据；操作留有审计记录；不把客户数据带离客户允许的环境。安全方法见[《安全工程师》](12-安全工程师.md)。

#### 06.3 可运维

方案上线后需要有人负责：监控与告警由谁处理？数据接入失败怎么办？FDE 离开后谁来维护？在方案设计时就回答这些问题，并写进交接材料。

#### 06.4 定制代码的维护

每一段定制代码都是长期的维护负担。记录定制代码的清单、用途与负责人，平台升级时检查兼容性，并持续推动可以产品化的部分进入产品。

**本章练习**：审查一个现场方案的代码、配置、权限与运维安排，列出不符合上述要求的地方与风险，制定改进计划并完成其中最重要的三项。

<a id="ch07"></a>

### 07 证明价值与推动采用

#### 07.1 衡量价值

在开始前记录基线，上线后用同样的口径比较。口径与数据来源要经过客户确认，避免各说各话。能用金额、时间或错误率表达的价值，比“用户反馈不错”更有说服力。指标设计的方法见[《数据分析师与产品分析师》](16-数据分析师与产品分析师.md)。

#### 07.2 推动采用

- 培养关键用户，让他们帮助身边的同事。
- 把方案嵌入用户已有的工作流程，减少额外的步骤。
- 及时处理使用中的问题，让用户感到被重视。
- 统计实际的使用情况，对不使用的用户了解原因。

#### 07.3 向客户管理层汇报

定期向客户管理层汇报：解决了什么问题、带来了什么变化、下一步建议做什么、需要客户提供什么支持。汇报内容以客户的业务语言表达。

**本章验收**：为一个上线的方案编写价值报告，包括基线、上线后的变化、计算口径与客户的确认；统计使用情况，对使用率低的用户群体完成一次原因调查与改进。

<a id="ch08"></a>

### 08 从现场到产品：反馈与产品化

#### 08.1 区分一次性需求与共性需求

| 类型 | 判断 | 处理 |
| --- | --- | --- |
| 客户特有 | 只与这个客户的流程或系统有关 | 用配置或少量定制解决，记录在客户档案中 |
| 可能共性 | 在一个客户中出现，推测其他客户也有 | 记录为产品缺口，观察其他客户 |
| 已确认共性 | 在多个客户中出现 | 推动产品化，定制方案逐步迁移到产品 |

#### 08.2 产品缺口记录

```text
问题（用户在什么情况下遇到什么困难）：
涉及的客户与用户角色：
出现的频率与影响：
当前的变通方式与成本：
建议的产品能力（可选）：
相关的现场代码或配置：
```

#### 08.3 推动产品化

- 定期与产品经理和产品工程师一起评审产品缺口，提供客户的原话与使用数据。
- 参与产品化的设计，把现场的经验与边界情况带给产品团队。
- 产品能力发布后，把客户的定制方案迁移到标准能力上。

如果 FDE 团队长期只做定制、没有任何经验进入产品，团队就会变成成本很高的外包团队；产品化的比例是衡量 FDE 团队健康的重要信号。

**本章练习**：整理过去三个月的现场需求，按上表分类；为最重要的一项共性需求写出完整的产品缺口记录，并与产品团队完成一次评审。

<a id="ch09"></a>

### 09 沟通、信任与现场工作方式

#### 09.1 与客户的各个层级沟通

| 对象 | 关心的问题 | 沟通方式 |
| --- | --- | --- |
| 一线用户 | 能否让工作更轻松 | 现场观察、快速响应问题 |
| 信息技术部门 | 安全、集成、运维负担 | 技术方案评审、书面确认 |
| 业务负责人 | 业务指标是否改善 | 定期回顾、价值报告 |
| 管理层 | 投入是否值得、下一步方向 | 简短的汇报与建议 |

#### 09.2 建立信任

信任来自持续地兑现承诺：说到的事情按时做到，遇到困难提前说明，出现问题时坦诚承认并尽快修复。不要为了让客户满意而承诺产品路线、交付时间或效果，这些需要与公司内部确认。

#### 09.3 期望管理

说明方案能做什么、不能做什么；说明范围变化对时间的影响；说明 AI 等技术的局限。期望管理越早，后期的冲突越少。

#### 09.4 现场工作与自我管理

驻场、出差与多客户切换会带来很大的压力。约定可持续的工作安排，保留与公司团队交流的时间，定期回顾自己的负荷，必要时向经理提出调整。

**本章练习**：为当前的客户画出沟通对象地图，写出每类对象的关注点与沟通频率；回顾最近一个月的承诺与兑现情况，找出一项需要改进的期望管理。

## 第三篇：专项与进阶

<a id="ch10"></a>

### 10 AI 应用的现场落地

#### 10.1 选择用例

优先选择价值明确、数据可得、错误代价可控、能够评测的用例。例如“起草回复由人确认后发送”比“自动发送回复”更适合作为第一步。用例评估的方法见[《解决方案架构师》第 13 章](22-解决方案架构师.md#ch13)。

#### 10.2 构建

- 检索客户的文档与数据时，遵守原有的访问权限。
- 工作流中的高风险操作需要人工确认。
- 记录模型、提示词、检索数据与工具定义的版本。

#### 10.3 评测

用客户的真实问题与数据建立评测集，上线前达到约定的标准，每次修改后重新评测。评测方法见[《算法与机器学习工程师》第 12 章](18-算法与机器学习工程师.md#ch12)。

#### 10.4 风险

- **提示词注入**：客户的文档、邮件或用户输入中可能包含试图改变模型行为的文字。[B04](#ref-b04) 外部内容作为数据处理，不作为指令。
- **过度授权**：给模型的工具与权限超出任务所需，一旦被诱导可能造成损害。[B05](#ref-b05) 工具按最小权限设计。
- **数据泄露**：输出中可能包含用户无权查看的信息，检索与输出都需要权限控制。
- **准确性**：模型会出错，重要的结果需要人工复核，并让用户能够反馈错误。

大模型应用工程见[《算法与机器学习工程师》第 11 章](18-算法与机器学习工程师.md#ch11)。

**本章验收**：为一个 AI 用例完成用例评估、评测集与通过标准、权限与人工确认的设计，并在上线前完成一次评测与安全检查。

<a id="ch11"></a>

### 11 受监管与高敏感的环境

政府、金融、医疗等客户通常有严格的要求：安全审查、数据不能离开指定的环境、隔离的网络、人员的背景审查、详细的审计记录。在这些环境中工作时：

- 事先了解并遵守客户的安全制度与访问流程。
- 预留审批与审查的时间，把它们写进计划。
- 在受限的环境中准备离线可用的工具与依赖。
- 所有操作留有记录，变更经过客户的审批。

本手册只描述工程层面的做法，具体的合规义务由客户与公司的法务和合规负责人确认。

**本章练习**：为一个高敏感环境的项目列出所有需要的审批与审查，估计所需的时间，并据此调整项目计划。

<a id="ch12"></a>

### 12 赋能客户团队与交接

#### 12.1 赋能

让客户的工程师与分析师能够自己使用与扩展方案：一起结对开发，讲解平台的使用方法，提供文档与示例，逐步把日常的修改交给客户团队完成。

#### 12.2 交接

FDE 的工作不应无限期地持续。为每个客户制定交接计划：哪些工作交给客户团队，哪些交给实施或客户成功团队，哪些需要产品团队支持。交接材料包括方案说明、数据字典、业务对象模型、定制代码清单、运维方式与负责人。交接的方法见[《实施与交付工程师》第 09 章](23-实施与交付工程师.md#ch09)。

**本章练习**：为当前的客户制定赋能与交接计划，列出交接的内容、接手人与时间表，并完成一次接手人独立操作的验证。

<a id="ch13"></a>

### 13 FDE 团队的组织与度量

#### 13.1 组织方式

FDE 团队可以按客户、按行业或按产品能力组织。无论哪种方式，都需要与产品团队、销售、客户成功建立清楚的接口，并让 FDE 定期回到公司内部交流，避免与产品团队脱节。

#### 13.2 度量

| 维度 | 示例 |
| --- | --- |
| 客户价值 | 价值报告中的业务改善、客户的续约与扩展 |
| 采用 | 方案的活跃用户与使用频率 |
| 产品反馈 | 提交的产品缺口、被产品化的比例 |
| 可扩展 | 定制代码的数量变化、方案在多个客户中的复用 |
| 团队健康 | 负荷、出差时间、人员流动 |

#### 13.3 经济性

FDE 的成本很高，只有在客户的价值足够大、或者现场经验能够转化为产品能力时，这种投入才是合理的。团队需要持续关注：哪些工作只能由 FDE 完成，哪些可以交给实施、客户成功或客户自己完成。

**本章练习**：用上表的维度评估一个 FDE 团队过去半年的工作，找出定制代码最多的三个客户，判断哪些部分可以产品化或交接。

<a id="ch14"></a>

### 14 职业发展与能力迁移

#### 14.1 适合的人

喜欢多变的问题与环境，能在不确定中推进，愿意与各种背景的人沟通，同时具备扎实的工程能力。更喜欢长期深耕一个系统的人，通常更适合产品工程师的路线。

#### 14.2 常见的发展方向

| 方向 | 迁移的能力 |
| --- | --- |
| 产品经理 | 对客户问题的深刻理解、价值判断 |
| 解决方案架构师 | 方案设计、客户沟通、技术广度 |
| 产品工程师 | 把现场经验带入产品设计 |
| 工程经理或 FDE 团队负责人 | 带领团队、客户关系、跨团队协作 |
| 创业 | 发现问题、快速交付、证明价值 |

#### 14.3 从外包与实施经历出发

做过外包或实施的开发者已经具备在客户环境中工作的经验。向 FDE 发展时，重点补充三项能力：主动发现问题而不只是实现需求；用数据证明价值；把定制经验沉淀为可复用的产品能力。

**本章练习**：对照 14.1 与 14.2，写出你目前最突出的两项能力与最需要补充的两项能力，选择一个发展方向，并列出未来半年可以争取的三个实践机会。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与产品工程师的协作接口

#### 15.1 FDE 需要产品工程师提供的内容

| 内容 | 作用 |
| --- | --- |
| 平台的扩展点与文档 | 在不修改产品的情况下构建方案 |
| 对现场问题的支持 | 快速定位平台的问题 |
| 对产品缺口的评审 | 判断哪些需求应当产品化 |
| 版本与兼容性说明 | 评估平台升级对现场方案的影响 |

#### 15.2 产品工程师需要 FDE 提供的内容

真实的使用场景与边界情况、可复现的问题报告、经过整理的产品缺口与客户原话、现场代码中值得产品化的部分。

#### 15.3 共同的做法

- 产品工程师定期到客户现场或参与客户会议，了解真实的使用情况。
- FDE 参与产品设计评审，带来现场的经验。
- 产品化的能力发布后，双方一起把现场方案迁移到标准能力上。

<a id="ch16"></a>

### 16 开发者怎样借用 FDE 的方法

#### 16.1 外包开发者

不只按需求单开发：到客户的现场看一看实际的工作，问清楚需求背后的问题；用小版本尽早让真实用户使用；记录在不同客户中反复出现的需求，把它们沉淀为可复用的模块。

#### 16.2 独立开发者

和第一批用户坐在一起，观察他们怎样使用你的产品；每周交付一个改进；用数据说明产品为用户带来的变化。

#### 16.3 技术背景的常见偏差

- 只按需求文档写代码，不了解客户的实际工作。
- 每个客户都从零开始，没有积累。
- 为了快而忽视权限、测试与运维。
- 只在出问题时联系客户。

### 17 贯穿实战：为连锁企业落地 AI 招聘助手

本章以求职平台的企业版为例：一家拥有 200 家门店的连锁企业使用平台筛选应聘者，平台派出一名前沿部署工程师，帮助客户把 AI 能力用到门店的招聘工作中。人员与数字均为示意。

#### 17.1 发现问题

FDE 在两家门店各跟岗一天，发现店长最耗时的不是筛选简历，而是每天晚上回复候选人的消息：询问岗位要求、薪资区间、面试时间与地点，平均每天约一小时。客户最初提出的需求是“更智能的简历评分”，但现场观察表明，消息回复与面试时间协调才是更大的瓶颈。

#### 17.2 选择用例与定义成功

- **用例**：AI 根据岗位信息与门店排班，起草对候选人常见问题的回复与面试时间建议，由店长确认后发送。
- **成功标准**：店长每天处理候选人消息的时间减少一半；候选人从申请到面试的平均时间缩短；错误回复率低于约定的阈值。
- **基线**：在 10 家试点门店记录两周的处理时间与面试安排时间。

#### 17.3 数据与构建

- 接入岗位信息、门店地址与营业时间、店长的排班；与人事专员一起编写数据字典，确认“岗位状态”与“排班”的含义。
- 在平台上搭建工作流：识别候选人的问题，检索岗位与门店信息，起草回复与面试时间建议，店长在手机上确认或修改后发送。
- 排班系统没有现成的接口，FDE 编写了一个只读的集成，纳入版本控制与测试，并记录为定制代码。

#### 17.4 评测与上线

- 用 300 条真实的候选人问题（已脱敏）建立评测集，包含薪资、地点、面试时间等常见问题，以及要求承诺录用、试图让 AI 透露其他候选人信息等不当请求。
- 回复只能引用岗位与门店信息中实际存在的内容；涉及薪资承诺与录用决定的问题，一律提示由店长回复。
- 评测达到约定的标准后，在 10 家门店试点两周。

#### 17.5 价值与采用

- 试点门店店长处理候选人消息的时间从每天约 60 分钟降到约 25 分钟；申请到面试的平均时间缩短了约 1 天。
- 两位店长因为习惯电话沟通而很少使用。FDE 与他们沟通后，增加了“生成电话沟通要点”的功能，使用率随之提升。
- 价值报告经客户的人事总监确认后，推广到全部门店。

#### 17.6 产品化与交接

- 面试时间协调的需求在另外两家连锁客户中也出现了。FDE 提交了产品缺口记录，产品团队将“基于排班的面试时间建议”做成标准功能，三家客户的定制方案随后迁移到标准能力上。
- 排班系统的集成保留为定制代码，交接给实施团队维护，并写入客户档案。
- 日常使用与续约交给客户成功团队，FDE 转向下一个客户。

- [ ] 数据的含义经业务人员确认，并有质量检查。
- [ ] 优先使用平台能力，定制代码有清单与负责人。
- [ ] 代码与配置纳入版本控制，关键逻辑有测试。
- [ ] 权限遵守客户的体系，操作留有记录。
- [ ] AI 用例有评测集、人工确认与注入防护。
- [ ] 价值报告使用客户认可的口径。
- [ ] 共性需求记录为产品缺口，并与产品团队评审。
- [ ] 有赋能与交接计划，接手人能独立操作。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| FDE 就是驻场的外包开发 | FDE 基于公司的产品工作，并把现场经验转化为产品能力 |
| FDE 就是实施工程师 | 实施按既定方案落地，FDE 在现场发现问题并构建方案 |
| 客户要什么就做什么 | 需要找到需求背后真正的问题 |
| 为了快可以不管工程质量 | 客户依赖的方案同样需要测试、权限与运维 |
| 演示成功就是交付成功 | 真实用户在日常工作中使用才算成功 |
| 定制越多客户越满意 | 定制越多维护负担越重，共性需求应当产品化 |
| FDE 只需要沟通能力 | 扎实的工程与数据能力同样关键 |
| AI 用例可以直接全自动 | 先从人工确认的方式开始，并建立评测 |
