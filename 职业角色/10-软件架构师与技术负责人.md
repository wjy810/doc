# 软件架构师与技术负责人进阶全景手册

> 从为一个功能选对技术方案，到为系统划定边界、控制复杂度、管理技术风险，再到建立组织的技术决策机制。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：准备承担技术负责职责的开发者、独立负责系统设计的全栈与后端工程师、外包项目的技术负责人，以及希望系统提升的在职架构师。

软件架构师与技术负责人要回答的核心问题是：系统中哪些决定重要且难以改变，应该怎样做出这些决定，以及怎样让团队在长期变化中持续交付。架构不是画在墙上的框图，也不是“用了多少中间件”；它体现在系统的边界、依赖方向、数据归属、质量属性的取舍，以及团队怎样围绕这些边界协作。

技术负责人（Tech Lead）和架构师的侧重点有所不同。技术负责人带领一个团队交付：做技术决定、评审代码与设计、排除障碍、培养成员，同时通常仍然写代码。架构师关注跨越更大范围与更长时间的结构性决定：系统如何划分、技术如何选型、风险如何控制、各团队的方案怎样保持一致。在很多团队中，两种职责由同一个人承担。

本手册先建立角色坐标，然后讲解质量属性与取舍、系统边界与模块划分、技术选型与决策记录、架构表达、技术风险与演进、非功能需求与容量、技术负责人的日常工作；随后进入分布式与数据、安全、云与成本、AI 系统、架构治理等专项；最后说明怎样与开发团队协作，以及开发者怎样成长为技术负责人和架构师。系统设计中的具体技术机制，见[《后端进阶全景手册》](../技术方向/后端进阶全景手册.md)。

主线是：**理解业务与质量目标 → 划定边界与依赖 → 做出可解释的技术决定 → 让团队理解并执行 → 管理风险与技术债 → 让架构随业务演进 → 建立组织的技术决策机制。**

不同公司中，这些职责可能对应技术负责人、软件架构师、资深或主任工程师（Staff／Principal Engineer）、解决方案架构师或企业架构师等岗位，职责划分差异很大。本手册描述架构与技术领导的职责本身；D1—D6 分级是学习组织方式，不对应任何职级体系。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 架构师与技术负责人负责什么

#### 01.1 什么是架构

国际标准 ISO/IEC/IEEE 42010 把架构理解为系统在其环境中的基本概念或属性，体现在其元素、关系以及设计与演进的原则之中，并区分“架构本身”与“描述架构的文档”。[B01](#ref-b01) 实践中常用一个更直接的说法：架构是那些重要且难以改变的决定。[B02](#ref-b02) 什么是“重要”，取决于业务：对支付系统，数据一致性与审计是重要的；对内容平台，扩展性与成本可能更重要。

#### 01.2 两种角色的侧重

| 方面 | 技术负责人 | 架构师 |
| --- | --- | --- |
| 范围 | 一个团队及其负责的系统 | 多个团队、系统或整个产品线 |
| 时间 | 当前与近期的交付 | 更长期的结构与演进 |
| 主要工作 | 技术决定、代码与设计评审、排除障碍、培养成员 | 边界划分、选型、风险、跨团队一致性 |
| 编码 | 通常持续编码 | 视组织而定，保持一定的动手能力很重要 |
| 成功标准 | 团队稳定交付、质量可靠、成员成长 | 系统可演进、风险可控、决策一致 |

资深工程师的职业路径常被总结为几种原型：带领团队的技术负责人、负责跨团队技术方向的架构师、深入解决难题的攻坚者，以及协助管理者推动组织事项的角色。[B03](#ref-b03) 不同原型需要的能力组合不同，不必都走同一条路。

#### 01.3 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 架构概览与视图 | 让团队理解系统结构 | 面向读者选择视图，保持与实现一致 |
| 架构决策记录 | 记录重要决定与理由 | 写明背景、选项、取舍和后果 |
| 质量属性场景 | 把非功能需求变成可验证的目标 | 有触发、响应和度量 |
| 技术方案评审 | 在实现前发现问题 | 聚焦风险与取舍，结论明确 |
| 技术规范与约束 | 让团队一致地做对 | 有理由、有示例，能自动检查的就自动检查 |
| 风险与技术债清单 | 管理不确定性与长期成本 | 有影响评估、负责人和处理计划 |
| 演进路线 | 从现状走向目标结构 | 分阶段、可回退、每一步都能交付价值 |

#### 01.4 与相邻角色的分工

| 事项 | 架构师／技术负责人的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 业务目标与优先级 | 参与 | 产品经理主导 | 技术方案服务于业务目标 |
| 技术方案与选型 | 主导 | 团队成员 | 重要决定需要听取受影响者的意见 |
| 实现 | 指导或参与 | 开发团队 | |
| 质量与测试策略 | 共同负责 | 测试工程师 | 见[《测试工程师与测试开发》](11-测试工程师与测试开发.md) |
| 安全设计 | 共同负责 | 安全工程师 | 见[《安全工程师》](12-安全工程师.md) |
| 运行与可靠性 | 共同负责 | SRE、运维 | 见[《运维工程师与 SRE》](13-运维工程师与SRE.md) |
| 进度与资源 | 参与 | 项目经理、研发经理 | 提供技术估算与风险 |
| 人员管理 | 视组织而定 | 研发经理 | 见[《研发经理与工程经理》](25-研发经理与工程经理.md) |
| 客户方案 | 参与 | 解决方案架构师 | 见[《解决方案架构师》](22-解决方案架构师.md) |

**本章练习**：列出你所在系统中五个“重要且难以改变”的决定，写出当初做出这些决定的原因；如果今天重新决定，是否会不同？

<a id="ch02"></a>

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **业务与领域理解**：理解业务目标、领域模型与变化方向。
2. **质量属性与取舍**：明确性能、可用性、安全、可维护性等目标及其冲突。
3. **边界与结构**：模块、服务、数据与团队的划分。
4. **技术选型与决策**：比较方案，做出可解释、可追溯的决定。
5. **架构表达与沟通**：用图、文档和讨论让不同读者理解。
6. **风险与演进**：识别技术风险，管理技术债，规划演进路径。
7. **技术领导**：评审、规范、指导与排除障碍。
8. **可靠性与运行**：可观测性、容量、故障与恢复。
9. **安全与合规**：威胁、权限、数据保护与合规约束。
10. **成本与组织**：系统的经济性，以及组织结构对架构的影响。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 能解释系统结构与常见模式，参与方案讨论 | 方案评审中的有效问题 |
| D2 独立完成 | 独立设计一个功能或模块的技术方案 | 技术方案、实现与复盘 |
| D3 负责结果 | 作为技术负责人，对一个系统的质量与交付负责 | 系统演进、事故减少、团队稳定交付 |
| D4 系统与跨团队 | 负责多个系统或团队的架构一致性与演进 | 跨团队边界、迁移路线、决策记录 |
| D5 方法与机制 | 建立组织的技术决策、评审与架构治理机制 | 决策流程、原则、技术雷达、评审机制 |
| D6 创新与影响 | 提出新的架构方法或开源基础设施，影响行业 | 公开的方法与工具、广泛采用的项目 |

#### 02.3 成长中的常见偏差

- 把架构等同于选择流行的技术，而不是解决具体的质量与业务问题。
- 过早拆分服务，在业务边界尚不清楚时承担分布式系统的全部复杂度。
- 做决定时只考虑技术，忽视团队能力、运维成本和组织结构。
- 决定只存在于少数人的记忆中，没有记录理由，后来者无法判断能否修改。
- 成为团队的瓶颈：所有决定都要经过自己，团队无法独立前进。
- 长期不写代码，与系统的真实情况脱节。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 质量属性与取舍

#### 03.1 质量属性

软件产品质量模型 ISO/IEC 25010 在 2023 版中把产品质量分为功能适合性、性能效率、兼容性、交互能力、可靠性、信息安全、可维护性、灵活性和功能安全九个特性。[B04](#ref-b04) 架构工作的核心之一，是明确哪些质量属性对这个系统最重要，以及它们之间怎样取舍。

#### 03.2 用场景表达质量要求

“系统要高可用”“性能要好”无法指导设计。质量属性场景把要求变成可验证的形式：

| 要素 | 示例 |
| --- | --- |
| 来源与触发 | 招聘季开始，提交简历分析的请求在 10 分钟内增加到平时的 5 倍 |
| 环境 | 正常运行，一个可用区故障 |
| 系统响应 | 新的分析请求被受理并排队，已受理的任务不丢失 |
| 度量 | 受理接口的第 99 百分位延迟低于 500 毫秒；排队任务在 30 分钟内完成 |

#### 03.3 取舍是架构的常态

质量属性之间常常冲突：更强的一致性可能降低可用性或增加延迟；更细的服务拆分提高独立部署能力，也增加运维与调试成本；更多的缓存提升性能，也带来数据新鲜度问题。架构决定需要明确说明选择了什么、放弃了什么，以及在什么条件下需要重新考虑。

**本章验收**：为一个系统写出 5 个最重要的质量属性场景，标出其中两组相互冲突的场景，并说明当前设计怎样取舍。

<a id="ch04"></a>

### 04 系统边界与模块划分

#### 04.1 好的边界

好的边界让相关的东西放在一起，让不相关的东西互不影响：一个模块内部变化时，其他模块不需要跟着修改。判断边界的依据包括：业务领域的划分、数据的归属、变化的频率与原因、团队的分工。领域驱动设计中的限界上下文是划分业务边界的常用方法（见[《领域专家》第 04 章](04-领域专家.md#ch04)）。

#### 04.2 模块化单体与微服务

| 方面 | 模块化单体 | 微服务 |
| --- | --- | --- |
| 部署 | 一起部署 | 独立部署 |
| 模块间调用 | 进程内调用，事务较简单 | 网络调用，需要处理失败与一致性 |
| 运维成本 | 较低 | 较高：服务发现、监控、追踪、发布协调 |
| 团队独立性 | 依赖模块边界的纪律 | 边界由部署单元强制 |
| 适合阶段 | 业务边界尚在探索，团队规模较小 | 边界清楚、团队较多、需要独立扩展与发布 |

在业务边界还不清楚时，先构建边界清晰的模块化单体，通常比过早拆分微服务风险更低；当某个模块有明确的独立扩展、发布或隔离需要时，再按边界拆出。Java 生态中，Spring Modulith 等工具可以帮助定义与验证模块边界，[B05](#ref-b05) ArchUnit 可以把依赖规则写成测试。[B06](#ref-b06) 模块与架构模式的更多讨论见[《后端进阶全景手册》第 12 章](../技术方向/后端进阶全景手册.md#ch12)。

#### 04.3 组织结构与系统结构

Conway 指出，设计系统的组织会产出与其沟通结构相似的系统。[B07](#ref-b07) 这意味着架构与团队结构需要一起设计：如果两个团队必须频繁协调才能完成普通需求，说明边界或分工可能不合适。有时可以反过来，先调整团队结构，引导系统形成期望的边界。

**本章验收**：为一个系统画出模块与依赖关系图，找出至少一处违反预期依赖方向的地方，并用自动化测试防止它再次出现。

<a id="ch05"></a>

### 05 技术选型与决策记录

#### 05.1 选型的依据

技术选型应从问题出发，而不是从技术出发。比较候选方案时考虑：

- 是否满足关键的质量属性场景。
- 团队的熟悉程度与学习成本。
- 运维负担、社区与供应商支持、版本与安全更新。
- 与现有系统的集成成本。
- 退出成本：如果选错了，替换需要多大代价。
- 总拥有成本：许可、资源、人力与支持。

优先选择“最简单的可行方案”，并说明什么条件下需要更复杂的方案。

#### 05.2 可逆与不可逆的决定

不同决定的修改成本不同：数据库与核心数据模型、公共接口、主要编程语言通常难以改变，需要更充分的论证；内部实现细节、可替换的库通常容易修改，可以快速决定并在实践中调整。把精力集中在难以改变的决定上。

#### 05.3 架构决策记录

架构决策记录（ADR）用简短的文档记录一个重要决定的背景、决定、理由与后果，与代码一起版本化管理。[B08](#ref-b08) 它让后来的人理解“为什么这样做”，从而判断条件变化后能否修改。

```text
ADR-007：分析任务队列使用数据库表实现，暂不引入独立消息中间件
状态：已接受（2026-10-25）
背景：分析任务量预计每天数万，需要可靠的受理、领取与重试；团队熟悉 PostgreSQL，暂无消息中间件运维经验。
决定：使用数据库表加条件更新实现任务领取与租约；通过发件箱记录需要通知的事件。
理由：满足当前吞吐与可靠性场景；减少一个需要运维的组件；事务边界清晰。
后果：吞吐上限受数据库约束；需要监控任务表的积压与锁等待。
重新评估条件：任务量增长到当前 10 倍，或出现多个异构消费者需要订阅事件。
```

**本章验收**：为你系统中最近的三个重要决定补写 ADR，请一位新成员阅读后说出每个决定的理由与重新评估的条件。

<a id="ch06"></a>

### 06 架构表达：图与文档

#### 06.1 面向读者选择视图

不同读者需要不同的视图：业务方关心系统的上下文与边界，开发者关心模块与依赖，运维关心部署与运行，安全人员关心数据流与信任边界。C4 模型用系统上下文、容器、组件、代码四个层级组织架构图，适合从整体到细节逐层说明。[B09](#ref-b09) arc42 提供了一套架构文档的模板结构。[B10](#ref-b10)

#### 06.2 让文档保持真实

- 文档与代码放在一起，用版本控制管理。
- 用代码生成图（图即代码），减少图与实现的偏离。
- 只写需要长期维护的内容：上下文、关键决定、约束与运行要点。
- 在评审和事故复盘中检查文档是否仍然准确。

#### 06.3 沟通

架构的价值只有在被理解时才能体现。用具体场景解释抽象的结构，例如“当一份简历上传后，会经过哪些组件，失败时会发生什么”。对不同的听众调整细节与术语。

**本章练习**：用 C4 模型为一个系统画出上下文图和容器图，请产品经理和一位新开发者分别阅读，记录他们的疑问并修改。

<a id="ch07"></a>

### 07 技术风险、技术债与演进

#### 07.1 识别与降低风险

在方案阶段列出技术风险：不熟悉的技术、性能是否达标、外部依赖是否可靠、数据迁移是否可行。对高风险项先做小规模的技术验证（探针或原型），而不是在完整实现之后才发现问题。

#### 07.2 技术债

技术债是为了短期速度而接受的、会增加未来修改成本的设计或实现。不是所有技术债都需要立即偿还：记录它的影响（事故、变更耗时、知识集中），决定立即修复、逐步替换还是暂时接受，并设定重新评估的条件（见[《后端进阶全景手册》第 12 章](../技术方向/后端进阶全景手册.md#ch12)）。

#### 07.3 渐进演进

大规模重写的风险很高：在新系统完成之前，旧系统仍在变化，业务无法等待。更稳妥的方式是渐进替换：在旧系统周围逐步建立新功能，把流量逐步迁移过去，最终替换旧系统。这种方式常被称为“绞杀者模式”。[B11](#ref-b11) 每一步都应能独立交付价值，并保留回退能力。数据与接口的兼容迁移见[《后端进阶全景手册》第 25 章](../技术方向/后端进阶全景手册.md#ch25)。

#### 07.4 适应度函数

把重要的架构特征写成可自动检查的规则，例如模块依赖方向、接口兼容性、性能预算、关键路径的延迟。这些检查在持续集成中运行，让架构在日常变化中不被悄悄破坏。

**本章验收**：为一个系统建立技术债清单，评估每项的影响，选择一项制定渐进替换计划，并为一个关键架构特征编写自动检查。

<a id="ch08"></a>

### 08 非功能需求与容量规划

#### 08.1 与产品一起明确目标

性能、可用性、恢复时间、数据新鲜度、安全、成本等非功能目标需要与产品经理和业务方一起确定，因为它们直接影响用户与成本。早期没有准确数字时，先写可验证的假设，并约定重新评估的时间。

#### 08.2 容量规划

| 步骤 | 内容 |
| --- | --- |
| 估算负载 | 用户数、请求频率、峰值倍数、数据增长 |
| 识别瓶颈 | 数据库、外部依赖、CPU、内存、网络、第三方配额 |
| 建立模型 | 资源随负载增长的关系 |
| 验证 | 压力测试与真实数据对比 |
| 规划 | 扩容触发条件、成本与提前量 |

服务等级目标、性能与容量的工程方法见[《后端进阶全景手册》第 15 章](../技术方向/后端进阶全景手册.md#ch15)与[第 16 章](../技术方向/后端进阶全景手册.md#ch16)。

**本章练习**：为一个系统估算一年后的负载，找出最先成为瓶颈的资源，写出扩容的触发条件和预计成本。

<a id="ch09"></a>

### 09 技术负责人的日常：评审、规范与交付

#### 09.1 代码与设计评审

评审的目的是提高质量、传播知识和保持一致，而不是证明谁更聪明。Google 公开的代码评审指南提出了一个实用的标准：只要一次修改整体上改善了代码库的健康程度，即使不完美，也应该被批准。[B12](#ref-b12) 技术负责人应关注：行为是否正确、设计是否合适、是否有足够的测试、是否引入了不必要的复杂度。风格类的问题尽量交给自动化工具。

#### 09.2 规范与工程习惯

建立团队约定：代码风格、分支与提交、测试要求、日志与错误处理、依赖引入、发布流程。规范要说明理由，能自动检查的就自动检查，并在实践中定期修订。

#### 09.3 交付与排除障碍

- 把大任务拆成可独立交付的小块，尽早暴露风险。
- 给出估算时说明不确定性。
- 及时发现并移除阻碍团队的问题：等待其他团队、环境不稳定、需求不清。
- 关注生产环境：事故、告警、性能，确保团队对自己的系统负责。

#### 09.4 培养团队

技术负责人的成功在于团队能力的提高：把有挑战的任务交给合适的成员，在评审中解释原因，鼓励成员主导方案设计，并在需要时提供支持。避免所有关键决定和关键代码都集中在自己身上。

**本章练习**：回顾你最近评审的 10 次修改，统计评论中有多少是风格问题、多少是设计与正确性问题；为风格问题配置自动化检查。

## 第三篇：专项与进阶

<a id="ch10"></a>

### 10 分布式系统与数据架构

#### 10.1 数据归属

每类数据应有明确的权威来源与负责的模块或服务。其他模块需要数据时，通过接口获取或订阅变化，而不是直接读写对方的数据库。数据归属不清，是分布式系统中一致性问题和团队冲突的常见来源。

#### 10.2 跨边界的一致性

一旦跨越进程或服务的边界，就不再能依赖单个数据库事务。需要明确：哪些不变量必须严格保持，哪些可以接受短暂的不一致；用什么机制处理重复、乱序和部分失败（幂等、发件箱、补偿、对账）。这些机制的细节见[《后端进阶全景手册》第 18 章](../技术方向/后端进阶全景手册.md#ch18)至[第 20 章](../技术方向/后端进阶全景手册.md#ch20)。

#### 10.3 数据架构

数据架构关注数据怎样产生、存储、流动、加工和退役：业务数据库、分析数据仓库、搜索索引、缓存、对象存储之间的关系；数据的血缘与质量；个人数据的保留与删除。数据平台的工程见[《数据工程师》](17-数据工程师.md)。

**本章练习**：为一个系统画出数据归属图，标出每类数据的权威来源、副本及其同步方式，找出归属不清的数据。

<a id="ch11"></a>

### 11 安全与合规架构

#### 11.1 在架构阶段考虑安全

安全问题的修复成本在架构阶段最低。架构设计中需要明确：信任边界在哪里、身份怎样传递、授权在哪里检查、敏感数据怎样存储与传输、密钥怎样管理、外部输入怎样校验。在方案评审中进行威胁建模（见[《安全工程师》](12-安全工程师.md)）。

#### 11.2 合规约束

数据存储地点、个人信息处理、审计留存、行业监管等合规要求会直接影响架构：数据能否跨境、日志保存多久、删除怎样实现。这些要求由法务与合规负责人确认，架构负责把它们转化为可实现、可验证的设计。

**本章练习**：为一个系统画出信任边界与数据流图，标出每个边界上的身份验证、授权与数据保护措施。

<a id="ch12"></a>

### 12 云、成本与架构经济性

#### 12.1 架构框架

主要云厂商都发布了架构框架，例如 AWS 的 Well-Architected 框架把架构评估分为卓越运营、安全、可靠性、性能效率、成本优化和可持续性六个支柱。[B13](#ref-b13) 这些框架适合作为架构评审的检查清单，但具体方案需要根据业务调整，不必照搬某一家的服务。

#### 12.2 成本是架构属性

云上的成本随架构变化：服务拆分、数据复制、跨区流量、日志与监控、闲置资源都会产生费用。把单位成本（例如每次分析的成本）纳入架构评估，并让工程团队能看到自己系统的成本。FinOps 是让工程、财务与业务团队共同管理云成本的实践。成本与技术决策的更多内容见[《后端进阶全景手册》第 34 章](../技术方向/后端进阶全景手册.md#ch34)。

#### 12.3 避免过度依赖

托管服务能减少运维负担，也会带来供应商依赖。对于核心数据与关键能力，评估迁移与退出的成本，保留必要的可移植性，但不必为所有组件追求“完全不依赖供应商”。

**本章练习**：计算一个系统核心操作的单位成本，找出成本最高的三个组成部分，提出不影响关键质量属性的优化方案。

<a id="ch13"></a>

### 13 AI 系统的架构

#### 13.1 AI 应用的典型组成

| 组件 | 作用 | 架构关注点 |
| --- | --- | --- |
| 模型接入层 | 统一调用一个或多个模型 | 超时、重试、限流、成本计量、版本管理 |
| 检索与上下文 | 为模型提供相关资料 | 权限过滤、新鲜度、索引更新 |
| 工具与执行 | 让模型调用业务能力 | 授权、幂等、副作用控制、审计 |
| 评测与监控 | 衡量输出质量 | 离线评测集、在线抽检、版本对比 |
| 防护 | 处理不可信输入与输出 | 提示注入、敏感信息、内容安全 |
| 任务与状态 | 管理长时间的处理 | 可恢复、可取消、结果版本 |

#### 13.2 关键设计问题

- **把模型调用当作不可靠的外部依赖**：设置超时、预算和降级方案，结果可能未知。
- **权限不交给模型判断**：授权在业务系统中检查，模型只能使用被授予的能力。
- **质量与性能分开度量**：接口成功不等于结果正确。
- **版本可追溯**：记录模型、提示词、检索数据与工具的版本。

这些问题的工程细节见[《后端进阶全景手册》第 32 章](../技术方向/后端进阶全景手册.md#ch32)，模型层面的方法见[《算法与机器学习工程师》](18-算法与机器学习工程师.md)。

**本章练习**：为 AI 简历分析画出组件图，标出信任边界、版本记录点、评测与监控点，以及模型不可用时的降级路径。

<a id="ch14"></a>

### 14 架构治理与组织

#### 14.1 从审批到建议

传统的架构评审委员会集中审批重要决定，容易成为瓶颈。一种替代方式是“建议流程”：任何人都可以做出架构决定，但必须先征求受影响者和相关专家的意见；配合决策记录、架构建议论坛、团队共同制定的原则和技术雷达，在保持团队自主的同时维持一致性。[B14](#ref-b14)

#### 14.2 原则与技术雷达

架构原则用少量可执行的规则指导日常决定，例如“优先使用托管服务”“每个服务拥有自己的数据”。技术雷达记录组织对各项技术的态度（采用、试用、评估、暂缓），帮助团队选型时参考已有经验。

#### 14.3 架构师的影响力

架构师很少能依靠职位命令他人，更多依靠影响力：清楚地解释理由、倾听不同意见、用原型和数据说话、帮助团队解决实际问题。好的架构治理让团队能够自己做出好的决定。

**本章练习**：为团队制定 5 条架构原则，每条附上理由与一个应用示例；组织一次建议流程，记录征求的意见与最终决定。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与开发团队的协作接口

#### 15.1 架构师与技术负责人应提供给团队的内容

| 内容 | 最低要求 | 常见缺失 |
| --- | --- | --- |
| 系统上下文与边界 | 模块职责与依赖方向 | 图与实现不一致 |
| 重要决定及理由 | 决策记录 | 只有结论，没有理由 |
| 质量目标 | 可验证的场景 | “要高性能”之类的描述 |
| 规范与约束 | 有理由、可自动检查 | 只存在于口头约定 |
| 技术风险 | 已知风险与应对 | 风险在实现后才暴露 |
| 及时的支持 | 方案讨论与问题解答 | 成为瓶颈，团队长时间等待 |

#### 15.2 团队应反馈给架构师的内容

实现中发现的约束与问题、方案执行的实际成本、规范是否好用、生产环境中的真实表现。架构需要根据这些反馈持续调整。

#### 15.3 与产品和业务的协作

把技术风险和技术债用业务能理解的语言表达：影响交付速度多少、增加多少事故风险、需要多少成本。与产品经理一起为技术工作安排优先级（见[《产品经理》第 07 章](01-产品经理.md#ch07)）。

<a id="ch16"></a>

### 16 从开发者成长为技术负责人与架构师

#### 16.1 能力的转变

| 从 | 到 |
| --- | --- |
| 解决分配给自己的问题 | 发现并定义需要解决的问题 |
| 关注自己的代码 | 关注整个系统与团队的产出 |
| 给出一个方案 | 比较多个方案并说明取舍 |
| 用技术语言沟通 | 根据听众调整表达 |
| 依靠自己的努力 | 通过他人完成目标 |

#### 16.2 可以立即开始的练习

- 为自己负责的模块写 ADR 和架构概览。
- 在方案评审中主动提出质量属性与失败场景的问题。
- 主导一次技术方案设计，邀请他人评审。
- 参与值班与事故复盘，理解系统在生产中的真实表现。
- 指导一位新成员完成一个完整的功能。

#### 16.3 独立开发者与外包项目

独立开发者和外包项目的技术负责人往往同时承担架构、开发、运维与沟通。这时更需要克制：选择团队（往往就是自己）能长期维护的最简单架构；把关键决定写下来，便于将来交接；为客户说明重要的技术取舍与长期成本，避免交付后难以维护。

### 17 贯穿实战：求职平台的可演进架构

本章展示一个系统从起步到演进的架构过程。数字都是示意。

#### 17.1 起步：模块化单体

团队规模 4 人，业务边界仍在探索。决定采用模块化单体加独立的任务工作进程：

| 模块 | 职责 | 拥有的数据 |
| --- | --- | --- |
| 账号与组织 | 注册、登录、组织与成员 | 用户、组织、成员关系 |
| 简历 | 上传、版本、解析结果 | 简历、版本、文件引用 |
| 分析 | 分析任务、结果与证据 | 分析操作、执行尝试、结果 |
| 岗位与匹配 | 岗位信息、匹配建议 | 岗位、匹配记录 |
| 额度与计费 | 额度预留、消耗与调整 | 额度记录 |
| 通知 | 站内消息、邮件 | 通知记录 |

模块之间只通过公开的接口或事件交互，用自动化测试检查依赖方向。关键决定（数据库、任务队列实现、对象存储、模型接入方式）都写成 ADR。

#### 17.2 质量属性与取舍

最重要的质量属性场景是：招聘季高峰时分析请求不丢失、受理快速；简历与分析结果的权限隔离；单次分析的成本可控。为此选择异步任务、额度预留、模型调用超时与预算控制。可靠提交路径的设计见[《后端进阶全景手册》第 43 章](../技术方向/后端进阶全景手册.md#ch43)。

#### 17.3 演进

一年后业务增长，出现两个明确的拆分信号：

1. **岗位搜索**的查询模式与写入完全不同，需要独立的搜索索引与扩展方式，于是把它拆为独立服务，通过事件同步岗位数据。
2. **模型推理**的资源需求（GPU、批处理）与主应用差异很大，于是把模型接入层独立部署，统一管理多个模型的路由、限流与成本计量。

其他模块仍保留在单体中。每次拆分前写 ADR，采用渐进迁移：先在单体内把边界整理干净，再把流量逐步切换到新服务，保留回退能力。

#### 17.4 治理

团队扩展到 3 个小组后，引入建议流程：重要决定在架构建议论坛上征求意见，结果写入 ADR；每季度更新一次团队的技术雷达。技术负责人从“做所有决定”转向“帮助各小组做出好的决定”。

#### 18.1 能力矩阵

| 技术领导 | 参与评审／主导一个功能的技术 | 技术负责人／多团队技术协调 | 评审与规范体系／领导方法创新 |
| 可靠性与运行 | 理解监控与容量／容量估算 | 系统可靠性负责／跨系统可靠性 | 可靠性架构标准／可靠性研究 |
| 安全与合规 | 了解常见风险／信任边界设计 | 系统安全架构／跨系统合规架构 | 安全架构标准／安全架构创新 |
| 成本与组织 | 了解成本构成／单位成本计算 | 系统经济性负责／组织与架构协同 | 架构经济性机制／组织架构研究 |

#### 18.2 学习路线

| 阶段 | 学习重点 | 实践目标 | 进入下一阶段的信号 |
| --- | --- | --- | --- |
| A 方案设计 | 01—06 章 | 独立设计一个模块并写 ADR | 方案经评审后能稳定实现 |
| B 技术负责 | 07—09 章 | 作为技术负责人带领一个小团队交付 | 团队稳定交付，成员能独立承担任务 |
| C 系统架构 | 10—13 章 | 负责一个系统的架构演进 | 完成一次渐进迁移，质量目标可验证 |
| D 组织影响 | 14、18 章 | 建立跨团队的决策与治理机制 | 各团队能借助机制独立做出一致的决定 |

#### 18.3 技术方案模板

```text
背景与目标（业务目标、质量属性场景）：
现状与约束（技术、团队、时间、成本、合规）：
候选方案（每个方案：概述、优点、缺点、风险、成本）：
推荐方案与理由：
关键设计（边界、数据、接口、失败处理、安全、可观测性）：
迁移与发布计划（含回退）：
风险与验证计划：
待决问题：
评审人与结论：
```

#### 18.4 检查清单

方案评审时：

- [ ] 方案对应明确的业务目标与质量属性场景。
- [ ] 考虑了至少一个更简单的替代方案。
- [ ] 边界清楚，数据归属明确。
- [ ] 失败、重复、超时与部分成功的处理已设计。
- [ ] 安全：信任边界、身份、授权与敏感数据已考虑。
- [ ] 可观测性：日志、指标、追踪与告警已规划。
- [ ] 迁移、发布与回退方案可行。
- [ ] 运维与成本影响已评估。
- [ ] 重要决定写入 ADR，包含重新评估的条件。

长期维护时：

- [ ] 架构文档与实现一致。
- [ ] 关键架构特征有自动检查。
- [ ] 技术债清单定期评估。
- [ ] 决策机制没有让架构师成为瓶颈。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 架构就是选技术栈 | 架构是重要且难以改变的决定，技术栈只是其中一部分 |
| 微服务比单体更先进 | 架构应适合业务、团队与运行需求，模块化单体也可以很成熟 |
| 架构师不需要写代码 | 保持动手能力有助于做出符合实际的决定 |
| 好的架构一开始就能设计好 | 架构需要随业务演进，重要的是保留演进的能力 |
| 架构评审就是审批 | 评审的目的是发现风险与改进方案，也可以采用建议流程 |
| 技术债必须全部还清 | 技术债需要按影响管理，有些可以长期接受 |
| 重写比渐进改造更快 | 大规模重写风险很高，渐进替换通常更稳妥 |
| 技术负责人要做所有决定 | 技术负责人的目标是让团队能做出好的决定 |
| 文档越多越好 | 只维护对读者有用、能保持真实的文档 |
