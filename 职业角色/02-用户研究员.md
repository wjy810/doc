# 用户研究员进阶全景手册

> 从组织一次可靠的访谈，到为产品决策提供可信证据，再到建立组织的研究体系与方法。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：希望转向用户研究的设计师、产品经理与开发者，需要自己做研究的独立开发者，以及希望系统提升的在职研究员。

用户研究员要回答的核心问题是：用户实际上怎样做事、遇到什么困难、在什么情境下需要什么，以及这些发现对产品决策意味着什么。用户研究不是“问用户想要什么功能”，也不是为已经做出的决定寻找支持材料。它的价值在于用可追溯的证据减少团队对用户的错误假设，并在合适的时间影响决定。

本手册先建立角色坐标，然后按照研究的完整过程展开：从决策问题出发制定计划，招募参与者，执行访谈、观察、可用性测试和问卷，分析与综合数据，最后把洞察传达给团队并跟踪它是否被采用。随后进入研究伦理、研究运营、特殊情境与混合方法等专项，最后说明研究员与开发者如何协作，以及开发者怎样在资源有限时做轻量研究。

主线是：**明确要支持的决策 → 选择方法与参与者 → 收集数据 → 分析与综合 → 传达洞察并影响决策 → 积累知识与建设研究体系。**

不同组织中，用户研究可能由专职研究员、设计师、产品经理或市场研究团队承担，名称也可能是“用户体验研究员”“设计研究员”“UX Researcher”。本手册描述研究职责与方法本身；D1—D6 分级是学习组织方式，不对应任何职级体系。涉及个人信息、未成年人和录音录像的内容只说明研究中需要考虑的问题，具体义务由法务或隐私负责人依适用规则确认。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 用户研究员负责什么

#### 01.1 核心问题：为决策提供关于用户的证据

团队每天都在依据对用户的假设做决定：用户会从哪里进入、能否理解某个说法、为什么放弃某个步骤。用户研究把这些假设变成可以检验的问题，并通过观察、对话和测量获得证据。英国政府数字服务手册把用户研究描述为帮助团队了解用户及其需要、在整个服务生命周期中持续进行的工作，而不是项目开始时的一次性活动。[B01](#ref-b01)

研究员的成果不以报告页数衡量，而以三件事衡量：证据是否可信、是否在决策发生前到达、是否真正改变或确认了决定。一份严谨却在功能上线后才交付的报告，价值有限。

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 研究计划 | 对齐要回答的问题、方法与时间 | 从决策出发，说明方法为什么能回答这些问题 |
| 招募筛选问卷 | 找到合适的参与者 | 能区分目标人群，避免引导参与者“答对” |
| 讨论指南或测试脚本 | 保证数据收集的一致性 | 开放、不诱导，留出追问空间 |
| 原始记录 | 保存可追溯的证据 | 有时间、参与者编号、上下文，遵守隐私约定 |
| 分析与综合结果 | 从数据中形成模式 | 结论能追溯到具体证据，区分观察与解释 |
| 洞察与建议 | 支持团队决策 | 说明证据强度、适用范围与对决策的含义 |
| 旅程地图、人物角色等模型 | 让团队共享对用户的理解 | 基于真实数据，标明来源与更新时间 |
| 可用性问题清单 | 指导修改 | 有严重程度、发生频率与复现条件 |
| 研究知识库 | 让过去的发现可被检索和复用 | 有标签、来源、时效说明和访问权限 |

#### 01.3 职责边界与相邻角色

| 事项 | 用户研究员的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 确定要研究的问题 | 共同负责 | 产品经理、设计师 | 研究问题应来自真实的决策需要 |
| 选择方法、设计研究 | 主导 | 设计师、数据分析师 | 研究员对方法的适当性负责 |
| 招募与参与者沟通 | 主导 | 研究运营、客服、销售 | 企业客户的招募常需客户成功团队协助 |
| 主持访谈和测试 | 主导 | 团队成员观察 | 鼓励开发者和产品经理旁听 |
| 分析与综合 | 主导 | 团队共同参与 | 共同分析能提高团队对结论的认同 |
| 基于洞察的设计与产品决定 | 参与 | 产品经理、设计师主导 | 研究员提供证据与含义，不代替决策 |
| 行为数据分析 | 协作 | 数据分析师主导 | 定性与定量互相解释（见 13 章） |
| 市场规模与品牌调研 | 协作 | 市场研究团队 | 关注点与方法不同，可以互补 |

英国政府数字与数据能力框架把用户研究员描述为计划、设计并开展与用户的研究活动，帮助团队深入理解服务使用者的角色，并把能力分为从初级到研究负责人的多个级别。[B02](#ref-b02)

#### 01.4 不同组织中的形态

- **嵌入式**：研究员加入一个产品团队，深入了解领域，研究与决策联系紧密，但可能缺少跨团队视角。
- **集中式**：研究团队为多个产品服务，方法和质量统一，但离具体决策较远。
- **混合式**：研究员嵌入团队，同时属于一个研究职能组织，共享方法、工具和知识库。
- **研究民主化**：设计师、产品经理也开展研究，研究员负责培训、审核与复杂研究。需要护栏，避免低质量研究产生误导性结论（见 11 章）。
- **没有专职研究员的团队**：研究工作由产品经理、设计师或开发者承担，方法上更需要克制与诚实（见 15 章）。

**本章练习**：回顾最近一次团队讨论中的三个“用户会……”的说法，分别写出它所依据的证据；没有证据的，写出可以用什么方法在两周内获得证据。

<a id="ch02"></a>

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **研究规划**：从决策问题出发确定研究问题、方法、样本和时间。
2. **生成式研究**：探索用户的情境、需求与行为，发现新机会。
3. **评估式研究**：检验方案或现有产品能否被理解和使用。
4. **定量研究**：问卷、度量与统计推断。
5. **分析与综合**：从原始数据中形成可靠的模式与洞察。
6. **沟通与影响**：让洞察在合适的时间进入决策。
7. **研究伦理与参与者保护**：知情同意、隐私、弱势群体与数据安全。
8. **研究运营**：招募、工具、流程与知识库建设。
9. **特殊人群与情境**：专业用户、残障用户、跨文化、线下服务、AI 产品。
10. **混合方法**：把定性研究与行为数据、实验结合起来。

#### 02.2 六级纵向深度

| 深度 | 用户研究员的能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 能说明常见方法的用途，协助记录与整理 | 观察记录、整理过的访谈笔记 |
| D2 独立完成 | 独立完成一项边界清楚的研究，从计划到报告 | 研究计划、讨论指南、洞察报告 |
| D3 负责结果 | 为一个产品领域持续提供研究，影响关键决定 | 研究路线图、被采用的洞察及其后续结果 |
| D4 系统与跨团队 | 组织跨产品、跨地区或长期的研究项目 | 跨团队研究计划、纵向研究、综合模型 |
| D5 方法与机制 | 建立研究标准、培训、运营流程和知识库 | 研究规范、招募体系、知识库与培训材料 |
| D6 创新与影响 | 提出并验证新的研究方法，影响行业实践 | 方法论文、公开工具、行业采用的研究框架 |

#### 02.3 成长中的常见偏差

- 方法先行：先决定“做访谈”，再寻找要问的问题。
- 把参与者的观点当作事实：用户说“我会用”，不等于用户会用。
- 只报告有趣的发现，不报告与团队预期一致的发现，也不报告研究的局限。
- 研究结束就算完成，不跟踪洞察是否影响了决定。
- 用研究的复杂程度证明专业性，忽视团队的时间约束。

## 第二篇：核心研究方法

<a id="ch03"></a>

### 03 从决策问题到研究计划

#### 03.1 区分三种问题

- **决策问题**：团队需要做出的决定，例如“简历分析第一版应该先做内容完整性建议，还是岗位匹配建议？”
- **研究问题**：为了做这个决定需要知道的事实，例如“学生在投递前最不确定的是简历的哪些方面？他们怎样判断修改是否有效？”
- **访谈或测试中的问题**：向参与者提出的具体问题，例如“请回忆你上一次修改简历的经过。”

研究问题不能直接拿去问参与者。“你最需要哪种建议”会得到猜测和礼貌性回答；询问具体经历、观察实际行为，才能得到可分析的数据。

#### 03.2 选择方法

方法选择取决于想了解什么、在什么情境下、需要多大程度的确定性。一个常用的分类框架从三个维度比较研究方法：关注态度（人们说什么）还是行为（人们做什么）；定性（为什么、怎样）还是定量（多少、多频繁）；以及在什么使用情境中进行（真实环境、按脚本进行、脱离产品，或几者结合）。[B03](#ref-b03)

| 想了解的问题 | 常用方法 | 主要局限 |
| --- | --- | --- |
| 用户怎样完成某项任务、遇到什么困难 | 情境调查、观察、日记研究 | 成本较高，样本小 |
| 用户怎样理解某个问题、动机是什么 | 半结构化访谈 | 依赖回忆与表达 |
| 方案能否被理解和使用 | 可用性测试 | 测试情境与真实使用存在差异 |
| 内容应该怎样分类与命名 | 卡片分类、树测试 | 不检验界面中的视觉与交互 |
| 某种态度或行为的分布 | 问卷 | 题目与抽样偏差影响大 |
| 用户实际在哪一步流失 | 行为数据分析 | 不能直接说明原因 |
| 改动是否引起行为变化 | 对照实验 | 需要足够流量与正确设计 |

#### 03.3 研究计划

```text
研究计划模板
要支持的决策与决策时间：
研究问题（3—5 个）：
已有的证据与假设：
方法与选择理由：
参与者（人群、筛选条件、数量、配额）：
研究材料（讨论指南、原型、任务）：
时间安排与团队参与方式：
数据记录、存储与保留：
伦理与同意：
产出形式与分享方式：
已知局限：
```

计划需要与产品经理和设计师一起确认，尤其是“要支持的决策”和“决策时间”。如果研究结束时决定已经做出，就应缩小研究范围或改用更快的方法。

**本章练习**：选一个团队正在讨论的决定，写出决策问题、三个研究问题和对应的方法，并说明每种方法不能回答什么。

### 04 参与者招募与样本

#### 04.1 找到合适的人

招募的目标是找到能代表决策所涉及人群的参与者，而不只是“愿意参加的人”。筛选问卷应基于行为和经历（例如“过去三个月是否投递过实习”），而不是自我评价（“你是否擅长写简历”）；问题不要暴露研究目的，避免参与者猜测“正确答案”。

常见招募来源包括：产品内邀请、已有用户名单、客服与销售接触的客户、专业招募机构、社群与校园渠道。每种来源都有偏差：产品内招募只能接触现有用户；社群招募偏向活跃用户。计划中要写明来源及可能的偏差。

#### 04.2 定性研究的样本量

定性研究追求的是理解模式，而不是统计代表性。样本量取决于人群的差异程度、研究问题的范围以及新信息出现的速度。当新的访谈不再带来新的重要主题时，可以认为接近饱和。

关于可用性测试，Nielsen 提出：在用户群相对一致、以发现问题为目的、并且迭代进行多轮测试的前提下，每轮约 5 名参与者就能发现大部分常见问题，比一次测试很多人更划算。[B04](#ref-b04) 这一结论不适用于需要统计估计的定量研究，不意味着 5 人能发现所有问题，也不适用于差异很大的多个人群；人群不同时，应分别覆盖。

#### 04.3 包容性招募

主动纳入容易被忽视的人群：残障用户、年长用户、低数字技能用户、不同地区与语言的用户、网络条件较差的用户。为他们准备合适的参与方式，例如屏幕阅读器兼容的测试材料、远程参与的替代方案、更长的时间安排（见 12 章）。

#### 04.4 报酬与关系

报酬应与参与时间和难度相称，不能高到让人为报酬而夸大资格，也不能让参与者感到必须配合。企业客户的参与者可能不能接受现金报酬，需要遵守其公司规定。记录每位参与者的参与历史，避免同一个人频繁参加而成为“职业参与者”。

**本章验收**：为一项研究写筛选问卷，请同事扮演不同类型的候选人填写，检查问卷能否准确区分目标人群，且不泄露研究意图。

<a id="ch05"></a>

### 05 访谈、情境调查与日记研究

#### 05.1 半结构化访谈

半结构化访谈有一份讨论指南，但允许根据参与者的回答追问和调整顺序。好的讨论指南：

- 从参与者熟悉的经历开始，逐步进入研究主题。
- 询问具体事件：“请讲讲上一次……的经过”，而不是“你通常会……”。
- 使用开放问题，避免诱导：“你当时怎么想的？”而不是“你是不是觉得很麻烦？”
- 留出追问：“能多说一点吗？”“为什么这么做？”“当时还考虑过什么？”
- 把对方案的反馈放到最后，避免影响对真实经历的描述。

访谈中，研究员要注意自己的反应：点头、赞同或惊讶都会影响参与者后续的回答。记录时区分参与者的原话、观察到的行为与自己的解释。

#### 05.2 关键事件法

请参与者回忆一次印象特别深的成功或失败经历，追问当时的情境、行动、结果和感受。具体事件比概括性描述更可靠，也更容易发现团队没有想到的情境。

#### 05.3 情境调查

情境调查在用户的真实环境中观察其工作，并在过程中提问，研究员像学徒一样向“师傅”学习。它适合理解复杂工作流程、专业工具的使用和环境约束，例如招聘专员筛选简历时同时使用哪些系统。观察到的“绕路做法”，例如自己维护的表格、便签和重复录入，往往指向重要的机会。

#### 05.4 日记研究

日记研究让参与者在一段时间内持续记录相关的行为和感受，适合研究长周期或间歇发生的过程，例如整个求职季中的投递、准备与情绪变化。它能捕捉访谈中难以回忆的细节，但需要精心设计提示频率和记录方式，并通过中途沟通维持参与。[B05](#ref-b05)

**本章练习**：写一份 45 分钟的访谈讨论指南，请同事试访一次，录音后逐句检查：哪些问题是诱导性的，哪些地方错过了追问。

<a id="ch06"></a>

### 06 可用性测试与信息架构研究

#### 06.1 可用性的定义

国际标准 ISO 9241-11 把可用性定义为：特定用户在特定使用情境中，为实现特定目标而使用产品时达到的有效性、效率和满意度。[B06](#ref-b06) 这个定义提醒我们：可用性总是相对于“谁、做什么、在什么情境”而言，测试设计也要从这三点出发。

#### 06.2 设计测试任务

- 任务应来自真实目标，用参与者能理解的语言描述，不使用界面上的按钮名称作为提示。
- 写清成功标准，例如“找到并下载修改建议报告”。
- 任务顺序从简单到复杂，避免前一个任务的答案泄露后一个任务的线索。
- 准备真实的测试数据：长姓名、空字段、格式异常的文件。

#### 06.3 主持与出声思维

请参与者一边操作一边说出自己的想法（出声思维），能让研究员看到其理解过程。主持人应少说话，不解释界面，不在参与者困惑时立刻帮忙；需要干预时，用中性的问题，例如“你正在找什么？”出声思维是最常用也最有价值的可用性方法之一。[B07](#ref-b07)

#### 06.4 记录与评定问题

记录每个任务的完成情况、耗时、错误和关键的原话。对发现的问题评定严重程度，综合考虑发生频率、对任务的影响以及用户能否自行克服。[B08](#ref-b08) 一个出现频率低但会导致数据丢失的问题，可能比频繁出现的小困惑更严重。

| 严重程度 | 判断依据 | 处理建议 |
| --- | --- | --- |
| 严重 | 阻止任务完成或造成数据错误、损失 | 上线前必须修复 |
| 较重 | 显著拖慢任务或导致多数人犯错 | 优先修复 |
| 一般 | 引起困惑但能自行克服 | 排期修复 |
| 轻微 | 外观或措辞问题 | 有时间时修复 |

#### 06.5 远程、无主持与现场测试

远程主持测试可以接触更广的地区与人群；无主持测试样本大、成本低，但无法追问；现场测试适合需要观察环境或实体设备的场景。选择时考虑任务复杂度、参与者的技术条件和隐私要求。

#### 06.6 信息架构研究

- **卡片分类**：请参与者把内容卡片分组并命名，了解用户怎样理解内容之间的关系。开放式分类让参与者自建分组；封闭式分类给定分组。[B09](#ref-b09)
- **树测试**：只给出文字形式的导航结构，请参与者寻找特定内容，检验分类与命名是否容易找到。[B10](#ref-b10)

两者结合使用：先用卡片分类了解用户的心智模型，再用树测试验证新的导航结构。

**本章验收**：对一个真实页面完成 5 人可用性测试，产出带严重程度的问题清单，以及每个严重问题的视频片段或原话证据。

<a id="ch07"></a>

### 07 问卷与定量研究

#### 07.1 问卷设计

- 每个问题只问一件事，避免“这个功能是否有用且易用”这样的双重问题。
- 避免诱导性措辞和社会期望偏差；对敏感问题提供“不愿回答”选项。
- 量表的选项要平衡、有明确含义；同一份问卷中保持量表方向一致。
- 先做小范围试填，检查理解是否一致、填写时间是否合理。

#### 07.2 标准化量表

标准化量表的优点是可比较。系统可用性量表（SUS）由 10 个题目组成，得分范围 0—100；根据 MeasuringU 汇总的大量研究，平均分约为 68。SUS 分数不是百分比：68 分表示大约处于中等水平，而不是“68% 可用”。[B11](#ref-b11) 净推荐值（NPS）便于跟踪趋势，但作为单一题目，解释力有限，不应代替对具体任务和原因的研究。

#### 07.3 抽样与误差

问卷结论的可信度取决于样本是否代表目标人群，以及样本量带来的误差。以估计一个比例为例，95% 置信水平下，比例接近 50% 时，100 份有效回答的误差范围约为正负 10 个百分点，400 份约为正负 5 个百分点。回答率低、只有特定人群愿意回答时，样本量再大也可能有偏差。

#### 07.4 与数据分析师合作

复杂的统计分析、长期跟踪和实验设计应与数据分析师合作。研究员擅长设计问题和解释原因，分析师擅长处理数据质量、统计方法和指标口径（见[《数据分析师与产品分析师》](16-数据分析师与产品分析师.md)）。

**本章练习**：审查一份现有问卷，找出至少 5 个双重问题、诱导问题或量表不平衡的问题，并改写。

<a id="ch08"></a>

### 08 分析与综合

#### 08.1 从原始数据到主题

主题分析是定性研究中最常用的分析方法之一。Braun 与 Clarke 描述了一个六阶段过程：熟悉数据、生成初始编码、寻找主题、审查主题、定义并命名主题、撰写报告。[B12](#ref-b12) 关键在于主题要能追溯到数据，并经过反复检查，而不是从记忆中挑选印象深刻的片段。

实践中常用亲和图：把观察和原话写在便签上，按相似性分组，再为每组命名并寻找组与组之间的关系。邀请团队成员参与分组，可以减少研究员个人视角的偏差，也能让团队更认同结论。

#### 08.2 写出好的洞察

一条洞察应包含：观察到的现象、对现象的解释、对产品决策的含义。

```text
洞察的结构
观察：12 名参与者中有 9 名在修改简历后，会把同一份简历发给不同的人征求意见。（证据：访谈 P02、P05……）
解释：他们缺少判断修改是否有效的标准，只能依赖他人意见，而不同人的意见经常矛盾。
含义：仅提供建议不足以帮助学生判断修改效果；需要解释建议的依据，并支持修改前后的比较。
证据强度：中等。来自访谈，尚未在行为数据中验证。
```

洞察和建议要分开写：洞察描述用户，建议描述团队可以做什么。产品团队可能有不同的解决方案，研究员不必把建议写成唯一答案。

#### 08.3 证据强度与偏差

报告中标明每条结论的证据强度：多少参与者、什么方法、是否与其他来源一致。注意常见偏差：

- **确认偏误**：更容易注意到支持自己预期的数据。
- **显著性偏差**：被生动的个案吸引，忽视更普遍的模式。
- **样本偏差**：参与者不能代表目标人群。
- **主持偏差**：研究员的提问方式影响了回答。

#### 08.4 人物角色与旅程地图

人物角色和旅程地图是把研究结果综合成团队共享模型的工具。它们需要基于真实数据，标明来源和更新时间；如果从未经过研究、只是团队想象，反而会固化错误假设。旅程地图适合呈现跨时间、跨渠道的体验，便于发现断点与情绪低谷。

**本章验收**：对一组访谈记录完成编码与主题分析，每个主题至少有 3 条可追溯的原始证据，并写出 3 条包含观察、解释与含义的洞察。

<a id="ch09"></a>

### 09 传达洞察与影响决策

#### 09.1 让团队亲眼看到用户

最有说服力的方式是让产品经理、设计师和开发者直接观察研究过程：旁听访谈、观看测试录像。研究后组织简短的回顾会，让观察者先说出看到了什么，再由研究员补充。团队成员亲眼看到的问题，比报告中的文字更容易推动改变。

#### 09.2 选择合适的形式

| 形式 | 适用场景 | 注意 |
| --- | --- | --- |
| 简短的结论摘要 | 快速决策、团队已参与研究 | 附上证据链接 |
| 完整报告 | 重要决策、需要存档或跨团队共享 | 开头写结论，正文支撑 |
| 视频精选 | 让未参与者感受用户的困难 | 获得参与者同意，避免断章取义 |
| 工作坊 | 需要团队共同决定下一步 | 研究员主持，产出明确的行动 |
| 知识库条目 | 长期复用 | 写明时效与适用范围 |

#### 09.3 跟踪影响

记录每条重要洞察后来的去向：是否改变了某个决定、产生了什么设计改动、改动后的结果如何。这既是研究价值的证据，也能帮助研究员了解哪些形式和时机更有效。

**本章练习**：把一份已完成的研究报告改写成一页摘要，并在下一次产品评审中使用；之后记录哪些洞察被讨论、哪些被忽略，分析原因。

## 第三篇：专项与进阶

<a id="ch10"></a>

### 10 研究伦理、隐私与参与者保护

#### 10.1 知情同意

每次研究都应获得参与者的知情同意，包括本组织的员工。参与者需要理解：谁在做研究、研究目的、会收集哪些数据、数据如何使用与保存多久、参与是自愿的并可以随时退出。同意的证据可以是签署的表格，也可以是远程研究中对同意内容的确认记录。[B13](#ref-b13)

#### 10.2 个人信息与录音录像

- 只收集研究所必需的个人信息，尽早把参与者信息替换为编号。
- 录音录像需要单独说明并获得同意，说明谁能观看、保存多久。
- 研究材料存放在有访问控制的位置，按约定期限删除。
- 不把含有个人信息的录音或记录上传到未经评估的外部工具，包括 AI 转写与总结服务。

中国《个人信息保护法》规定，不满十四周岁未成年人的个人信息属于敏感个人信息，处理时应取得其父母或其他监护人的同意。[B14](#ref-b14) 面向其他地区参与者的研究，还要遵守当地的规定。

#### 10.3 避免伤害

研究可能触及参与者的痛苦经历，例如求职失败、经济困难或健康问题。允许参与者跳过任何问题；发现参与者不适时暂停；不在研究中诱导参与者透露与研究无关的隐私。对弱势人群的研究需要更严格的审查，学术研究通常还需要伦理委员会批准。

#### 10.4 行业准则

市场、民意与社会研究领域有成熟的自律准则。国际商会与 ESOMAR 联合发布的国际准则在 2025 年修订，覆盖数据收集、参与者权利与研究结论的可信度，并关注 AI、合成数据等新问题。[B15](#ref-b15) 即使团队不属于这一行业，也可以把它作为研究伦理的参照。

**本章验收**：为一项涉及录屏的远程研究编写参与者信息说明和同意表，并说明数据的存放位置、访问权限和删除时间。

<a id="ch11"></a>

### 11 研究运营与知识管理

#### 11.1 研究运营的内容

研究运营（ResearchOps）负责让研究可以稳定、高效、合规地进行，包括：参与者招募与管理、报酬发放、同意与数据管理、工具与模板、研究排期、知识库和培训。研究量增长后，没有运营支持，研究员会把大量时间花在行政事务上。

#### 11.2 研究知识库

把研究发现拆成可检索的单元（观察、洞察、证据），用标签关联到产品领域、用户群和时间。知识库的难点不在工具，而在维护：

- 每条发现标明来源、日期和适用范围。
- 定期审查过时的结论，标注“可能已不适用”。
- 控制访问权限，原始数据与综合结论分级管理。
- 在开始新研究前先查询知识库，避免重复研究。

#### 11.3 研究民主化的护栏

当设计师、产品经理也开展研究时，研究员的角色转向赋能与把关：提供模板和培训，审核研究计划与讨论指南，对高风险研究（涉及敏感人群、重大决策）保持主导。明确哪些研究可以自主开展，哪些需要研究员参与。

**本章练习**：把团队过去一年的研究整理成知识库条目，统计有多少发现被重复研究过，并设计一个“开展新研究前先检索”的流程。

<a id="ch12"></a>

### 12 特殊情境的研究：B 端、无障碍、跨文化与 AI

#### 12.1 B 端与专业用户

企业产品的使用者往往是专业人员，时间宝贵，工作流程复杂，并受公司规定约束。研究时需要通过客户成功或销售团队协调，遵守客户的保密要求；更多使用情境调查与工作流程分析；区分购买者、管理员和使用者的不同需求。

#### 12.2 与残障用户一起研究

邀请使用屏幕阅读器、放大工具、语音输入、键盘操作的用户参与研究，能发现自动检查工具发现不了的问题。准备工作包括：确认参与者使用的辅助技术，确保测试材料和会议工具本身可访问，安排更充足的时间，并尊重参与者的专业经验（见[《无障碍专家》](09-无障碍专家.md)）。

#### 12.3 跨文化与国际化研究

语言、礼貌习惯和对权威的态度会影响参与者的表达方式。跨地区研究最好由熟悉当地文化的研究员主持或协助，访谈指南需要本地化而不只是翻译。不要把一个地区的结论直接推广到其他地区。

#### 12.4 AI 产品的研究

AI 产品带来新的研究问题：用户怎样理解系统的能力和局限、何时过度信任或完全不信任、怎样发现和纠正错误、对生成内容的归属与隐私有什么顾虑。研究时可以用“人工模拟”原型提前测试交互方式；测试中要刻意加入错误或不确定的结果，观察用户能否察觉。微软的 HAX 工具包整理了人与 AI 交互的设计指南和研究材料，可作为研究问题的检查清单。[B16](#ref-b16)

#### 12.5 AI 作为研究工具

AI 可以协助转写、初步编码、整理笔记和起草讨论指南，但需要注意：

- 自动转写和总结可能遗漏或曲解原意，关键结论必须回到原始记录核对。
- 上传录音和记录前，确认工具的数据处理方式符合同意条款和隐私要求。
- 由模型模拟的“合成用户”不能代替真实参与者。它可以帮助准备问题，但不能作为关于真实用户的证据。

**本章练习**：为 AI 简历分析设计一次可用性测试，在原型中故意放入一条明显错误的建议，记录有多少参与者察觉，以及察觉后怎样处理。

<a id="ch13"></a>

### 13 混合方法与行为数据

#### 13.1 定性与定量互相解释

行为数据显示“在哪里发生了什么”，定性研究解释“为什么”。常见的组合方式：

- **先定量后定性**：数据显示 40% 的用户在上传后离开，再通过访谈和测试了解原因。
- **先定性后定量**：访谈发现几类不同的使用动机，再用问卷估计各类人群的比例。
- **并行三角验证**：同一个问题用多种方法从不同角度回答，结论一致时可信度更高。

#### 13.2 与实验配合

研究可以帮助确定实验要验证的假设和要观察的指标；实验结束后，研究可以解释为什么某个版本表现更好或更差。不要用研究结论代替实验，也不要在实验结果出乎意料时忽视原因研究。

#### 13.3 解读行为数据的注意事项

行为数据有口径与采集问题，也只记录产品内发生的事情。用户在产品外完成的部分、离开的真实原因、没有使用产品的人群，都不在数据中。与数据分析师一起确认指标定义，再做解释。

**本章验收**：选一个产品指标的异常变化，结合数据分析和至少 5 次用户访谈，写出对变化原因的解释，并标明哪些部分有证据、哪些仍是推测。

## 第四篇：协作、实战与成长

<a id="ch14"></a>

### 14 与开发者的协作接口

#### 14.1 研究员需要开发者提供的支持

| 支持 | 用途 | 说明 |
| --- | --- | --- |
| 可测试的原型或测试环境 | 可用性测试 | 准备真实感的测试数据，避免测试中断 |
| 行为数据与日志 | 选择研究对象，验证研究发现 | 遵守数据访问与隐私规定 |
| 技术约束说明 | 判断建议的可行性 | 帮助研究员提出现实的建议 |
| 产品内招募入口 | 接触真实用户 | 控制频率，避免打扰 |
| 埋点补充 | 验证定性发现 | 与数据分析师共同设计 |

#### 14.2 开发者能从研究中获得的东西

- 旁听访谈和测试，直接理解用户遇到的问题，减少返工。
- 看到异常情况的真实发生方式，例如用户上传了什么奇怪的文件、在什么网络环境下使用。
- 理解优先级背后的原因，从而在实现中做出更合适的细节判断。

建议每位开发者每季度至少旁听一次研究。观察时只记录，不当场解释产品；结束后在回顾会上分享看到的现象。

<a id="ch15"></a>

### 15 开发者怎样做轻量研究

#### 15.1 适合开发者的轻量方法

在没有专职研究员的团队，开发者可以承担一部分研究，前提是对方法保持克制和诚实：

- **5 次访谈**：围绕一个具体问题，询问最近一次真实经历，不推销产品。
- **走廊测试**：找几位与目标用户相近的人完成一个任务，观察其卡住的位置。
- **支持记录分析**：每周阅读工单和用户反馈，按主题计数。
- **使用录屏与错误日志**：在获得同意、做好脱敏的前提下，观察真实使用中的问题。

#### 15.2 开发者做研究的常见陷阱

- 一边测试一边解释产品，或在用户困惑时立刻教用户怎么用。
- 询问“你会不会用这个功能”，然后把礼貌性的“会”当作需求证据。
- 只找朋友和同事，样本与真实用户差别很大。
- 只记得支持自己方案的反馈。

#### 15.3 外包项目中的研究

客户通常不会为研究单独付费，但可以在需求阶段争取：观察一次客户员工的实际工作、访谈两三位最终使用者、用原型做一次走查。这些活动成本低，能显著减少后期返工和验收争议。业务流程的梳理方法见[《业务分析师》](03-业务分析师.md)。

### 16 贯穿实战：求职平台的简历分析研究

本章展示一项完整研究的过程。案例中的数字都是示意。

#### 16.1 决策与研究问题

- **决策问题**：简历分析第一版先提供哪类建议？建议应该怎样呈现？
- **研究问题**：学生在投递前对简历最不确定的是什么？他们目前怎样获得和判断修改意见？什么样的建议能让他们愿意修改、知道怎么改？

#### 16.2 方法与样本

| 阶段 | 方法 | 样本 | 目的 |
| --- | --- | --- | --- |
| 第 1 周 | 半结构化访谈 | 10 名近三个月投递过实习的学生，覆盖不同专业与年级 | 了解现有做法与困难 |
| 第 2 周 | 支持工单与行为数据分析 | 近三个月相关工单与上传流程数据 | 估计问题的普遍程度 |
| 第 3 周 | 原型可用性测试 | 6 名学生，两轮迭代 | 比较建议的呈现方式 |

#### 16.3 关键发现示例

1. 学生最不确定的是“这段经历值不值得写、怎么写才算具体”，而不是格式问题（10 人中 8 人提及）。
2. 学生会把简历发给多人征求意见，但意见经常矛盾，最终依靠直觉决定（10 人中 7 人）。
3. 在原型测试中，“问题＋原因＋修改示例”的呈现方式比只列出问题更容易被理解和采纳（6 人中 5 人能据此独立修改）。
4. 当建议看起来像通用模板时，参与者明显降低信任；引用简历原文的建议更受信任。

#### 16.4 对决策的含义

- 第一版优先做“经历描述”的建议，格式检查作为辅助。
- 每条建议引用简历中的原文，并给出修改示例。
- 支持修改前后对比，帮助学生判断修改是否有效。
- 在界面上说明建议的依据和局限，避免学生把建议当作唯一标准。

#### 16.5 跟踪

上线后与数据分析师一起观察“建议采纳率”和“修改后重新分析率”，两个月后再做 5 次回访，检查第一版是否解决了研究中发现的问题。

#### 17.5 检查清单

研究前：

- [ ] 研究问题来自明确的决策，并确认了决策时间。
- [ ] 方法能够回答研究问题，局限已写明。
- [ ] 筛选问卷基于行为与经历，不泄露研究意图。
- [ ] 同意材料、数据存放与删除计划已准备。

研究中：

- [ ] 讨论指南经过试访，问题开放且不诱导。
- [ ] 记录区分原话、观察与解释。
- [ ] 团队成员有机会旁听。

研究后：

- [ ] 每条结论都能追溯到原始证据，标明证据强度。
- [ ] 洞察与建议分开表达。
- [ ] 结论在决策前送达，并记录后续影响。
- [ ] 原始数据按约定期限保存或删除。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 用户研究就是问用户想要什么 | 研究关注用户的实际经历与行为，方案由团队设计并验证 |
| 5 个用户就够了 | 这一结论适用于迭代的定性可用性测试，不适用于定量估计或差异很大的人群 |
| 样本越大越可信 | 代表性与方法同样重要，大样本也可能有系统性偏差 |
| 参与者说喜欢就说明方案好 | 喜好与能否完成任务、是否会持续使用不同 |
| 研究报告越详细越专业 | 研究价值取决于能否在决策前提供可信、可用的证据 |
| 人物角色是固定的用户分类 | 人物角色是基于研究的综合模型，需要随新证据更新 |
| 定性研究不严谨 | 定性研究有系统的方法与质量标准，回答的是不同类型的问题 |
| 数据能说明一切 | 行为数据说明发生了什么，原因往往需要定性研究解释 |
| AI 总结可以代替分析 | AI 可以辅助整理，结论必须回到原始数据核对 |
| 合成用户可以代替真实用户 | 模拟回答不是关于真实用户的证据 |

### C.2 内容边界

本手册覆盖产品与服务设计中的用户研究，不展开学术研究中的完整统计方法、心理测量理论或特定行业的研究法规。涉及未成年人、医疗健康、金融等敏感领域的研究，需要遵守相应的伦理审查与法律要求，具体义务由相应负责人确认。

相邻角色的展开见本系列其他各册，总览见[《职业角色全景》](README.md)。
