# 内容设计师／UX 文案进阶全景手册

> 从写清楚一个按钮和一条错误提示，到为产品建立统一的语言与内容体系，再到让内容在多语言、多渠道和 AI 生成中保持清楚可信。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：希望把界面文字写清楚的开发者和设计师、准备转向内容设计或 UX 文案的编辑与写作者，以及希望系统提升的在职内容设计师。

内容设计师要回答的核心问题是：用户在这个时刻需要知道什么，用什么形式、什么词语告诉他们最清楚。界面上的文字往往被当作“最后填进去的东西”，但用户正是靠文字理解按钮会做什么、出了什么错、下一步该做什么。一个含糊的按钮名称、一条只写“操作失败”的提示，都可能让精心设计的流程失效。

英国政府数字服务把内容设计描述为一种以用户需要和证据为出发点、在用户需要的时间以用户期待的方式提供内容的工作方法。[B01](#ref-b01) 它与“写得漂亮”的文案不同：内容设计先判断是否需要这段内容、以什么形式呈现，再决定怎样写；有时最好的内容设计是删掉一段说明，改进界面本身。

本手册先建立角色坐标，然后依次讲解从用户需要出发设计内容、通俗清楚的表达、界面文案、错误信息、语气与风格规范、术语与内容模型、内容测试；随后进入通知与多渠道内容、帮助与引导、本地化、AI 时代的内容设计、内容治理；最后说明内容设计师与开发者怎样协作，以及开发者怎样写好界面文字。

主线是：**理解用户需要与情境 → 决定是否需要内容、以什么形式呈现 → 用清楚的语言写作 → 保持术语、语气与风格一致 → 测试内容是否被理解 → 管理内容的整个生命周期。**

不同组织中，这一职责可能由内容设计师、UX 文案、内容策略师、产品经理或设计师承担，营销文案和技术文档则通常由其他角色负责。本手册描述产品与服务中的内容设计；D1—D6 分级是学习组织方式，不对应任何职级体系。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 内容设计师负责什么

#### 01.1 核心问题：让用户理解并行动

内容设计关注的是用户理解与行动，而不是文字本身是否优美。英国政府数字与数据能力框架把内容设计师描述为让信息更容易被人理解和使用的角色，工作范围可以是单条内容，也可以是一项服务的完整旅程，并且需要从发现阶段开始与用户研究员、服务设计师和交互设计师紧密合作。[B02](#ref-b02)

内容设计的成果常常不显眼：一个用户不再犹豫的按钮、一条让人自己解决问题的错误提示、一封减少了大量客服咨询的通知。衡量内容设计的，是用户是否理解、是否完成任务、是否少犯错。

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 内容清单与审计 | 了解现有内容的数量、质量与问题 | 覆盖所有触点，标明负责人与状态 |
| 语气与风格规范 | 统一产品的语言 | 规则具体，有正反示例 |
| 术语表 | 保持概念命名一致 | 定义清楚，与产品、代码、客服一致 |
| 界面文案 | 引导用户完成任务 | 清楚、简短、一致，经过测试 |
| 错误信息与提示 | 帮助用户恢复 | 说明发生了什么、怎样解决 |
| 通知与消息 | 在合适的时间告知用户 | 及时、相关、可行动、不过度打扰 |
| 帮助与引导内容 | 解答问题、支持学习 | 能被找到，与界面同步更新 |
| 内容模型 | 结构化管理可复用的内容 | 字段清楚，支持多渠道与本地化 |

#### 01.3 职责边界与相邻角色

| 事项 | 内容设计师的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 内容需要与结构 | 主导 | 用户研究员、交互设计师 | 先判断用户需要什么信息 |
| 界面文案与提示 | 主导 | 交互设计师、产品经理 | 文字与交互一起设计 |
| 流程与交互 | 参与 | 交互设计师主导 | 很多文案问题其实是流程问题 |
| 品牌语言 | 共同负责 | 品牌与市场团队 | 产品语言与品牌语言协调 |
| 营销文案 | 协作 | 市场团队主导 | 目标和写法不同，但术语要一致 |
| 技术文档与接口文档 | 协作 | 技术写作者主导 | 见[《技术写作者与文档工程师》](24-技术写作者与文档工程师.md) |
| 法律与合规文本 | 参与 | 法务主导 | 内容设计师帮助提高可读性，法律含义由法务确认 |
| 翻译与本地化 | 共同负责 | 本地化团队 | 源文本质量决定翻译质量 |

#### 01.4 不同组织中的形态

- **内容设计师**：参与从研究到上线的全过程，决定内容的需要、结构与表达。
- **UX 文案**：专注于界面文字，与交互设计师紧密配合。
- **内容策略师**：负责内容的规划、治理与跨渠道一致性。
- **兼任者**：在没有专职岗位的团队，由设计师、产品经理或开发者兼任。

**本章练习**：截取一个你常用产品的 10 条界面文字（按钮、提示、错误信息），逐条判断：用户能否据此知道发生了什么、下一步做什么？改写其中最差的 3 条。

<a id="ch02"></a>

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **用户需要与内容规划**：判断用户在什么情境下需要什么信息。
2. **清楚的语言**：通俗、准确、简洁的表达。
3. **界面文案**：按钮、标签、提示、空状态、确认信息。
4. **错误与恢复**：帮助用户理解问题并解决。
5. **语气与风格**：建立并维护统一的语言规范。
6. **术语与内容模型**：命名一致，内容结构化、可复用。
7. **内容测试与度量**：用证据检验内容是否被理解。
8. **多渠道内容**：通知、邮件、短信、帮助中心。
9. **本地化**：写便于翻译的源文本，支持多语言。
10. **内容治理**：负责人、审核、更新与下线。

#### 02.2 六级纵向深度

| 深度 | 内容设计师的能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 按规范修改文字，发现明显的歧义与错误 | 修改记录 |
| D2 独立完成 | 独立完成一个功能的全部内容，并经过测试 | 文案方案、测试记录 |
| D3 负责结果 | 负责一个产品的语言一致性与内容质量 | 风格规范、术语表、内容审计 |
| D4 系统与跨团队 | 协调多产品、多渠道、多语言的内容 | 跨产品术语、本地化流程 |
| D5 方法与机制 | 建立内容设计流程、审核与治理机制 | 内容治理流程、工具、培训 |
| D6 创新与影响 | 推动内容方法或语言规范在行业中的改进 | 公开规范、方法论、行业采用 |

#### 02.3 成长中的常见偏差

- 只修改措辞，不质疑内容是否必要、放在哪里、以什么形式出现。
- 追求文字有趣或有个性，牺牲了清楚。
- 同一个概念在不同地方用不同的词。
- 只写正常情况的文字，错误与边界情况由开发者临时填写。
- 写完不测试，认为“我觉得很清楚”就足够。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 从用户需要出发设计内容

#### 03.1 先问“用户需要什么”，再问“怎么写”

写任何内容之前，先回答：

- 用户是谁？在什么情境下看到这段内容？带着什么问题？
- 用户看完需要知道什么、能做什么？
- 用户已经知道什么？哪些信息是多余的？
- 这段内容是必需的吗？能否通过改进界面让它变得不必要？

英国政府服务手册在关于界面写作的指南中指出：如果需要解释界面怎样使用，说明界面本身出了问题，应当修正界面，而不是增加说明。[B03](#ref-b03)

#### 03.2 内容的形式

同样的信息可以用不同形式呈现：按钮文字、行内提示、表格、步骤列表、图示、视频、帮助文章。选择形式时考虑：用户是快速扫视还是仔细阅读？需要比较还是需要按顺序操作？在手机还是电脑上？

#### 03.3 内容的位置与时机

信息应在用户需要的时刻、在用户正在看的地方出现：输入格式的要求放在输入框旁边，而不是页面顶部；费用说明放在提交前，而不是提交后。过早出现的信息容易被忽略，过晚出现的信息可能已经来不及。

**本章练习**：选一个包含大段说明文字的页面，列出用户在这个页面需要知道的信息，删除不必要的内容，把必要信息移到用户需要的位置，比较修改前后的字数与任务完成情况。

<a id="ch04"></a>

### 04 清楚的语言

#### 04.1 通俗语言

国际标准 ISO 24495-1 规定了通俗语言写作的原则：内容与读者相关、读者能找到所需信息、能理解、能使用。[B04](#ref-b04) 通俗语言不是降低水平，而是减少读者理解所需的努力；专业读者同样受益于清楚的表达。

#### 04.2 写作要点

- **重要的先说**：先写结论和用户需要做的事，再写原因和细节。
- **一句话一个意思**：长句拆短，减少从句和嵌套的定语。
- **用用户熟悉的词**：避免内部术语、技术名称和缩写；必须使用时加以解释。
- **具体而不是抽象**：“3 个工作日内”比“尽快”清楚。
- **用主动语态说明谁做什么**：“我们会在 24 小时内回复”比“回复将在 24 小时内进行”清楚。
- **删除不必要的词**：“进行……的操作”“对……进行处理”通常可以简化为一个动词。

#### 04.3 中文写作的常见问题

| 问题 | 示例 | 改进 |
| --- | --- | --- |
| 冗长的动词结构 | 请对简历进行上传操作 | 请上传简历 |
| 过长的定语 | 您所上传的用于本次岗位申请的简历文件 | 您为这个岗位上传的简历 |
| 滥用被动 | 您的申请已被系统成功提交 | 申请已提交 |
| 空泛的形容 | 系统将为您提供优质的分析服务 | 分析会指出简历中需要修改的段落，并给出修改示例 |
| 术语未解释 | 请检查 PDF 是否为扫描件 | 请上传可以选中文字的 PDF；扫描或拍照生成的 PDF 无法识别 |

中文排版规范（中英文之间的空格、全角标点、数字的写法等）可以参考社区整理的《中文文案排版指北》。[B05](#ref-b05)

**本章验收**：把一段 300 字以上的说明文字改写为通俗语言，请 3 位目标用户阅读后用自己的话复述，检查理解是否准确。

<a id="ch05"></a>

### 05 界面文案：按钮、标签与提示

#### 05.1 按钮与操作

- 按钮文字说明点击后会发生什么，通常以动词开头：“上传简历”“开始分析”“删除这份简历”。
- 避免含糊的“确定”“提交”“是”，尤其在不可撤销的操作中。
- 同一个操作在各处使用同一个词：不要这里叫“保存”，那里叫“存储”。
- 确认对话框中的按钮重复操作本身：“删除简历”和“保留”，比“确定”和“取消”更不容易误操作。

#### 05.2 表单标签与说明

- 每个输入框都有清楚、可见的标签。占位文字在输入后会消失、对比度通常较低，不能代替标签。[B06](#ref-b06)
- 格式要求、长度限制等说明放在输入框旁边，在用户输入前就能看到。
- 可选项标注“选填”，或只标注必填项，在整个产品中保持一致。

#### 05.3 空状态、成功与确认

- **空状态**：说明这里会出现什么、为什么现在是空的、用户可以做什么。
- **成功信息**：确认发生了什么，并告诉用户下一步，例如“简历已上传。分析大约需要 1 分钟，完成后我们会通知你。”
- **确认信息**：只在操作有重要或不可逆后果时使用，并写清后果。

#### 05.4 长度与布局

界面空间有限，文字长度直接影响布局。与交互和视觉设计师一起确定每个位置的长度上限，并考虑翻译后的长度变化（见 12 章）。

**本章练习**：为一个表单写出全部标签、说明、按钮、成功与错误信息，在设计稿中检查长度是否合适，并请他人只看文字说出每一步的作用。

<a id="ch06"></a>

### 06 错误信息与问题恢复

#### 06.1 好的错误信息

好的错误信息清楚地表明出了问题，用人能理解的语言说明问题是什么，不责备用户，并给出解决办法。[B07](#ref-b07)

| 要素 | 说明 | 示例 |
| --- | --- | --- |
| 发生了什么 | 具体说明问题 | 无法读取这份简历中的文字 |
| 为什么 | 用户能理解的原因 | 文件可能是扫描件或图片 |
| 怎么办 | 可执行的下一步 | 请上传可以选中文字的 PDF 或 Word 文件，或者直接粘贴简历内容 |
| 保留了什么 | 减少用户的损失 | 你填写的目标岗位已保留 |

#### 06.2 常见问题

- “操作失败，请稍后重试”：没有说明原因，也不知道重试是否有用。
- 显示错误代码或技术信息：“错误 500”“NullPointerException”。技术信息可以记录在日志中，必要时提供一个可以告诉客服的编号。
- 责备用户：“您输入的内容无效”。改为说明需要什么：“请输入 11 位手机号码”。
- 错误信息与出错的位置分开：表单错误应出现在对应字段旁，并在页面顶部汇总。

#### 06.3 从源头减少错误

与交互设计师和开发者一起，尽量在用户出错前提供帮助：清楚的格式要求、合理的默认值、实时校验、接受多种合理的输入格式（例如带空格或不带空格的手机号码）。

**本章验收**：列出一个功能所有可能的错误情况（至少 10 种），为每种写出错误信息，并请开发者确认每种错误在系统中确实可以被区分。

<a id="ch07"></a>

### 07 语气、风格与语言规范

#### 07.1 语气与风格

- **语气**：产品说话的“个性”，相对稳定，例如“清楚、友好、可靠”。
- **口吻**：随情境调整的表达方式。成功时可以轻松，出错时要冷静、直接，涉及金钱和隐私时要严谨。

#### 07.2 风格规范的内容

| 部分 | 内容 |
| --- | --- |
| 语气原则 | 产品的语言个性，以及在不同情境下的调整 |
| 称呼 | “你”还是“您”，怎样称呼用户和产品自身 |
| 用词 | 推荐用词、避免用词、术语表链接 |
| 语法与标点 | 中英文混排、标点、数字、日期、单位的写法 |
| 界面组件文案 | 按钮、标签、提示、错误、空状态的写法规则 |
| 包容性语言 | 避免性别、年龄、地区、能力等方面的刻板印象 |
| 示例 | 每条规则的正反示例 |

成熟的公开规范可以作为参考，例如英国政府的写作风格指南、微软写作风格指南和 Mailchimp 内容风格指南。[B08](#ref-b08) [B09](#ref-b09) 参考时注意语言差异：英文规范中的许多规则不能直接用于中文。

#### 07.3 让规范被使用

规范只有被使用才有价值：放在团队容易找到的地方，提供可以直接复制的示例，在设计评审中引用，把可以自动检查的规则（例如标点、空格、禁用词）交给工具检查。

**本章练习**：为一个产品写一页风格规范，包含语气原则、10 条用词规则和 5 条标点规则，每条附正反示例。

<a id="ch08"></a>

### 08 术语与内容模型

#### 08.1 术语管理

同一个概念在产品、客服、帮助中心和代码中使用不同的名字，会让用户困惑、让团队误解。术语表记录每个概念的标准名称、定义、允许的同义词、禁止使用的名称和使用示例。新功能命名时先查术语表，确定新名称后同步更新。

#### 08.2 内容模型

当同类内容大量出现（例如岗位说明、帮助文章、通知模板），可以用内容模型把它结构化：定义每类内容包含哪些字段、哪些是必填、字段之间的关系。结构化内容便于在网页、应用、邮件中复用，也便于翻译和检索。

```text
内容类型：简历建议
字段：
  建议编号（系统生成）
  针对的简历段落（引用原文）
  问题（不超过 30 字）
  原因（不超过 60 字）
  修改示例（不超过 120 字）
  严重程度（重要／建议）
  依据说明（可选）
```

#### 08.3 动态内容与变量

含变量的文字需要考虑所有取值情况：数量为 0、1 和多个时的表达；名称很长或为空时的显示。不要用字符串拼接组合句子，因为语序在不同语言中不同（见 12 章）。

**本章练习**：为一个产品整理 20 个核心术语，找出至少 3 个不一致之处并统一；为一类重复出现的内容设计内容模型。

<a id="ch09"></a>

### 09 内容测试与度量

#### 09.1 测试内容的方法

| 方法 | 做法 | 能发现的问题 |
| --- | --- | --- |
| 理解测试 | 请用户阅读后用自己的话复述 | 误解与歧义 |
| 标记测试 | 请用户用两种颜色标出让人有信心和让人困惑的部分 | 令人困惑或不信任的措辞 |
| 任务测试 | 在可用性测试中观察用户是否根据文字正确操作 | 文字与行为之间的差距 |
| 完形填空测试 | 删去部分词语，请用户补全 | 文本的整体可读性 |
| A/B 测试 | 比较不同文案对行为的影响 | 在有足够流量时比较效果 |

#### 09.2 内容相关的度量

- 任务完成率与错误率（尤其是与文案相关的错误）。
- 与某段内容相关的客服咨询数量。
- 帮助文章的搜索、访问与“是否有帮助”反馈。
- 通知的打开、行动与退订情况。

度量的变化需要结合定性研究解释，避免把所有变化归因于文案。

**本章验收**：对一个功能的关键文案做 5 人理解测试，记录误解的位置并修改，再测一轮验证改进。

## 第三篇：专项与进阶

<a id="ch10"></a>

### 10 通知、邮件与多渠道内容

#### 10.1 通知的内容设计

每条通知都在争夺用户的注意力。发送前回答：用户需要现在知道吗？需要做什么吗？通过什么渠道最合适？好的通知：

- 标题说明发生了什么，而不是“您有一条新消息”。
- 正文说明用户需要做什么、截止时间是什么。
- 提供直接到达相关页面的入口。
- 敏感信息不放在通知正文中，而是通过登录后的页面查看。

#### 10.2 渠道的差异

| 渠道 | 特点 | 内容要点 |
| --- | --- | --- |
| 站内消息 | 用户在产品中时看到 | 可以包含较多细节与操作 |
| 推送 | 可能打断用户，篇幅短 | 只发送重要且及时的信息 |
| 邮件 | 篇幅可以较长，容易被忽略 | 主题行决定是否被打开 |
| 短信 | 篇幅短，成本高，打扰性强 | 只用于重要且紧急的信息 |

营销类消息通常需要用户同意并提供退订方式，具体要求由法务确认。通知的工程实现见[《后端进阶全景手册》第 28 章](../技术方向/后端进阶全景手册.md#ch28)。

**本章练习**：为一个业务事件设计站内消息、推送和邮件三种版本，说明各自的触发条件与内容差异。

<a id="ch11"></a>

### 11 帮助内容与引导

#### 11.1 帮助内容的层次

- **界面内的提示**：最靠近问题，解决“这是什么、怎么填”。
- **引导**：帮助新用户完成第一次关键任务，可以跳过和重新查看。
- **帮助中心文章**：解决较复杂的问题，按用户的问题组织，而不是按产品菜单组织。
- **客服**：内容无法解决时的兜底。

#### 11.2 帮助文章的写法

标题用用户会搜索的问题（“简历上传后显示无法识别怎么办”），开头直接给出答案，再分步骤说明；配合截图时注意界面更新后同步修改。技术类文档的方法见[《技术写作者与文档工程师》](24-技术写作者与文档工程师.md)。

**本章练习**：整理一个月的客服问题，找出最常见的 5 类，为其中可以通过内容解决的问题写帮助文章或修改界面文案，一个月后比较咨询数量。

<a id="ch12"></a>

### 12 本地化与国际化内容

#### 12.1 写便于翻译的源文本

- 句子清楚完整，避免俚语、双关和文化特定的比喻。
- 不用字符串拼接组合句子，因为不同语言的语序不同。
- 为译者提供上下文：文字出现在哪里、长度限制、变量的含义。
- 预留空间：翻译后的文字可能比原文长很多。

#### 12.2 复数、性别与变量

不同语言的复数规则差异很大：中文通常不区分单复数，英语区分单数与复数，有些语言有更多形式。Unicode 的 ICU 消息格式提供了处理复数、选择和变量的标准写法，许多国际化库都支持它。[B10](#ref-b10)

```text
{count, plural,
  =0 {还没有分析记录}
  other {共 # 条分析记录}
}
```

#### 12.3 本地化不只是翻译

日期、时间、数字、货币、地址和姓名的格式随地区变化；图片、颜色和示例也可能需要调整。本地化后需要由熟悉当地语言的人员在真实界面中检查。

**本章练习**：检查一个功能的所有文字，找出拼接字符串、硬编码的格式和缺少上下文说明的文字，改为便于翻译的形式。

<a id="ch13"></a>

### 13 AI 时代的内容设计

#### 13.1 AI 生成的内容

当产品使用 AI 生成文字（例如简历建议、客服回复、摘要），内容设计师的工作从“写每一句话”扩展到“为生成内容制定规范并检验”：

- **输出规范**：生成内容的语气、长度、结构、用词、禁止事项。
- **提示词与系统说明**：它们本身就是内容，需要与风格规范一致，并像其他内容一样版本化、评审和测试。
- **评价标准**：与领域专家一起定义什么样的输出是清楚、准确、有帮助的（见[《领域专家》第 09 章](04-领域专家.md#ch09)）。
- **抽检与反馈**：定期抽查真实输出，发现语气偏离、事实错误和不当表达。

#### 13.2 AI 功能的界面文字

- **设定预期**：说明 AI 能做什么、不能做什么，以及结果可能出错。
- **表达不确定性**：用“可能”“建议”等词语准确反映结果的性质，避免把建议写成定论。
- **避免拟人化误导**：不要让用户误以为在与真人交流。
- **说明来源与依据**：引用原文或资料来源，便于用户判断。
- **提供纠正入口**：“这条建议不适用”“重新生成”“反馈问题”。

#### 13.3 标识与透明

中国《人工智能生成合成内容标识办法》自 2025 年 9 月 1 日起施行，对生成合成内容的显式与隐式标识提出要求。[B11](#ref-b11) 内容设计师需要与产品、法务一起确定标识的文字、位置和形式，使其清楚而不干扰使用。

**本章练习**：为 AI 简历建议制定输出规范（语气、结构、长度、禁止事项），抽查 30 条生成结果，统计不符合规范的比例并提出改进。

<a id="ch14"></a>

### 14 内容治理与生命周期

#### 14.1 内容的生命周期

内容和代码一样需要维护：创建、审核、发布、更新、下线。没有治理的内容会逐渐过时、重复、互相矛盾。每条重要内容应有负责人、审核人、上次更新时间和下次复查时间。

#### 14.2 内容审计

定期审计内容：列出所有内容，检查是否准确、是否仍然需要、是否与术语和风格一致、是否有人负责。审计的结果是删除、合并、更新或保留的决定。

#### 14.3 审核流程

根据风险确定审核方式：普通界面文字由内容设计师审核；涉及费用、隐私、法律后果的内容需要相应负责人确认；面向大量用户的通知在发送前预览和测试。

**本章练习**：审计一个产品的帮助中心，统计过时、重复和无人负责的文章数量，制定治理计划。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与开发者的协作接口

#### 15.1 内容设计师应提供给开发者的内容

| 内容 | 最低要求 | 常见缺失 |
| --- | --- | --- |
| 全部界面文字 | 包括所有状态与错误 | 只有正常状态的文字 |
| 变量与复数规则 | 说明变量含义与各种取值的写法 | 拼接字符串，0 和 1 的情况未处理 |
| 长度限制 | 每个位置的长度上限 | 文字过长导致布局问题 |
| 术语 | 与术语表一致 | 同一概念多种叫法 |
| 上下文说明 | 给译者和开发者的说明 | 译者不知道文字出现在哪里 |

#### 15.2 开发者应反馈给内容设计师的内容

系统中实际存在的错误类型（以便为每种错误写出具体信息）、文字在界面中的实际显示情况、动态内容的取值范围、无法实现的文字需求（例如需要系统无法获得的信息）。

#### 15.3 文字在代码中的管理

- 界面文字放在资源文件中，不写死在代码里，便于修改与翻译。
- 资源键名表达位置与用途，例如 `resume.upload.error.unreadable`，而不是 `error23`。
- 约定文字修改的流程：谁可以修改、谁审核、怎样同步到设计稿。
- 发布前进行文字走查，检查截断、拼接、缺失的翻译和占位符。

<a id="ch16"></a>

### 16 开发者怎样写好界面文字

#### 16.1 五个立刻可用的习惯

1. **按钮写动作**：“保存草稿”而不是“确定”。
2. **错误写解决办法**：说明问题和下一步，不显示技术错误信息。
3. **同一件事用同一个词**：建立一个简单的术语表。
4. **删掉一半的说明**：先问这段话是否必要。
5. **让别人读一遍**：找一位不了解项目的人复述文字的意思。

#### 16.2 技术背景的常见偏差

- 使用系统内部的名称（“任务”“作业”“实体”）代替用户熟悉的说法。
- 把异常信息直接显示给用户。
- 为了省事复用同一条错误信息处理多种不同的错误。
- 用字符串拼接组合句子，导致语法错误和翻译困难。

<a id="ch17"></a>

### 17 贯穿实战：简历分析的界面内容

本章展示一个功能的内容设计过程。文字均为示意。

#### 17.1 理解需要

研究发现，学生在上传简历时最担心两件事：隐私是否安全、分析结果是否可信；在查看结果时，最需要知道“哪里要改、为什么、怎么改”（见[《用户研究员》第 16 章](02-用户研究员.md#ch16)）。

#### 17.2 关键文字

| 位置 | 文字 | 说明 |
| --- | --- | --- |
| 上传页标题 | 上传简历，获取修改建议 | 说明能获得什么 |
| 上传说明 | 支持 PDF 和 Word 文件，不超过 10 MB。简历仅用于本次分析，你可以随时删除。 | 回应格式与隐私顾虑 |
| 主要按钮 | 开始分析 | 动词开头 |
| 分析中 | 正在分析，大约需要 1 分钟。你可以先离开，完成后我们会通知你。 | 设定预期，允许离开 |
| 解析失败 | 无法读取这份简历中的文字。文件可能是扫描件或图片。请上传可以选中文字的文件，或直接粘贴简历内容。本次不消耗分析次数。 | 问题、原因、办法、损失说明 |
| 额度不足 | 本月的免费分析次数已用完，下月 1 日恢复。 | 说明原因与恢复时间 |
| 结果页说明 | 以下建议由 AI 根据你的简历生成，仅供参考。你可以标记不适用的建议。 | 设定预期，提供控制 |
| 旧版本提示 | 你已修改简历，这些建议基于修改前的版本。重新分析 | 说明原因与行动 |

#### 17.3 AI 建议的输出规范

- 每条建议包含问题（30 字以内）、原因（60 字以内）、修改示例（120 字以内）。
- 引用简历原文，不编造经历。
- 使用“建议”“可以考虑”，不使用“必须”“错误”等绝对化的词。
- 不评价与岗位无关的个人信息，例如年龄、婚育状况、籍贯。

内容设计师与领域专家一起制定了评价标准，每次更新提示词后抽查 50 条输出。

#### 17.4 测试与改进

理解测试中，5 名学生有 3 人把“标记为不适用”理解为“删除这段经历”。修改为“这条建议不适用”并增加一行说明后，再次测试没有出现误解。上线一个月后，与“简历上传失败”相关的客服咨询明显减少。

#### 18.5 检查清单

- [ ] 每段内容都有明确的用户需要，不必要的内容已删除。
- [ ] 重要信息放在前面，一句话一个意思。
- [ ] 按钮说明操作结果，确认对话框的按钮重复操作本身。
- [ ] 每个输入框都有可见标签，说明放在输入框旁边。
- [ ] 每种错误都有具体的说明与解决办法，不显示技术信息。
- [ ] 术语与术语表一致，同一操作使用同一个词。
- [ ] 变量与复数情况都已处理，没有拼接字符串。
- [ ] 文字长度经过实际布局检查，并为翻译预留空间。
- [ ] 关键文字经过理解测试。
- [ ] AI 生成内容有输出规范、评价标准和标识。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 文案是最后填进去的 | 文字是交互的一部分，需要从设计开始一起考虑 |
| 文字越多越周到 | 不必要的内容会掩盖重要信息，删减常常比补充更有效 |
| 有趣的文案更好 | 清楚优先，个性要服务于理解 |
| 错误信息写“操作失败”就够了 | 需要说明问题、原因与解决办法 |
| 占位文字可以代替标签 | 占位文字会消失、对比度低，不能代替标签，相关要求见 WCAG 2.2 第 3.3 节。[B12](#ref-b12) |
| 翻译是本地化团队的事 | 源文本的写法决定了翻译的质量与成本 |
| AI 可以替代内容设计 | AI 生成内容同样需要规范、评价与抽检 |
| 风格规范写好就会被遵守 | 规范需要易于获取、有示例、并融入评审与工具 |

### C.2 内容边界

本手册覆盖产品与服务中的内容设计，不展开营销文案、品牌写作、新闻写作与技术文档的完整方法。法律、隐私与费用相关文字的法律含义由法务确认。

相邻角色的展开见本系列其他各册，总览见[《职业角色全景》](README.md)。
