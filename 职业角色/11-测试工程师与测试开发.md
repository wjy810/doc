# 测试工程师与测试开发进阶全景手册

> 从设计能让功能失败的测试，到为系统建立可信的质量证据，再到让整个团队以可验证的方式交付。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：希望提升测试能力的开发者、准备转向测试或测试开发（SDET）的工程师、需要自己保证质量的独立开发者与外包团队，以及希望系统提升的在职测试工程师。

测试工程师要回答的核心问题是：这个系统在哪些情况下会出错，出错的后果有多严重，以及我们有多少证据相信它可以发布。测试不是在开发结束后“点一遍”，也不只是找出缺陷的数量；它为团队和决策者提供关于质量与风险的信息。好的测试工程师会主动寻找让系统失败的方式：边界、并发、异常输入、中断、恢复、权限、真实的数据与环境。

测试开发工程师（SDET）在此基础上更多承担工程工作：设计可维护的自动化测试、建设测试框架与测试数据、把测试接入持续集成、提高测试的速度与稳定性。两种角色的核心都是相同的：用可靠的证据判断质量。

本手册先建立角色坐标，然后讲解质量风险与测试策略、测试设计技术、探索性测试、自动化与测试开发、非功能测试、缺陷管理与质量度量、发布质量；随后进入契约与集成测试、性质与模糊测试、生产环境的质量、AI 系统的测试、质量文化；最后说明测试与开发的协作，以及开发者怎样做好测试。测试在后端工程中的位置与验证层次，见[《后端进阶全景手册》第 13 章](../技术方向/后端进阶全景手册.md#ch13)。

主线是：**识别质量风险 → 制定测试策略 → 设计能发现问题的测试 → 探索未知的问题 → 自动化可重复的检查 → 管理缺陷并度量质量 → 支持发布决策 → 推动团队的质量文化。**

不同公司中，测试职责可能由测试工程师、质量保证工程师、测试开发工程师、质量工程师承担，也可能主要由开发者自己完成。本手册描述测试与质量的职责本身；D1—D6 分级是学习组织方式，不对应任何职级体系。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 测试工程师负责什么

#### 01.1 核心问题：提供关于质量与风险的证据

测试的目的包括：发现缺陷、评估质量、降低风险、验证需求是否被满足、为决策提供信息，以及建立对系统的信心。国际软件测试资格委员会（ISTQB）总结的测试原则中，第一条是“测试只能证明缺陷存在，不能证明缺陷不存在”。[B01](#ref-b01) 因此，测试工程师的职责不是保证“没有缺陷”，而是让团队清楚地知道：测了什么、发现了什么、还有哪些风险没有覆盖。

#### 01.2 测试的七条原则

| 原则 | 含义 | 实践中的提醒 |
| --- | --- | --- |
| 测试表明缺陷存在 | 测试无法证明没有缺陷 | 报告时说明未覆盖的范围 |
| 穷尽测试不可能 | 不可能测试所有输入组合 | 依据风险选择测试 |
| 尽早测试 | 越早发现问题，修复成本越低 | 在需求与设计阶段参与 |
| 缺陷集群 | 少数模块包含多数缺陷 | 关注历史缺陷多、变化频繁的区域 |
| 测试会失效 | 重复同样的测试，发现新问题的能力下降 | 定期更新和补充测试 |
| 测试依赖上下文 | 不同系统需要不同的测试方式 | 支付系统与内容网站的测试重点不同 |
| “没有缺陷”不等于有用 | 符合需求但不满足用户需要的系统仍然失败 | 关注真实使用场景 |

#### 01.3 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 测试策略 | 明确测什么、怎样测、测到什么程度 | 基于风险，说明取舍与未覆盖范围 |
| 测试用例与测试数据 | 系统地检验功能与边界 | 可追溯到需求与风险，覆盖异常 |
| 探索性测试记录 | 发现脚本化测试遗漏的问题 | 有明确的目标、时间与发现 |
| 自动化测试 | 快速、可重复地检验 | 稳定、快速、可维护，失败时能定位原因 |
| 缺陷报告 | 让问题被理解和修复 | 可复现、有证据、有影响说明 |
| 质量报告 | 支持发布决策 | 说明风险、覆盖与已知问题 |
| 测试基础设施 | 支持团队高效测试 | 环境稳定、数据可控、反馈快速 |

#### 01.4 职责边界与相邻角色

| 事项 | 测试工程师的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 需求的可测试性 | 参与评审 | 产品经理、业务分析师 | 在需求阶段发现模糊与遗漏 |
| 单元与组件测试 | 指导与评审 | 开发者主导 | 开发者对自己代码的测试负责 |
| 集成、系统与端到端测试 | 主导或共同负责 | 开发者 | |
| 测试自动化框架 | 主导（测试开发） | 开发者、平台工程师 | |
| 性能、安全、无障碍测试 | 共同负责 | 专项工程师 | 复杂专项由专业人员主导 |
| 发布决定 | 提供质量信息 | 产品经理、技术负责人 | 测试提供证据，决定由负责人做出 |
| 生产环境质量 | 共同负责 | SRE、客服 | |

“质量保证”与“测试”常被混用。测试是检验产品的活动；质量保证关注让团队以能产出高质量产品的方式工作，例如评审、规范、流程改进。现代团队中，质量是整个团队的责任，测试工程师是推动者和专家，而不是质量的唯一负责人。

**本章练习**：回顾你所在项目最近上线后发现的三个缺陷，分析它们本可以在哪个阶段、用什么测试发现，以及当时为什么没有发现。

<a id="ch02"></a>

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **风险分析与测试策略**：识别质量风险，制定测试的范围与重点。
2. **测试设计**：用系统的技术设计能发现问题的测试。
3. **探索性测试**：在执行中学习系统并发现未知问题。
4. **测试自动化**：设计可维护、稳定的自动化测试。
5. **测试基础设施**：环境、数据、工具与持续集成。
6. **非功能测试**：性能、安全、无障碍、兼容性与可靠性。
7. **缺陷与质量度量**：缺陷管理、根因分析与质量指标。
8. **发布与生产质量**：发布标准、生产验证与监控。
9. **领域与业务理解**：理解业务规则与用户的真实使用方式。
10. **质量文化与协作**：推动团队共同对质量负责。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 按用例执行测试，清楚地报告缺陷 | 测试执行记录、缺陷报告 |
| D2 独立完成 | 独立为一个功能设计测试并实现自动化 | 测试设计、自动化测试、测试报告 |
| D3 负责结果 | 对一个产品或系统的质量负责 | 测试策略、质量趋势、发布决策支持 |
| D4 系统与跨团队 | 负责多系统的集成质量与测试基础设施 | 契约测试体系、测试平台、跨团队策略 |
| D5 方法与机制 | 建立组织的质量体系、测试平台与方法 | 质量流程、平台、培训与度量 |
| D6 创新与影响 | 提出新的测试方法或工具并验证效果 | 开源工具、研究成果、行业采用 |

#### 02.3 成长中的常见偏差

- 只测正常路径，或只按需求文档逐条测试，不主动探索。
- 用测试用例数量或代码覆盖率衡量测试质量。
- 自动化一切，包括不稳定、维护成本高、价值低的测试。
- 容忍不稳定的测试，团队逐渐忽视测试失败。
- 把自己定位为“守门员”，在最后阶段阻止发布，而不是从一开始参与。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 质量风险与测试策略

#### 03.1 基于风险的测试

测试资源有限，需要投入到风险最高的地方。风险由两个因素决定：出问题的可能性（复杂度、变化频率、历史缺陷、新技术）与出问题的影响（用户数量、资金、数据、合规、声誉）。

| 风险项 | 可能性 | 影响 | 测试重点 |
| --- | --- | --- | --- |
| 额度在并发下被多扣或少扣 | 中 | 高 | 并发测试、对账测试 |
| 简历被其他用户看到 | 低 | 很高 | 权限测试、跨租户测试 |
| 扫描件解析失败 | 高 | 中 | 多种文件格式与异常文件 |
| 分析结果页布局在小屏幕错位 | 中 | 低 | 抽样兼容性检查 |

#### 03.2 测试层次与测试类型

- **测试层次**：单元或组件测试、集成测试、系统测试、验收测试。层次越低，测试越快、定位越准；层次越高，越接近真实使用。
- **测试类型**：功能测试、非功能测试（性能、安全、可用性、兼容性等）、回归测试、确认测试（验证缺陷已修复）。

测试金字塔建议大量快速的低层测试、适量的集成测试、少量的端到端测试，以获得快速可靠的反馈。[B02](#ref-b02) 它是一个思考框架，而不是固定的比例：对集成复杂、逻辑简单的系统，集成测试的比例可能更高。

#### 03.3 敏捷测试象限

Lisa Crispin 与 Janet Gregory 在《Agile Testing》中推广的测试象限，从“面向业务还是面向技术”“支持团队还是评价产品”两个维度，把测试分为四类：支持团队的技术测试（单元、组件）、支持团队的业务测试（功能示例、原型）、评价产品的业务测试（探索性测试、可用性测试、验收测试）、评价产品的技术测试（性能、安全等）。它提醒团队不要只做其中一两类测试。

#### 03.4 测试策略

```text
测试策略要点
范围与目标：
质量风险与优先级：
测试层次与类型的安排：
自动化范围与工具：
测试环境与测试数据：
非功能测试计划：
进入与退出标准：
未覆盖的范围与接受的风险：
角色与职责：
```

**本章验收**：为一个功能做风险分析，列出至少 8 个风险项及其可能性与影响，据此写出测试策略，并说明未覆盖的风险。

<a id="ch04"></a>

### 04 测试设计技术

#### 04.1 等价类划分与边界值分析

把输入划分为系统处理方式相同的类，每类选择代表值；再在类的边界处重点测试，因为缺陷常出现在边界。以“简历文件不超过 10 MB”为例：

| 类别 | 测试值 |
| --- | --- |
| 有效：正常大小 | 2 MB |
| 边界：最小 | 1 字节；空文件（0 字节）应作为无效情况单独测试 |
| 边界：上限附近 | 10 MB 减 1 字节、正好 10 MB、10 MB 加 1 字节 |
| 无效：过大 | 50 MB |

还要确认“10 MB”的定义（按 1000 还是 1024 换算），这本身就是需要澄清的需求问题。

#### 04.2 决策表

条件组合较多的规则，用决策表列出所有组合，每列设计一个测试。以“是否消耗分析额度”为例：

| 条件与结果 | 1 | 2 | 3 | 4 |
| --- | --- | --- | --- | --- |
| 文件解析成功 | 是 | 是 | 否 | 是 |
| 分析完成 | 是 | 否（系统错误） | — | 否（用户取消） |
| 消耗额度 | 是 | 否 | 否 | 按取消规则 |

决策表能暴露需求中未定义的组合，例如“用户在分析完成前一刻取消”应该怎样处理。

#### 04.3 状态转换测试

对有生命周期的对象，测试所有合法的状态转换，以及非法转换是否被拒绝。分析任务的状态模型见[《后端进阶全景手册》第 19 章](../技术方向/后端进阶全景手册.md#ch19)，例如：已取消的任务不能再变为成功；“结果未知”只能通过查询推进；重复的取消请求不产生副作用。

#### 04.4 组合测试

当参数很多（浏览器、操作系统、文件类型、语言）时，测试所有组合不现实。两两组合测试（覆盖任意两个参数的所有取值组合）能用少得多的测试发现大部分由参数交互引起的问题。

#### 04.5 基于经验的技术

错误推测（根据经验猜测容易出错的地方）、检查清单、历史缺陷模式。例如：空值、超长字符串、特殊字符、时区与夏令时、并发提交、重复点击、网络中断、权限变化。

**本章验收**：为一个功能分别用等价类与边界值、决策表、状态转换三种技术设计测试，并说明每种技术发现了哪些其他技术没有覆盖的情况。

<a id="ch05"></a>

### 05 探索性测试

#### 05.1 什么是探索性测试

探索性测试是同时进行学习、测试设计和测试执行的方法：测试者根据对系统的观察，不断调整下一步要测试的内容。它擅长发现脚本化测试没有想到的问题，尤其是复杂交互、边界情况和真实使用中的问题。探索性测试不是随意点击，而是有目标、有记录、有时间限制的系统工作。

#### 05.2 测试章程与时间盒

每次探索用一个章程说明目标，例如“用各种不寻常的文件探索简历上传，以发现解析与错误处理的问题”。设定时间盒（例如 60 到 90 分钟），记录做了什么、发现了什么、产生了哪些新的问题和想法。

#### 05.3 探索的启发

| 方向 | 示例 |
| --- | --- |
| 改变输入 | 空文件、超大文件、加密文件、扫描件、多语言、特殊字符 |
| 改变时序 | 快速重复点击、中途刷新、网络中断后恢复、两个标签页同时操作 |
| 改变用户 | 不同角色、权限被撤销、账号被禁用、新用户与老用户 |
| 改变环境 | 不同浏览器、小屏幕、慢网络、系统时间与时区 |
| 改变数据量 | 没有数据、一条数据、大量数据 |
| 违反假设 | 跳过步骤直接访问链接、修改请求参数、重放请求 |

**本章验收**：完成 3 次有章程的探索性测试，每次 60 分钟，整理发现的问题与新的测试想法，并把有价值的发现转化为自动化测试。

<a id="ch06"></a>

### 06 测试自动化与测试开发

#### 06.1 自动化什么

适合自动化的测试：需要频繁重复执行的回归测试、计算与规则逻辑、接口契约、需要大量数据组合的测试、发布前的冒烟测试。不适合或暂缓自动化的：频繁变化的界面细节、需要人判断的体验问题、只执行一次的测试。

#### 06.2 不同层次的自动化

| 层次 | 工具示例 | 特点 |
| --- | --- | --- |
| 单元测试 | JUnit、Vitest 等 | 快速、定位准，由开发者编写 |
| 集成测试 | 测试容器中运行真实数据库与依赖 | 验证与真实依赖的交互 [B03](#ref-b03) |
| 契约测试 | 消费者驱动的契约（见 10 章） | 验证服务之间的接口约定 |
| 端到端测试 | Playwright 等浏览器自动化工具 | 接近真实用户，但较慢、较脆弱 [B04](#ref-b04) |

#### 06.3 可维护的自动化

- 测试代码与产品代码一样需要设计：清楚的结构、可复用的辅助方法、页面对象或类似的抽象。
- 每个测试独立：不依赖执行顺序，不共享会被修改的数据。
- 失败时提供足够的信息：截图、日志、请求与响应。
- 使用稳定的定位方式：优先使用面向用户的语义（角色、标签、文本），而不是脆弱的样式选择器。

#### 06.4 不稳定的测试

不稳定的测试（有时通过、有时失败）会严重损害团队对测试的信任。Google 曾公开讨论其大规模测试中不稳定测试的成因与处理方式。[B05](#ref-b05) 常见原因包括：依赖时间与等待、测试之间共享状态、依赖外部服务、并发与顺序问题、测试环境不稳定。处理方式：记录与跟踪不稳定的测试，尽快修复根本原因；不要简单地增加重试次数来掩盖问题。

#### 06.5 测试数据

测试数据需要可控、可重复、有代表性。可以使用数据工厂按需生成数据，为每个测试准备独立的数据；用脱敏或合成的数据代替生产数据；准备覆盖边界与异常的专门数据集。

**本章验收**：为一个功能实现单元、集成与端到端三个层次的自动化测试，接入持续集成，并统计一周内的执行时间与不稳定次数。

<a id="ch07"></a>

### 07 非功能测试

#### 07.1 性能测试

明确要回答的问题：在预期负载下的响应时间？系统的容量上限？长时间运行是否稳定？负载突增时的表现？测试时注意负载模型（开放与封闭）、测试数据的规模、缓存状态、测量的边界与资源监控。性能测试的方法见[《后端进阶全景手册》第 16 章](../技术方向/后端进阶全景手册.md#ch16)。

#### 07.2 安全测试

测试工程师可以覆盖常见的安全检查：越权访问（用一个用户的身份访问另一个用户的数据）、输入校验、会话与登录、敏感信息泄露。OWASP 的 Web 安全测试指南提供了系统的测试方法。[B06](#ref-b06) 深入的安全测试由安全工程师主导（见[《安全工程师》](12-安全工程师.md)）。

#### 07.3 无障碍测试

把自动化无障碍检查、键盘测试与屏幕阅读器抽查纳入常规测试（见[《无障碍专家》第 07 章](09-无障碍专家.md#ch07)）。

#### 07.4 兼容性与可靠性测试

兼容性测试覆盖目标浏览器、设备、操作系统与网络条件；可靠性测试检查故障与恢复：依赖不可用、进程中途退出、网络分区时系统的行为。故障注入与混沌实验通常与 SRE 合作（见[《运维工程师与 SRE》](13-运维工程师与SRE.md)）。

**本章练习**：为一个关键接口设计性能测试：负载模型、测试数据、观察指标与通过标准，执行后写出容量结论与主要瓶颈。

<a id="ch08"></a>

### 08 缺陷管理与质量度量

#### 08.1 好的缺陷报告

```text
标题：简短说明问题与位置
环境：版本、浏览器、设备、账号类型
前置条件：
复现步骤：
实际结果：（附截图、日志、请求编号）
期望结果：
影响：哪些用户、多严重、是否有绕过方法
复现频率：
```

好的缺陷报告让开发者不需要再来询问就能复现和定位问题。

#### 08.2 严重程度与优先级

严重程度描述问题对系统和用户的影响；优先级描述修复的紧急程度。两者相关但不同：一个影响很小但出现在首页的拼写错误，严重程度低但可能需要尽快修复；一个严重但极少出现的问题，可能安排在下一个版本。优先级通常由产品经理与技术负责人共同决定。

#### 08.3 根因分析

对重要的缺陷和逃逸到生产环境的缺陷做根因分析：为什么会产生这个缺陷？为什么测试没有发现？把结论转化为改进：补充测试、改进规范、修复同类问题。

#### 08.4 质量度量

| 指标 | 含义 | 注意 |
| --- | --- | --- |
| 逃逸缺陷 | 上线后才发现的缺陷数量与严重程度 | 最能反映测试有效性的指标之一 |
| 缺陷修复时间 | 从发现到修复的时间 | 关注严重缺陷 |
| 自动化测试的稳定性 | 不稳定测试的比例 | 稳定性比数量更重要 |
| 反馈时间 | 从提交代码到获得测试结果的时间 | 影响开发效率 |
| 需求与风险的覆盖 | 关键风险是否有测试 | 比代码覆盖率更有意义 |

代码覆盖率说明哪些代码被执行过，不说明是否被正确检验；缺陷数量受报告习惯影响。任何指标一旦成为考核目标，都可能被“优化”而失去意义，度量应用于改进而不是考核个人。

**本章练习**：分析最近一个季度的逃逸缺陷，按根本原因分类，提出三项具体的改进措施。

<a id="ch09"></a>

### 09 发布质量与验收

#### 09.1 发布标准

事先约定发布标准，例如：关键风险的测试全部通过；没有未解决的严重缺陷；性能与安全检查通过；已知问题已记录并告知支持团队。标准是讨论的依据，而不是机械的门槛：最终决定由产品与技术负责人在了解风险后做出。

#### 09.2 用户验收测试

在企业项目和外包项目中，客户进行用户验收测试（UAT）。测试工程师可以帮助客户准备验收场景、测试环境与数据，记录验收中的问题，并区分缺陷、需求变更和使用问题（见[《业务分析师》](03-业务分析师.md)与[《项目经理与交付经理》](21-项目经理与交付经理.md)）。

#### 09.3 渐进发布与生产验证

通过灰度发布和功能开关降低发布风险：先对少量用户开放，观察错误率与关键指标，再逐步扩大。发布后立即进行生产环境的冒烟验证，确认核心流程可用。

**本章验收**：为一次发布写出发布标准与质量报告，说明测试覆盖、已知问题、剩余风险与建议。

## 第三篇：专项与进阶

<a id="ch10"></a>

### 10 契约测试与集成质量

#### 10.1 服务之间的约定

当多个服务或前后端由不同团队开发时，接口约定的变化是集成问题的主要来源。端到端测试可以发现这类问题，但慢、脆弱、定位困难。

#### 10.2 消费者驱动的契约测试

消费者驱动的契约测试由接口的使用方定义它期望的请求与响应，提供方在自己的构建中验证是否满足所有使用方的契约。这样在提供方修改接口时，就能立即知道哪个使用方会受影响。Pact 是常用的契约测试工具。[B07](#ref-b07)

#### 10.3 使用真实依赖

模拟对象无法证明数据库的隔离行为、约束与索引是否符合预期。集成测试中，使用容器运行真实版本的数据库、消息队列等依赖，能更可靠地发现问题。

**本章练习**：为前端与后端之间的一个接口编写消费者驱动的契约测试，故意修改提供方的响应字段，验证契约测试能否发现问题。

<a id="ch11"></a>

### 11 性质测试、模糊测试与变形测试

#### 11.1 性质测试

性质测试不写具体的输入与输出，而是描述对所有输入都应成立的性质，由工具自动生成大量输入来检验。例如“任何合法的操作序列都不会使额度为负”“序列化后再反序列化得到相同的对象”。工具发现反例后会自动缩小，给出最简单的失败输入。Java 中可以使用 jqwik 等工具。[B08](#ref-b08)

#### 11.2 模糊测试

模糊测试向程序输入大量随机或变异的数据，寻找崩溃、异常和安全问题，特别适合解析器、文件处理和协议实现。简历上传中的文件解析，就是模糊测试的典型对象。

#### 11.3 变形测试

当很难判断单个输出是否正确时（例如搜索、推荐、AI 输出），可以检查多个相关输入的输出之间应满足的关系，这种关系称为变形关系。[B09](#ref-b09) 例如：把简历中的姓名替换为另一个姓名，分析建议不应发生实质变化；调整简历中各段落的顺序，主要发现不应消失。

**本章练习**：为一个规则模块写 3 个性质测试，为文件解析器运行一次模糊测试，为一个搜索或推荐功能设计 3 个变形关系。

<a id="ch12"></a>

### 12 生产环境中的质量

#### 12.1 测试环境的局限

无论测试环境多么接近生产，都无法完全复现真实的数据、流量、用户行为与依赖。因此，质量工作需要延伸到生产环境。

#### 12.2 生产环境中的质量手段

- **合成监控**：定期在生产环境执行关键流程的自动化检查。
- **错误追踪**：收集前端与后端的错误，按影响排序处理。
- **灰度与功能开关**：控制新功能的暴露范围，出现问题时快速关闭。
- **用户反馈**：把客服工单和用户反馈与版本和功能关联。
- **业务指标异常**：关键指标的突然变化往往说明有问题。

生产环境中的测试需要谨慎：使用测试账号与测试数据，避免影响真实用户和触发真实的外部副作用（例如付款、发送邮件）。

**本章练习**：为一个核心流程设计合成监控，说明检查频率、使用的测试账号与数据、失败时的告警与处理方式。

<a id="ch13"></a>

### 13 AI 系统的测试

#### 13.1 AI 测试的特殊性

- **输出不确定**：同一输入可能有不同输出，不能用固定的期望值断言。
- **正确性难以判断**：很多任务没有唯一正确答案，需要评价标准。
- **质量随版本变化**：模型、提示词、检索数据的变化都可能影响质量。
- **新的风险**：提示注入、敏感信息泄露、越权的工具调用、有偏见的输出。

#### 13.2 测试方法

| 方法 | 做法 | 注意 |
| --- | --- | --- |
| 评测集 | 用有代表性的输入与评价标准衡量质量分布 | 由领域专家参与制定标准，定期更新 |
| 回归评测 | 每次变更后在固定评测集上比较 | 关注质量下降的样本，而不只看平均分 |
| 结构与约束检查 | 检查输出格式、长度、必须包含与禁止的内容 | 格式正确不等于内容正确 |
| 变形测试 | 检查相关输入的输出关系 | 适合检查一致性与偏见 |
| 对抗测试 | 构造提示注入、越权请求等恶意输入 | 验证防护在模型之外是否生效 |
| 模型评审 | 用另一个模型按标准评分 | 需要与人工评分对照校准，注意其自身的偏差 |
| 人工抽检 | 由专家定期检查真实输出 | 重点检查高风险场景 |

AI 系统的评测标准与领域专家的参与，见[《领域专家》第 09 章](04-领域专家.md#ch09)；工程层面的版本与评测见[《后端进阶全景手册》第 32 章](../技术方向/后端进阶全景手册.md#ch32)。

**本章验收**：为 AI 简历分析建立 100 条样本的评测集与评分标准，实现格式检查、3 个变形关系和 10 个提示注入测试，接入每次提示词变更的检查流程。

<a id="ch14"></a>

### 14 质量文化与测试左移

#### 14.1 测试左移与右移

测试左移指更早地参与：在需求阶段评审可测试性，在设计阶段识别风险，与开发者一起定义验收示例。测试右移指延伸到生产环境：监控、灰度、生产验证与用户反馈。两者结合，让质量贯穿整个过程。

#### 14.2 团队共同对质量负责

- 开发者编写单元与集成测试，并对自己的代码质量负责。
- 测试工程师作为质量专家：制定策略、设计复杂的测试、建设工具、指导团队。
- 产品经理在需求中写清验收标准。
- 完成的定义包含测试与质量要求。

#### 14.3 测试工程师作为教练

成熟团队中，测试工程师的价值越来越多地体现在帮助他人做好测试：评审开发者的测试、分享测试设计技术、建设让测试更容易的工具，而不是独自承担所有测试。

**本章练习**：组织一次三方会谈（业务、开发、测试），为一个需求共同写出验收示例，比较这样做前后的缺陷数量与返工情况。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与开发者的协作接口

#### 15.1 测试工程师应提供给开发者的内容

| 内容 | 最低要求 | 常见缺失 |
| --- | --- | --- |
| 测试策略与风险 | 开发前共享 | 开发完成后才开始测试 |
| 验收示例 | 包括边界与异常 | 只有正常路径 |
| 缺陷报告 | 可复现、有证据 | “有时候不行” |
| 测试结果 | 快速反馈 | 几天后才反馈 |
| 测试工具 | 开发者可以在本地运行 | 只有测试团队能运行 |

#### 15.2 开发者应提供给测试工程师的内容

可测试的设计（可注入的时间、可控制的依赖、清楚的日志）、变更的影响范围、已知的风险与不确定之处、单元与集成测试的覆盖情况、测试环境与数据的支持。

#### 15.3 一起提高可测试性

可测试性是设计质量的一部分：依赖可以替换、状态可以观察、时间与随机数可以控制、关键行为有清楚的日志与指标。在设计评审中提出可测试性的要求，比事后编写复杂的测试更有效。

<a id="ch16"></a>

### 16 开发者怎样做好测试

#### 16.1 开发者的测试习惯

- **先想清楚怎样证明代码是对的**：在写代码前列出要验证的情况，包括边界与异常。
- **测试行为，而不是实现细节**：重构后测试仍然有效。
- **关键数据库行为用真实数据库测试**：模拟对象无法证明事务与约束的行为。
- **把每个修复的缺陷变成回归测试**。
- **并发问题检查最终的业务不变量**，而不只是“没有抛出异常”。
- **测试要快、要稳定**：不稳定的测试比没有测试更伤害团队。

#### 16.2 独立开发者与外包项目

独立开发者最容易忽视测试，因为“没有人检查”。建议至少做到：核心业务规则有单元测试；关键流程有一条端到端测试；每次发布前运行一遍；每个线上缺陷都补一个测试。外包项目中，在合同中约定测试范围与验收方式，交付测试代码与测试报告，能显著减少验收争议。

<a id="ch17"></a>

### 17 贯穿实战：简历分析功能的测试策略

本章展示一个功能的完整测试策略。数字都是示意。

#### 17.1 风险分析

| 风险 | 可能性 | 影响 | 应对 |
| --- | --- | --- | --- |
| 简历被他人访问 | 低 | 很高 | 权限测试覆盖所有访问路径，包括分享链接与搜索 |
| 额度在并发或失败时计算错误 | 中 | 高 | 并发测试、失败注入、对账测试 |
| 各种文件无法解析或导致崩溃 | 高 | 中 | 文件样本库、模糊测试 |
| 分析任务卡住或重复执行 | 中 | 高 | 状态转换测试、进程中断测试 |
| AI 建议质量下降或出现不当内容 | 中 | 高 | 评测集、变形测试、对抗测试 |
| 结果页在不同设备上显示异常 | 中 | 低 | 抽样兼容性检查 |

#### 17.2 测试安排

| 层次 | 内容 |
| --- | --- |
| 单元测试 | 额度规则、文件校验、状态转换规则（开发者编写，测试工程师评审） |
| 集成测试 | 在真实数据库上测试额度的并发扣减、任务的领取与租约 |
| 契约测试 | 前端与分析接口、分析服务与模型接入层 |
| 端到端测试 | 上传、分析、查看结果、重新分析四条关键路径 |
| 专项测试 | 文件解析的模糊测试；AI 评测集与对抗测试；权限测试；性能测试 |
| 探索性测试 | 每个迭代 2 次，章程覆盖异常文件、中断与恢复、权限变化 |

#### 17.3 发现与改进

- 探索性测试发现：用户在分析完成前删除简历，任务仍然完成并消耗了额度。需求中没有定义这种情况，经产品经理确认后改为取消任务并退回额度，补充了回归测试。
- 模糊测试发现：一类损坏的 PDF 会让解析进程长时间占用内存。修复后为解析增加了时间与内存上限。
- 变形测试发现：替换简历中的姓名后，部分建议的语气发生变化。与领域专家讨论后调整了提示词，并把这一关系加入回归评测。

#### 17.4 发布

发布标准：关键风险的测试全部通过；没有未解决的严重缺陷；评测集质量不低于上一版本，且“安全与公平”维度没有不合格样本。先对 10% 的新用户开放，观察错误率、额度对账结果与用户反馈，一周后扩大到全部用户。

<a id="ch18"></a>

### 18 能力矩阵、学习路线与模板

#### 18.1 能力矩阵

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 测试可以保证没有缺陷 | 测试只能表明缺陷存在，并提供关于风险的信息 |
| 测试是开发结束后的阶段 | 测试从需求阶段开始，延伸到生产环境 |
| 代码覆盖率高说明测试充分 | 覆盖率只说明代码被执行，不说明行为被正确检验 |
| 自动化可以替代手工测试 | 探索性测试与体验评估仍然需要人 |
| 端到端测试越多越好 | 端到端测试慢且脆弱，应以低层测试为主 |
| 不稳定的测试加重试就行 | 重试会掩盖问题，应修复根本原因 |
| 质量是测试团队的责任 | 质量是整个团队的责任，测试工程师是专家与推动者 |
| AI 输出不确定，所以无法测试 | 可以用评测集、约束、变形与对抗测试衡量 |
| 测试人员决定能否发布 | 测试提供证据，发布由负责人在了解风险后决定 |
