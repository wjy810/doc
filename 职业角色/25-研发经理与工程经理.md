# 研发经理与工程经理进阶全景手册

> 从带好一个小团队，到让团队持续交付有价值的结果、让每个人都在成长，再到建设能够自我改进的工程组织。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：刚开始带团队的技术负责人与开发者、准备转向工程管理岗位的工程师，以及希望系统提升的在职研发经理、工程经理与技术总监。

研发经理（也称工程经理）对团队与人负责：招聘合适的人，建立清楚的目标与期望，给出反馈，帮助每个人成长，处理绩效问题，保护团队的健康与可持续的节奏，同时对团队交付的结果负责。随着管理范围扩大，研发经理还要设计团队的结构、管理其他经理、规划预算与人员，并在组织中争取资源、协调方向。

从工程师成为经理，最大的变化是成果的来源：工程师主要通过自己的工作产生成果，经理主要通过团队产生成果。很多新经理在压力下回到自己最熟悉的事情上，亲自写最难的代码、亲自救火，团队却因此缺少方向、反馈与成长。好的经理把时间投入到那些只有经理能做好的事情上：让目标清楚、让人才成长、让团队以可持续的方式持续交付。

本手册先建立角色坐标，然后讲解团队的使命与目标、招聘与入职、一对一与反馈、成长与职业发展、绩效管理、交付与执行、团队健康与工程文化；随后进入管理经理与多团队、组织设计、预算与向上管理、远程与分布式团队、AI 时代的工程管理；最后说明经理与开发者的协作，并用求职平台一个团队的一年演示完整的管理工作。

主线是：**明确团队的使命与目标 → 招到合适的人并帮助他们上手 → 建立信任与清楚的期望 → 持续反馈并帮助每个人成长 → 让团队以可持续的节奏交付 → 改进工作方式与工程文化 → 与组织对齐并管理各方关系。**

不同公司中，这些职责可能由研发经理、工程经理、技术经理、开发组长、技术总监或研发总监承担，有的团队由技术负责人兼任部分管理职责。本手册描述工程管理的职责与方法；D1—D6 分级是学习组织方式，不对应任何职级体系。涉及劳动关系的事项（录用、调岗、薪酬、解除合同等）必须由人力资源与法务按适用的法律和公司制度处理。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 研发经理负责什么

#### 01.1 四个方面的职责

| 方面 | 主要工作 | 关注的结果 |
| --- | --- | --- |
| 人 | 招聘、入职、反馈、成长、绩效、留任 | 每个人清楚期望并持续成长 |
| 团队 | 目标、分工、协作方式、团队健康 | 团队互相信任，能自主解决问题 |
| 交付 | 优先级、容量、障碍、质量与节奏 | 持续、可预期地交付有价值的结果 |
| 组织 | 团队结构、跨团队协作、资源与预算 | 团队与组织的方向一致 |

Google 的 Project Oxygen 研究分析了内部数据，总结出优秀管理者共同的行为，例如做好教练、赋能团队而不微观管理、关心成员的成功与福祉、清楚地沟通愿景与目标、支持职业发展。[B01](#ref-b01) 这些行为大多与“通过他人取得成果”有关，而不是经理个人的技术产出。

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 团队章程与目标 | 统一团队的方向与职责 | 成员能用自己的话说清团队为什么存在 |
| 招聘与入职计划 | 补充团队能力 | 评价标准统一，新人按计划上手 |
| 一对一与反馈记录 | 持续了解与帮助每个人 | 定期进行，反馈具体，有跟进 |
| 发展计划 | 支持成员成长 | 目标明确，有机会与支持 |
| 绩效评估 | 公正地评价与激励 | 基于证据，没有意外 |
| 交付与健康的观察 | 发现问题并改进 | 趋势可见，改进有行动 |
| 组织与人员规划 | 支持业务的发展 | 与业务目标一致，有依据 |

#### 01.3 职责边界与相邻角色

| 事项 | 研发经理的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 做什么、为什么做 | 协作 | 产品经理 | 见[《产品经理》](01-产品经理.md) |
| 技术方向与架构 | 支持并保证质量 | 技术负责人、架构师 | 见[《软件架构师与技术负责人》](10-软件架构师与技术负责人.md) |
| 项目计划与跨团队交付 | 协作 | 项目经理、交付经理 | 见[《项目经理与交付经理》](21-项目经理与交付经理.md) |
| 人员的成长、绩效与招聘 | 主导 | 人力资源 | 劳动关系事项由人力资源与法务处理 |
| 团队的健康与工作方式 | 主导 | 整个团队 | 见 09 章 |
| 平台与工具 | 提出需求，推动采用 | 平台工程师 | 见[《平台工程师与研发效能》](14-平台工程师与研发效能.md) |

几组容易混淆的角色：

- **研发经理与技术负责人**：技术负责人对技术方向、架构与代码质量负责；研发经理对人与团队负责。小团队中常由一人兼任，但两类工作都需要时间，兼任时要清楚自己在哪一类工作上投入不足。
- **研发经理与项目经理**：项目经理对项目的计划与交付负责，通常不管理团队成员；研发经理对团队的长期能力与成员的发展负责。
- **管理路线与专家路线**：资深工程师可以选择成为经理，也可以继续走技术专家路线，承担技术负责人、架构师、攻坚者等角色。Will Larson 总结了资深工程师的几种原型。[B02](#ref-b02) 两条路线都需要影响他人，管理路线以人和团队为主要工作对象。

#### 01.4 从工程师到经理

| 工程师时期 | 经理时期 |
| --- | --- |
| 成果来自自己的工作 | 成果来自团队的工作 |
| 反馈周期短：代码能否运行很快可知 | 反馈周期长：一个人的成长需要几个月 |
| 专注于少数复杂的问题 | 时间被会议与沟通切分，需要主动安排 |
| 自己解决问题 | 帮助他人解决问题，有时要克制自己动手 |

新经理最常见的两种偏差：继续把大部分时间用在编码上，忽视团队；或者完全脱离技术，无法判断技术决策与工作量。比较稳妥的做法是：保留对代码与架构的理解（参与评审、阅读设计文档），但不承担关键路径上的开发任务。

**本章练习**：记录自己一周的时间分配，按“人、团队、交付、组织、个人技术工作”分类，与你认为理想的分配比较，写出下周的调整计划。

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **方向与目标**：团队使命、目标设定、与产品和业务对齐。
2. **招聘**：岗位分析、结构化面试、评价与决策、候选人体验。
3. **入职与培养**：入职计划、导师、学习机会与拉伸任务。
4. **反馈与沟通**：一对一、具体的反馈、困难对话。
5. **绩效与职业发展**：期望、评估、校准、晋升与表现不佳的处理。
6. **交付与执行**：优先级、容量、障碍、质量与可持续节奏。
7. **团队健康与文化**：心理安全、信任、会议与沟通方式、倦怠的预防。
8. **组织设计**：团队边界、团队结构、跨团队协作。
9. **资源与关系**：预算、人员规划、向上与横向的沟通。
10. **技术判断**：理解架构与技术债，支持技术决策与工程质量。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 带新人、组织会议、承担部分管理工作 | 导师记录、会议纪要 |
| D2 独立完成 | 独立管理一个小团队的人与交付 | 一对一记录、发展计划、交付结果 |
| D3 负责结果 | 负责一个团队的长期结果，处理复杂的人员问题 | 团队健康与交付趋势、人员成长记录 |
| D4 系统与跨团队 | 管理多个团队或经理，设计团队结构 | 组织设计、跨团队协作机制 |
| D5 方法与机制 | 建立组织的招聘、绩效、成长与工程文化机制 | 招聘体系、职业阶梯、管理者培养 |
| D6 创新与影响 | 提出新的组织或管理方法并验证 | 公开分享、方法推广 |

#### 02.3 成长中的常见偏差

- 继续做团队里最主要的开发者，管理工作被挤到最后。
- 回避困难的对话，问题积累到无法挽回。
- 绩效评估让成员感到意外，平时没有反馈。
- 用加班弥补计划与优先级的问题。
- 只向上汇报好消息，或者只替团队抱怨而不提出方案。
- 用个人的度量数据排名，破坏团队的协作。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 团队的使命、目标与边界

#### 03.1 团队章程

```text
团队名称：
使命（团队为什么存在，为谁创造什么价值）：
负责的产品、系统与服务：
主要的用户与内部客户：
成功的衡量方式：
不负责的范围：
工作方式（节奏、会议、值班、决策方式）：
与其他团队的接口与依赖：
```

团队章程让成员知道团队的方向与边界，也让其他团队知道该找谁。章程需要团队一起讨论，并在团队职责变化时更新。

#### 03.2 目标设定

为一个季度或半年设定少量目标，每个目标有可衡量的结果，例如“简历分析的完成率从 85% 提升到 95%”“分析耗时的第 95 百分位降到 30 秒以内”。目标与产品经理一起制定，既包括业务结果，也包括工程质量、可靠性与技术债等工程目标。

目标不宜过多：如果每件事都是目标，就等于没有优先级。

#### 03.3 团队边界与认知负荷

一个团队能够有效负责的系统与领域是有限的。负责的系统太多、太杂，团队会陷入频繁的切换与救火。Team Topologies 用认知负荷描述团队需要掌握的知识总量，并提出按业务流组织团队、通过平台团队降低其他团队负担等方法。[B03](#ref-b03) 当团队长期超负荷时，需要调整职责边界，而不是简单地要求更努力。

#### 03.4 与产品经理配合

研发经理与产品经理是团队的两个支柱：产品经理负责做什么与为什么，研发经理负责团队能否以可持续的方式做好。两人定期对齐优先级、容量与风险，在团队面前保持一致；有分歧时私下讨论，必要时一起向上寻求决策。

**本章练习**：与团队一起写出团队章程，请三位其他团队的同事阅读，记录他们对团队职责的理解与章程的差异，并修改章程。

### 04 招聘与入职

#### 04.1 明确需要什么人

招聘前先回答：团队缺少什么能力？这个岗位一年后应当取得什么成果？哪些能力必须在入职时具备，哪些可以在工作中培养？把答案写成岗位说明与评价标准，面试官按同一份标准评价。

#### 04.2 结构化面试

结构化面试为同一岗位的候选人使用统一的问题与评分标准。Google 的 re:Work 指南总结了它的做法与好处：事先准备与岗位相关的问题，用带有行为描述的评分标准打分，比非结构化的面试更能预测工作表现。[B04](#ref-b04)

| 环节 | 考察的能力 | 做法 |
| --- | --- | --- |
| 技术实践 | 编码、调试、代码质量 | 与实际工作相近的问题，允许使用常用工具 |
| 系统设计 | 拆解问题、权衡取舍 | 开放式问题，关注思考过程 |
| 过往经历 | 协作、负责、学习 | 询问具体的经历：当时的情况、做了什么、结果如何 |
| 价值观与协作 | 沟通、反馈、团队合作 | 情境问题与过往经历 |

#### 04.3 评价与决策

- 面试官在讨论之前独立写下评分与依据，避免被他人的意见影响。
- 依据评价标准讨论，而不是“感觉合不合适”。
- 警惕常见的偏差：偏好与自己相似的人、因为一个突出的优点忽视其他方面、过度依赖学校与公司的名气。
- 招聘的过程与要求遵守平等就业等适用的规定，由人力资源确认。

#### 04.4 候选人体验

及时告知进度与结果，面试安排尊重候选人的时间，结束时说明后续流程。即使没有录用，好的体验也会影响候选人对公司的评价。

#### 04.5 入职计划

| 时间 | 目标 | 示例 |
| --- | --- | --- |
| 第一周 | 环境就绪，认识团队，完成第一个小改动并上线 | 修复一个小问题，走完一次完整的发布流程 |
| 第一个月 | 理解团队负责的系统，独立完成小功能 | 参与一次值班的旁听，完成一个小功能 |
| 第三个月 | 独立负责一个模块或功能 | 负责一个中等规模的功能，从设计到上线 |

为新人安排一位导师，负责解答日常问题；经理在第一个月更频繁地进行一对一，了解新人的困难。新人发现的文档缺失与流程问题，是改进团队的好机会。

**本章验收**：为一个岗位写出岗位说明、评价标准与结构化面试的问题和评分表；为新成员制定三个月的入职计划，并在第三个月末与新成员一起回顾。

### 05 一对一与反馈

#### 05.1 一对一

一对一是经理与每位成员定期的单独交谈，通常每周或每两周一次。它的目的是了解对方的状态与想法、提供支持与反馈、讨论成长，而不是汇报进度。

- 议程以对方为主，经理补充需要讨论的事项。
- 关注对方的困难、想法、成长与职业目标。
- 记录讨论的要点与约定的行动，下次跟进。
- 尽量不取消；需要调整时提前改期。

常用的问题：“最近工作中最有成就感的是什么？”“有什么在阻碍你？”“有什么我可以做得更好？”“半年后你希望自己在哪些方面有进步？”

#### 05.2 给出反馈

反馈要具体、及时，并说明行为的影响。一种常用的结构是：描述情境，描述具体的行为，说明这一行为带来的影响，再讨论接下来怎样做。

```text
情境：昨天的设计评审中
行为：你在其他人发言时多次打断，直接否定了方案
影响：两位新同事之后没有再发言，我们可能错过了他们的想法
讨论：你怎么看？下次评审时我们可以怎样做？
```

- 正面的反馈同样要具体，让对方知道哪些做法应当继续。
- 改进的反馈私下进行，对事不对人。
- 反馈之后跟进，关注变化。

#### 05.3 接收反馈

经理也需要反馈：定期请成员评价自己的管理方式，对收到的意见表示感谢并说明会怎样处理。经理接受反馈的态度，决定了团队是否敢于提出问题。

#### 05.4 困难的对话

绩效问题、冲突、不被采纳的意见、坏消息，都需要困难的对话。做法：提前准备要表达的事实与期望；直接说明主题，不绕圈子；倾听对方的看法；明确下一步与时间；会后书面确认要点。

**本章练习**：与每位成员进行一次以对方为主的一对一，记录要点与行动；用情境、行为、影响的结构给出三条具体的反馈，两周后跟进变化。

<a id="ch06"></a>

### 06 成长与职业发展

#### 06.1 清楚的期望

成长需要清楚的期望：在当前级别上，好的表现是什么样？下一个级别需要哪些能力与影响范围？很多公司用职业阶梯描述各级别的期望，通常从技术能力、交付、影响范围、协作与领导等方面描述。本系列使用的 D1—D6 分级是学习组织方式，不能直接作为职业阶梯。

#### 06.2 发展计划

```text
职业目标（一到两年）：
需要加强的能力：
计划中的机会（项目、职责、拉伸任务）：
需要的支持（培训、导师、经理的帮助）：
如何判断进展：
回顾时间：
```

成长主要来自工作中的机会，而不只是培训。经理的重要职责是把合适的机会交给合适的人，并提供必要的支持。

#### 06.3 委派与拉伸任务

委派不只是分配任务，还包括转交责任与决策权。委派时说明期望的结果、约束与可以自主决定的范围，约定检查的时间点；对方遇到困难时提供支持，而不是收回任务。拉伸任务略高于对方现有的能力，是成长最快的方式，但需要承担失败的可能与相应的支持。

#### 06.4 管理路线与专家路线

成员希望转向管理时，可以先承担带新人、组织会议、负责一个小项目等工作，体验管理的日常；成员希望走专家路线时，帮助他找到更大范围的技术问题与影响机会。两条路线都应当有清楚的发展空间。

#### 06.5 导师与举荐

导师提供建议与经验；举荐者在关键的机会出现时推荐成员。经理既要做导师，也要在合适的场合举荐团队成员，让他们的工作被看见。

**本章验收**：与每位成员共同制定发展计划，为其中至少两人安排拉伸任务，三个月后回顾进展，并记录哪些支持有效、哪些需要调整。

<a id="ch07"></a>

### 07 绩效管理

#### 07.1 没有意外

绩效评估的结果不应让成员感到意外。如果平时有清楚的期望与持续的反馈，评估只是对已经讨论过的内容进行总结。

#### 07.2 基于证据评估

- 收集一个周期内的证据：完成的工作及其影响、协作与行为、成长。
- 区分结果与过程：结果受很多因素影响，也要看成员的决策与行为是否合理。
- 参加校准会，与其他经理一起对照标准，减少不同经理之间的松紧差异。
- 评估反馈具体，说明依据与下一阶段的期望。

#### 07.3 表现不佳

1. **尽早发现**：表现下滑时尽早沟通，了解原因：期望不清楚、能力不足、工作分配不合适，还是个人原因。
2. **明确期望**：说明差距与需要达到的标准，并提供具体的例子。
3. **提供支持**：调整工作、提供指导或培训，约定检查的时间。
4. **记录**：记录沟通的内容、约定与进展。
5. **按规定处理**：如果经过支持仍然无法改善，涉及调岗、改进计划或解除合同等事项，与人力资源和法务一起按适用的法律与公司制度处理。

很多表现问题源于不清楚的期望或不合适的工作安排。先检查管理方面的原因，再判断个人的问题。

#### 07.4 晋升

晋升通常基于成员已经稳定地在更高级别上工作，而不是对未来的期望。经理负责收集证据、说明成员的影响，并在晋升没有通过时说明差距与下一步。

**本章练习**：为一位成员整理一个周期的绩效证据，按团队的期望写出评估；与另一位经理交换评估，讨论各自标准的差异。

<a id="ch08"></a>

### 08 交付与执行

#### 08.1 经理在交付中的角色

- 保证优先级清楚：团队知道现在最重要的是什么。
- 移除障碍：协调资源、依赖与决策。
- 平衡负荷：避免少数人承担过多的工作或值班。
- 保证质量：给测试、评审、重构与技术债留出时间。
- 保持可持续的节奏：用计划与取舍而不是长期加班来应对压力。

项目计划与风险管理的方法见[《项目经理与交付经理》](21-项目经理与交付经理.md)。

#### 08.2 观察交付的趋势

DORA 的研究使用变更前置时间、部署频率、失败部署的恢复时间、变更失败率与部署返工率等指标，衡量软件交付的吞吐与稳定性。[B05](#ref-b05) SPACE 框架则提醒，开发者的效能涉及满意度与幸福感、绩效、活动、沟通与协作、效率与流动等多个维度，不能用单一的指标衡量。[B06](#ref-b06)

这些度量用于观察团队与系统的趋势、发现改进的方向，不应用于个人的排名或考核。以代码行数、提交次数或工单数量评价个人，会鼓励错误的行为。

#### 08.3 技术债

技术债会逐渐降低团队的交付速度与质量。与产品经理约定一定比例的时间用于技术债与工程质量，并用具体的影响说明它的价值，例如“某个模块的变更失败率是其他模块的三倍”。

#### 08.4 事故与复盘

事故发生后，组织无责复盘：关注系统与流程中的原因，而不是追究个人。Google SRE 书中的复盘文化一章说明了这种做法的原则。[B07](#ref-b07) 复盘的改进项需要负责人与期限，经理负责跟进落实。

**本章练习**：收集团队最近一个季度的交付指标与事故记录，找出一个最影响交付的问题，与团队一起制定改进计划，并在下个季度检查效果。

<a id="ch09"></a>

### 09 团队健康与工程文化

#### 09.1 心理安全

心理安全指团队成员共同相信，在团队中承担人际风险是安全的：提出问题、承认错误、提出不同意见不会受到惩罚或羞辱。Edmondson 的研究发现，团队的心理安全与学习行为相关，而学习行为又影响团队的表现。[B08](#ref-b08)

建立心理安全的做法：

- 经理先承认自己的错误与不确定。
- 对提出问题与坏消息的人表示感谢。
- 讨论问题时关注系统与过程，而不是指责个人。
- 邀请较少发言的人表达意见。

#### 09.2 信息流动的文化

社会学家 Westrum 按组织处理信息的方式，把组织文化分为权力导向、规则导向与绩效导向三类。DORA 的研究发现，高信任、重视信息流动的绩效导向文化，与更好的软件交付表现和组织表现相关。[B09](#ref-b09) 这类文化的特征包括：高度合作、传递坏消息的人受到重视、失败引发调查而不是追责、新想法会被尝试。

#### 09.3 会议与沟通

- 每个会议有明确的目的与议程，没有必要的会议就取消。
- 重要的讨论与决定写成文档，便于没有参会的人了解。
- 为团队保留整块的专注时间。
- 区分需要即时回复与可以稍后处理的沟通。

#### 09.4 倦怠与可持续的节奏

长期加班、过重的值班负担、频繁的打扰与缺乏成就感，会导致倦怠。经理需要关注这些信号：工作质量下降、情绪变化、请假增多、参与度降低。应对的方法包括调整工作量、改进值班与告警（见[《运维工程师与 SRE》](13-运维工程师与SRE.md)）、减少不必要的打扰，并在一对一中直接关心。

#### 09.5 公平与包容

工作的分配、发言的机会、晋升与认可都应当公平。注意那些不被看见的工作，例如帮助新人、改进文档、处理值班，确保它们在评估中得到认可。

**本章验收**：用匿名问卷了解团队的心理安全与工作负荷，与团队一起讨论结果，选择两项改进并在一个季度后再次调查。

## 第三篇：专项与进阶

<a id="ch10"></a>

### 10 管理经理与多个团队

#### 10.1 管理经理

管理经理时，工作重心从直接管理工程师转向培养经理、设计组织与协调方向：

- 与每位经理定期一对一，讨论团队的状况与他们自己的成长。
- 定期与经理所带团队的成员进行跨级交谈，了解一线的情况，但不绕过经理做决定。
- 帮助新经理建立管理的基本功：一对一、反馈、招聘与绩效。

#### 10.2 系统结构与组织结构

组织的沟通结构会影响它设计出的系统结构，这一观察常被称为康威定律，源自 Conway 在 1968 年发表的文章。[B10](#ref-b10) 因此，调整团队结构时需要同时考虑系统的边界；反过来，希望系统形成某种结构时，也可以相应地组织团队。架构与组织的关系见[《软件架构师与技术负责人》](10-软件架构师与技术负责人.md)。

**本章练习**：画出所管理的团队与它们负责的系统，标出跨团队的依赖与经常需要协调的地方，判断是否存在团队边界与系统边界不一致的问题。

<a id="ch11"></a>

### 11 组织设计与团队结构

#### 11.1 常见的团队类型

Team Topologies 描述了四种基本的团队类型：

| 类型 | 职责 |
| --- | --- |
| 业务流团队 | 面向一条业务流或一类用户，端到端交付价值 |
| 平台团队 | 提供内部平台，降低业务流团队的负担 |
| 赋能团队 | 帮助其他团队掌握新的能力，然后退出 |
| 复杂子系统团队 | 负责需要深度专业知识的子系统 |

团队之间的协作方式包括密切协作、以服务的方式提供能力，以及引导与辅导。[B03](#ref-b03) 平台团队的做法见[《平台工程师与研发效能》](14-平台工程师与研发效能.md)。

#### 11.2 调整团队结构

调整结构之前，先说明要解决的问题：团队之间依赖过多、团队规模过大、职责不清、认知负荷过高。频繁的调整会破坏团队的稳定与信任，每次调整都需要清楚的理由、沟通与过渡安排。

#### 11.3 团队规模

团队过小，难以承担值班与人员变动；团队过大，沟通成本上升，一对一与反馈难以保证。团队扩大时，按业务流或系统边界拆分，并为新团队明确职责与负责人。

**本章练习**：为一个正在扩张的团队设计两种拆分方案，比较各自的依赖、认知负荷与过渡成本，并与团队讨论后选择。

<a id="ch12"></a>

### 12 预算、人员规划与向上管理

#### 12.1 人员规划

人员规划从业务目标出发：要达成这些目标需要哪些能力与多少人？现有团队能承担多少？缺口用招聘、调配、外部合作还是调整目标来解决？规划要考虑招聘与培养所需的时间。

#### 12.2 预算

工程预算通常包括人员、基础设施与云服务、工具与软件、外部服务与培训。了解每一项的用途与变化趋势，并能说明投入与业务价值的关系。

#### 12.3 向上管理

- 定期向上级说明团队的进展、风险与需要的支持，坏消息尽早说。
- 提出问题时同时提出可选的方案与建议。
- 了解上级与组织的目标，把团队的工作与之联系起来。
- 在上级做出决定后，向团队清楚地解释原因，即使自己曾持不同意见。

#### 12.4 横向关系

与产品、设计、运营、销售等部门的负责人建立日常的联系，提前了解彼此的计划与困难，而不是在冲突发生时才第一次沟通。

**本章练习**：为团队写出下一年的人员与预算规划，说明与业务目标的关系；向上级做一次汇报，记录收到的问题并完善规划。

<a id="ch13"></a>

### 13 远程与分布式团队

- **书面优先**：决定、设计与状态以文字记录，让不同地点与时区的成员获得相同的信息。
- **重叠时间**：约定团队共同在线的时段，重要的同步讨论安排在这一时段。
- **异步协作**：减少需要即时回复的沟通，明确各类消息的期望回复时间。
- **建立联系**：定期安排非工作的交流，必要时组织线下见面。
- **公平**：远程成员同样获得重要的工作机会与可见度。

**本章练习**：检查团队最近一个月的重要决定，有多少只发生在会议或私聊中而没有书面记录；为团队制定一份沟通约定，规定各类信息的渠道与期望的回复时间。

<a id="ch14"></a>

### 14 AI 时代的工程管理

#### 14.1 引入 AI 工具

- **评估实际效果**：用交付与质量的数据评估，而不只依赖使用者的感受；关注变更失败率与返工的变化。
- **安全与数据**：明确哪些代码与数据可以发送给哪些工具，遵守公司的安全与合规要求。
- **评审与质量**：AI 生成的代码同样需要评审与测试，提交者对代码负责。
- **度量误用**：不以使用 AI 的次数或生成的代码量评价个人。

研发效能与 AI 辅助开发的研究见[《平台工程师与研发效能》](14-平台工程师与研发效能.md)。

#### 14.2 新人的成长

AI 工具让完成简单任务变得更快，但新人也可能因此缺少理解基础知识的机会。为新人安排需要深入理解的任务，在评审中询问实现的原因与取舍，帮助他们建立判断力。

#### 14.3 招聘与面试

候选人可能在面试中使用 AI 工具。明确面试中允许使用哪些工具，并设计更关注理解、权衡与沟通的问题，例如让候选人解释一段代码的问题与改进方向。

**本章练习**：为团队制定 AI 工具的使用约定，包括允许的工具与数据范围、评审要求与效果的评估方式，三个月后用数据回顾。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与开发者的协作接口

#### 15.1 开发者需要经理提供的内容

| 内容 | 说明 |
| --- | --- |
| 清楚的期望 | 工作的目标、优先级与评价标准 |
| 具体的反馈 | 及时、具体，包括做得好的与需要改进的 |
| 成长的机会 | 合适的任务、拉伸的机会与支持 |
| 专注的时间 | 减少不必要的会议与打扰 |
| 障碍的移除 | 协调资源、依赖与决策 |
| 公平 | 工作分配、认可与评估的公平 |

#### 15.2 经理需要开发者提供的内容

透明的进展与风险、遇到困难时主动沟通、对自己成长的投入、对团队与管理方式的反馈、帮助同事与新人。

#### 15.3 一对一是双向的

开发者可以在一对一中提出自己的想法与需求：希望学习什么、希望承担什么职责、对团队有什么建议。经理与开发者都为这段关系负责。

<a id="ch16"></a>

### 16 开发者怎样借用管理方法

#### 16.1 技术负责人与资深开发者

- 带新人时，制定入职计划，给出具体的反馈。
- 分配任务时说明期望的结果与约束，而不是只给出做法。
- 组织技术讨论时，邀请每个人发言，记录决定与原因。

#### 16.2 小团队负责人与外包团队负责人

管理合作者与外包人员时，同样需要清楚的期望、定期的沟通与具体的反馈；用书面方式确认职责、交付物与验收标准。

#### 16.3 技术背景的常见偏差

- 认为管理就是分配任务与检查进度。
- 自己承担所有困难的工作，团队得不到成长。
- 回避冲突与困难的对话。
- 只关注技术，忽视成员的感受与动机。

<a id="ch17"></a>

### 17 贯穿实战：简历分析团队的一年

本章以求职平台的“简历分析”团队为例，展示一年中的管理工作。人员与数字均为示意。

#### 17.1 起点

团队有 6 名工程师，与一位产品经理、一位共享的设计师协作，负责简历上传、解析与 AI 简历分析。经理上任时发现：团队没有明确的章程，值班告警很多，两位资深工程师承担了大部分的值班，一位新人入职一个月仍未完成第一次上线。

#### 17.2 第一个季度

- 与团队一起写出团队章程与季度目标：分析完成率从 85% 提升到 95%，并把每周的告警数量减半。
- 与每位成员开始每两周一次的一对一，了解到两位资深工程师因值班负担过重而疲惫。
- 与运维一起清理告警，删除无法处理的告警，补充处理手册，值班改为全员轮值。
- 为新人重新制定入职计划，安排导师，第二周完成了第一次上线。

#### 17.3 第二个季度

- 一位工程师的表现明显下滑。一对一中了解到家庭的原因，经理调整了他的工作量与值班安排，约定一个月后回顾；两个月后他的状态恢复。
- 一位资深工程师希望走专家路线。经理与他一起制定发展计划，让他负责分析服务的性能与成本优化，并在跨团队的架构评审中介绍方案。
- 季度目标中的完成率提升到 93%，没有完全达成；复盘发现大文件解析的问题需要与平台团队协作，列入下季度目标。

#### 17.4 第三、第四季度

- AI 功能的上线压力增大。经理与产品经理一起把需求拆为两期，保证第一期的评测与安全检查完整，避免为赶时间跳过质量工作。
- 团队扩张到 10 人后，沟通成本明显上升。经理按业务流把团队拆分为“简历解析”与“分析与建议”两个团队，并从团队内部培养了一位新的经理。
- 年末的匿名调查显示，心理安全与工作负荷的评分都有提升；交付指标中的变更失败率下降，部署频率提高。

#### 17.5 回顾

- **有效的做法**：先解决值班负担，团队的精力才能回到目标上；入职计划与导师显著缩短了新人上手的时间。
- **需要改进**：目标中的跨团队依赖应当在制定目标时就识别；拆分团队前应更早与成员沟通，减少不确定感。

#### 18.5 检查清单

- [ ] 团队有章程与少量可衡量的目标，成员能说清团队为什么存在。
- [ ] 招聘使用统一的评价标准与结构化面试。
- [ ] 每位新成员都有入职计划与导师。
- [ ] 与每位成员定期一对一，反馈具体并有跟进。
- [ ] 每位成员都有发展计划与合适的机会。
- [ ] 绩效评估基于证据，结果不让成员意外。
- [ ] 交付度量用于团队改进，不用于个人排名。
- [ ] 为技术债与工程质量保留时间。
- [ ] 关注值班负担、工作量与倦怠信号。
- [ ] 劳动关系相关的事项与人力资源、法务一起处理。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 技术最好的人最适合当经理 | 管理需要不同的能力，技术专家路线同样重要 |
| 经理不需要懂技术了 | 需要保持足够的理解，才能判断技术决策与工作量 |
| 一对一就是汇报进度 | 一对一关注对方的状态、成长与阻碍 |
| 绩效评估只在年底做 | 期望与反馈是持续的，评估只是总结 |
| 表现不好就是个人的问题 | 先检查期望、工作安排与支持是否合适 |
| 用代码行数或提交次数衡量效率 | 这类指标会鼓励错误的行为，效能需要多维度观察 |
| 加班能解决进度问题 | 长期加班导致倦怠与质量下降，需要调整范围与计划 |
| 好团队不需要冲突 | 健康的团队能够公开地讨论分歧 |
| 组织调整越快越好 | 每次调整都需要理由、沟通与过渡 |
