# 数据工程师进阶全景手册

> 从把数据可靠地搬到需要它的地方，到建设可信、可演进、可治理的数据体系，再到让数据成为组织能够放心使用的资产。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：需要为业务建设数据管道的后端开发者、准备转向数据工程的工程师，以及希望系统提升的在职数据工程师和大数据开发者。

数据工程师负责让数据从产生它的系统，可靠地到达使用它的人和系统：分析师需要口径一致的历史数据，算法工程师需要可复现的训练数据，运营需要按时更新的报表，有些业务功能需要实时的加工结果。数据工程师建设这条链路上的采集、存储、加工、质量与治理。

数据工程的难点很少在于“把数据导过去”，而在于长期运行中的各种变化：上游改了字段、事件重复发送、数据迟到、口径被各自复制、个人信息流向了不该去的地方、成本悄悄翻倍。好的数据工程师会把管道当作长期运行的产品来设计：可重跑、可监控、可追溯，并且清楚每份数据的含义、负责人与使用者。

本手册先建立角色坐标，然后讲解需求与来源、数据建模、采集与集成、批处理、流处理、存储与计算、质量与契约；随后进入元数据与血缘、安全与隐私、可靠性与成本、数据平台、为机器学习与 AI 提供数据；最后说明数据工程师与开发者的协作，并用求职平台的数据管道演示一次完整的数据工程工作。

主线是：**理解数据的使用者与来源 → 设计数据模型与契约 → 构建可重跑的采集与加工管道 → 保证质量、时效与成本 → 治理权限、隐私与血缘 → 把数据作为产品持续运营。**

不同公司中，这些职责可能由数据工程师、大数据开发、分析工程师、数据平台工程师或后端开发者承担，与数据库工程师、算法工程师的分工也各不相同。本手册描述数据工程的职责与方法；D1—D6 分级是学习组织方式，不对应任何职级体系。文中提到的工具只作为示例，不构成选型建议。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 数据工程师负责什么

#### 01.1 数据在组织中的流动

业务系统产生数据，数据被采集、存储与加工，再提供给分析、报表、实验、模型与业务系统。数据工程师负责这条链路的可靠性。

| 环节 | 典型问题 | 数据工程师的工作 |
| --- | --- | --- |
| 来源 | 数据分散在多个系统，结构各异 | 盘点来源，确定权威数据 |
| 采集 | 漏数、重复、延迟 | 增量抽取、变更数据捕获、事件采集 |
| 存储 | 成本、性能、格式选择 | 选择存储与表格式，设计分区 |
| 加工 | 口径分散、重复计算 | 分层建模，建设可重跑的管道 |
| 服务 | 使用者找不到、看不懂、不敢用 | 数据目录、文档、契约与权限 |
| 治理 | 隐私、安全与合规 | 分类分级、访问控制、保留与删除 |

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 数据模型与数据集 | 支持分析与应用 | 粒度明确，口径有文档，可追溯来源 |
| 数据管道 | 采集与加工数据 | 可重跑、可监控，失败后可恢复 |
| 数据契约 | 约定上下游的结构与质量 | 有负责人，变更有流程 |
| 质量检查与监控 | 及时发现问题 | 覆盖关键数据，告警可处理 |
| 数据目录与血缘 | 帮助查找与理解数据 | 与实际一致，能做影响分析 |
| 平台与工具 | 让他人自助使用数据 | 有文档、有护栏、成本可见 |

#### 01.3 职责边界与相邻角色

| 事项 | 数据工程师的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 业务数据库设计与运维 | 协作 | 后端开发者、数据库工程师 | 见[《数据库工程师／DBA》](15-数据库工程师DBA.md) |
| 指标定义与分析 | 支持 | 数据分析师主导 | 见[《数据分析师与产品分析师》](16-数据分析师与产品分析师.md) |
| 埋点 | 接收、校验与存储 | 分析师设计，开发者实现 | 三方共同验证 |
| 训练数据与特征 | 协作 | 算法工程师 | 见[《算法与机器学习工程师》](18-算法与机器学习工程师.md) |
| 数据平台基础设施 | 主导或协作 | 平台工程师、运维工程师 | 见[《平台工程师与研发效能》](14-平台工程师与研发效能.md) |
| 数据安全与合规 | 落实技术措施 | 安全工程师、法务 | 具体义务由相应负责人确认 |

几组容易混淆的角色：

- **数据工程师与后端开发者**：后端开发者为业务操作设计数据；数据工程师为分析与模型重新组织数据。两者在业务表结构变更与事件设计上紧密相关。
- **数据工程师与分析工程师**：分析工程师侧重用 SQL 与软件工程方法建设面向分析的数据模型，位于数据工程师与分析师之间。很多团队由数据工程师兼任。
- **数据工程师与数据库工程师**：数据库工程师负责业务数据库的稳定与性能；数据工程师负责从这些数据库中采集与加工数据。
- **数据工程师与大数据开发**：国内常用“大数据开发”称呼基于分布式计算与存储框架的数据工程工作，职责与数据工程师大体相同。

**本章练习**：画出所在组织的数据流动图，包括主要来源、采集方式、存储位置、加工环节与使用者，标出你认为最不可靠的环节并说明理由。

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **需求理解**：数据的使用者、粒度、时效与历史要求。
2. **数据建模**：维度建模、分层、命名与文档。
3. **采集与集成**：批量抽取、变更数据捕获、事件采集。
4. **批处理**：编排、增量计算、回填与测试。
5. **流处理**：事件时间、窗口、状态与投递语义。
6. **存储与计算**：仓库、湖、开放表格式与计算引擎。
7. **质量与契约**：数据测试、监控、契约与模式演进。
8. **治理与隐私**：血缘、目录、分类分级、访问控制、保留与删除。
9. **可靠性与成本**：数据的服务目标、可观测性、事故与成本。
10. **平台与数据产品**：自助平台、数据产品、为机器学习与 AI 提供数据。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 能编写查询与简单的数据任务，理解分层与调度 | 数据任务、查询脚本 |
| D2 独立完成 | 独立建设一条从来源到数据集的管道，含测试与监控 | 管道、数据测试、文档 |
| D3 负责结果 | 负责一个业务领域数据的质量、时效与成本 | 服务目标达成记录、事故复盘 |
| D4 系统与跨团队 | 设计跨团队的数据架构、契约与集成方式 | 架构方案、数据契约、迁移记录 |
| D5 方法与机制 | 建立组织的数据平台、质量与治理机制 | 平台、规范、治理流程 |
| D6 创新与影响 | 提出新的数据处理方法或工具并验证 | 开源贡献、公开研究 |

#### 02.3 成长中的常见偏差

- 追逐工具与框架，忽视数据的含义与使用者。
- 管道能跑通就上线，没有测试、监控与重跑方案。
- 数据量很小时就引入复杂的分布式系统。
- 为每个需求单独建宽表，口径与计算重复。
- 不关心上游变化，上游一改字段，下游全部出错。
- 把隐私与权限当作上线以后再补的事情。

## 第二篇：核心工作方法

### 03 理解数据需求与数据来源

#### 03.1 从使用场景出发

不同的使用场景对数据有不同的要求，建设前先弄清楚数据给谁用、用来做什么。

| 使用场景 | 主要关注点 |
| --- | --- |
| 分析与报表 | 口径一致、历史完整、按天或按小时更新 |
| 实验分析 | 分组信息准确、事件完整、能按用户关联 |
| 模型训练 | 历史时点正确、标签可靠、能够复现 |
| 实时功能 | 延迟低、可用性高、与业务数据一致 |
| 回流业务系统 | 准确、按时更新、失败有处理 |

回流业务系统指把加工结果同步回客服、营销等业务工具，常被称为反向 ETL。它让分析结果直接影响业务操作，因此对准确性和失败处理的要求更高。

#### 03.2 盘点数据来源

| 来源 | 特点 | 常见问题 |
| --- | --- | --- |
| 业务数据库 | 结构化、权威，记录当前状态 | 只保留最新值，历史变化丢失；直接查询会影响线上服务 |
| 事件埋点 | 记录用户行为的过程 | 丢失、重复、口径变化 |
| 服务日志 | 量大、半结构化 | 格式不一致，可能含敏感信息 |
| 第三方与合作方 | 由外部提供 | 质量不可控，接口会变化 |
| 文件与表格 | 人工维护 | 格式随意，版本混乱 |

同一个业务事实可能出现在多个来源中，例如“分析完成”既在业务库的任务表中，也在埋点事件中。需要事先确定哪个来源是权威数据，其他来源用于补充与核对。

#### 03.3 数据需求单

```text
数据需求：
使用者与使用场景：
要支持的决定或功能：
粒度（每行代表什么）：
时效（多久更新一次，最晚何时可用）：
历史范围（需要多长的历史，是否需要记录历史变化）：
质量要求（允许的缺失与误差）：
来源与权威数据：
访问权限与敏感字段：
负责人与验收方式：
```

**本章练习**：选一个现有数据集，按需求单补全它的描述，找出至少一项从未被明确约定的要求，并与使用者确认。

### 04 数据建模

#### 04.1 业务库与分析库

| 方面 | 业务数据库（联机事务处理） | 分析数据库（联机分析处理） |
| --- | --- | --- |
| 主要操作 | 少量行的读写 | 大量行的扫描与聚合 |
| 模型 | 规范化，减少冗余 | 面向查询，允许冗余 |
| 历史 | 通常只保存当前状态 | 保留历史与变化 |
| 存储 | 以行式为主 | 以列式为主 |

把业务库的表原样复制到分析环境，并不等于完成了建模。分析需要按业务过程重新组织数据，并保留变化的历史。

#### 04.2 维度建模

维度建模是分析数据建模最常用的方法，Kimball Group 整理了它的主要技术。[B01](#ref-b01)

- **粒度**：事实表中每一行代表什么，例如“一次分析任务”。建模的第一步是确定粒度，粒度不清会导致重复计算。
- **事实**：可度量的数值，例如分析耗时、建议数量。
- **维度**：描述事实的上下文，例如用户、简历版本、目标岗位、日期。
- **一致性维度**：多个事实表共享的同一维度，保证跨主题分析时口径一致。
- **缓慢变化维度**：维度属性随时间变化时的处理方式。类型 1 直接覆盖，不保留历史；类型 2 增加新行并记录有效期，保留历史。需要按当时的属性分析时，使用类型 2。

#### 04.3 分层

| 层次 | 内容 | 原则 |
| --- | --- | --- |
| 原始层 | 来源数据的原样副本 | 只追加，不修改，保留重新处理的能力 |
| 清洗层 | 去重、类型转换、标准化 | 一张表对应一个来源实体，含基本质量检查 |
| 整合层 | 按业务过程建模的事实与维度 | 统一口径，使用一致性维度 |
| 应用层 | 面向特定场景的汇总与宽表 | 有明确的使用者与负责人 |

国内常见 ODS、DWD、DWS、ADS 等分层命名，一些湖仓平台使用铜、银、金三层的说法。名称并不重要，重要的是每一层的职责清楚，下层的修改不破坏上层。

#### 04.4 宽表的代价

宽表把多个维度预先关联在一起，便于使用。但如果每个需求都单独建一张宽表，相同的口径会被复制多次，修改时很难保证一致。宽表应建立在整合层之上，由明确的负责人维护，并在数据目录中说明来源。

#### 04.5 命名与文档

- 统一的命名规则，体现层次、主题与粒度。
- 每张表说明粒度、主键、更新方式、来源与负责人。
- 每个字段说明含义、单位、取值与是否可为空。
- 模型的修改通过评审，并记录变更。

**本章验收**：为一个业务过程设计维度模型：确定粒度，列出事实与维度，指出需要按类型 2 处理的维度属性，写出各层表的说明，并请一位分析师按说明独立完成一次查询。

<a id="ch05"></a>

### 05 数据采集与集成

#### 05.1 批量抽取与增量抽取

| 方式 | 做法 | 局限 |
| --- | --- | --- |
| 全量抽取 | 每次复制整张表 | 简单，数据量大时成本高 |
| 按更新时间增量 | 每次抽取更新时间之后变化的行 | 依赖可靠的更新时间，无法识别物理删除 |
| 变更数据捕获 | 读取数据库的事务日志 | 建设与运维更复杂 |

#### 05.2 变更数据捕获

变更数据捕获读取数据库的事务日志，获得每一次插入、更新与删除。它能捕获删除和每一次中间变化，对业务库的查询压力也较小。Debezium 等开源工具是常见的实现。

需要注意：

- 初始全量快照与之后增量数据的衔接，不能遗漏也不能重复。
- 来源表结构变更时，下游如何处理新字段与删除的字段。
- 同一主键的多次变更必须按顺序处理。
- 数据库日志的保留时间有限，采集中断过久会产生无法补回的缺口。

#### 05.3 事件与日志

把所有变化按顺序追加到日志中，下游各自按需消费与重放，是数据集成中一个重要的统一抽象。Kreps 的文章系统阐述了这一思想，也是许多消息系统设计的出发点。[B02](#ref-b02)

事件采集的基本要求：

- 每个事件有唯一编号，重试发送时保持不变。
- 同时记录事件时间与接收时间。
- 事件包含模式版本，便于处理结构变化。
- 敏感信息不写入事件（见 11 章）。

业务系统需要同时更新数据库并发送事件时，可以在同一事务中写入业务数据与待发送事件表，再由独立的进程发送，这种做法常被称为发件箱模式。它避免了“数据库已更新、事件没发出”的不一致，具体设计见[《后端进阶全景手册》第 19 章](../技术方向/后端进阶全景手册.md#ch19)。

#### 05.4 第三方数据与文件

校验格式、字段与数量；保留原始文件；记录来源、接收时间与版本；对外部接口的变化设置监控；与提供方约定数据的含义与更新方式。

#### 05.5 幂等、去重与重放

- 至少一次投递是常态，下游需要按事件编号或业务主键去重。
- 写入使用覆盖分区或按主键合并的方式，重复执行得到相同的结果。
- 原始层保留足够长的时间，出现问题时可以重新处理。

幂等设计的通用方法见[《后端进阶全景手册》第 18 章](../技术方向/后端进阶全景手册.md#ch18)。

**本章验收**：为一张业务表建立增量采集，说明采集方式、删除与结构变更的处理方法以及去重规则；人为制造一次重复发送与一次采集中断，验证结果仍然正确。

<a id="ch06"></a>

### 06 批处理管道

#### 06.1 ETL 与 ELT

ETL 在加载到目标系统之前完成转换；ELT 先加载原始数据，再在仓库中用 SQL 转换。在现代云数据仓库中，ELT 更常见：原始数据得以保留，转换逻辑可以像代码一样版本化管理与评审。

#### 06.2 编排

编排管理任务之间的依赖、调度时间、重试、超时、告警与回填，Apache Airflow 等工具是常见选择。任务设计的原则：一个任务只做一件事，输入与输出明确，失败时能够单独重跑。

#### 06.3 可重跑

- 按分区处理，每次运行覆盖目标分区，或按主键合并。
- 不依赖“当前时间”，而是依赖传入的处理日期参数。
- 不在数据任务中执行不可重复的副作用，例如发送通知；需要时把副作用与数据处理分开。

#### 06.4 增量计算

只处理新增或变化的数据可以节省成本，但需要处理迟到数据与历史更新。常见做法是按更新时间增量合并，同时定期做全量校验，发现增量逻辑遗漏的变化。

#### 06.5 回填

修复逻辑或补充历史时，需要重新运行历史分区。回填前确认：资源占用是否影响日常任务、下游是否也要重新计算、使用者是否需要通知、回填期间使用者看到的是哪个版本的数据。

#### 06.6 测试

| 测试类型 | 检查内容 |
| --- | --- |
| 逻辑测试 | 用小样本数据验证转换逻辑 |
| 数据测试 | 主键唯一、非空、取值范围、引用完整 |
| 对比测试 | 修改逻辑前后结果的差异是否符合预期 |
| 对账 | 与来源或权威数据的行数、金额是否一致 |

**本章验收**：建设一条日级批处理管道：处理日期参数化，按分区覆盖写入，包含数据测试；演示一次失败后的重跑与一次 30 天的回填，结果与预期一致。

<a id="ch07"></a>

### 07 流处理与实时数据

#### 07.1 什么时候真正需要实时

实时管道的建设和运维成本明显高于批处理。先确认：使用者真的需要秒级或分钟级的数据吗？延迟一小时会造成什么损失？很多“实时”需求用小时级甚至更短周期的批处理即可满足。

#### 07.2 事件时间、窗口与水位线

- **事件时间与处理时间**：事件时间是事件实际发生的时间，处理时间是系统处理它的时间。网络延迟、客户端离线都会使两者不同，按处理时间统计会把数据归到错误的时间段。
- **窗口**：按时间段聚合，例如每 5 分钟的分析请求数。
- **水位线**：系统对“某个事件时间之前的数据已基本到齐”的估计，用于决定何时输出窗口的结果。
- **迟到数据**：水位线之后才到达的数据，需要决定丢弃、更新已输出的结果还是单独处理。

Dataflow 模型的论文系统讨论了在无界、乱序的数据上，如何在正确性、延迟与成本之间权衡。[B03](#ref-b03)

#### 07.3 投递语义

| 语义 | 含义 | 代价 |
| --- | --- | --- |
| 至多一次 | 可能丢失，不会重复 | 实现简单，只适合可以容忍丢失的数据 |
| 至少一次 | 不会丢失，可能重复 | 下游需要去重或幂等写入 |
| 精确一次 | 每条数据对结果的影响恰好一次 | 依赖检查点以及事务性或幂等的写入 |

“精确一次”通常指对状态与输出的效果恰好一次，而不是数据在网络上只传输一次。端到端的精确一次需要来源、处理引擎与写入目标都提供相应支持。评估某个系统的“精确一次”时，确认它覆盖的范围是否包含你的来源与写入目标。

#### 07.4 状态、检查点与回放

去重、聚合、关联等有状态的计算需要定期保存检查点，故障后从检查点恢复。修正处理逻辑后，需要能从日志重放历史数据，并替换已经输出的错误结果。

#### 07.5 流批一致

同一指标的实时结果与批处理结果不一致是常见问题。约定哪一个是权威结果（通常是批处理的修正结果），实时结果标明为预估，并定期对账。

**本章验收**：实现一个按事件时间统计的窗口聚合，人为制造乱序与迟到数据，说明结果如何变化；比较实时结果与批处理结果的差异，并写出对账规则。

<a id="ch08"></a>

### 08 存储与计算

#### 08.1 数据仓库、数据湖与湖仓

| 形态 | 特点 | 适合的场景 |
| --- | --- | --- |
| 数据仓库 | 结构化，管理完善，查询性能好 | 报表与分析 |
| 数据湖 | 在对象存储中保存各种格式的数据，成本低 | 原始数据保存、机器学习、大规模处理 |
| 湖仓 | 在数据湖之上通过开放表格式提供事务与模式管理 | 希望分析与机器学习共用同一份数据 |

湖仓架构的提出与论证见 Armbrust 等人在 CIDR 2021 发表的论文。[B04](#ref-b04)

#### 08.2 列式存储与分区

列式格式（如 Parquet）只读取需要的列，压缩率也更高。按日期等常用过滤条件分区，可以减少查询扫描的数据量。分区过细会产生大量小文件，反而降低性能并增加元数据的负担。

#### 08.3 开放表格式

开放表格式在数据文件之上记录表的元数据与快照，提供原子提交、模式演进、读取历史版本、行级更新与删除等能力。Apache Iceberg 的表规范详细描述了这些机制。[B05](#ref-b05) Delta Lake、Apache Hudi 是其他常见的选择。

开放表格式也需要日常维护：合并小文件、清理过期快照、整理删除记录。不维护时，查询会越来越慢，存储成本也会上升。

#### 08.4 计算引擎

可选的计算方式包括仓库自带的查询引擎、分布式批处理引擎（如 Apache Spark）和流处理引擎（如 Apache Flink）。选择时考虑数据量、延迟要求、团队技能与运维成本。数据量在单机能够处理的范围内时，单机工具往往更简单，也更快。

#### 08.5 成本

主要成本包括存储、计算（扫描量与运行时间）和数据传输。常见的节省方法：

- 分区裁剪与列裁剪，只读取需要的数据。
- 生命周期管理：冷数据转入低成本存储，过期数据按保留期限删除。
- 避免重复计算，复用整合层的结果。
- 为每个数据集与任务标注负责人，让成本可见。

**本章练习**：估算一个主要数据集一年的存储与计算成本，找出两项可以降低成本的措施，并估计效果与代价。

<a id="ch09"></a>

### 09 数据质量与数据契约

#### 09.1 质量维度

| 维度 | 含义 | 检查示例 |
| --- | --- | --- |
| 完整性 | 应该有的数据都在 | 每日行数与历史同期相比的波动 |
| 唯一性 | 没有重复 | 主键唯一 |
| 有效性 | 取值符合规则 | 枚举值、范围、格式 |
| 一致性 | 不同来源或不同表之间一致 | 汇总表与明细表对账 |
| 时效性 | 数据按时可用 | 最新分区的到达时间 |
| 准确性 | 与真实情况一致 | 抽样与业务数据核对 |

#### 09.2 测试与监控

在管道中设置两类检查：阻断式检查失败时停止下游任务，告警式检查只发出告警。关键规则使用阻断式检查，避免错误数据流向使用者。同时监控行数、空值率与取值分布的变化，发现规则没有覆盖的异常。

#### 09.3 数据契约

数据契约是数据的提供者与使用者之间关于结构、含义、质量与服务目标的约定，通常包括：字段与类型、字段含义、质量规则、更新时效、负责人与变更流程。开放数据契约标准（ODCS）提供了一种通用的描述格式，便于用工具自动校验。[B06](#ref-b06)

契约的价值在于执行：在提供者的持续集成中检查结构变更是否破坏契约，在使用者一侧检查数据是否满足质量规则。

#### 09.4 模式演进

| 变化 | 通常的兼容性 |
| --- | --- |
| 新增可为空的字段 | 通常兼容 |
| 删除字段 | 不兼容，使用者可能依赖它 |
| 修改字段类型或含义 | 不兼容 |
| 重命名字段 | 不兼容，相当于删除后再新增 |

不兼容的变更需要提前通知，在一段时间内同时提供新旧版本，确认使用者迁移后再下线旧版本。

#### 09.5 数据事故

处理步骤：发现 → 借助血缘评估影响范围 → 通知使用者 → 止损（暂停下游、在数据上标注）→ 修复与回填 → 复盘。事故处理的通用方法见[《运维工程师与 SRE》](13-运维工程师与SRE.md)。

**本章验收**：为一个关键数据集编写契约，包括字段、质量规则、时效与变更流程；为其中的规则建立自动检查，并演练一次上游不兼容变更的处理过程。

## 第三篇：专项与进阶

### 10 元数据、血缘与数据目录

#### 10.1 三类元数据

- **技术元数据**：结构、分区、大小、存储位置。
- **业务元数据**：含义、口径、负责人、敏感级别。
- **运行元数据**：运行时间、处理行数、质量检查结果。

#### 10.2 血缘

血缘记录数据从哪里来、经过哪些加工、流向哪里。它支持三类工作：影响分析（修改一张表会影响谁）、问题溯源（错误的数据来自哪一步）和合规审查（个人信息流向了哪里）。OpenLineage 是一个收集血缘元数据的开放标准，许多编排与计算工具都提供了集成。[B07](#ref-b07)

#### 10.3 数据目录

数据目录帮助使用者查找、理解与申请数据。目录的价值取决于内容是否准确：技术元数据与血缘自动采集，业务含义由负责人维护，并标注数据的可信程度，例如“经过契约与质量检查”或“仅供探索”。

**本章练习**：为一个重要指标画出完整的血缘，从来源表到报表，标出每一步的负责人，并说明修改其中一张表需要通知谁。

<a id="ch11"></a>

### 11 数据安全、隐私与合规

#### 11.1 分类分级

根据数据的敏感程度与重要性分类分级，不同级别采用不同的保护措施。我国《数据安全法》建立了数据分类分级保护制度；《网络数据安全管理条例》自 2025 年 1 月 1 日起施行，对网络数据处理活动提出了更具体的要求。[B08](#ref-b08) 本手册只描述工程做法，具体义务由法务与合规负责人确认。

#### 11.2 访问控制

按最小权限和角色授权，敏感数据单独审批，访问留有记录。避免共享账号与长期有效的高权限凭证，定期复核权限。

#### 11.3 脱敏与去标识

数据进入分析环境前，对敏感字段进行掩码、哈希、泛化或删除。需要注意：取值空间很小的字段（例如手机号）简单哈希后可以通过枚举还原；去标识的数据组合起来仍可能识别个人。相关讨论见[《数据分析师与产品分析师》第 14 章](16-数据分析师与产品分析师.md#ch14)。

#### 11.4 保留与删除

每类数据都应有保留期限。用户删除个人信息的请求需要传递到所有派生数据，包括清洗层与整合层的表、宽表、模型训练数据和向量索引；备份中的数据按备份的保留策略处理。后端的删除与数据退出设计见[《后端进阶全景手册》第 23 章](../技术方向/后端进阶全景手册.md#ch23)。

#### 11.5 管道自身的安全

管道使用的凭证妥善保管并定期轮换，数据在传输与存储中加密，第三方工具对数据的访问经过评估。系统性的安全方法见[《安全工程师》](12-安全工程师.md)。

**本章练习**：为一个数据集做分类分级，列出敏感字段与处理方式；设计一个用户删除请求在各层数据中的处理流程，并说明怎样确认处理完成。

<a id="ch12"></a>

### 12 可靠性、可观测性与成本

#### 12.1 数据的服务目标

为关键数据设定服务目标，例如“每天 6:00 前完成前一日的数据，每月达成率不低于 99%”“关键表重复率为 0”。目标与使用者一起确定，并公开达成情况。服务目标的通用方法见[《运维工程师与 SRE》](13-运维工程师与SRE.md)。

#### 12.2 可观测性

- **管道层面**：运行状态、耗时、失败率、重试次数。
- **数据层面**：新鲜度、行数、质量检查结果。
- **成本层面**：每个任务与数据集的计算与存储成本。

告警要能够处理：说明影响、负责人与处理手册。只会响却没人知道怎么办的告警，很快会被忽视。

#### 12.3 常见的可靠性问题

上游延迟、资源争抢、数据倾斜、小文件过多、任务依赖形成环、凭证过期、时区与夏令时处理错误。为关键管道准备处理手册，写明每类问题的判断与处理方法。

#### 12.4 成本治理

为数据集与任务标注负责人；定期清理无人使用的数据集与任务；按使用者分摊成本；为大型查询设置限额与审批。

**本章验收**：为关键管道设定服务目标，建立新鲜度与质量的监控面板，统计一个月的达成情况，并分析每一次未达成的原因。

<a id="ch13"></a>

### 13 数据平台与自助服务

#### 13.1 平台即产品

数据平台的使用者是分析师、算法工程师与开发者。用产品的方式运营平台：了解使用者的任务，提供模板与文档，度量使用情况与满意度。平台工程的通用方法见[《平台工程师与研发效能》](14-平台工程师与研发效能.md)。

#### 13.2 数据网格

组织规模变大后，集中式的数据团队容易成为瓶颈。数据网格提出四个原则：按业务领域负责数据、数据作为产品、自助的数据基础设施平台、联邦式的计算治理。[B09](#ref-b09) 它是组织与架构层面的方法，需要领域团队具备相应的数据能力，并不适合所有组织。

#### 13.3 自助的护栏

- 模板化的管道，默认包含测试、监控与文档。
- 默认开启的质量检查与成本统计。
- 清楚的权限申请与审批流程。
- 每个数据集都有负责人与生命周期。

**本章练习**：访谈三位数据使用者，列出他们使用数据时最耗时的三个环节，设计一个能减少其中一项耗时的平台功能，并定义衡量效果的指标。

<a id="ch14"></a>

### 14 为机器学习与 AI 提供数据

#### 14.1 训练数据

- **时点正确**：构建训练样本时，只能使用样本发生时已经存在的数据，否则会把未来信息泄漏给模型，使离线效果虚高。
- **可复现**：记录数据版本、抽取条件与处理代码，能够重新生成同一份训练数据。
- **标签质量**：说明标签的来源与标注规则，检查标注的一致性。
- **线上线下一致**：训练时计算特征的逻辑与线上服务时一致，避免离线效果好、上线后变差。

#### 14.2 检索增强生成的数据管道

| 环节 | 要点 |
| --- | --- |
| 采集 | 来源、更新频率，原文删除后同步删除 |
| 解析 | 文档格式、表格与图片的处理，解析质量检查 |
| 切分 | 切分粒度，保留必要的上下文 |
| 向量化 | 记录向量模型的版本，更换模型需要重新生成 |
| 索引与元数据 | 来源、时间、权限标签，便于过滤与溯源 |
| 权限 | 检索结果遵守原文档的访问权限 |
| 评测 | 维护评测问题集，评估检索质量 |

检索与评测的方法见[《后端进阶全景手册》第 22 章](../技术方向/后端进阶全景手册.md#ch22)，AI 应用的后端设计见[第 32 章](../技术方向/后端进阶全景手册.md#ch32)。

#### 14.3 与算法工程师的协作

约定特征与训练数据的负责人、更新频率与质量要求，共同监控数据分布的漂移。详见[《算法与机器学习工程师》](18-算法与机器学习工程师.md)。

**本章练习**：为一个模型构建训练数据集，说明样本的时间点与特征的截止时间，记录数据版本，并验证能够重新生成同一份数据。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与开发者的协作接口

#### 15.1 数据工程师需要开发者提供的内容

| 内容 | 最低要求 | 常见缺失 |
| --- | --- | --- |
| 业务表的结构与含义 | 字段说明、主键、状态取值 | 状态值的含义只写在代码里 |
| 变更通知 | 结构变更提前通知 | 上线后下游才发现 |
| 可靠的时间字段 | 创建时间与更新时间，含时区 | 部分操作不更新“更新时间” |
| 删除方式 | 说明物理删除还是软删除 | 增量抽取无法识别物理删除 |
| 事件设计 | 唯一编号、事件时间、模式版本 | 重试时生成新的编号 |

#### 15.2 数据工程师应提供给开发者的内容

数据契约、可用的数据集与访问方式、影响分析（修改业务表会影响哪些下游）、读取方式的约束（例如不在业务库上运行大型分析查询，改用只读副本或数据仓库）。

#### 15.3 共同的做法

- 把业务表结构变更纳入评审，涉及下游的变更通知数据负责人。
- 在持续集成中检查数据契约。
- 发布记录同步给数据团队，便于解释数据的变化。
- 重要的业务事实以业务库或服务端记录为权威来源。

<a id="ch16"></a>

### 16 开发者怎样借用数据工程方法

#### 16.1 小团队与独立开发者

- 数据量不大时，从只读副本或每日导出开始，在轻量的分析数据库中用 SQL 加工。
- 转换逻辑写成版本化的 SQL 文件，而不是散落在报表工具里。
- 定时任务的处理日期参数化，可以重跑。
- 为关键表写最基本的数据测试：主键唯一、非空、行数波动。
- 等数据量与团队规模确实需要时，再引入分布式系统。

#### 16.2 外包与交付项目中的数据工作

数据迁移是交付项目中风险最高的工作之一：字段映射、清洗规则、对账方法、切换与回退方案都需要与客户书面确认，并在正式切换前完成至少一次完整演练。报表需求要在需求阶段确定口径，上线后才补采历史数据通常不可行。交付时移交数据字典、管道说明与运维手册。实施与迁移的方法见[《实施与交付工程师》](23-实施与交付工程师.md)。

#### 16.3 技术背景的常见偏差

- 直接在业务库上运行分析查询，影响线上服务。
- 用定时任务复制数据，没有去重与重跑方案。
- 只关心数据能否进来，不关心含义与质量。
- 把个人信息原样复制到分析环境。

### 17 贯穿实战：求职平台的数据管道

本章以求职平台为例，展示一次完整的数据工程工作。数字均为示意。

#### 17.1 需求

| 使用者 | 需求 | 时效 |
| --- | --- | --- |
| 数据分析师 | 简历分析功能的指标与实验分析 | 每天 6:00 前可用 |
| 算法工程师 | 岗位匹配模型的训练数据 | 每周更新，可复现 |
| 运营 | 每日运营报表 | 每天 8:00 前可用 |

#### 17.2 来源与采集

| 来源 | 内容 | 采集方式 |
| --- | --- | --- |
| 业务库 | 用户、简历版本、分析任务、建议、岗位 | 变更数据捕获 |
| 交互事件 | 上传、提交分析、标记建议等 | 事件采集服务 |
| 实验配置 | 用户的分组记录 | 每日导出 |

隐私设计：简历原文不进入分析环境；分析环境中只保留简历的结构化特征（例如工作年限区间、技能标签），用户以假名化的编号关联；能够还原真实身份的映射表单独存放，访问需要审批。

#### 17.3 模型

- **事实表**：分析任务（粒度为一次分析任务）、建议标记（粒度为一条建议的一次标记）。
- **维度**：用户（按类型 2 记录在校生、毕业生等身份的变化）、日期、岗位类别、模型版本。
- **应用层**：分析功能的每日汇总，供看板与实验分析使用。

#### 17.4 契约与质量

- 与后端约定分析任务表的契约：状态取值、更新时间、删除方式；结构变更提前一周通知。
- 阻断式检查：分析任务主键唯一；事件编号唯一；每日完成数与业务库的差异小于 0.5%。
- 告警式检查：最新分区在 5:30 前到达；各状态的占比与上周相比波动不超过设定范围。

#### 17.5 一次数据事故

1. **现象**：某天看板显示分析完成数比前一天高约 3%，分析师在对账时发现与业务库不一致。
2. **原因**：客户端重试时为同一次完成生成了新的事件编号，去重失效。
3. **处理**：暂停应用层更新并在看板上标注；改为以服务端的任务状态为完成数的权威来源；与开发者修正事件编号的生成方式；回填受影响的 3 天分区；通知分析师重新计算期间的实验结果。
4. **预防**：增加“事件完成数与任务表完成数差异”的阻断式检查；在事件契约中写明重试时编号保持不变。

#### 17.6 删除请求

用户注销后，业务库删除其个人信息；管道在下一次运行时删除或匿名化各层中该用户的数据，训练数据集在下一个版本中排除该用户，向量索引中的相关内容同步删除；处理结果记录在案，便于核查。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 实时总是比批处理好 | 实时的成本更高，先确认使用者对时效的真实需要 |
| 数据湖可以先存了再说 | 没有目录与治理的数据湖难以使用，还带来隐私与成本风险 |
| 精确一次意味着数据只传输一次 | 指对结果的效果恰好一次，依赖来源与写入目标的支持 |
| 管道跑通就可以上线 | 还需要测试、监控、重跑与回填方案 |
| 宽表越多使用越方便 | 重复的宽表会导致口径分化与维护困难 |
| 加一个字段不会影响下游 | 通常兼容，但仍需检查依赖全部字段或字段顺序的用法 |
| 哈希之后就是匿名数据 | 取值空间小的字段哈希后可能被枚举还原 |
| 删除业务库的数据就完成了删除 | 派生数据、训练数据与向量索引也需要处理 |
| 数据量大就必须用分布式系统 | 很多场景用单机工具或云数据仓库即可满足 |
