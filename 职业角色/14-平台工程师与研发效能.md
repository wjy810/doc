# 平台工程师与研发效能工程师进阶全景手册

> 从把重复的开发与交付步骤自动化，到为团队建设好用的内部平台，再到用证据改进组织的研发效能与开发者体验。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：经常为团队搭建工具、流水线和环境的开发者，准备转向平台工程、DevOps 或研发效能方向的工程师，以及希望系统提升的在职平台工程师。

平台工程师要回答的核心问题是：怎样让开发团队以更少的认知负担、更短的等待和更可靠的方式，把代码变成在生产中运行的服务。随着系统和团队规模增长，每个团队都要处理环境、构建、部署、监控、权限、数据库、安全扫描等大量与业务无关的工作。如果每个团队各自摸索，就会出现重复建设、做法不一致和大量隐性成本。平台工程把这些共同需求做成可自助使用的产品，让业务团队专注于业务。

研发效能工程师关注的是更广的问题：开发者在哪里浪费时间、哪些流程拖慢了交付、怎样用可信的数据衡量并改进。两者常常在同一个团队中：平台提供能力，效能度量说明哪里最需要改进、改进是否有效。

本手册先建立角色坐标，然后讲解平台即产品、黄金路径与自助服务、持续集成与交付、开发环境与构建系统、开发者门户、研发效能度量、开发者体验研究；随后进入基础设施抽象、平台的可靠性与安全、内部开源、AI 辅助开发、平台团队的组织；最后说明平台团队与开发团队的协作，并用求职平台演示一次黄金路径建设。

主线是：**理解开发团队的需要与阻碍 → 把平台当作产品来设计 → 提供黄金路径与自助服务 → 缩短反馈与交付周期 → 用多维证据度量效能 → 持续改进开发者体验 → 让平台团队与业务团队有效协作。**

不同公司中，这些职责可能由平台工程师、DevOps 工程师、基础设施工程师、工程效率团队或研发效能团队承担。本手册描述平台与研发效能的职责本身；D1—D6 分级是学习组织方式，不对应任何职级体系。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 平台工程师与研发效能工程师负责什么

#### 01.1 平台是什么

在软件组织中，平台是一组能力、工具与服务的集合，让使用它的团队能够自助、一致地完成某类工作，例如创建一个新服务、获得一个数据库、部署到生产环境、查看监控。云原生计算基金会（CNCF）的平台工作组发布了关于平台的白皮书与平台工程成熟度模型，说明平台的价值在于减少使用者的认知负担，并提供一致的、可自助的体验。[B01](#ref-b01)

一个常被引用的观点是：好的平台像一个产品，它的价值由使用者的采用程度与获得的收益决定，而不是由它包含多少技术组件决定。[B02](#ref-b02)

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 黄金路径与模板 | 让常见任务有推荐的做法 | 开箱即用，覆盖安全与可观测性，能被偏离 |
| 自助服务 | 无需等待就能获得资源 | 有清楚的接口与文档，有安全的默认值 |
| 持续集成与交付流水线 | 快速可靠地交付 | 反馈快、稳定、可追溯 |
| 开发环境与构建工具 | 让开发高效 | 可复现、启动快、构建快 |
| 开发者门户与服务目录 | 统一入口与所有权信息 | 信息准确、能找到负责人与文档 |
| 效能度量与报告 | 发现瓶颈、验证改进 | 多维度、团队可理解、不用于考核个人 |
| 平台文档与支持 | 让使用者自主使用 | 以任务组织，有示例，支持渠道清楚 |

#### 01.3 职责边界与相邻角色

| 事项 | 平台工程师的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 平台能力与路线图 | 主导 | 业务团队、架构师 | 平台路线图由使用者的需要驱动 |
| 业务服务的开发与运行 | 支持 | 业务团队主导 | 业务团队对自己的服务负责 |
| 可靠性标准与事故 | 协作 | SRE | 见[《运维工程师与 SRE》](13-运维工程师与SRE.md) |
| 安全工具与流程 | 协作 | 安全工程师 | 安全检查内置到平台中 |
| 数据库与数据平台 | 协作 | DBA、数据工程师 | |
| 研发流程与组织 | 提供证据 | 研发经理 | 见[《研发经理与工程经理》](25-研发经理与工程经理.md) |

平台工程与 DevOps、SRE 的关系：DevOps 强调开发与运维共同负责；SRE 用工程方法管理可靠性；平台工程把这些实践做成可复用的产品，让每个团队不必从零开始。

#### 01.4 不同组织中的形态

- **小团队**：没有专门的平台团队，由一两名资深开发者维护流水线与环境。
- **中型组织**：设立平台团队，提供标准的部署、监控与环境。
- **大型组织**：多个平台团队分别负责开发者门户、构建系统、运行平台、数据平台等；有专门的研发效能团队负责度量与研究。

**本章练习**：记录你一周内花在与业务无关的工程事务上的时间（等待构建、搭建环境、处理部署问题、寻找文档和负责人），按类别统计，找出最大的一项。

<a id="ch02"></a>

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **平台产品管理**：理解使用者，规划路线图，推动采用。
2. **黄金路径与模板**：为常见任务提供推荐做法。
3. **持续集成与交付**：流水线、发布与制品管理。
4. **开发环境与构建**：可复现的环境、快速的构建与测试。
5. **基础设施抽象**：在云与编排平台之上提供更简单的接口。
6. **开发者门户与目录**：服务目录、所有权、文档与评分。
7. **效能度量**：交付指标、开发者体验与系统数据。
8. **开发者体验研究**：访谈、调查与摩擦分析。
9. **平台可靠性与安全**：平台自身的稳定、安全与供应链。
10. **组织与协作**：团队拓扑、内部开源与支持模式。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 维护流水线与脚本，解决常见的构建与部署问题 | 修复记录、脚本 |
| D2 独立完成 | 独立建设一项平台能力（如服务模板、部署流水线） | 能力文档、采用情况 |
| D3 负责结果 | 对一个平台领域的采用与效果负责 | 采用率、交付指标改善、满意度 |
| D4 系统与跨团队 | 设计跨团队的内部开发者平台 | 平台架构、黄金路径、服务目录 |
| D5 方法与机制 | 建立组织的研发效能度量与改进机制 | 度量体系、开发者体验调查、改进流程 |
| D6 创新与影响 | 创造被广泛采用的平台工具或方法 | 开源项目、公开研究 |

#### 02.3 成长中的常见偏差

- 先建设“完整的平台”，再寻找使用者，结果没人采用。
- 把平台做成强制的关卡，团队只能等待平台团队处理。
- 抽象过度，隐藏了团队需要理解和控制的细节。
- 只度量容易获得的数据（例如提交次数），用来评价个人。
- 平台本身不稳定，一次故障影响所有团队。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 平台即产品

#### 03.1 了解使用者

平台的使用者是开发团队。像产品经理研究用户一样研究他们：他们在做什么、遇到什么阻碍、现在怎样绕过、哪些事情最耗时（见 09 章）。不同团队的需求可能差异很大，例如新业务团队需要快速起步，成熟团队需要稳定与可控。

#### 03.2 价值与采用

平台的价值体现在使用者的收益上：新服务上线所需的时间、发布的频率与成功率、事故的减少、开发者满意度的提高。衡量平台时，看采用率与使用者的结果，而不是平台包含了多少功能。采用应主要靠平台好用，而不是靠强制；当某项能力必须统一（例如安全扫描），也要让它尽量不增加负担。

#### 03.3 最薄可行平台

不要一开始就建设大而全的平台。从最痛的问题开始，提供最薄的一层能力：可能只是一份清楚的文档和一个模板，然后根据使用反馈逐步扩展。《Team Topologies》提出了“最薄可行平台”的说法，强调平台应保持足够小，只做真正有价值的部分。[B03](#ref-b03)

**本章练习**：为你的团队写一页平台产品简报：使用者、最痛的三个问题、第一项要提供的能力、成功的度量方式。

<a id="ch04"></a>

### 04 黄金路径与自助服务

#### 04.1 黄金路径

黄金路径（也称铺好的路）是平台为常见任务提供的推荐做法，例如“用 Java 构建一个 Web 服务”的模板：包含项目结构、构建配置、测试框架、日志与指标、健康检查、容器化、部署流水线、安全扫描与文档模板。走黄金路径的团队能在很短时间内得到一个符合组织标准的服务。

黄金路径的关键是：

- **默认就好**：安全、可观测性、可靠性的最佳实践都已内置。
- **可以偏离**：有特殊需要的团队可以偏离，但需要自己承担相应的责任。
- **持续维护**：模板与依赖随时间更新，已有服务能获得更新。

#### 04.2 自助服务

自助服务让团队无需提交工单、等待他人，就能获得需要的资源：创建服务、申请数据库、配置域名与证书、开通监控。自助服务需要清楚的接口、安全的默认值、权限控制与成本可见。

#### 04.3 护栏而不是关卡

关卡要求每次变更都经过人工审批；护栏在自动化流程中检查并阻止明显的错误，允许大多数变更自动通过。例如：在流水线中自动检查依赖漏洞与配置错误，而不是让安全团队逐个审批发布。

**本章验收**：为一种常见的服务类型建设黄金路径模板，邀请两个团队试用，统计从创建到首次部署到生产的时间，并收集改进意见。

<a id="ch05"></a>

### 05 持续集成与交付流水线

#### 05.1 快速反馈

开发者提交代码后，越快得到反馈越好。缩短反馈时间的方法：缓存依赖与构建结果、并行执行测试、只运行受影响的测试、把耗时的检查放到合并之后、修复不稳定的测试。

#### 05.2 主干开发与小批量

主干开发让开发者频繁地把小的修改合并到主干，减少长期分支带来的合并冲突与集成风险。[B04](#ref-b04) 它需要配合自动化测试、功能开关与代码评审。

#### 05.3 流水线的组成

| 阶段 | 内容 |
| --- | --- |
| 构建 | 编译、打包，生成唯一可追溯的制品 |
| 检查 | 单元测试、静态分析、依赖与密钥扫描 |
| 集成验证 | 集成测试、契约测试 |
| 部署 | 同一制品依次部署到各环境，渐进发布到生产 |
| 验证 | 自动比较新旧版本的指标，异常时停止 |

制品的可追溯性与供应链安全见[《后端进阶全景手册》第 14 章](../技术方向/后端进阶全景手册.md#ch14)。

**本章验收**：测量团队流水线从提交到可部署的时间，找出最慢的三个步骤，实施优化后再测量。

<a id="ch06"></a>

### 06 开发环境与构建系统

#### 06.1 可复现的开发环境

新成员加入或切换项目时，花费大量时间搭建环境是常见的浪费。可以用容器化的开发环境（例如开发容器规范）描述项目需要的工具、依赖与配置，让环境一键可得。[B05](#ref-b05) 同时提供本地运行依赖服务的方式与测试数据。

#### 06.2 构建系统

大型代码库的构建速度直接影响开发效率。增量构建、远程缓存、并行执行和依赖图分析能显著缩短构建时间。选择构建系统时，权衡速度与学习、维护成本。

#### 06.3 单仓库与多仓库

| 方式 | 优点 | 代价 |
| --- | --- | --- |
| 单仓库 | 统一的依赖版本、原子的跨项目修改、便于代码复用与搜索 | 需要强大的构建工具与权限管理 |
| 多仓库 | 团队独立、边界清楚、工具简单 | 依赖版本分散，跨仓库修改困难 |

两种方式都可以成功，关键是配套的工具与规范。

**本章练习**：让一位新成员按文档搭建开发环境，记录耗时与遇到的问题，改进后让另一位新成员再试一次。

<a id="ch07"></a>

### 07 开发者门户与服务目录

#### 07.1 服务目录

服务目录记录组织中的每个服务、库、数据集与基础设施：负责团队、文档、依赖关系、运行状态、值班信息。当事故发生、需要修改依赖或寻找某项能力时，服务目录让人快速找到需要的信息。所有权信息尤其重要：没有负责人的服务是风险。

#### 07.2 开发者门户

开发者门户把服务目录、模板、文档、自助服务与工具集中到一个入口。Backstage 是常用的开源开发者门户框架。[B06](#ref-b06) 门户本身不解决问题，关键在于其中的信息准确、能力好用。

#### 07.3 评分卡

评分卡按组织的标准检查每个服务的状态，例如是否有负责人、是否有运行手册、依赖是否过期、是否接入监控。评分卡用于帮助团队发现改进点，而不是排名与惩罚。

**本章练习**：为团队的服务建立目录，填写负责人、文档、依赖与值班信息，设计一个包含 5 项检查的评分卡。

<a id="ch08"></a>

### 08 研发效能度量

#### 08.1 交付表现

DORA 用五项指标衡量软件交付表现：变更前置时间、部署频率、失败部署的恢复时间、变更失败率与部署返工率。[B07](#ref-b07) 这些指标适合观察团队交付系统的整体表现与趋势。

#### 08.2 多维度看待效能

研发效能不能用单一指标衡量。SPACE 框架提出从满意度与幸福感、表现、活动、沟通与协作、效率与流动五个维度看待开发者效能，并建议同时使用多个维度、结合主观与客观数据。[B08](#ref-b08) 开发者体验（DevEx）研究进一步指出，影响开发者效能的三个核心因素是反馈回路、认知负担与心流状态，并建议把开发者的感受与系统数据结合起来衡量。[B09](#ref-b09)

#### 08.3 度量的陷阱

| 陷阱 | 说明 |
| --- | --- |
| 度量个人 | 提交次数、代码行数无法反映贡献，用于考核会扭曲行为 |
| 只看活动 | 活动多不等于产出好 |
| 单一指标 | 任何单一指标都可能被“优化”而失去意义 |
| 忽视主观感受 | 开发者的感受能揭示系统数据看不到的问题 |
| 只度量不行动 | 度量的价值在于指导改进并验证效果 |

**本章验收**：为一个团队建立包含交付指标、系统数据与开发者调查的效能看板，选择一项改进，在一个季度后比较变化。

<a id="ch09"></a>

### 09 开发者体验研究

#### 09.1 研究方法

- **访谈**：了解开发者日常工作中的阻碍与绕过方式。
- **调查**：定期了解满意度、认知负担与主要阻碍，追踪趋势。
- **摩擦日志**：请开发者在完成一项任务时记录每一个让人停下来或困惑的地方。
- **旅程分析**：分析从需求到上线的完整过程中的等待与交接。
- **系统数据**：构建时间、流水线等待、评审等待、环境故障。

研究方法与用户研究相同（见[《用户研究员》](02-用户研究员.md)），只是“用户”是开发者。

#### 09.2 从发现到行动

把发现按影响范围与改进成本排序，选择少数几项集中改进，并告诉开发者“我们听到了什么、做了什么、结果如何”。让开发者看到反馈产生了改变，是维持调查参与度的关键。

**本章练习**：请三位开发者在完成一项常见任务（如新增一个接口并上线）时记录摩擦日志，汇总后找出最常见的阻碍，提出改进方案。

<a id="part-3"></a>

## 第三篇：专项与进阶

<a id="ch10"></a>

### 10 基础设施抽象与策略

#### 10.1 抽象的层次

在云与编排平台之上，平台可以提供不同层次的抽象：只提供标准化的配置模板；提供更简单的服务描述，由平台生成底层配置；提供完全托管的运行环境。抽象越高，使用越简单，但灵活性越低。好的抽象隐藏不必要的复杂度，同时保留团队需要理解和控制的部分（例如资源限制、扩缩容、故障行为）。

#### 10.2 策略即代码

把组织的规则写成可自动执行的策略，例如“容器不能以特权模式运行”“存储桶不能公开”“生产部署必须有负责人”。开放策略代理（OPA）等工具支持在部署与准入时检查策略。[B10](#ref-b10) 策略需要清楚的错误信息，告诉团队怎样修复，而不只是拒绝。

#### 10.3 成本可见

让每个团队看到自己服务的资源使用与成本，并提供优化建议。成本可见是团队做出合理取舍的前提。

**本章练习**：为一项常见的安全或成本规则编写策略，接入部署流程，检查错误信息是否能让团队自己修复问题。

<a id="ch11"></a>

### 11 平台的可靠性与安全

#### 11.1 平台的影响范围

平台的故障会影响所有使用它的团队：流水线不可用，所有团队都无法发布；配置平台出错，所有服务都可能受影响。平台需要更高的可靠性标准：服务等级目标、变更的渐进发布、隔离与降级、事故响应（见[《运维工程师与 SRE》](13-运维工程师与SRE.md)）。

#### 11.2 流水线与供应链安全

流水线拥有很高的权限：访问代码、密钥、制品仓库与生产环境。需要保护：最小权限、短期凭证、隔离的构建环境、制品签名与来源记录、依赖与密钥扫描（见[《安全工程师》第 08 章](12-安全工程师.md#ch08)）。

**本章练习**：审查团队流水线的权限与密钥管理，找出过宽的权限与长期有效的凭证，制定整改计划。

<a id="ch12"></a>

### 12 内部开源与知识共享

#### 12.1 内部开源

内部开源把开源的协作方式用于组织内部：代码对内公开，其他团队可以提交修改，维护者负责评审与合并。它能减少“只能等待平台团队”的瓶颈，让使用者参与改进。InnerSource Commons 社区整理了内部开源的模式与实践。[B11](#ref-b11)

#### 12.2 文档与支持

平台的文档以任务组织（“怎样创建一个服务”“怎样排查部署失败”），配合示例与常见问题。支持渠道要清楚：哪些问题在文档中自助解决，哪些通过讨论群，哪些需要工单。分析支持请求，把重复的问题转化为文档或产品改进（见[《技术写作者与文档工程师》](24-技术写作者与文档工程师.md)）。

**本章练习**：统计一个月的平台支持请求，找出最常见的 5 类，为其中 3 类编写文档或改进平台，下个月比较请求数量。

<a id="ch13"></a>

### 13 AI 辅助开发与平台

#### 13.1 AI 编码助手的引入

AI 编码助手已被广泛使用。DORA 在 2025 年关于 AI 辅助软件开发的研究中认为，AI 的主要作用像一个放大器：放大高绩效组织的优势，也放大困难组织的问题。[B12](#ref-b12) 这意味着引入 AI 工具本身不能自动提高效能，配套的工程实践（测试、评审、小批量交付、清楚的文档）更为重要。

#### 13.2 平台团队的职责

- **治理**：选择符合数据与安全要求的工具，明确哪些代码与数据可以发送给外部服务。
- **集成**：把 AI 工具接入开发环境、代码评审与流水线。
- **上下文**：让 AI 工具能获得组织的文档、规范与代码结构，提高建议的相关性。
- **质量保护**：AI 生成的代码同样需要测试、评审与安全扫描；关注许可证与依赖问题。
- **度量**：用交付指标、质量指标与开发者体验衡量影响，而不是只看“生成了多少代码”。

#### 13.3 自动化代理

越来越多的团队在流水线中使用 AI 代理完成依赖升级、测试补全、缺陷修复等任务。需要为代理设定清楚的权限、审查流程与回退方式，并把它们的修改与人类的修改一样纳入评审。

**本章练习**：为团队引入 AI 编码助手制定使用规范（数据、评审、测试、许可证），选择两项指标在引入前后比较。

<a id="ch14"></a>

### 14 平台团队的组织与演进

#### 14.1 团队拓扑

《Team Topologies》描述了四种团队类型（流对齐团队、平台团队、赋能团队、复杂子系统团队）与三种协作方式（协作、作为服务提供、促进）。[B03](#ref-b03) 平台团队的目标是以“作为服务提供”的方式，减少流对齐团队的认知负担；在探索新能力时，可以与使用团队短期协作；在推广新实践时，可以由赋能团队提供帮助。

#### 14.2 避免平台团队成为瓶颈

- 能力以自助服务提供，而不是靠工单。
- 通过内部开源让使用者参与贡献。
- 明确平台与业务团队的责任边界。
- 平台的路线图公开，接受使用者的反馈。

#### 14.3 成熟度

CNCF 的平台工程成熟度模型从投入、采用、界面、运营与度量等方面描述平台的成熟度，可用于评估现状与规划下一步。[B13](#ref-b13)

**本章练习**：用团队拓扑的概念画出你所在组织的团队与协作方式，找出认知负担过重或协作方式不合适的地方。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与开发团队的协作接口

#### 15.1 平台团队应提供给开发团队的内容

| 内容 | 最低要求 | 常见缺失 |
| --- | --- | --- |
| 能力与边界 | 平台负责什么、团队负责什么 | 责任不清，出问题互相推诿 |
| 文档与示例 | 以任务组织，可直接使用 | 只有参考说明 |
| 变更通知 | 提前通知、迁移指南与期限 | 平台变更导致团队构建失败 |
| 支持渠道 | 响应时限与升级路径 | 问题无人回应 |
| 路线图 | 公开并接受反馈 | 团队不知道平台的计划 |

#### 15.2 开发团队应反馈给平台团队的内容

阻碍与痛点、偏离黄金路径的原因、对平台变更的意见、事故中平台的问题。

#### 15.3 一起改进

邀请业务团队参与平台能力的设计与试用；对于重要的变更，先在少数团队中试点；定期举行平台的用户反馈会。

<a id="ch16"></a>

### 16 开发者怎样改进自己团队的效能

#### 16.1 从最痛的地方开始

- 测量团队的构建、测试与部署时间，找出最慢的环节。
- 修复不稳定的测试，它们浪费大量时间并损害信任。
- 把重复的手工步骤写成脚本，再把脚本放进流水线。
- 为新成员写一份能真正跑通的环境搭建文档。
- 减少等待：评审等待、环境等待、他人审批。

#### 16.2 独立开发者与外包项目

独立开发者可以从一开始就使用托管的持续集成与部署服务，保持“一条命令构建、一条命令部署”。外包项目交付时，把构建、测试与部署流水线一并交付给客户，并提供文档，这能显著降低客户后续维护与再开发的成本。

<a id="ch17"></a>

### 17 贯穿实战：为求职平台团队建设黄金路径

本章展示一次平台建设。数字均为示意。

#### 17.1 起点

求职平台的工程团队扩展到 4 个小组。调查发现：新建一个服务从创建仓库到第一次部署到生产平均需要两周；各服务的日志格式、指标、部署脚本各不相同；流水线平均需要 35 分钟，其中三分之一的失败由不稳定的测试导致。

#### 17.2 第一步：最薄的黄金路径

平台小组（2 人）先做一件事：Java 服务的黄金路径模板。内容包括项目结构、构建配置、统一的日志与指标、健康检查、容器化、部署流水线（含测试、依赖与密钥扫描、渐进发布）、运行手册模板。邀请正在启动新服务的岗位搜索小组试用。

#### 17.3 改进流水线

- 为依赖与构建结果启用缓存，测试并行执行。
- 建立不稳定测试的跟踪，每周修复最常失败的 5 个。
- 把耗时的端到端测试移到合并之后运行。

#### 17.4 结果与度量

| 指标 | 之前 | 三个月后 |
| --- | --- | --- |
| 新服务首次部署到生产 | 约两周 | 约一天 |
| 流水线时长（中位数） | 35 分钟 | 12 分钟 |
| 由不稳定测试导致的失败 | 约三分之一 | 低于十分之一 |
| 开发者调查中“构建与部署”满意度 | 低 | 明显提高 |

#### 17.5 下一步

调查中排名第一的新问题是“不知道某个服务由谁负责”。平台小组建立服务目录，要求每个服务登记负责人与值班信息，并在开发者门户中提供统一入口。

#### 18.5 检查清单

- [ ] 平台能力从使用者最痛的问题出发，并有采用与效果的度量。

- [ ] 流水线反馈快速稳定，不稳定测试被跟踪修复。

- [ ] 平台自身有服务等级目标与渐进发布。
- [ ] 平台变更提前通知并提供迁移指南。
- [ ] AI 编码工具有使用规范，影响用多维指标评估。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 平台就是 Kubernetes | 平台是一组面向开发团队的能力，Kubernetes 只是可能的基础之一 |
| 平台建好了团队自然会用 | 平台需要像产品一样研究使用者并推动采用 |
| 平台应该强制所有团队使用 | 好的平台靠好用被采用，必须统一的部分也要尽量减少负担 |
| 抽象得越多越好 | 过度抽象会隐藏团队需要理解和控制的细节 |
| 研发效能可以用提交次数衡量 | 效能需要多维度衡量，活动数量不等于产出 |
| 效能指标可以用来考核个人 | 指标用于团队改进，用于考核会被扭曲 |
| 引入 AI 工具就能提高效能 | AI 会放大已有的优势与问题，需要配套的工程实践 |
| 平台团队负责所有基础设施问题 | 平台提供能力，业务团队对自己的服务负责 |
