# 产品经理进阶全景手册

> 从判断一个功能值不值得做，到对一条产品线的结果负责，再到建立组织的产品决策方法。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：准备转向产品岗位的开发者与设计者、需要兼任产品职责的独立开发者和外包负责人、希望系统提升的在职产品经理。

产品经理要回答的核心问题是：在有限的时间、人力和资金下，为哪些用户解决哪些问题，做到什么程度，以及怎样知道这件事做对了。这个职位常被误解为“写需求文档的人”“排期的人”或“上级意见的传声筒”。文档和排期只是手段；产品经理真正负责的是一条从问题到结果的判断链，并让团队能够依据证据持续修正这条链。

本手册把产品工作拆成可以练习和验收的部分：先建立角色坐标，再依次学习理解用户与业务、定义问题和成功标准、发现与验证方案、表达需求、确定优先级、协作交付、衡量结果；随后进入商业、B 端与平台、AI 产品、战略与组织、信任与合规等专项；最后说明产品经理与开发者怎样协作，以及开发者在独立产品和外包项目中怎样借用这些方法。

主线是：**理解用户与业务 → 定义问题与成功标准 → 发现并验证方案 → 决定范围与优先级 → 与团队交付 → 衡量结果并学习 → 形成产品战略与组织方法。**

不同公司对“产品经理”“产品负责人”“产品运营”的分工差异很大，小团队中产品职责也常由创始人、技术负责人或设计师兼任。本手册描述产品职责本身，而不是某一家公司的岗位说明书；D1—D6 分级是学习组织方式，不对应任何职级体系。涉及法律、定价和合规的内容只说明产品决策需要考虑的问题，具体义务由相应负责人确认。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 产品经理负责什么

#### 01.1 核心问题：四类风险

产品失败通常不是因为代码写错，而是因为做了没人需要的东西、用户用不明白、团队做不出来，或者做出来以后公司无法持续支持。SVPG 把这些概括为四类风险：**价值**（用户是否愿意使用或购买）、**可用性**（用户能否弄明白怎么用）、**可行性**（团队能否在时间、技能和技术条件内做出来）、**商业可行性**（方案能否与销售、成本、法律、品牌等业务约束相容）。在这一分工中，产品经理主要对价值和商业可行性负责，可用性和可行性分别以设计负责人和工程负责人为主，但四类风险需要在同一场讨论中共同权衡。[B01](#ref-b01)

产品经理的价值体现在两件事上：让团队把有限资源投入到最可能产生结果的问题上；尽早发现错误判断，并以较低代价修正。文档、原型和路线图都是服务于这两件事的载体，本身不是成果。

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 产品愿景与战略 | 说明长期方向和取舍 | 能解释不做什么，能指导具体优先级 |
| 问题陈述与目标 | 统一团队对“为什么做”的理解 | 有目标用户、情境、证据和可测量的成功标准 |
| 机会与假设清单 | 管理不确定性 | 区分已验证事实、合理推测和待验证假设 |
| 需求说明 | 让团队理解范围和验收方式 | 包含状态、异常、非功能要求和明确不做的范围 |
| 路线图 | 沟通方向与先后顺序 | 说明目标与依据，承认不确定性，不把猜测写成承诺 |
| 指标定义与埋点方案 | 判断结果 | 口径可复算，与目标对应，设有护栏指标 |
| 发布计划 | 协调上线 | 有分批、停止条件、沟通和支持准备 |
| 复盘与决策记录 | 积累组织学习 | 写明当时的证据、取舍和后来的结果 |

#### 01.3 决策权与相邻角色

产品工作需要多种角色共同完成。下表是常见分工，具体以团队约定为准；关键是每类决定都有明确的主导者，而不是所有人都能否决、没人负责。

| 事项 | 产品经理的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 为谁解决什么问题 | 主导 | 用户研究员、业务负责人 | 需要证据，而不是个人偏好 |
| 成功标准与指标 | 主导 | 数据分析师 | 指标口径共同定义 |
| 业务规则与流程细节 | 共同负责 | 业务分析师、领域专家 | 复杂业务中常由业务分析师主导梳理 |
| 体验与交互方案 | 参与 | UX／交互设计师主导 | 产品经理提供目标、约束与优先级 |
| 技术方案与估算 | 参与 | 技术负责人主导 | 产品经理需要理解成本与风险来源 |
| 进度、资源与依赖 | 参与 | 项目／交付经理主导 | 小团队中常由产品经理兼任 |
| 上线后的触达与运营 | 参与 | 产品运营 | 运营反馈是重要的发现来源 |
| 定价与包装 | 共同负责 | 商业、销售、财务 | 涉及收入与合同时需要业务负责人决定 |

几组容易混淆的角色：

- **产品经理与项目经理**：产品经理关注做什么、为什么做、做到什么程度算成功；项目经理关注怎样在约定的范围、时间、成本和质量内交付。两者经常协作，小团队中也可能是同一个人，但职责应分开描述。
- **产品经理与产品负责人（Product Owner）**：Scrum 指南把 Product Owner 定义为对最大化产品价值负责的一个人，负责明确产品目标并对产品待办列表排序。[B02](#ref-b02) 很多公司的产品经理承担这一职责，也有公司把面向市场的产品管理与面向团队的待办管理分给不同的人。
- **产品经理与服务负责人**：英国政府数字服务手册把产品经理、交付经理、服务负责人等列为服务团队中的不同角色，各自承担不同职责。[B03](#ref-b03) 其能力框架把产品经理描述为平衡用户需求与业务需求、推动产品创造价值的角色。[B04](#ref-b04)

#### 01.4 不同组织中的形态

- **消费者产品（C 端）**：用户量大，依赖行为数据与实验；增长、留存和体验是重点。
- **企业产品（B 端／SaaS）**：购买者、管理员与使用者往往不是同一个人；实施、权限、集成和合同条款都会影响产品（见 11 章）。
- **平台与 API 产品**：用户是开发者或内部团队；接口契约、兼容和开发者体验是核心（见 11 章）。
- **数据与 AI 产品**：结果具有概率性；评测、数据质量和人机协作决定价值（见 12 章）。
- **外包与项目制交付**：客户提出需求，团队按合同交付；产品职责体现为把客户需求还原成业务问题、控制范围和确认验收（见 16 章）。
- **独立开发与创业早期**：产品、设计、开发和推广由少数人承担；最大的风险通常是价值与分发，而不是技术实现。

**本章练习**：选一个你做过的功能，按四类风险各写一段：当时有什么证据，哪类风险最大，事后看判断是否正确。

<a id="ch02"></a>

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **用户与市场洞察**：理解用户的任务、情境、替代方案和市场结构。
2. **问题定义与目标**：把模糊诉求转化为可验证的问题与成功标准。
3. **产品发现与验证**：识别关键假设，用低成本方式验证或否定。
4. **需求与方案表达**：用文档、原型和验收条件让团队准确理解范围。
5. **优先级与路线图**：在多个目标、约束和利益相关方之间取舍。
6. **交付协作**：与设计、工程、测试和运营一起把方案做出来并上线。
7. **度量与分析**：定义指标、读懂数据、设计实验、判断因果。
8. **商业与定价**：理解收入、成本、单位经济和定价包装。
9. **战略与组合**：确定长期方向，管理多条产品线与平台投资。
10. **领域与技术理解**：理解所在行业与技术约束，例如 B 端流程、接口契约、AI 系统。

#### 02.2 六级纵向深度

| 深度 | 产品经理的能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 能解释产品概念，协助整理需求、竞品和用户反馈 | 需求整理、竞品分析表、访谈记录 |
| D2 独立完成 | 独立负责一个边界清楚的功能，从问题定义到上线复盘 | 问题陈述、需求说明、上线复盘 |
| D3 负责结果 | 对一个产品领域的指标结果负责，处理取舍、异常和利益冲突 | 指标变化、成果路线图、决策记录 |
| D4 系统与跨团队 | 协调多个团队、多条产品线或平台投资 | 跨团队路线图、组合决策、依赖治理 |
| D5 方法与机制 | 建立组织的产品决策、发现和度量方法 | 评审机制、指标体系、产品流程与培训材料 |
| D6 创新与影响 | 开创新的产品形态或方法，并验证其效果 | 新品类、公开的方法论与可复现的成果 |

一个人可以在用户洞察上达到 D4，而在定价上只有 D1。分级用于找出下一步练习，不用于给人贴总标签。

#### 02.3 成长中的常见偏差

- 把“需求写得详细”当作产品能力。文档详细不等于问题正确。
- 把“满足所有人”当作好产品。取舍才是产品工作的核心。
- 只看结果指标，不看指标背后的用户行为和结果质量。
- 用“用户说想要”代替“用户实际怎样做”。
- 用“数据驱动”回避判断。数据回答不了所有问题；没有数据时，也要做出可以修正的决定，并说明依据和复查时间。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 理解用户、业务与市场

#### 03.1 从“用户是谁”到“用户在什么情境下要完成什么”

只写年龄、职业、爱好的用户画像，很难指导决策。更有用的是描述情境与任务：在什么时刻、因为什么触发、想取得什么进展、现在用什么办法、为什么不满意。Jobs to be Done 的思路把用户“雇用”产品看作在特定情境中取得进展的手段，它提醒我们：竞争对手不只是同类产品，也包括表格、人工服务，甚至“什么都不做”。[B05](#ref-b05)

以求职平台为例，“大三学生”只是人群；“第一次投递实习前，不知道简历哪里需要改，也不知道改了以后是否更有竞争力”才是可以设计的情境。

#### 03.2 证据的类型与强弱

| 证据类型 | 能回答的问题 | 主要局限 |
| --- | --- | --- |
| 行为数据（埋点、日志） | 用户实际做了什么、在哪一步流失 | 不能直接说明原因；口径和采集可能有误 |
| 访谈 | 用户怎样理解问题，有哪些情境与动机 | 回忆与表达偏差，样本小 |
| 可用性测试 | 用户能否完成任务、在哪里卡住 | 测试情境与真实使用存在差异 |
| 问卷 | 态度与分布 | 题目设计与样本偏差影响很大 |
| 支持工单与销售反馈 | 真实痛点与高频问题 | 偏向主动反馈的用户，容易被个别大客户放大 |
| 实验 | 某个改动是否引起指标变化 | 需要足够流量、时间和正确设计 |
| 市场与竞品资料 | 结构、趋势和替代方案 | 公开信息有限，需要交叉验证 |

产品经理不必亲自完成所有研究，但要知道每种证据能证明什么、不能证明什么。研究方法见[《用户研究员》](02-用户研究员.md)，数据方法见[《数据分析师与产品分析师》](16-数据分析师与产品分析师.md)。

#### 03.3 业务模式与约束

理解公司怎样获得收入、主要成本在哪里、谁做购买决定、销售周期多长、哪些客户贡献主要收入，以及法律、渠道和品牌方面有哪些约束。一个对用户很有价值的功能，如果单位成本高于收入，或与主要客户的合同冲突，仍可能不应该做，或者需要换一种做法。

#### 03.4 市场与竞品分析

竞品分析的目的不是复制功能清单，而是理解用户为什么选择对方、对方放弃了什么、市场上还有哪些未被满足的情境。建议按“目标用户、核心任务、关键差异、商业模式、明显弱点”整理，而不是按菜单罗列功能。只看到竞品“有”某个功能并不能说明它有效，最好结合用户评价、更新记录和实际使用观察。

**本章练习**：为一个真实产品写一页“用户情境卡”：触发事件、期望进展、现有替代方案、不满意的原因、成功时的表现，并为每一条注明证据来源。

<a id="ch04"></a>

### 04 定义问题与成功标准

#### 04.1 问题陈述

一个可用的问题陈述包含：谁、在什么情境下、遇到什么阻碍、造成什么后果、有什么证据、为什么现在值得解决。避免把方案写成问题：“缺少 AI 简历评分功能”是方案；“学生投递前无法判断简历的主要缺陷，导致反复投递却没有回应”才是问题。

```text
问题陈述模板
目标用户与情境：
当前做法与阻碍：
造成的后果（对用户、对业务）：
证据（来源、样本、时间）：
为什么现在解决：
不在本次范围内的相关问题：
```

#### 04.2 目标与指标的层次

- **结果指标**：用户或业务状态的变化，例如“投递后获得面试邀请的比例”。
- **产品行为指标**：用户在产品中的行为，例如“完成简历修改的比例”。
- **产出**：团队交付了什么，例如“上线 AI 分析功能”。产出不是目标。
- **护栏指标**：不能被牺牲的方面，例如错误建议的投诉率、单次分析成本、页面性能。

Google 的 HEART 框架把以用户为中心的指标分为愉悦度、参与度、采用率、留存率和任务成功率，并用“目标—信号—指标”把产品目标映射到可测量的数据。它适合作为检查清单，提醒团队不要只盯着单一的流量指标。[B06](#ref-b06)

北极星指标用一个指标概括产品为用户创造的核心价值，帮助团队对齐。单一指标容易被过度优化，需要配合护栏指标，并定期复核它是否仍然代表用户价值。

#### 04.3 在开发之前写下成功标准

开始开发前写下：观察哪个指标、预期变化方向和大致幅度、观察多久、什么结果算成功、什么结果说明应该修改或撤回。事后再寻找对自己有利的数字，会让复盘失去意义。

结果指标往往变化慢、受多种因素影响，例如面试邀请率还取决于岗位市场。此时可以选择更早出现、与结果有合理联系的行为指标作为先行信号，同时说明这种联系是假设，需要在更长周期中复查。

**本章验收**：把一条“请加一个某某功能”的需求，改写为问题陈述、一项结果指标、一项行为指标和两项护栏指标，并说明每个指标的数据来源和统计口径。

<a id="ch05"></a>

### 05 产品发现：机会、假设与验证

#### 05.1 发现与交付并行

产品发现回答“该做什么”，交付回答“怎样把它做好”。成熟团队让两者并行：在交付当前版本的同时，持续研究下一批机会。发现工作的产出是被验证或被否定的假设，以及由此得出的决定，而不只是需求文档。

#### 05.2 机会—方案树

机会—方案树（Opportunity Solution Tree）从期望结果出发，向下展开用户机会（需求、痛点与期望），再为每个机会列出候选方案，最后为方案设计假设测试。它让团队看到“为什么选这个方案”，避免直接从目标跳到第一个想到的功能。[B07](#ref-b07)

```text
期望结果：提高学生投递前完成简历修改的比例
├── 机会：不知道简历哪里有问题
│   ├── 方案：AI 逐段分析并给出建议
│   ├── 方案：按岗位类型提供检查清单
│   └── 方案：同学互评
├── 机会：知道问题但不知道怎么改
│   ├── 方案：给出修改示例
│   └── 方案：提供可直接套用的表达模板
└── 机会：改完以后不确定是否更好
    └── 方案：修改前后对比与解释
```

#### 05.3 识别关键假设

为每个候选方案按四类风险列出假设，再按“影响有多大、证据有多少”排序，优先验证影响大而证据少的假设。

| 风险 | 示例假设（AI 简历分析） | 低成本验证方式 |
| --- | --- | --- |
| 价值 | 学生愿意在投递前花 5 分钟获取简历建议 | 访谈、意向登记、由人工提供建议的小范围试点 |
| 可用性 | 学生能看懂建议并据此修改 | 原型可用性测试 |
| 可行性 | 系统能在 30 秒内给出有依据的建议，单次成本可控 | 技术探针、离线评测 |
| 商业可行性 | 免费额度与付费层级能够覆盖成本 | 成本模型、定价访谈 |

#### 05.4 验证手段与伦理边界

- **访谈与观察**：确认问题是否真实存在、频率与严重程度如何。
- **原型测试**：从纸面草图到可点击原型，验证理解与操作。
- **人工模拟**：由人在后台完成本应由系统完成的工作，验证价值后再投入自动化。应告知参与者，或至少确保不会造成误导与损害。
- **假门测试**：展示一个入口，观察点击意向。用户点击后要诚实说明功能尚未提供，不能收取费用，也不能借机收集不必要的数据。
- **小范围试点与 A/B 测试**：验证真实环境中的效果，前提是有足够流量和明确指标（见 09 章）。

验证的目的是降低决策风险，而不是证明自己正确。开始验证前写下“什么结果会让我放弃或修改这个方案”。

**本章练习**：为一个机会画出机会—方案树，至少包含三个候选方案；为最有希望的方案列出四类风险的假设，设计两个一周内能完成的验证。

<a id="ch06"></a>

### 06 需求表达与范围切分

#### 06.1 需求说明的组成

无论使用完整需求文档（PRD）、用户故事还是一页纸简报，核心内容相同：

```text
需求说明骨架
背景与问题：（链接问题陈述与证据）
目标与成功标准：
目标用户与使用场景：
范围：本次做什么／明确不做什么
用户流程与关键状态：（正常、加载、空、失败、权限不足、取消）
业务规则与数据：（规则、口径、保留与删除）
非功能要求：（性能、可用性、安全、隐私、可访问性、成本）
验收标准：
上线与度量计划：
待决问题与负责人：
```

文档的详细程度取决于风险与团队共识：高风险、跨团队、对外承诺的需求要写得更完整；小团队内部的低风险改动可以用简短说明加示例。

#### 06.2 用户故事与验收标准

用户故事“作为……我想……以便……”帮助说明使用者与目的，但还需要验收标准才能判断是否完成。常用“假如／当／那么”（Given／When／Then）格式写行为示例，它也是 Cucumber 等工具使用的 Gherkin 语法，支持中文关键字。[B08](#ref-b08) 验收标准应覆盖异常和边界，而不只是正常路径。

```gherkin
# language: zh-CN
功能: 简历分析结果

  场景: 上传的简历无法解析
    假如 学生上传了一份扫描版 PDF 简历
    当 系统无法从文件中提取文本
    那么 页面说明无法识别的原因
    而且 提供重新上传或手动粘贴文本的入口
    而且 本次不消耗分析额度
```

#### 06.3 范围切分

- **按用户价值纵向切分**：每一片都能让某类用户完成一件完整的事，而不是“先做后端、再做前端”。
- **先验证，再扩展**：最小可行版本中的“可行”指能够验证关键假设，不等于粗糙到用户无法使用。
- **用户故事地图**：把用户活动按时间从左到右排列，在每个活动下纵向排列细节，再横向切出每次发布的范围。Jeff Patton 在《User Story Mapping》中系统介绍了这种方法，适合讨论范围和发布顺序。

#### 06.4 需求变更

需求变化本身是正常的，问题在于变化不可见。记录变化的原因、影响范围、对目标和进度的影响，以及由谁决定。外包项目中的变更还涉及合同与费用，见[《项目经理与交付经理》](21-项目经理与交付经理.md)。

**本章验收**：为一个功能写需求说明，至少包含 6 种非正常状态的验收标准；请一位开发者和一位测试者独立阅读，记录他们提出的问题数量和类型，据此修改。

<a id="ch07"></a>

### 07 优先级与路线图

#### 07.1 优先级反映战略

优先级回答的是：先解决哪个问题、服务哪类用户、接受哪些风险。评分模型帮助结构化讨论，但不能代替判断。

| 方法 | 做法 | 适用场景 | 注意 |
| --- | --- | --- | --- |
| RICE | 覆盖人数 × 影响 × 信心 ÷ 工作量 | 比较同一阶段的多个候选 | 各项都是估计，信心项尤其容易被高估 [B09](#ref-b09) |
| Kano 模型 | 区分基本型、期望型、魅力型等需求 | 理解功能对满意度的不同作用 | 分类会随时间变化，魅力型会逐渐变成基本型 |
| 延迟成本 | 估算推迟一段时间造成的损失 | 有时间窗口、合同或季节性的事项 | 要写明损失来源与假设 |
| 价值—成本矩阵 | 按价值和成本分为四个象限 | 快速初筛 | 忽略了风险与依赖 |
| 机会评分 | 比较用户认为的重要程度与当前满意度 | 发现未被满足的需求 | 依赖调研质量 |

#### 07.2 路线图的形式

- **按时间排列的功能路线图**：适合合同和外部承诺明确的场景，但容易把猜测变成承诺。
- **按成果组织的路线图**：例如“现在、接下来、以后”三栏，写要解决的问题和目标，越远的部分越粗略，更诚实地表达不确定性。
- **对外与对内路线图分开**：对客户的承诺需要谨慎，不要把内部探索写成交付日期。

#### 07.3 技术债、平台与非功能工作

稳定性、性能、安全和可维护性工作也需要进入优先级讨论。产品经理应理解它们对用户和业务的影响，例如事故频率、交付速度、合规风险，而不是把它们看作“工程自己的事”。常见做法是为这类工作保留一定比例的容量，并定期按实际影响复核比例。

#### 07.4 拒绝与推迟

拒绝或推迟需求时，说明依据（目标、证据、成本），提供替代方案或重新评估的条件，并记录下来。面对上级或大客户的要求，同样回到问题与证据上讨论；如果最终因商业原因决定执行，也要在决策记录中写明，以便复盘。

**本章练习**：列出 10 个候选需求，分别用 RICE 和延迟成本排序，比较两种结果的差异，写一段最终取舍的理由。

<a id="ch08"></a>

### 08 与团队协作交付

#### 08.1 产品三角与协作节奏

产品经理、设计负责人和技术负责人共同构成产品决策的核心：发现阶段三方共同参与，交付阶段各自主导自己的领域。常见的协作节点包括需求评审（澄清问题与范围）、设计评审、技术方案评审、迭代计划、日常同步、演示与验收、复盘。节点的数量和形式应随团队规模调整，目的都是尽早暴露理解差异。

#### 08.2 开发过程中的产品职责

- 及时回答问题；必要时做出范围取舍，并记录理由。
- 参与验收：用真实数据和异常情况检查，而不只看演示路径。
- 管理范围蔓延：新增想法先记入待办列表，评估后再决定。
- 明确质量门槛：哪些问题必须修复才能上线，哪些可以作为已知问题记录并告知支持团队。

#### 08.3 发布与上线

上线前确认：分批或灰度计划、功能开关、观察指标、停止或回退条件、客服与运营准备、用户沟通、埋点验证。上线后观察的不只是错误率，还有目标行为是否真的发生。技术侧的发布机制见[《后端进阶全景手册》第 14 章](../技术方向/后端进阶全景手册.md#ch14)。

**本章验收**：为一次功能上线写发布清单，请开发、测试、运营各一人确认；上线后按清单复查实际执行情况，记录遗漏项。

<a id="ch09"></a>

### 09 度量、实验与复盘

#### 09.1 埋点与指标口径

为关键事件定义触发时机、主体、属性、去重规则和数据来源；为指标写清分子、分母、时间窗口和排除条件。“分析成功率”可以按点击、受理、完成或交付来统计，得出的结论完全不同。口径变化时保留说明，否则前后数据无法比较。

#### 09.2 A/B 测试的前提与陷阱

A/B 测试能在合适条件下识别因果关系，但需要：足够的样本、稳定的随机分组、预先确定的主要指标和护栏指标、覆盖使用周期的观察时间。常见陷阱包括：反复查看结果并在“显著”时提前停止；同时检验大量指标却只报告显著的那个；新奇效应；分组样本比例与设计不符；实验组和对照组相互影响。Kohavi 等人的《Trustworthy Online Controlled Experiments》系统讨论了这些问题。[B10](#ref-b10)

流量不足时，可以使用前后对比、分阶段上线、定性研究等方法，但要说明其因果证据较弱，并尽量排除季节、活动等同期因素。

#### 09.3 上线后复盘

在上线后的合适时间点（取决于产品使用周期，例如数周和数月各一次）复查：目标指标是否变化、护栏是否受损、用户反馈如何、实际成本如何。然后做出决定：保留、修改、扩大、缩小或撤回。撤回一个功能同样是有价值的决定，它减少了长期维护成本和界面复杂度。

```text
上线复盘模板
原始问题与目标：
上线范围与时间：
指标结果（含护栏指标）：
定性反馈与支持数据：
与预期的差异及可能原因：
决定（保留／修改／扩大／撤回）与理由：
学到的东西与下次改变的做法：
```

**本章验收**：为一个已上线的功能补写指标口径和复盘，判断当初的成功标准是否合理，并写出下次会怎样设定。

### 10 商业模式、定价与单位经济

#### 10.1 常见商业模式

订阅、按量计费、按席位计费、免费增值、交易抽成、广告、一次性授权和项目制服务各有适用条件。选择取决于用户获得的价值怎样随使用增长、用户的预算方式，以及产品的成本结构。

#### 10.2 定价与包装

定价不仅是一个价格数字，还包括：按什么计量（次数、席位、用量）、分几个层级、每层包含哪些能力、免费额度与试用、折扣与合同条款。计量单位最好与用户获得价值的方式一致，例如按“完成的分析报告”收费，比按“接口调用次数”更容易被用户理解和接受。

#### 10.3 单位经济

| 概念 | 含义 | 在产品决策中的用途 |
| --- | --- | --- |
| 获客成本 CAC | 获得一个付费用户的平均成本 | 评估渠道和增长方式 |
| 生命周期价值 LTV | 一个用户在整个关系期内带来的毛利 | 判断能承受多高的获客成本 |
| 毛利率 | 收入扣除直接成本后的比例 | AI、云资源成本高的产品尤其重要 |
| 回本周期 | 收回获客成本所需的时间 | 影响现金流与增长节奏 |
| 单次使用成本 | 一次核心操作消耗的资源成本 | 决定免费额度和定价下限 |

AI 产品的推理成本会随使用量增长，免费额度设计不当，可能出现“越受欢迎越亏损”。计量、额度与账务记录的工程实现见[《后端进阶全景手册》第 29 章](../技术方向/后端进阶全景手册.md#ch29)。

#### 10.4 定价实验的边界

对不同用户展示不同价格，可能引起公平争议、违反平台规则或适用法律。价格探索优先使用访谈、支付意愿调查、不同套餐结构的比较，或在新用户中分阶段调整，并提前评估合规与品牌风险。

**本章练习**：为一个 AI 功能建立单位经济模型：单次成本、免费额度、付费转化假设、毛利率；找出最可能让模型不成立的两个变量，并说明如何尽早验证。

### 11 B 端、平台与 API 产品

#### 11.1 企业产品的多种角色

购买决策者、预算负责人、管理员、日常使用者、IT 与安全审查者往往是不同的人。产品需要同时满足使用者的效率、管理员的控制、购买者的价值证明，以及 IT 部门的安全与集成要求。忽视其中任何一方，都可能导致“用户喜欢但买不进来”或“买进来却没人用”。

#### 11.2 B 端产品的特有问题

权限与组织结构、审批流程、数据导入与系统集成、单点登录、审计日志、合同与服务等级、实施与培训、定制需求。处理大客户的定制要求时，要区分“这个客户特有”和“一类客户共有”：后者才适合进入标准产品，前者可以通过配置、扩展点或项目服务解决。

#### 11.3 平台与 API 产品

平台和 API 的用户是开发者或内部团队。产品质量体现在接入成功所需的时间、文档与示例质量、错误信息是否可理解、兼容与版本策略、稳定性和支持响应。接口一旦被使用，修改成本很高，契约设计要比普通界面更谨慎，相关工程内容见[《后端进阶全景手册》第 07 章](../技术方向/后端进阶全景手册.md#ch07)与[第 33 章](../技术方向/后端进阶全景手册.md#ch33)。

**本章练习**：为一个 B 端功能列出所有相关角色及其各自的成功标准，找出彼此冲突的地方，并提出取舍方案。

<a id="ch12"></a>

### 12 AI 产品

#### 12.1 AI 功能的产品特性

- **结果具有概率性**：同一输入可能得到不同结果，需要用评测集衡量质量分布，而不是看几个演示样例。
- **质量、延迟和成本相互制约**：能力更强的模型可能更慢、更贵。
- **信任需要校准**：既不能让用户盲目相信，也不应让用户因偶发错误完全放弃。
- **失败方式多样**：事实错误、遗漏、格式错误、越权操作、被不可信内容操纵等。

#### 12.2 定义 AI 功能的成功

成功标准通常需要组合：任务完成率、结果质量（按评测标准评分）、用户采纳与修改行为、错误的严重程度分布、单次成本与延迟、投诉与风险事件。上线前建立代表性评测集，覆盖正常、信息缺失、相互矛盾、超长文本和恶意输入等情况，并确定上线门槛。

#### 12.3 人机协作与风险

明确哪些决定由系统做出、哪些需要用户确认；展示依据与不确定性；提供编辑、重新生成、撤销和反馈入口；对高影响操作要求人工确认。美国国家标准与技术研究院（NIST）的 AI 风险管理框架把可信 AI 的特征归纳为：有效可靠；不造成危害；能抵御攻击并从中恢复；可问责且透明；可解释；保护隐私；公平并管理有害偏差。这些特征可作为产品评审的检查维度。[B11](#ref-b11) OWASP 关于大模型应用的风险条目提醒产品团队，需要考虑提示注入、过度代理能力等风险，并把权限控制放在模型之外。[B12](#ref-b12)

#### 12.4 AI 产品的迭代

模型、提示词、检索数据和工具都会变化，需要版本管理和回归评测。用户反馈要能与具体的版本和输入关联，否则无法判断质量变化的原因。工程实现见[《后端进阶全景手册》第 32 章](../技术方向/后端进阶全景手册.md#ch32)，模型方法见[《算法与机器学习工程师》](18-算法与机器学习工程师.md)。

**本章验收**：为 AI 简历分析定义一份评测方案：评测集构成、评分标准、上线门槛、护栏指标和人工抽检频率。

<a id="ch13"></a>

### 13 产品战略、组合与组织

#### 13.1 愿景与战略

愿景描述长期希望用户和世界发生的变化；战略说明在当前条件下选择哪条路径接近它。一份可用的战略包含三部分：对现状和关键挑战的诊断、指导取舍的方针、彼此配合的行动，并明确不做什么。路线图是战略的执行计划，而不是战略本身。

#### 13.2 产品组合与平台投资

多条产品线需要决定资源分配、共享能力和退出时机。平台投资的回报来自多个业务的复用，应以真实使用者反复遇到的问题为起点，而不是先建设“通用平台”再寻找用户（见[《平台工程师与研发效能》](14-平台工程师与研发效能.md)）。

#### 13.3 产品组织与决策机制

产品团队按用户群、按功能领域还是按平台组织，会影响决策速度和协作成本。成熟组织会建立产品评审、指标体系、决策记录、发现与交付的节奏，以及产品运营（Product Ops）支持。D5 深度的产品经理负责设计和改进这些机制，让其他产品经理能稳定地做出好的决定。

**本章练习**：为一个产品写一页战略：诊断、方针、三项关键行动，以及明确不做的三件事。

<a id="ch14"></a>

### 14 信任、合规与产品伦理

#### 14.1 隐私与数据

坚持数据最小化：只收集实现目的所必需的数据，说明用途，提供查看、导出和删除的入口。中国《个人信息保护法》、欧盟《通用数据保护条例》（GDPR）等法律对处理个人信息的合法性基础、告知与同意、个人权利等作出规定。[B13](#ref-b13) [B14](#ref-b14) 产品经理的职责是在需求阶段识别个人信息处理活动，并提请法务与隐私负责人确认具体义务；删除与保留的工程实现见[《后端进阶全景手册》第 23 章](../技术方向/后端进阶全景手册.md#ch23)。

#### 14.2 避免操纵性设计

隐藏取消订阅入口、默认勾选同意、制造虚假紧迫感等操纵性设计，可能在短期内提高指标，但会损害信任，并已受到多个司法辖区的监管关注。例如，欧盟《数字服务法》第 25 条要求在线平台不得以欺骗或操纵用户、实质性扭曲用户自主决定的方式设计和运营界面。[B15](#ref-b15)

#### 14.3 可访问性与包容

可访问性是产品质量的一部分，在部分地区也是法律要求。应在需求阶段把它列为非功能要求，而不是上线后补救（见[《无障碍专家》](09-无障碍专家.md)）。

#### 14.4 负责任的增长

关注未成年人等需要特别保护的用户、成瘾性设计，以及 AI 建议对求职、医疗、金融等重要决定的影响。为高影响建议提供依据、适用范围说明和人工求助渠道。

**本章练习**：审查一个注册或订阅流程，列出可能被认为操纵用户的设计，并提出不损害主要目标的替代方案。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与开发者的协作接口

#### 15.1 产品经理应提供给开发者的内容

| 内容 | 最低要求 | 常见缺失 |
| --- | --- | --- |
| 问题与目标 | 为什么做、成功标准是什么 | 只给方案，不给问题 |
| 范围 | 做什么、明确不做什么 | 没有写出不做的部分 |
| 用户流程与状态 | 正常路径与异常路径 | 只有成功路径 |
| 业务规则 | 规则与例外集中记录 | 规则散落在聊天记录里 |
| 验收标准 | 能够判断是否完成 | “体验要好”等无法验证的描述 |
| 优先级与取舍理由 | 时间不够时先保什么 | 所有需求同等重要 |
| 数据与度量 | 埋点方案与指标口径 | 上线后才想起需要统计 |

#### 15.2 开发者应反馈给产品经理的内容

可行性与成本估计、技术风险、更简单的替代方案、对现有系统的影响（数据、兼容、性能、安全），以及技术带来的新机会，例如某项能力已经具备，可以低成本支持新场景。

#### 15.3 常见摩擦与处理

| 摩擦 | 常见原因 | 处理方式 |
| --- | --- | --- |
| 需求频繁变化 | 发现不足、利益相关方未对齐 | 加强前期发现；记录变更及其影响 |
| 估算被当作承诺 | 不确定性没有被说明 | 用范围或置信程度表达估算 |
| “这个很简单” | 不了解实现复杂度 | 开发说明复杂度来源，产品说明价值与优先级 |
| 技术债被持续推迟 | 影响没有被量化 | 用事故、交付速度、风险说明影响 |
| 验收时才发现理解不同 | 缺少示例和验收标准 | 开发前用具体示例对齐，过程中定期演示 |

<a id="ch16"></a>

### 16 开发者怎样承担产品职责

#### 16.1 独立产品

独立开发者最大的风险通常是价值与分发，而不是技术。建议：

- 开工前写一页产品简报：问题、目标用户、替代方案、成功标准、获客渠道、收费方式。
- 每周安排固定时间接触用户：访谈、观察使用、回复反馈。
- 先用人工或半自动方式交付价值，确认需求后再自动化。
- 每个功能上线前写下成功标准，上线后复查；撤掉没人使用的功能。
- 把定价和分发当作产品的一部分，而不是“做完再说”。

#### 16.2 外包与客户项目

客户提出的往往是方案（“做一个预约小程序”），需要还原为业务问题（“门店预约混乱，客户等待时间长而流失”）。在外包项目中，产品职责包括：

- 澄清业务目标与成功标准，确认谁是最终使用者、谁负责验收。
- 把需求写成可验收的范围，并明确不做的部分。
- 识别隐藏需求：权限、数据迁移、报表、通知、运维和培训。
- 管理变更：每次变更都记录影响和费用。
- 交付后了解实际使用情况，为后续合作积累依据。

业务流程与规则的梳理方法见[《业务分析师》](03-业务分析师.md)，合同、里程碑与验收见[《项目经理与交付经理》](21-项目经理与交付经理.md)。

#### 16.3 技术背景常见的产品偏差

- **方案先行**：先想到技术方案，再寻找能用上它的问题。
- **功能堆砌**：用功能数量代替解决问题的深度。
- **过度工程**：价值还未验证，就建设复杂架构。
- **忽视非使用者角色**：购买者、管理员、客服人员的需求。
- **把“能做”当作“应该做”**。

技术背景也有明显优势：能快速判断可行性与成本，能发现技术带来的新机会，能用原型快速验证想法。把这些优势用在发现阶段，比用在堆叠功能上更有价值。

### 17 贯穿实战：求职平台的 AI 简历分析

本章把前面的方法串成一个完整流程。案例中的数字都是示意，用于说明方法，不代表真实数据。

#### 17.1 问题与证据

访谈准备投递实习的学生，并整理平台已有的支持记录，发现一个高频情境：学生在第一次投递前反复修改简历，却无法判断修改是否有效；投递后长期没有回应，也不知道原因。现有替代方案是请学长学姐或老师看简历，但等待时间长、意见不一致。

```text
问题陈述
目标用户与情境：首次投递实习前的在校学生
当前做法与阻碍：依赖他人点评，等待时间长、意见不一致，无法判断修改是否有效
后果：投递积极性下降；平台简历完善率低
证据：访谈记录、支持工单中关于“简历怎么改”的问题占比（示意）
为什么现在：秋季招聘开始前是需求高峰
不在本次范围：岗位推荐、模拟面试
```

#### 17.2 目标与指标

| 层次 | 指标 | 说明 |
| --- | --- | --- |
| 结果 | 修改后投递的面试邀请率 | 周期长、受市场影响，作为长期观察 |
| 行为 | 分析完成率、建议采纳率、修改后重新分析率 | 作为先行信号 |
| 护栏 | 错误建议反馈率、单次分析成本、第 95 百分位生成时间 | 质量、成本与体验底线 |

#### 17.3 发现与验证

| 风险 | 验证 | 结果示例与决定 |
| --- | --- | --- |
| 价值 | 两周人工点评试点，记录学生是否按建议修改 | 多数参与者修改了简历，继续推进 |
| 可用性 | 用可点击原型测试建议的呈现方式 | 学生更容易理解“问题＋原因＋修改示例”的结构 |
| 可行性 | 用 100 份脱敏简历做离线评测 | 结构化提取可行；岗位相关性建议质量不稳定，暂缓 |
| 商业可行性 | 成本模型与付费意向访谈 | 首版提供有限免费额度，付费方案待验证 |

#### 17.4 范围与切片

- **第一版**：上传 PDF、结构化解析、两类建议（内容完整性、表达清晰度）、每条建议可标记“有用／没用”。
- **明确不做**：自动改写全文、岗位推荐、简历评分排名。
- **后续候选**：岗位相关性建议（等待评测质量达标）、修改前后对比。

#### 17.5 关键需求与验收

需求说明中写清以下状态：上传中、解析失败（扫描件、加密文件、超出大小）、分析排队、分析中、部分完成、完成、额度不足、用户取消、服务暂时不可用。每个状态都有对应的界面说明和额度规则，例如解析失败不消耗额度。分析任务的可靠性设计见[《后端进阶全景手册》第 43 章](../技术方向/后端进阶全景手册.md#ch43)。

#### 17.6 上线、复盘与决定

先向 10% 新用户开放，观察行为指标和护栏指标两周（示意）；确认解析失败率和错误建议反馈率在门槛内后扩大范围。一个月后复盘：如果建议采纳率高、重新分析率高，说明价值成立，可以投入岗位相关性建议；如果完成率高但采纳率低，回到可用性和建议质量上找原因，而不是急于增加新功能。

#### 18.5 检查清单

- [ ] 问题陈述有目标用户、情境和证据，而不只是方案描述。

- [ ] 需求说明写明不做的范围、关键状态和异常处理。
- [ ] 验收标准可判断，覆盖边界与失败情况。

- [ ] 发布计划有分批、停止条件和回退方式。

- [ ] 埋点在测试环境验证过。

上线后：

- [ ] 在约定时间复查指标与反馈。
- [ ] 做出保留、修改、扩大或撤回的决定，并记录理由。
- [ ] 把学到的东西更新到决策记录和下一轮发现中。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 产品经理就是写需求文档的人 | 文档是手段；产品经理对问题选择和结果负责 |
| 产品经理是团队的老板 | 产品经理主导问题与优先级，设计和技术决定由相应负责人主导 |
| 用户要什么就做什么 | 用户描述的是问题和期望，方案需要团队设计与验证 |
| 有数据就不需要判断 | 数据帮助判断，但无法替代对目标、取舍和不确定性的决定 |
| 功能上线就是成功 | 上线是产出；成功要看用户行为与业务结果是否按预期变化 |
| 路线图就是承诺的交付日期 | 路线图表达方向与顺序，远期部分本身带有不确定性 |
| A/B 测试显著就说明方案好 | 还要检查实验设计、样本、护栏指标和长期影响 |
| MVP 就是粗糙的版本 | MVP 是能验证关键假设的最小版本，仍需可用 |
| 技术债是工程团队自己的事 | 技术债影响交付速度、稳定性和风险，属于产品取舍 |
| AI 功能演示效果好就可以上线 | 需要评测集上的质量分布、成本、风险和人工兜底 |

### C.2 内容边界

本手册覆盖产品管理的通用职责与方法，不替代特定行业的专业知识，例如金融、医疗、教育等领域的监管要求与业务规则。法律、定价和合同相关内容只说明产品决策需要考虑的问题，具体义务与条款由相应负责人确认。方法与框架会随实践更新，引用资料时以原始来源为准。

相邻角色的展开见本系列其他各册，总览见[《职业角色全景》](README.md)。
