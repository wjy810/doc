# UX／交互设计师进阶全景手册

> 从把一个流程设计得让人用得明白，到为复杂产品建立一致的交互体系，再到推动团队以用户为中心做决定。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：准备转向交互设计的开发者与视觉设计师、需要自己设计界面的独立开发者和外包工程师，以及希望系统提升的在职 UX／交互设计师。

UX／交互设计师要回答的核心问题是：用户怎样完成他们的任务。具体来说，包括信息怎样组织才能被找到，步骤怎样安排才不会迷路，系统在每个时刻处于什么状态、怎样告诉用户，出错以后怎样恢复，以及同样的操作在整个产品中是否表现一致。界面“好不好看”主要由视觉设计负责；“能不能用、好不好用”是交互设计的核心。

本手册是职业角色系列中的一册，侧重交互设计师的职责、方法与协作。界面实现、视觉表达、动效与图形技术等内容，见[《前端与 UI／UX 设计进阶全景手册》](../技术方向/前端与UIUX设计进阶全景手册.md)；视觉设计职责见[《UI／视觉设计师》](06-UI视觉设计师.md)，研究方法见[《用户研究员》](02-用户研究员.md)。

主线是：**理解用户任务与情境 → 组织信息结构 → 设计流程与状态 → 原型与交互细节 → 评估与迭代 → 交付规格并协作实现 → 建立交互体系与设计质量机制。**

不同公司中，这一职责可能由交互设计师、UX 设计师、产品设计师或用户体验架构师承担，小团队中也常由产品经理或前端开发者兼任。本手册描述交互设计的职责与方法；D1—D6 分级是学习组织方式，不对应任何职级体系。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 UX／交互设计师负责什么

#### 01.1 核心问题：用户怎样完成任务

交互设计关注人与系统之间的“对话”：用户做出一个动作，系统给出什么回应；用户想达到一个目标，需要经过哪些步骤；用户犯了错，系统怎样帮助恢复。英国政府数字与数据能力框架把交互设计师描述为找出让用户与服务交互的最佳方式、既关注整体流程也关注单个界面元素的角色。[B01](#ref-b01)

交互设计的质量往往在“不正常”的时刻最明显：网络中断、文件格式不对、权限不足、两个人同时修改同一份数据、用户中途离开又回来。只设计了正常路径的方案，在真实使用中很快会暴露问题。

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 任务分析与场景 | 明确设计要支持什么 | 来自研究证据，覆盖主要情境 |
| 信息架构 | 组织内容与导航 | 分类与命名符合用户的心智模型，经过测试 |
| 用户流程图 | 展示完成任务的路径 | 包含入口、分支、异常、中断与恢复 |
| 状态清单与状态图 | 定义系统在各种情况下的表现 | 覆盖空、加载、部分、错误、权限、离线、冲突 |
| 线框图与原型 | 表达结构与交互，用于测试与沟通 | 保真度与目的匹配，可以被测试 |
| 交互说明与规格 | 让开发准确实现 | 写明触发、反馈、边界、无障碍要求 |
| 评估记录 | 证明方案有效或发现问题 | 有任务、证据与严重程度 |
| 交互模式与规范 | 保持产品一致 | 说明适用场景、反例与可访问性 |

#### 01.3 职责边界与相邻角色

| 事项 | 交互设计师的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 用户问题与目标 | 参与 | 产品经理、用户研究员 | 交互设计从真实问题出发 |
| 信息架构与流程 | 主导 | 内容设计师、业务分析师 | 业务规则由业务方确认 |
| 界面布局与交互方式 | 主导 | UI／视觉设计师 | 结构与视觉需要共同推敲 |
| 视觉风格与品牌表达 | 参与 | UI／视觉设计师主导 | |
| 文案与提示信息 | 共同负责 | 内容设计师 | 文字是交互的一部分 |
| 研究与测试 | 共同负责 | 用户研究员 | 小团队中常由设计师主持 |
| 技术实现方式 | 参与 | 前端与后端开发者主导 | 设计师需要理解实现约束 |
| 无障碍要求 | 共同负责 | 无障碍专家、前端开发者 | 从设计阶段开始考虑 |

几组容易混淆的说法：

- **UX 与 UI**：UX 关注用户完成目标的整体体验，UI 关注界面的视觉表达与组件。交互设计是 UX 中最直接作用于界面的部分。
- **交互设计师与产品经理**：产品经理决定解决什么问题、做到什么程度；交互设计师决定用户怎样完成任务。两者在发现阶段紧密合作。
- **交互设计师与服务设计师**：交互设计聚焦用户与界面的交互；服务设计关注跨渠道、跨人员、跨时间的整个服务过程（见[《服务设计师》](08-服务设计师.md)）。

#### 01.4 不同组织中的形态

- **产品设计师**：一人覆盖交互、视觉和部分研究，常见于中小团队。
- **专职交互设计师**：在大团队中专注于流程与交互，与视觉设计师分工。
- **设计系统设计师**：负责组件、模式与规范的设计和维护（见 13 章）。
- **专业工具与 B 端设计师**：面向复杂工作流、数据密集的界面（见 10 章）。
- **外包与项目制设计**：在合同范围内交付设计稿，需要特别注意状态完整性与交付规格。

**本章练习**：选一个你常用的应用，找出一个让你困惑或出错的地方，分析问题出在信息架构、流程、状态反馈还是文案，并提出修改方案。

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **用户与任务理解**：理解用户目标、情境、频率与约束。
2. **信息架构**：分类、命名、导航与搜索。
3. **流程与状态设计**：任务路径、分支、异常、中断与恢复。
4. **交互模式与反馈**：选择合适的控件和模式，设计反馈与错误处理。
5. **原型与表达**：用合适的保真度表达和测试想法。
6. **评估与可用性**：用启发式评估、走查和测试检验方案。
7. **内容与微文案协作**：让文字与交互共同引导用户。
8. **无障碍与包容性**：让不同能力和情境的用户都能完成任务。
9. **规格与交付**：让开发准确实现，并在实现后检查。
10. **交互体系与设计系统**：在整个产品中保持一致，沉淀可复用的模式。

#### 02.2 六级纵向深度

| 深度 | 交互设计师的能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 能解释常用交互原则，按规范绘制线框图 | 线框图、流程草图 |
| D2 独立完成 | 独立设计一个功能的完整流程与状态，并完成测试 | 流程图、状态清单、原型、测试记录 |
| D3 负责结果 | 对一个产品领域的体验质量负责 | 体验指标变化、设计决策记录、走查记录 |
| D4 系统与跨团队 | 协调多个团队的交互一致性与跨产品流程 | 跨产品流程、交互规范、评审机制 |
| D5 方法与机制 | 建立设计流程、模式库和质量机制 | 模式库、设计评审规范、培训 |
| D6 创新与影响 | 提出新的交互方式或设计方法并验证其效果 | 新交互模式、研究成果、行业采用 |

#### 02.3 成长中的常见偏差

- 只设计“快乐路径”，异常与边界留给开发者临场发挥。
- 追求新奇的交互方式，忽视用户已有的习惯和平台惯例。
- 交付漂亮的高保真稿，却说不清背后的任务与取舍。
- 把个人偏好当作用户需求，缺少评估证据。
- 设计稿交付后不再跟进，实现与设计逐渐偏离。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 以人为中心的设计过程

#### 03.1 六项原则

国际标准 ISO 9241-210 描述了以人为中心的设计原则：设计建立在对用户、任务和环境的明确理解之上；用户在整个设计与开发过程中参与；设计由以用户为中心的评估推动和完善；过程是迭代的；设计关注完整的用户体验；设计团队包含多学科的技能与视角。[B02](#ref-b02) 这些原则不规定具体方法，而是提供检查设计过程是否健全的框架。

#### 03.2 发散与收敛

英国设计委员会的“双钻”模型把设计过程表示为两次发散与收敛：第一次在问题空间中，先广泛了解问题，再聚焦到要解决的问题；第二次在方案空间中，先探索多种方案，再收敛到可交付的方案。[B03](#ref-b03) 它提醒设计师：不要跳过问题定义直接做方案，也不要只做一个方案就进入细化。

#### 03.3 与产品节奏结合

在真实项目中，设计过程与产品的发现、交付节奏交织在一起：

| 阶段 | 交互设计师的主要工作 | 产出 |
| --- | --- | --- |
| 发现 | 参与研究，梳理任务与问题 | 任务分析、机会、设计原则 |
| 构思 | 探索多个方案，快速草图与讨论 | 草图、概念流程 |
| 验证 | 做原型，组织测试 | 原型、测试记录 |
| 细化 | 完善流程、状态、细节与规格 | 交互说明、状态清单 |
| 实现 | 回答问题，检查实现 | 设计走查记录 |
| 上线后 | 观察数据与反馈，规划改进 | 复盘、改进清单 |

**本章练习**：回顾你最近的一个设计，按 ISO 9241-210 的六项原则逐条检查过程中做到了什么、缺了什么。

### 04 任务分析与信息架构

#### 04.1 任务分析

任务分析把用户目标拆成步骤，并记录每一步的信息需要、决策点、频率和常见问题。层级任务分析从目标开始逐层分解：

```text
目标：投递前改进简历
├── 1 获取对简历的反馈
│   ├── 1.1 上传或选择简历
│   ├── 1.2 选择目标岗位类型（可选）
│   └── 1.3 等待并查看分析结果
├── 2 理解并处理建议
│   ├── 2.1 判断建议是否适用
│   ├── 2.2 修改简历内容
│   └── 2.3 标记建议已处理或不适用
└── 3 判断修改是否有效
    ├── 3.1 重新分析
    └── 3.2 对比修改前后
```

任务分析帮助设计师发现：哪些步骤可以合并或自动化，哪些决策点需要额外的信息支持，哪些高频任务需要更短的路径。

#### 04.2 信息架构

信息架构决定内容怎样组织、怎样命名、怎样被找到。核心问题包括：

- **组织方式**：按任务、按对象、按时间还是按用户角色组织？不同组织方式适合不同的使用方式。
- **标签与命名**：使用用户熟悉的词，而不是内部术语或技术名称。
- **导航**：全局导航、局部导航、上下文链接、面包屑分别解决什么问题。
- **搜索**：何时需要搜索、搜索结果怎样组织、找不到结果时怎么办。

卡片分类和树测试是检验信息架构的常用方法（见[《用户研究员》第 06 章](02-用户研究员.md#ch06)）。

**本章验收**：为一个功能完成层级任务分析，并为一个包含 30 个以上内容项的产品区域设计信息架构，用树测试检验 5 个关键任务能否顺利找到入口。

<a id="ch05"></a>

### 05 用户流程与状态设计

#### 05.1 用户流程

用户流程图展示用户从入口到完成目标的路径，包括：

- **入口**：用户从哪里开始？通知、搜索、首页、外部链接？
- **步骤与决策**：每一步做什么，在哪里需要选择。
- **系统处理**：哪些步骤由系统完成，需要多久。
- **异常与分支**：失败、取消、超时、权限不足时去哪里。
- **出口**：完成后到哪里？下一步可以做什么？

#### 05.2 状态清单

每个界面、每个组件都可能处于多种状态。设计时逐项检查：

| 状态 | 需要回答的问题 | 简历分析示例 |
| --- | --- | --- |
| 初始与空状态 | 第一次使用时看到什么？怎样引导？ | 尚未上传简历：说明能获得什么，提供上传入口 |
| 加载与处理中 | 需要多久？能否离开？进度怎样表示？ | 分析中：显示阶段与预计时间，可以离开页面 |
| 部分完成 | 部分结果可用时怎样展示？ | 已完成格式检查，内容分析进行中 |
| 成功 | 结果是什么？下一步做什么？ | 显示建议列表，引导逐条处理 |
| 错误 | 发生了什么？用户能做什么？ | 文件无法解析：说明原因，提供替代方式 |
| 权限不足或额度不足 | 为什么不能做？怎样获得权限？ | 免费额度用完：说明规则与选项 |
| 离线或网络中断 | 已输入的内容怎样保护？ | 上传中断：保留文件，恢复后继续 |
| 冲突 | 多人或多端修改同一对象时怎样处理？ | 在另一台设备上修改了简历：提示版本差异 |
| 已过期或已变化 | 数据过期时怎样提示？ | 简历已修改：旧的分析结果标注“基于旧版本” |

#### 05.3 状态图

对于状态复杂的对象，用状态图描述状态与转换，并与开发者一起确认。设计中的状态应与系统真实的状态一致：界面显示“已取消”，后台任务也必须真的停止或被标记为取消。长任务状态的工程设计见[《后端进阶全景手册》第 19 章](../技术方向/后端进阶全景手册.md#ch19)。

#### 05.4 中断与恢复

用户随时可能离开：接电话、切换应用、关闭浏览器。设计时考虑：未完成的输入是否保存？回来后能否从中断处继续？长时间离开后，数据是否已变化？

**本章验收**：为一个功能完成流程图与状态清单，至少覆盖 8 种非正常状态；请一位开发者对照检查，记录其发现的遗漏。

<a id="ch06"></a>

### 06 交互原则、模式与反馈

#### 06.1 可用性启发式原则

Nielsen 的十条可用性启发式原则是最常用的交互检查框架：系统状态可见；系统与现实世界一致；用户有控制权和自由度；一致性与标准；预防错误；识别优于回忆；灵活高效；简洁的美学设计；帮助用户识别、诊断错误并从中恢复；帮助与文档。[B04](#ref-b04) 这些原则适合用于设计自查和评审，但不能代替用户测试。

#### 06.2 反馈的时间

用户对系统响应时间的感受有几个常被引用的界限：大约 0.1 秒以内，用户感觉系统是即时响应的；大约 1 秒以内，用户的思路不会被打断，但能察觉到延迟；超过大约 10 秒，用户的注意力难以保持，需要明确的进度反馈，并允许做其他事情。[B05](#ref-b05) 这些数值来自早期的人机交互研究，是设计反馈方式的参考，而不是精确的性能指标。

| 等待时间 | 推荐的反馈方式 |
| --- | --- |
| 很短 | 直接显示结果，无需加载提示 |
| 约 1 秒 | 轻量的加载指示，避免界面闪烁 |
| 数秒 | 显示加载状态，必要时显示占位内容 |
| 超过约 10 秒 | 显示进度或阶段，允许离开或取消，完成后通知 |

#### 06.3 预防错误与恢复

- **预防**：用合适的控件限制无效输入（例如日期选择器），在提交前提示可能的问题，给出合理的默认值。
- **确认与撤销**：对可逆的操作，提供撤销通常比弹出确认框更好；对不可逆、影响大的操作，使用明确的确认，并说明后果。
- **错误信息**：说明发生了什么、为什么、用户可以怎样解决；保留用户已输入的内容。

#### 06.4 交互成本

目标越远、越小，用户点中它所需的时间就越长，这一关系由 Fitts 定律描述。[B06](#ref-b06) 实践中：常用操作的目标要足够大、放在容易到达的位置；危险操作不要紧挨常用操作。触屏、鼠标、键盘的交互成本不同，需要分别考虑；可访问性标准中的点击目标尺寸要求见 11 章。

#### 06.5 选择合适的交互模式

优先使用用户熟悉的平台惯例和成熟模式，例如标准的表单控件、对话框、标签页、分页与筛选。只有在常规模式明显不能满足任务时，才设计新的交互方式，并通过测试验证。各平台的设计指南（如 Apple 人机界面指南、Material Design）和政府设计系统（如 GOV.UK 设计系统）提供了大量经过验证的模式。

**本章练习**：用十条启发式原则对一个现有页面进行自查，列出至少 10 个问题，按严重程度排序并给出修改方案。

<a id="ch07"></a>

### 07 原型与设计表达

#### 07.1 保真度与目的

| 原型类型 | 适合的目的 | 注意 |
| --- | --- | --- |
| 纸面草图 | 快速探索多个方向，讨论结构 | 成本最低，便于丢弃 |
| 线框图 | 确定布局与信息层级 | 不要过早纠结视觉细节 |
| 可点击原型 | 测试流程与交互 | 覆盖测试任务需要的路径 |
| 高保真原型 | 测试细节、视觉与文案，向外部展示 | 容易被误认为已经定稿 |
| 代码原型 | 测试真实数据、动效、性能和复杂交互 | 成本较高，适合关键交互 |

原型的保真度应与要回答的问题匹配。测试“用户能否找到入口”不需要高保真视觉；测试“动画是否让人理解卡片的去向”则需要接近真实的动效。

#### 07.2 用真实内容设计

使用真实或接近真实的内容：长姓名、长标题、空字段、超长列表、多语言文本。用“示例文本”设计的界面，遇到真实内容时常常崩溃。

#### 07.3 AI 生成的原型

AI 工具可以快速生成界面草图和可运行的原型，适合探索多个方向。需要注意：生成的界面往往只覆盖正常状态；可能使用不符合平台惯例或不可访问的模式；看起来完整，容易让团队过早认为“已经设计好了”。生成结果应当作为讨论材料，而不是最终方案。

**本章练习**：对同一个任务，用纸面草图做出三个不同的方案，选出一个做成可点击原型，完成 3 人的快速测试。

<a id="ch08"></a>

### 08 评估、评审与迭代

#### 08.1 评估方法

| 方法 | 做法 | 适用阶段 |
| --- | --- | --- |
| 启发式评估 | 几位评估者按原则独立检查后汇总 | 早期到上线前，成本低 |
| 认知走查 | 从新用户视角逐步检查每一步能否被理解 | 关注首次使用与易学性 |
| 可用性测试 | 观察真实用户完成任务 | 原型到上线后，证据最直接 |
| 数据分析 | 观察漏斗、错误与使用路径 | 上线后，发现问题位置 |
| A/B 测试 | 比较不同方案的效果 | 上线后，需要足够流量 |

启发式评估最好由多位评估者独立进行再汇总，因为单个评估者通常只能发现一部分问题。[B07](#ref-b07) 认知走查由 Wharton 等人在 1990 年代系统化，适合检查新用户能否在没有帮助的情况下完成任务。

#### 08.2 设计评审

设计评审（Design Critique）的目的是改进方案，而不是评判设计师。有效的评审：

- 设计师先说明目标、用户、约束和希望获得反馈的部分。
- 评审者围绕目标提出观察与问题，而不是表达个人喜好。
- 区分“必须解决的问题”和“可以考虑的建议”。
- 记录结论与后续行动。

#### 08.3 迭代

每次迭代聚焦少数关键问题，修改后再验证。保留各版本与决策理由，避免在同样的问题上反复摇摆。

**本章验收**：组织一次 3 人的启发式评估和一次设计评审，整理问题清单，完成一轮修改并用测试验证改进效果。

<a id="ch09"></a>

### 09 设计规格与开发交付

#### 09.1 交付什么

| 内容 | 说明 |
| --- | --- |
| 用户流程与状态清单 | 所有路径与状态，含异常与边界 |
| 交互说明 | 触发条件、反馈、动效参数、焦点变化 |
| 布局与响应式规则 | 不同宽度下怎样重排，内容超长时怎样处理 |
| 组件与设计令牌 | 使用哪些现有组件，新增组件的规格 |
| 文案 | 所有标签、提示、错误信息的最终版本 |
| 无障碍说明 | 键盘顺序、焦点管理、读屏文字、对比要求 |
| 数据与边界 | 字段长度、空值、排序、分页规则 |
| 埋点需求 | 与产品经理、数据分析师共同确认 |

#### 09.2 交付方式

规格不必写成厚文档。常用方式是在设计文件中标注关键说明，配合状态清单和流程图，再与开发者一起走查。复杂的交互用原型或录屏说明，比文字更准确。

#### 09.3 设计走查

开发完成后，设计师按规格检查实现：所有状态是否实现、交互细节是否一致、不同宽度与内容长度下是否正常、键盘与读屏是否可用。走查发现的问题按严重程度分级，与开发者一起决定处理方式。

**本章验收**：为一个功能准备完整的交付材料，开发完成后进行设计走查，记录实现与设计的差异，并分析差异的原因（规格不清、实现限制还是遗漏）。

## 第三篇：专项与进阶

<a id="ch10"></a>

### 10 复杂产品与专业工具的交互

#### 10.1 专业用户的特点

专业工具的用户每天长时间使用，追求效率；他们愿意学习，但不能容忍反复的低效操作。与面向大众的产品相比，专业工具更需要：

- **信息密度**：在一屏内展示更多信息，同时保持可读。
- **批量操作**：对多个对象同时执行操作，并清楚展示影响范围。
- **键盘快捷键与命令**：高频操作不依赖鼠标。
- **可配置的工作区**：列、筛选、视图可以保存。
- **可预测性**：相同的操作在各处表现一致。

#### 10.2 数据表格

表格是专业工具中最常见、也最复杂的组件。需要设计：列的优先级与隐藏、排序与筛选、分页或虚拟滚动、行选择与批量操作、行内编辑、空值与加载、列宽调整、导出。每一项都要考虑大量数据与长内容。

#### 10.3 多步骤与长流程

多步骤的向导适合首次完成复杂配置；但对于高频任务，用户更希望在一个页面完成。长流程需要显示进度、允许保存草稿、在步骤之间返回而不丢失数据。

**本章练习**：为招聘管理后台设计应聘者列表，支持筛选、批量更改状态、键盘操作和列配置，并说明在 1 万条数据时的表现方式。

<a id="ch11"></a>

### 11 无障碍与包容性交互

#### 11.1 从设计阶段开始

无障碍不只是开发阶段的技术问题，很多障碍在设计阶段就已产生：只用颜色区分状态、焦点顺序混乱、自定义控件无法用键盘操作、错误信息只在视觉上显示。《Web 内容无障碍指南》（WCAG）2.2 把要求组织为可感知、可操作、可理解、健壮四个原则。[B08](#ref-b08)

#### 11.2 交互设计中的关键检查

- 所有功能都能用键盘完成，焦点顺序符合阅读与操作顺序，焦点始终可见。
- 状态和信息不只依靠颜色表达，还有文字或图标。
- 点击目标足够大：WCAG 2.2 的 AA 级要求一般不小于 24×24 CSS 像素，或与相邻目标保持足够间距。
- 表单有可见的标签，错误信息与对应字段关联，并说明怎样修正。
- 有时间限制的操作可以延长或关闭。
- 动画可以被减少，不会引起不适。
- 自定义组件遵循 WAI-ARIA 创作实践中的键盘交互模式。[B09](#ref-b09)

更完整的方法与验收见[《无障碍专家》](09-无障碍专家.md)。

**本章练习**：只使用键盘完成你设计的一个完整流程，记录所有无法完成或困难的地方，并修改设计。

<a id="ch12"></a>

### 12 AI 产品的交互设计

#### 12.1 AI 带来的交互问题

AI 功能的结果具有不确定性，这给交互设计带来新的问题：怎样设定用户对能力的预期？怎样表达不确定性？用户怎样纠正错误？系统为什么给出这个结果？用户怎样控制系统的行为？

微软研究院与合作者总结了人与 AI 交互的 18 条指南，按交互的时间顺序分为四组：交互开始时（说明系统能做什么、做得多好）、交互过程中（根据情境提供服务、遵循社会规范、减少偏见）、出错时（支持高效地调用、忽略和纠正，说明系统为什么这样做）、随时间推移（记住最近的交互、谨慎地更新、鼓励细粒度的反馈、通知变化）。[B10](#ref-b10) Google 的 People + AI Guidebook 从用户需求与成功定义、数据、心智模型、可解释与信任、反馈与控制、错误与平稳失败六个方面提供方法与工作表。[B11](#ref-b11)

#### 12.2 常见的 AI 交互模式

| 问题 | 设计方式 |
| --- | --- |
| 等待时间长 | 流式输出、阶段提示、允许取消与后台继续 |
| 结果可能出错 | 展示依据与来源，提供编辑、重新生成与反馈入口 |
| 用户过度信任 | 说明适用范围与局限，对高影响结果要求确认 |
| 用户不知道能做什么 | 提供示例输入与能力说明 |
| 结果与输入版本不一致 | 标明结果基于哪个版本的输入 |
| 系统执行了操作 | 清楚展示执行了什么、影响了哪些对象，并支持撤销 |

#### 12.3 设计与评测结合

AI 交互的设计需要与评测一起进行：在原型中加入错误或不确定的结果，观察用户能否察觉和纠正（见[《用户研究员》第 12 章](02-用户研究员.md#ch12)）。

**本章验收**：为 AI 简历分析设计结果页，覆盖依据展示、单条建议的接受与拒绝、整体重新生成、反馈入口和“基于旧版本”的提示，并用 18 条指南逐条自查。

<a id="ch13"></a>

### 13 交互体系与设计系统

#### 13.1 一致性的价值与代价

一致的交互让用户在产品各处使用相同的知识，减少学习成本和错误。但一致性也有代价：规范过于僵硬会让特殊场景难以设计好。好的交互体系说明每个模式的适用场景、不适用的场景和例外处理方式。

#### 13.2 交互模式库

交互模式库记录可复用的解决方案，例如“表单错误处理”“批量操作”“长任务进度”“空状态”。每个模式包括：要解决的问题、适用与不适用场景、交互规则、状态、文案指南、无障碍要求、代码组件链接和使用示例。模式库与组件库应保持对应，组件实现见[《前端与 UI／UX 设计进阶全景手册》第 13 章](../技术方向/前端与UIUX设计进阶全景手册.md#chapter-13)。

#### 13.3 治理

设计系统需要明确：谁可以新增或修改模式、怎样提出变更、怎样通知使用者、旧模式怎样迁移和淘汰。没有治理的设计系统会逐渐出现大量重复和互相矛盾的组件。

**本章练习**：从一个产品中找出同一类交互的 3 种不同实现，统一为一个模式，写出完整的模式说明。

<a id="ch14"></a>

### 14 度量用户体验

#### 14.1 常用指标

| 指标 | 含义 | 获取方式 |
| --- | --- | --- |
| 任务成功率 | 用户能否完成任务 | 可用性测试、产品数据 |
| 任务耗时 | 完成任务需要的时间 | 可用性测试、产品数据 |
| 错误率 | 用户犯错的频率与类型 | 测试观察、错误日志 |
| 满意度 | 主观感受，例如 SUS 量表 | 问卷 |
| 采用与留存 | 用户是否开始使用并持续使用 | 产品数据 |

Google 的 HEART 框架提供了从目标到指标的映射方法，可以参考[《产品经理》第 04 章](01-产品经理.md#ch04)。

#### 14.2 指标的局限

指标说明“发生了什么”，不一定说明“为什么”；单一指标可能误导，例如页面停留时间增加，可能是用户更投入，也可能是用户找不到想要的东西。体验度量应与定性研究结合，并在设计前确定要观察的指标。

**本章练习**：为一个设计改动定义 3 个体验指标，写清数据来源与口径，上线后观察并结合 5 次用户访谈解释结果。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与开发者的协作接口

#### 15.1 交互设计师应提供给开发者的内容

| 内容 | 最低要求 | 常见缺失 |
| --- | --- | --- |
| 流程与状态 | 所有路径与状态 | 只有正常流程的静态页面 |
| 交互细节 | 触发、反馈、焦点、动效参数 | “参考某某应用”而没有具体说明 |
| 响应式规则 | 不同宽度下的布局与优先级 | 只有一个宽度的设计稿 |
| 内容边界 | 长文本、空值、大量数据的处理 | 只用理想内容设计 |
| 无障碍要求 | 键盘、焦点、读屏文字 | 完全没有提及 |
| 取舍理由 | 为什么这样设计 | 开发者无法在细节上做出一致的判断 |

#### 15.2 开发者应反馈给交互设计师的内容

实现成本特别高的交互及替代方案、技术约束（例如某个操作需要数秒才能完成）、组件库已有的能力、设计稿中遗漏的状态、实际数据与设计假设的差异。

#### 15.3 早合作，常对齐

在方案阶段邀请开发者参与，比在交付后才讨论更有效：开发者能提前指出约束，也能提出设计师没有想到的可能性。开发过程中，用简短的同步代替长篇的文档往返；遇到规格未覆盖的情况，开发者先询问，而不是自行假设。

<a id="ch16"></a>

### 16 开发者怎样做好交互设计

#### 16.1 独立开发者和外包工程师的实用做法

- **先写状态清单，再画界面**：对每个页面列出空、加载、错误、权限、离线等状态，逐一设计。
- **使用成熟的组件库与设计系统**：遵循其交互规范，避免自创控件。
- **用真实数据测试布局**：长名称、空字段、大量数据。
- **只用键盘走一遍**：能发现大量交互和无障碍问题。
- **找 3 个人试用**：观察他们卡在哪里，而不是问他们觉得怎么样。
- **用启发式原则自查**：每次发布前花 30 分钟检查。

#### 16.2 技术背景的常见偏差

- 按数据库结构设计界面：字段按表结构排列，而不是按用户的任务顺序。
- 暴露技术术语和错误信息给用户。
- 只考虑实现方便的交互，忽视用户的效率。
- 认为“功能都在，用户自己会找”。

技术背景也有优势：了解系统的真实状态和约束，能设计出与系统行为一致的反馈；能用代码原型快速验证复杂交互。

<a id="ch17"></a>

### 17 贯穿实战：简历上传与分析流程

本章展示交互设计的完整过程。数字均为示意。

#### 17.1 起点

产品经理与研究员确定了问题：学生投递前不知道简历哪里需要改，也无法判断修改是否有效（见[《产品经理》第 17 章](01-产品经理.md#ch17)）。研究发现，学生更容易理解“问题＋原因＋修改示例”的建议结构，并希望看到修改前后的对比。

#### 17.2 流程与状态

1. 完成任务分析：获取反馈、理解并处理建议、判断修改是否有效。
2. 绘制用户流程：从首页入口、个人中心入口和投递前提示三个入口进入；覆盖上传失败、解析失败、分析超时、额度不足、中途离开、在其他设备修改简历等情况。
3. 编写状态清单，共 14 种状态，其中“分析中”允许离开页面，完成后站内通知。
4. 与后端开发者确认：分析任务有明确的状态，取消后不再消耗额度；旧版本的结果会被标记。

#### 17.3 原型与测试

- 第一轮：三个结果页方案的纸面原型，与 3 名学生讨论，选择“按简历段落组织建议”的方案。
- 第二轮：可点击原型，5 名学生完成“上传、查看建议、修改一条经历、重新分析”的任务。发现两个严重问题：学生不知道“标记为不适用”的含义；重新分析后找不到修改前后的对比入口。
- 第三轮：修改后再测 5 人，两个问题均已解决，任务成功率明显提高。

#### 17.4 交付与走查

交付材料包括流程图、14 种状态的设计、交互说明、文案（与内容设计师共同完成）、无障碍说明（键盘顺序、建议列表的读屏结构）和埋点需求。开发完成后进行设计走查，发现 6 处差异，其中“超长段落的建议定位”在小屏幕上错位，与前端开发者一起修正。

#### 17.5 上线后

观察“建议采纳率”和“重新分析率”，结合 5 次回访，发现学生经常在手机上查看建议、在电脑上修改简历，于是把“跨设备继续”列为下一轮的改进重点。

#### 18.5 检查清单

设计时：

- [ ] 设计从任务与证据出发，而不是从界面元素出发。
- [ ] 流程覆盖入口、分支、异常、中断与恢复。
- [ ] 状态清单覆盖空、加载、部分、成功、错误、权限、离线、冲突、过期。
- [ ] 优先使用成熟模式，新交互经过测试。
- [ ] 用真实内容与边界数据检验布局。
- [ ] 键盘、焦点、对比、目标尺寸符合无障碍要求。

交付与实现：

- [ ] 交付材料包含流程、状态、交互细节、响应式规则、文案与无障碍说明。
- [ ] 开发前与开发者走查过方案。
- [ ] 实现后完成设计走查，差异已记录并处理。

上线后：

- [ ] 观察预先确定的体验指标，并结合定性反馈解释。
- [ ] 发现的问题进入下一轮改进。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 交互设计就是画线框图 | 线框图是表达工具，核心是任务、流程、状态与反馈 |
| 好看就是好用 | 视觉质量与可用性相关但不同，需要分别检验 |
| 设计稿交付就完成了 | 实现后的设计走查和上线后的验证同样重要 |
| 用户会自己摸索 | 用户通常不会花时间摸索，找不到就会离开或出错 |
| 新颖的交互更有竞争力 | 违背惯例的交互会增加学习成本，需要测试证明其价值 |
| 确认框可以防止所有错误 | 频繁确认会让用户习惯性点击，可逆操作更适合撤销 |
| 无障碍是开发阶段的事 | 很多障碍在设计阶段产生，需要从设计开始考虑 |
| 启发式评估可以代替用户测试 | 启发式评估成本低，但不能代替观察真实用户 |
| AI 可以直接生成完整的交互设计 | AI 生成的方案常缺少状态与边界，需要设计师判断与测试 |
