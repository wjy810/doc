# 数据库工程师／DBA 进阶全景手册

> 从让一个数据库稳定运行，到为业务设计可靠、高效、可恢复的数据存储，再到建立组织的数据库平台与变更治理。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：经常与数据库打交道的后端开发者、需要自己维护数据库的独立开发者与外包团队、准备转向数据库方向的工程师，以及希望系统提升的在职 DBA。

数据库工程师（DBA）要回答的核心问题是：业务数据能否被正确地保存、高效地访问、在故障后完整地恢复，以及在持续变化中安全地演进。数据库常常是系统中最难扩展、最难修改、出问题时影响最大的部分：一条没有索引的查询可以拖垮整个服务，一次锁表的结构变更可以让业务停止，一份没有验证过的备份可能在需要时无法恢复。

传统的 DBA 侧重于安装配置、性能调优、备份恢复与权限管理。随着托管数据库与自动化的普及，这个角色逐渐演变为数据库可靠性工程：用工程方法管理数据库的可靠性、变更与容量，把经验做成工具与平台，并更早地参与数据模型与查询的设计。

本手册先建立角色坐标，然后讲解数据建模与设计评审、查询与索引优化、事务与锁、监控与诊断、备份与恢复、高可用与复制、模式变更与数据迁移；随后进入容量与存储引擎选择、安全与合规、分布式数据库、数据库平台化、AI 与数据库；最后说明与开发者的协作，以及开发者应掌握的数据库基本功。示例以 PostgreSQL 与 MySQL 为主，具体行为以所用版本的官方文档为准。数据库在后端工程中的作用与事务语义，见[《后端进阶全景手册》第 09 章](../技术方向/后端进阶全景手册.md#ch09)。

主线是：**理解业务数据与访问模式 → 设计正确的模型与约束 → 让查询高效 → 控制并发与锁 → 可观测与诊断 → 可备份、可恢复、高可用 → 安全地变更与迁移 → 平台化与自助服务。**

不同组织中，这些职责可能由 DBA、数据库可靠性工程师、平台工程师或后端开发者承担，使用托管数据库时部分工作由云厂商负责。本手册描述数据库工程的职责本身；D1—D6 分级是学习组织方式，不对应任何职级体系。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 数据库工程师负责什么

#### 01.1 核心职责

| 职责 | 内容 |
| --- | --- |
| 可用与可靠 | 高可用架构、复制、故障切换、监控与告警 |
| 性能 | 查询与索引优化、配置调优、容量规划 |
| 数据安全 | 权限、加密、审计、脱敏 |
| 可恢复 | 备份、时间点恢复、恢复演练 |
| 变更 | 结构变更、数据迁移、版本升级 |
| 设计支持 | 数据模型与查询的评审 |
| 成本 | 资源使用、存储增长、实例选择 |

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 设计评审意见 | 在上线前发现模型与查询问题 | 具体、可执行，说明原因与替代方案 |
| 监控看板与告警 | 及时发现问题 | 覆盖延迟、连接、锁、复制、存储与慢查询 |
| 备份与恢复方案 | 证明可以恢复 | 恢复目标明确，定期演练 |
| 高可用方案 | 减少停机 | 切换流程经过测试，避免数据丢失与双主 |
| 变更规范与工具 | 安全地修改结构与数据 | 不锁业务、可观察、可回退或可前向修复 |
| 运行手册 | 处理常见问题 | 步骤可执行，经过演练 |
| 容量计划 | 提前准备资源 | 基于增长数据与预测 |

#### 01.3 职责边界与相邻角色

| 事项 | DBA 的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 数据模型与查询 | 评审与指导 | 后端开发者主导 | 开发者对自己的查询负责 |
| 数据库运行与可靠性 | 主导 | SRE、平台工程师 | |
| 分析型数据与数据仓库 | 协作 | 数据工程师 | 见[《数据工程师》](17-数据工程师.md) |
| 数据库安全 | 共同负责 | 安全工程师 | |
| 云数据库资源与成本 | 共同负责 | 平台工程师、财务 | |
| 业务数据修复 | 执行与把关 | 业务方、开发者 | 修复需要业务确认与记录 |

#### 01.4 不同组织中的形态

- **传统 DBA**：负责自建数据库的全部运维，常见于金融、电信与大型企业。
- **数据库可靠性工程师**：用工程方法与自动化管理数据库，参与设计与平台建设。
- **托管数据库时代的 DBA**：云厂商负责硬件与基础运维，DBA 专注于设计、性能、变更与成本。
- **开发者兼任**：小团队中由后端开发者负责，更依赖托管服务与规范。

**本章练习**：为你使用的数据库列出“如果它今天坏了会怎样”：多长时间能恢复、会丢失多少数据、谁能处理、步骤是什么，找出最不确定的部分。

<a id="ch02"></a>

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **数据建模**：表结构、约束、类型、分区与生命周期。
2. **查询与索引**：执行计划、索引设计、查询改写。
3. **事务与并发**：隔离、锁、死锁、长事务与多版本。
4. **监控与诊断**：指标、慢查询、等待事件与根因分析。
5. **备份与恢复**：备份方式、时间点恢复与演练。
6. **高可用与复制**：主从、切换、复制延迟与一致性。
7. **变更与迁移**：在线结构变更、数据回填、版本升级。
8. **容量与成本**：增长预测、存储管理、实例选择。
9. **安全与合规**：权限、加密、审计与脱敏。
10. **平台与自动化**：数据库自助服务、变更流水线与自动化工具。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 能读懂执行计划，执行常规运维操作 | 操作记录、优化过的查询 |
| D2 独立完成 | 独立完成性能优化、备份恢复与结构变更 | 优化报告、恢复演练、变更记录 |
| D3 负责结果 | 对一组数据库的可靠性、性能与容量负责 | 可用性、延迟、容量计划、事故复盘 |
| D4 系统与跨团队 | 设计跨团队的数据库架构与标准 | 高可用架构、分片方案、设计规范 |
| D5 方法与机制 | 建立数据库平台、变更治理与自助服务 | 变更流水线、自动评审、数据库平台 |
| D6 创新与影响 | 改进数据库技术或工具，影响社区 | 开源贡献、内核改进、公开研究 |

#### 02.3 成长中的常见偏差

- 只在出问题后介入，没有参与设计评审。
- 优化时只加索引，不分析访问模式与写入代价。
- 备份从未演练恢复，或只备份了数据库而遗漏了相关的配置与文件。
- 在业务高峰执行风险较高的变更。
- 所有变更都由 DBA 手工执行，成为团队瓶颈。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 数据建模与设计评审

#### 03.1 设计评审关注什么

| 方面 | 检查要点 |
| --- | --- |
| 实体与关系 | 是否反映业务；主键是否稳定；外键与唯一约束是否对应业务规则 |
| 类型 | 数值、金额、时间、文本的类型与精度是否合适 |
| 约束 | 非空、检查约束、唯一约束是否把规则交给数据库保证 |
| 访问模式 | 主要查询是什么，需要哪些索引，写入频率多高 |
| 数据量与增长 | 一年后多大，是否需要分区或归档 |
| 生命周期 | 数据保留多久，怎样删除与归档 |
| 并发 | 是否有热点行、是否需要条件更新或乐观锁 |

#### 03.2 常见问题

- 用字符串保存时间或金额，导致排序、计算与比较错误。
- 缺少唯一约束，只靠应用代码保证唯一，在并发下失效。
- 把多个值存在一个字段中（例如逗号分隔），无法索引与约束。
- 大表缺少分区与归档计划，几年后难以维护。
- 为了“灵活”大量使用无结构的字段，失去了类型与约束的保护。

**本章验收**：对一个新功能的表设计进行评审，按上表逐项检查，写出评审意见与修改建议。

<a id="ch04"></a>

### 04 查询与索引优化

#### 04.1 从执行计划开始

优化查询的第一步是看执行计划：数据库打算怎样执行这条查询，使用哪些索引，估计处理多少行，实际处理多少行。PostgreSQL 的 `EXPLAIN ANALYZE` 会实际执行查询并显示真实的耗时与行数。[B01](#ref-b01) 估计行数与实际行数相差很大时，通常说明统计信息过时或数据分布特殊。

#### 04.2 索引设计

- 索引服务于查询：先确定主要的查询条件与排序，再设计索引。
- 复合索引的列顺序很重要：通常把等值条件的列放在前面，范围条件与排序的列放在后面。
- 覆盖索引让查询只读索引即可完成，避免回表。
- 每个索引都有写入与存储成本，不要为每个字段都建索引。
- 定期检查未被使用的索引与重复的索引。

“Use The Index, Luke” 是一份免费、面向开发者的 SQL 索引与性能教程，覆盖多种数据库。[B02](#ref-b02)

#### 04.3 常见的慢查询原因

| 原因 | 表现 | 处理 |
| --- | --- | --- |
| 缺少合适的索引 | 全表扫描 | 按访问模式设计索引 |
| 统计信息不准 | 执行计划选择错误 | 更新统计信息，检查数据分布 |
| 返回数据过多 | 网络与内存压力 | 只查询需要的列与行，使用分页 |
| 深分页 | 偏移量越大越慢 | 使用基于游标的分页 |
| N+1 查询 | 大量相似的小查询 | 批量查询或连接 |
| 函数或类型转换使索引失效 | 有索引但未使用 | 改写条件或建立表达式索引 |
| 锁等待 | 查询本身快，但等待时间长 | 见 05 章 |

**本章验收**：从慢查询日志中选出最耗时的 5 条查询，逐条分析执行计划，优化后比较耗时，并说明每项优化的写入代价。

<a id="ch05"></a>

### 05 事务、锁与并发问题

#### 05.1 隔离级别

隔离级别规定了并发事务之间可以看到什么。不同数据库对同一级别的实现不同，例如 PostgreSQL 的“读未提交”实际按“读已提交”实现。[B03](#ref-b03) 使用事务时要明确需要防止哪些异常，并在对应的数据库与版本中验证（见[《后端进阶全景手册》第 09 章](../技术方向/后端进阶全景手册.md#ch09)）。

#### 05.2 锁与等待

- **行锁与表锁**：结构变更、某些维护操作可能需要表级的锁，阻塞所有读写。[B04](#ref-b04)
- **锁等待**：一个长事务持有锁，后续的请求排队等待，连接池被耗尽，最终整个服务不可用。
- **死锁**：两个事务互相等待对方持有的锁。数据库会检测并中止其中一个，应用需要能重试。

#### 05.3 长事务与多版本

采用多版本并发控制的数据库，会保留旧版本的数据以供正在进行的事务读取。长时间运行的事务会阻止旧版本被清理，导致表膨胀与性能下降。PostgreSQL 依靠清理（vacuum）回收空间，需要关注清理是否跟得上，以及事务编号回卷的风险。[B05](#ref-b05)

#### 05.4 热点行

大量请求同时更新同一行（例如一个全局计数器、一个热门商品的库存）会形成锁竞争。可以拆分计数、批量合并、使用队列串行化，或调整业务规则。

**本章练习**：在测试环境中制造一次锁等待与一次死锁，用数据库的监控视图找到阻塞者与被阻塞者，写出诊断步骤。

<a id="ch06"></a>

### 06 监控与诊断

#### 06.1 关键指标

| 类别 | 指标 |
| --- | --- |
| 负载 | 每秒查询与事务数、活跃连接数 |
| 延迟 | 查询延迟的分布，慢查询数量 |
| 资源 | CPU、内存、磁盘使用与读写、网络 |
| 并发 | 锁等待、死锁、长事务 |
| 复制 | 复制延迟、复制状态 |
| 存储 | 表与索引的大小与增长、膨胀、剩余空间 |
| 缓存 | 缓冲区命中率 |
| 维护 | 清理与统计信息更新的状态 |

PostgreSQL 提供了丰富的统计视图，[B06](#ref-b06) `pg_stat_statements` 扩展可以按查询汇总执行次数与耗时，是找出最耗资源查询的常用工具。[B07](#ref-b07)

#### 06.2 诊断的思路

从现象出发：延迟升高？连接数打满？CPU 飙升？然后查看等待事件与正在执行的查询：数据库在等待什么——锁、磁盘、CPU 还是网络？结合最近的变更（发布、配置、数据量变化）缩小范围。连接池满往往是结果而不是原因，根源可能是慢查询、长事务或外部等待。

**本章验收**：为一个数据库建立监控看板与告警，编写“连接数打满”“复制延迟过大”“磁盘即将写满”三份运行手册。

<a id="ch07"></a>

### 07 备份、恢复与时间点恢复

#### 07.1 备份方式

| 方式 | 特点 | 适用 |
| --- | --- | --- |
| 逻辑备份 | 导出为语句或数据文件，跨版本可移植 | 小数据量、迁移、部分恢复 |
| 物理备份 | 复制数据文件，恢复快 | 大数据量的整体恢复 |
| 连续归档 | 物理备份加上持续的日志归档 | 时间点恢复 |
| 快照 | 存储或云平台的快照 | 快速恢复，需注意一致性 |

PostgreSQL 的连续归档基于基础备份与预写日志，可以恢复到任意时间点，但恢复的是整个数据库集群，而不是任意的一部分。[B08](#ref-b08)

#### 07.2 恢复演练

只有恢复过的备份才是可信的。定期在隔离环境中恢复，记录实际的恢复时间与数据完整性，并与恢复目标比较。局部误删时，可以先在隔离环境中恢复到误删前的时间点，再提取需要的数据合并回生产环境，避免覆盖误删之后的正常写入（见[《后端进阶全景手册》第 24 章](../技术方向/后端进阶全景手册.md#ch24)）。

#### 07.3 备份本身的安全

备份包含全部数据，需要加密、访问控制与独立存储，防止被误删或被勒索软件加密。备份的保留期限也要符合数据删除的要求。

**本章验收**：完成一次时间点恢复演练：在测试环境中模拟误删一张表，恢复到误删前，提取数据并验证完整性，记录全过程的时间。

<a id="ch08"></a>

### 08 高可用与复制

#### 08.1 复制

主库处理写入，从库通过复制获得数据，可以分担读取并在主库故障时接管。同步复制保证提交的数据在从库上也存在，但增加写入延迟；异步复制性能更好，但主库故障时可能丢失最近提交的数据。PostgreSQL 的文档详细说明了各种高可用与复制方案的特点。[B09](#ref-b09)

#### 08.2 读写分离的陷阱

从库的数据可能落后于主库。刚写入的数据立即从从库读取，可能读不到。需要根据业务要求决定哪些读取必须走主库，或者在应用中处理复制延迟。

#### 08.3 故障切换

切换需要可靠的故障检测，避免误判；需要防止两个节点同时认为自己是主库（脑裂）；需要应用能连接到新的主库。切换流程要定期演练，并记录切换过程中丢失或需要核对的数据。

**本章练习**：在测试环境中搭建一主一从，模拟主库故障并完成切换，记录切换时间、数据丢失情况与应用的表现。

<a id="ch09"></a>

### 09 模式变更与数据迁移

#### 09.1 变更的风险

结构变更可能锁表、导致长时间的重写、影响复制，或者与正在运行的旧版本代码不兼容。在大表上直接执行某些变更，可能让业务停止数分钟甚至更长。

#### 09.2 在线结构变更

对于需要重写表的变更，可以使用在线变更工具：创建一张新结构的影子表，逐步复制数据并同步增量变化，最后快速切换。MySQL 生态中常用 gh-ost 与 pt-online-schema-change。[B10](#ref-b10) 在 PostgreSQL 中，许多变更可以通过合适的方式避免长时间锁表，例如并发创建索引、分步添加约束。

#### 09.3 扩展与收缩

与应用发布配合的安全变更通常分为几步：先扩展（新增字段或表，兼容新旧代码）；部署能同时读写新旧结构的代码；回填历史数据并核对；切换到新结构；确认旧代码不再使用后收缩（删除旧字段）。每一步都可以独立发布与观察（见[《后端进阶全景手册》第 25 章](../技术方向/后端进阶全景手册.md#ch25)）。

#### 09.4 数据回填与修复

大批量的数据修改需要：分批与限速，避免影响业务与复制；记录检查点，可以中断后继续；执行前预览影响范围；执行后核对结果。数据修复属于业务变更，需要业务方确认并留下记录。

**本章验收**：为一张有持续写入的大表设计一次字段类型变更方案，分步骤说明兼容性、回填、核对与回退方式，在测试环境中执行并测量对业务的影响。

## 第三篇：专项与进阶

### 10 容量、成本与存储选择

#### 10.1 容量规划

跟踪数据量、查询量与资源使用的增长，预测何时会触及上限：磁盘空间、连接数、内存、写入吞吐。提前规划：扩容、归档历史数据、分区、优化查询，或者调整架构。

#### 10.2 存储选择

| 类型 | 适合 | 注意 |
| --- | --- | --- |
| 关系数据库 | 事务、约束、复杂查询 | 水平扩展需要额外设计 |
| 键值存储 | 按键快速读写 | 查询能力有限 |
| 文档数据库 | 结构多变的文档 | 仍需要模式与约束的设计 |
| 列式数据库 | 分析与聚合查询 | 不适合频繁的单行更新 |
| 时序数据库 | 带时间戳的指标与事件 | 保留与降采样策略 |
| 搜索引擎 | 全文检索与相关性排序 | 通常作为派生数据，不是权威来源 |
| 对象存储 | 文件与大对象 | 与数据库之间没有自动的事务 |

选择时比较访问模式、一致性需要、扩展方式、运维成本与团队能力。多种存储并存时，明确每类数据的权威来源与同步方式。

#### 10.3 托管与自建

托管数据库减少了硬件、备份与基础运维的负担，但仍需要关注配置、性能、成本、版本升级与供应商限制。自建提供更多控制，也需要更多的人力。

**本章练习**：为一个数据库做一年的容量预测，找出最先触及的上限，比较扩容、归档与优化三种方案的成本与风险。

<a id="ch11"></a>

### 11 安全与合规

#### 11.1 权限

- 应用使用权限最小的数据库账号，不使用超级用户。
- 区分读写账号、只读账号、迁移账号与管理员账号。
- 人员访问生产数据库需要审批、记录与时限。
- 定期审查权限，回收不再需要的账号。

#### 11.2 行级安全

PostgreSQL 的行级安全策略可以在数据库层面限制每个角色能看到和修改的行，作为多租户隔离的一层保护。需要注意：超级用户与具有绕过行级安全属性的角色不受策略限制，表的所有者默认也不受限制，除非强制启用。[B11](#ref-b11)

#### 11.3 加密、审计与脱敏

传输与存储加密；对敏感数据的访问进行审计；非生产环境使用脱敏或合成数据，而不是直接复制生产数据。个人信息的保留与删除要求由法务确认，工程实现见[《后端进阶全景手册》第 23 章](../技术方向/后端进阶全景手册.md#ch23)。

**本章练习**：审查一个数据库的账号与权限，找出权限过大的账号，制定整改方案；为一张包含个人信息的表设计脱敏规则。

<a id="ch12"></a>

### 12 分布式数据库与分片

#### 12.1 何时需要分片

单个数据库实例的写入能力或存储容量不足时，可以考虑分片：把数据按某个键分布到多个实例。分片带来显著的复杂度：跨分片的查询与事务、数据重新平衡、热点分片、运维与备份。在分片之前，先尝试优化查询、读写分离、垂直拆分、归档历史数据与升级硬件。

#### 12.2 分片键

分片键决定了数据的分布与查询的效率。好的分片键让大多数查询只访问一个分片，并让数据与负载均匀分布。以租户编号分片适合多租户系统，但大租户可能形成热点。

#### 12.3 分布式 SQL 数据库

一些数据库在内部实现了自动分片、复制与分布式事务，对应用呈现为一个数据库。它们简化了应用的分片逻辑，但仍需要理解其一致性模型、延迟特性、热点问题与运维要求。

**本章练习**：为一个多租户系统设计分片方案，选择分片键，说明跨分片查询的处理方式与大租户的应对。

<a id="ch13"></a>

### 13 数据库平台化与自助服务

#### 13.1 从手工到平台

当团队与数据库数量增长时，DBA 逐一处理请求会成为瓶颈。数据库平台提供：

- 自助创建数据库，默认包含备份、监控、权限与安全配置。
- 结构变更流水线：变更脚本与代码一起提交，在流水线中自动检查风险（锁表、缺少索引、不兼容的修改）并在测试环境执行。
- 查询评审：自动检查新查询的执行计划与潜在问题。
- 统一的监控、慢查询分析与容量报告。

#### 13.2 变更治理

为不同风险的变更设定不同的流程：低风险变更自动执行；中风险变更需要评审；高风险变更（大表重写、数据修复）需要专门的计划、时间窗口与回退方案。治理的目标是让大多数变更安全而快速，而不是让所有变更都排队等待（平台建设的方法见[《平台工程师与研发效能》](14-平台工程师与研发效能.md)）。

**本章练习**：为团队设计结构变更流水线，列出自动检查的规则，并为一次高风险变更编写变更计划。

<a id="ch14"></a>

### 14 AI 与数据库

#### 14.1 向量检索

AI 应用常需要按语义相似度检索内容。可以使用专门的向量数据库，也可以在已有的数据库中使用扩展，例如 PostgreSQL 的 pgvector。[B12](#ref-b12) 在已有数据库中实现向量检索，便于与业务数据一起查询和过滤权限，但需要评估索引的构建时间、内存占用、召回率与对其他业务查询的影响。

#### 14.2 用 AI 生成和优化查询

AI 可以帮助编写查询、解释执行计划和提出优化建议，但需要注意：

- 生成的查询可能在语义上不正确，或在大数据量下性能很差，需要审查与测试。
- 让模型直接根据自然语言查询数据库时，必须使用权限受限的只读账号、限制可访问的表与返回的行数，并防止通过输入注入恶意的语句。
- 不要把包含敏感数据的查询结果发送给未经评估的外部服务。

**本章练习**：在测试环境中为一张业务表添加向量检索，比较开启前后的业务查询延迟与资源占用，并评估检索的召回率。

### 15 与开发者的协作接口

#### 15.1 DBA 应提供给开发者的内容

| 内容 | 最低要求 | 常见缺失 |
| --- | --- | --- |
| 设计规范 | 命名、类型、约束、索引的规则与示例 | 只有口头约定 |
| 变更流程 | 怎样提交、评审与执行结构变更 | 开发者直接在生产执行变更 |
| 查询分析工具 | 开发者能自己查看执行计划与慢查询 | 只有 DBA 能看到 |
| 及时的评审 | 设计阶段的评审 | 上线前才发现问题 |
| 运行信息 | 数据量、增长、热点与资源使用 | 开发者不了解生产数据的规模 |

#### 15.2 开发者应提供给 DBA 的内容

新功能的访问模式与数据量预估、计划中的结构变更与数据迁移、关键查询、业务高峰的时间、出现问题时的业务影响。

#### 15.3 共同负责

开发者对自己的查询与数据模型负责，DBA 提供标准、工具与专业支持。把数据库评审纳入设计评审与代码评审，而不是上线前的额外关卡。

<a id="ch16"></a>

### 16 开发者的数据库基本功

#### 16.1 十条基本功

1. 为业务规则建立数据库约束：主键、外键、唯一、非空、检查。
2. 选择正确的类型：金额用精确的数值类型，时间用时间类型并明确时区。
3. 为主要查询设计索引，并查看执行计划。
4. 避免 N+1 查询，只查询需要的列。
5. 控制事务的范围，不在事务中等待外部调用或用户输入。
6. 并发修改同一数据时，使用条件更新、乐观锁或唯一约束。
7. 分页使用基于游标的方式，避免深分页。
8. 结构变更兼容新旧代码，大表变更使用在线方式。
9. 关键的数据库行为在真实数据库上测试。
10. 了解生产数据的规模与增长。

#### 16.2 独立开发者与外包项目

独立开发者优先使用托管数据库，并开启自动备份；至少每季度做一次恢复测试。外包项目交付时，提供数据模型说明、索引设计的理由、备份与恢复方案、结构变更的历史脚本，以及常见问题的处理方法。

### 17 贯穿实战：一次数据库性能事故与治理

本章展示一次事故的处理与之后的治理。数字均为示意。

#### 17.1 事故

招聘季的一个上午，求职平台的接口延迟大幅升高，部分请求超时。监控显示数据库连接数打满，大量查询处于等待状态。

#### 17.2 诊断

1. 查看正在执行的查询，发现大量请求在等待同一张表上的锁。
2. 找到阻塞者：一个后台任务正在为“申请记录”表添加带默认值的新字段，并且在一个长事务中逐批回填数据，持有锁的时间远超预期。
3. 同时发现一条新上线的岗位搜索查询没有使用索引，在高峰时进一步消耗了资源。

#### 17.3 止损与恢复

终止回填任务的事务，锁被释放，连接逐步恢复；为搜索查询临时关闭了新的筛选条件。服务在 20 分钟后恢复正常。

#### 17.4 复盘与治理

| 原因 | 改进 |
| --- | --- |
| 结构变更与回填在高峰期执行，且回填在一个长事务中进行 | 结构变更走流水线自动检查锁风险；回填改为分批的独立小事务，限速并避开高峰 |
| 新查询没有经过执行计划检查 | 在代码评审中加入关键查询的执行计划检查；建立慢查询的每日报告 |
| 没有对长事务与锁等待告警 | 新增长事务、锁等待与连接使用率的告警 |
| 开发者不了解生产数据规模 | 在开发者门户中展示主要表的数据量与增长 |

三个月后，团队的结构变更全部通过流水线执行，没有再发生由变更引起的锁表事故。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 慢就加索引 | 先看执行计划找原因，索引有写入与存储成本 |
| 用了事务就不会有并发问题 | 还需要明确隔离级别、约束与原子边界 |
| 有备份就能恢复 | 只有演练过的恢复才可信 |
| 从库的数据和主库一样 | 异步复制下从库可能落后 |
| 托管数据库不需要 DBA | 设计、性能、变更与成本仍然需要专业判断 |
| 分片能解决所有扩展问题 | 分片带来很高的复杂度，应先尝试其他方法 |
| 加个字段很简单 | 在大表上可能锁表或重写，需要选择合适的方式 |
| 隔离级别名称相同行为就相同 | 不同数据库的实现不同，需要查阅对应文档 |
| AI 生成的 SQL 可以直接上线 | 需要审查语义、性能与权限 |
