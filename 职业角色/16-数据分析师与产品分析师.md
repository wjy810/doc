# 数据分析师／产品分析师进阶全景手册

> 从回答一个业务问题，到为产品建立可信的指标与实验体系，再到让组织依靠证据做决定。  
> 版本：1.0 · 整理日期：2026-10-25  
> 适用对象：希望用数据判断产品效果的开发者与产品经理、准备转向数据分析或产品分析的工程师（包括有数据科学背景的学习者），以及希望系统提升的在职分析师。

数据分析师要回答的核心问题是：发生了什么、为什么发生、某个改动是否真的带来了变化，以及接下来应该怎样做。产品分析师是专注于产品使用与产品决策的数据分析师：功能上线后有没有人用、用户在哪一步流失、新版本是否比旧版本更好。

数据分析的价值不在于报表的数量，而在于帮助团队做出更好的决定。一份没有人看的看板、一个口径含糊的指标、一次设计有缺陷的实验，都可能让团队在错误的方向上越走越远。好的分析师会先问“这个分析要支持什么决定”，然后确保数据可信、方法恰当、结论的边界清楚。

本手册先建立角色坐标，然后讲解从业务问题到分析问题、指标体系与口径、埋点与数据采集、描述与诊断分析、实验设计与分析、因果推断、可视化与沟通；随后进入数据质量、自助分析与语义层、预测建模基础、AI 产品的分析、隐私与伦理；最后说明分析师与开发者的协作，并用简历分析功能演示一次完整的指标与实验工作。

主线是：**从决策出发提出问题 → 定义可复算的指标 → 采集可信的数据 → 描述与诊断 → 用实验或因果方法判断影响 → 清楚地沟通结论与边界 → 让组织持续用证据决策。**

不同公司中，这些职责可能由数据分析师、产品分析师、商业分析师、数据科学家或产品经理承担，与数据工程师、算法工程师的分工也各不相同。本手册描述数据分析的职责与方法；D1—D6 分级是学习组织方式，不对应任何职级体系。统计方法只介绍使用要点与常见陷阱，深入的理论需要阅读专门的教材。

## 第一篇：角色定位与能力坐标

<a id="ch01"></a>

### 01 数据分析师负责什么

#### 01.1 四类分析问题

| 类型 | 回答的问题 | 示例 |
| --- | --- | --- |
| 描述性 | 发生了什么 | 上周有多少学生完成了简历分析 |
| 诊断性 | 为什么发生 | 完成率下降集中在哪类用户和哪个步骤 |
| 因果性 | 某个改动是否引起了变化 | 新的建议呈现方式是否提高了采纳率 |
| 预测与决策 | 将会怎样，应该怎样做 | 下个月的分析需求量，需要准备多少容量 |

很多错误来自把一类问题当作另一类：用描述性的相关关系回答因果问题，或者在数据不可信时就开始诊断。

#### 01.2 主要产出与质量标准

| 产出 | 用途 | 好的标准 |
| --- | --- | --- |
| 指标定义与指标体系 | 统一团队对“好坏”的判断 | 口径清楚、可复算、与目标对应 |
| 埋点方案 | 采集需要的行为数据 | 事件命名一致，属性完整，经过验证 |
| 分析报告 | 回答具体的业务问题 | 结论先行，证据充分，局限清楚 |
| 实验设计与结果 | 判断改动的因果影响 | 事先确定指标与样本量，检查有效性 |
| 看板 | 持续监控关键指标 | 面向决策，口径与报告一致 |
| 数据质量检查 | 保证数据可信 | 发现缺失、重复、延迟与口径变化 |

#### 01.3 职责边界与相邻角色

| 事项 | 分析师的位置 | 主要协作者 | 说明 |
| --- | --- | --- | --- |
| 业务问题与决策 | 协助澄清 | 产品经理、业务负责人 | 决定由负责人做出 |
| 指标定义 | 主导 | 产品经理、数据工程师 | 共同确认口径 |
| 埋点与采集 | 设计与验证 | 开发者负责实现 | 埋点是功能的一部分，见 15 章 |
| 数据管道与数据模型 | 协作 | 数据工程师主导 | 见[《数据工程师》](17-数据工程师.md) |
| 实验平台 | 使用与改进 | 平台工程师、数据工程师 | 见[《平台工程师与研发效能》](14-平台工程师与研发效能.md) |
| 预测模型与算法 | 协作 | 算法工程师、数据科学家 | 见[《算法与机器学习工程师》](18-算法与机器学习工程师.md) |
| 用户研究 | 协作 | 用户研究员 | 定量与定性互相解释，见[《用户研究员》](02-用户研究员.md) |

几组容易混淆的角色：

- **数据分析师与数据科学家**：分析师侧重回答业务问题、建立指标与实验；数据科学家通常更深入统计建模与机器学习。许多公司两者职责重叠。
- **数据分析师与数据工程师**：分析师使用数据回答问题；数据工程师建设采集、存储与加工数据的系统。
- **数据分析师与商业智能开发**：商业智能侧重报表与看板的建设和维护。

**本章练习**：列出你所在团队最近的三个决定，分别说明当时使用了什么数据、属于哪类分析问题、证据是否足以支持结论。

<a id="ch02"></a>

### 02 能力坐标：横向分支与纵向深度

#### 02.1 十个横向分支

1. **问题定义**：把业务问题转化为可回答的分析问题。
2. **指标设计**：指标体系、口径、北极星与护栏指标。
3. **数据采集**：埋点设计、身份关联、数据验证。
4. **数据处理**：SQL、数据清洗、数据建模基础。
5. **描述与诊断**：漏斗、留存、分群、归因。
6. **实验**：对照实验的设计、分析与解读。
7. **因果推断**：在无法实验时估计因果影响。
8. **统计基础**：分布、置信区间、假设检验、功效。
9. **沟通与可视化**：报告、看板与讲述。
10. **数据治理**：质量、隐私、口径管理与自助分析。

#### 02.2 六级纵向深度

| 深度 | 能力表现 | 典型证据 |
| --- | --- | --- |
| D1 理解与协助 | 能写查询、制作报表，理解基本指标 | 报表、查询脚本 |
| D2 独立完成 | 独立完成一个分析问题，从定义到结论 | 分析报告、埋点方案 |
| D3 负责结果 | 负责一个产品领域的指标体系与实验 | 指标体系、实验记录、决策影响 |
| D4 系统与跨团队 | 统一多个团队的指标口径与分析标准 | 统一的指标层、跨团队实验规范 |
| D5 方法与机制 | 建立组织的实验平台、指标治理与分析规范 | 实验平台、治理流程、培训 |
| D6 创新与影响 | 提出新的分析或实验方法并验证 | 公开研究、方法贡献 |

#### 02.3 成长中的常见偏差

- 先拿数据再找问题，产出大量没有决策价值的分析。
- 把相关关系当作因果关系。
- 不检查数据质量就下结论。
- 只报告平均值，忽视分布、分群与异常。
- 结论表述过度确定，不说明不确定性与局限。
- 指标被当作考核目标，开始被“优化”而失去意义。

## 第二篇：核心工作方法

<a id="ch03"></a>

### 03 从业务问题到分析问题

#### 03.1 先问决策

收到一个分析需求，先了解：这个分析要支持什么决定？什么时候需要？不同的结论会导致不同的行动吗？如果无论结果如何决定都不会改变，这个分析的价值就很有限。

#### 03.2 把问题具体化

| 模糊的问题 | 具体的分析问题 |
| --- | --- |
| 简历分析功能效果怎么样 | 上线后 4 周，使用过分析的学生与未使用者相比，修改简历并投递的比例有何差异？其中有多少可归因于功能本身？ |
| 用户为什么流失 | 注册后 7 天内未完成首次分析的用户，在哪一步停止？不同来源渠道的停止位置是否不同？ |
| 要不要做岗位推荐 | 现有用户中，有多少人在完成分析后搜索岗位？他们的搜索行为有什么特点？ |

#### 03.3 提出假设

在分析前写下假设与预期，例如“完成率下降主要来自移动端的上传失败”。假设让分析有方向，也能防止在大量数据中“碰巧”找到某个模式就当作结论。

**本章练习**：把一个模糊的分析需求改写为具体的分析问题，写出要支持的决定、假设、需要的数据与预期的分析方法。

<a id="ch04"></a>

### 04 指标体系与口径

#### 04.1 指标的层次

- **北极星指标**：概括产品为用户创造的核心价值，例如“每周完成简历修改并投递的学生数”。
- **输入指标**：团队能直接影响、并推动北极星指标的指标，例如分析完成率、建议采纳率。
- **护栏指标**：不能被牺牲的指标，例如错误建议的投诉率、单次分析成本、页面性能。
- **诊断指标**：用于定位问题的细分指标，例如各步骤的转化率。

Google 的 HEART 框架提供了从产品目标到信号再到指标的映射方法，可以帮助建立以用户为中心的指标。[B01](#ref-b01)

#### 04.2 口径定义

每个指标都需要完整的定义：

```text
指标名称：分析完成率
定义：在统计周期内，提交分析请求的用户中，至少有一次分析成功完成的用户比例
分子：周期内至少一次分析状态为“完成”的去重用户数
分母：周期内至少提交一次分析请求的去重用户数
时间窗口：按自然周，北京时间
去重规则：按用户编号；未登录用户不计入
排除条件：内部测试账号；被判定为异常流量的请求
数据来源：分析任务表（权威），埋点数据用于核对
负责人与更新记录：
```

同一个名称的指标，在不同报表中口径不同，是团队争论与错误决策的常见原因。口径变化时要记录，并说明变化前后的数据能否比较。

**本章验收**：为一个产品建立指标树（北极星、输入、护栏、诊断），为其中 5 个指标写出完整的口径定义，请两位同事独立计算同一组数据，核对结果是否一致。

<a id="ch05"></a>

### 05 埋点与数据采集

#### 05.1 埋点方案

埋点方案是分析师与开发者之间的契约：采集哪些事件、何时触发、包含哪些属性、属性的取值与类型。

| 事件 | 触发时机 | 关键属性 |
| --- | --- | --- |
| 简历上传成功 | 文件上传并通过校验后 | 文件类型、大小、入口 |
| 分析请求提交 | 用户点击开始分析并被系统受理后 | 分析编号、简历版本、目标岗位类型 |
| 分析完成 | 系统生成结果后（服务端事件） | 分析编号、耗时、建议数量、模型版本 |
| 建议标记 | 用户标记建议有用或不适用 | 分析编号、建议编号、标记类型 |
| 重新分析 | 用户修改后再次分析 | 分析编号、前一次分析编号 |

#### 05.2 设计要点

- **命名一致**：使用统一的命名规则，例如“对象＋动作”，避免同一事件多种叫法。
- **服务端与客户端**：关键的业务结果（完成、支付）以服务端记录为准；客户端事件适合记录交互，但可能丢失或重复。
- **身份关联**：处理匿名用户登录后的身份合并、多设备与多账号。
- **版本**：记录应用版本、实验分组、模型版本，便于分析变化的原因。
- **验证**：上线前在测试环境验证事件是否按预期触发、属性是否正确。
- **隐私**：只采集必要的数据，不在埋点中记录敏感个人信息（见 14 章）。

**本章验收**：为一个功能编写埋点方案，与开发者一起在测试环境验证所有事件，记录发现的问题并修正。

<a id="ch06"></a>

### 06 描述与诊断分析

#### 06.1 常用分析方法

| 方法 | 回答的问题 |
| --- | --- |
| 漏斗分析 | 用户在流程的哪一步流失 |
| 留存分析 | 用户是否持续使用，按首次使用时间分组比较 |
| 分群对比 | 不同用户群体的行为有什么差异 |
| 分布分析 | 数值的分布形态、长尾与异常 |
| 路径分析 | 用户实际经过哪些页面与操作 |
| 归因分析 | 结果与哪些渠道或触点有关 |

#### 06.2 常见的陷阱

- **辛普森悖论**：分组后的趋势与整体趋势相反。例如两个渠道的转化率都上升，但由于低转化渠道的用户占比增加，整体转化率反而下降。[B02](#ref-b02) 发现整体指标变化时，按主要维度拆开检查。
- **幸存者偏差**：只分析留下来的用户，忽视已经离开的用户。
- **平均值的误导**：少数极端值会拉动平均值，同时报告中位数与分位数。
- **季节与外部因素**：招聘季、节假日、市场变化都会影响指标。
- **口径与采集变化**：指标的突然变化可能来自埋点或口径的改变，而不是用户行为。

**本章练习**：选择一个指标的近期变化，按渠道、设备、新老用户等维度拆解，判断变化来自哪里，并检查是否存在辛普森悖论或采集问题。

<a id="ch07"></a>

### 07 实验设计与分析

#### 07.1 为什么需要实验

产品改动上线后指标上升，可能是改动的作用，也可能是季节、市场活动或其他改动的影响。随机对照实验（A/B 测试）把用户随机分为对照组与实验组，使两组在其他方面平均而言相同，从而能够估计改动的因果影响。Kohavi 等人的著作系统介绍了在线对照实验的方法与陷阱。[B03](#ref-b03)

#### 07.2 设计实验

| 要素 | 内容 |
| --- | --- |
| 假设 | 改动是什么，预期影响哪个指标，方向与大致幅度 |
| 主要指标 | 事先确定一个主要的判断指标 |
| 护栏指标 | 不能被损害的指标 |
| 随机单位 | 按用户、会话还是请求分组，避免同一用户看到两个版本 |
| 样本量与时长 | 根据基线、波动与希望发现的最小差异计算，并覆盖完整的使用周期 |
| 分流比例 | 通常各半；风险较高时可以先小比例 |

估算样本量的一个常用经验公式是：在 5% 显著性水平与 80% 统计功效下，每组大约需要 16σ²/Δ² 个样本，其中 σ² 是指标的方差，Δ 是希望发现的最小差异。例如基线转化率为 10%（方差约为 0.09），希望发现 1 个百分点的绝对提升，每组约需 16 × 0.09 ÷ 0.0001 ≈ 14400 个用户。这只是粗略估算（公式的推导与适用条件见 [B03](#ref-b03)），正式实验应使用专门的计算工具。

#### 07.3 分析与检查

- **先检查实验是否有效**：两组的实际比例是否与设计一致。比例明显偏离（样本比例失衡）说明分流或数据有问题，此时结果不可信，应先排查原因。[B04](#ref-b04)
- **不要反复查看并提前停止**：频繁检查结果，在“显著”时停止，会大大增加误报。如果需要持续监控，应使用专门的序贯检验方法。
- **多重比较**：同时检验很多指标或很多分群，总会有一些“显著”是偶然的。事先确定主要指标，分群结果作为探索性发现。
- **新奇效应与学习效应**：用户对新变化的短期反应可能与长期不同，观察足够长的时间。
- **相互影响**：在社交、市场类产品中，实验组用户的行为可能影响对照组，需要特殊的设计。

#### 07.4 方差缩减

使用实验前的数据作为协变量，可以减少指标的波动，用更少的样本发现同样大小的差异。这种方法常被称为 CUPED。[B05](#ref-b05)

**本章验收**：为一个产品改动设计实验方案，包括假设、主要与护栏指标、随机单位、样本量估算与时长；实验结束后先做有效性检查，再报告结果与不确定性。

<a id="ch08"></a>

### 08 因果推断与观察性研究

#### 08.1 不能实验时怎么办

有些问题无法用随机实验回答：改动已经全量上线、随机分组不道德或不可行、流量太小。这时可以使用观察性数据的因果推断方法，但每种方法都依赖特定的假设。

| 方法 | 思路 | 关键假设 |
| --- | --- | --- |
| 双重差分 | 比较处理组与对照组在改动前后的变化差异 | 没有改动时两组的趋势平行 |
| 断点回归 | 比较规则阈值两侧的个体 | 阈值附近的个体在其他方面相似，且无法精确操纵自己位于哪一侧 |
| 工具变量 | 利用只通过处理影响结果的外部因素 | 工具与处理相关，且只通过处理影响结果 |
| 匹配与倾向得分 | 为处理组寻找相似的对照个体 | 所有影响处理与结果的因素都已被观测到 |

Hernán 与 Robins 的《Causal Inference: What If》是一本免费的因果推断教材，系统讲解这些方法与假设。[B06](#ref-b06)

#### 08.2 诚实地表达

观察性研究的结论比实验弱。报告时说明使用的方法、依赖的假设、假设是否合理、对假设被违反时结果的敏感程度。“使用 AI 分析的学生投递成功率更高”不能直接说明是 AI 分析的作用，因为愿意使用新功能的学生可能本来就更积极。

**本章练习**：为一个已经全量上线的功能，选择一种观察性方法估计其影响，写出方法、假设、检验假设的方式与结论的局限。

<a id="ch09"></a>

### 09 可视化与沟通

#### 09.1 选择合适的图表

- 比较数值：条形图。
- 随时间的变化：折线图。
- 分布：直方图、箱线图。
- 部分与整体：堆叠条形图；类别很少时可以用饼图。
- 关系：散点图。

图表要标明单位、时间范围、数据来源与口径，避免误导性的坐标轴截断。

#### 09.2 报告的结构

结论先行：第一段说明发现了什么、对决定意味着什么、建议怎样做；然后提供支撑的证据与方法；最后说明局限与下一步。避免把分析过程按时间顺序全部罗列。

#### 09.3 表达不确定性

用区间而不是单个数值表达估计结果；区分“显著”与“重要”：统计上显著的差异可能小到没有业务意义，统计上不显著不等于没有影响，可能只是样本不足。

#### 09.4 看板与分析报告的区别

看板用于持续监控已知的指标，回答“现在怎么样”；分析报告用于回答具体的问题，回答“为什么”与“怎么办”。看板不能代替分析，过多的看板会让人难以找到重点。

**本章练习**：把一份分析报告改写为结论先行的一页摘要，用一张图表展示核心证据，并用区间表达估计结果。

## 第三篇：专项与进阶

<a id="ch10"></a>

### 10 数据质量与可信度

#### 10.1 常见的数据问题

| 问题 | 表现 | 检查方式 |
| --- | --- | --- |
| 缺失 | 某些事件或字段没有数据 | 按时间与来源监控数据量 |
| 重复 | 同一事件被记录多次 | 按唯一标识去重检查 |
| 延迟 | 数据到达较晚，近期数据不完整 | 检查数据新鲜度 |
| 口径变化 | 埋点或计算逻辑改变 | 记录变更，对比前后差异 |
| 异常流量 | 机器人、测试账号、攻击 | 识别与排除规则 |
| 不一致 | 不同来源的同一指标不同 | 与权威来源对账 |

#### 10.2 建立信任

- 关键指标与权威的业务数据对账（例如埋点中的完成数与任务表中的完成数）。
- 为关键数据设置自动化的质量检查与告警。
- 在报告中注明数据的已知问题。
- 与数据工程师一起建立数据契约，约定数据的结构与质量（见[《数据工程师》](17-数据工程师.md)）。

**本章练习**：为三个关键指标建立与权威数据的每日对账，设置差异超过阈值的告警。

<a id="ch11"></a>

### 11 自助分析与语义层

#### 11.1 让更多人能够分析

分析师的时间有限。自助分析让产品经理、运营与开发者能自己回答简单的问题：提供整理好的数据集、统一的指标定义与易用的工具。

#### 11.2 语义层

语义层集中定义指标与维度，各种报表和工具都从这里获取，保证同一个指标在各处口径一致。没有统一定义时，每个人各自写查询，口径很快就会分化。

#### 11.3 自助的护栏

- 提供经过验证的数据集，而不是让所有人直接查询原始数据。
- 对关键指标只提供统一定义的版本。
- 提供培训与示例。
- 重要决策使用的分析由分析师审核。

**本章练习**：为一个产品领域整理一份自助数据集与 10 个统一定义的指标，编写使用说明，邀请三位非分析人员试用并收集反馈。

<a id="ch12"></a>

### 12 预测与建模基础

#### 12.1 常见的预测问题

- **时间序列预测**：下个月的分析需求量、服务器负载。
- **分类**：哪些用户可能流失、哪些申请可能被接受。
- **分群**：根据行为把用户分成几类。

#### 12.2 使用要点

- 先建立简单的基线（例如上周同期、移动平均），复杂模型需要证明比基线更好。
- 用模型训练时没有见过的数据评估效果，按时间划分训练与测试数据。
- 关注模型在不同群体上的表现差异。
- 说明预测的不确定性。
- 预测用于支持决定，而不是自动替代判断。

当问题需要复杂的模型、生产环境的部署与持续维护时，与算法工程师合作（见[《算法与机器学习工程师》](18-算法与机器学习工程师.md)）。

**本章练习**：为一个业务指标建立简单基线与一个预测模型，用最近的数据比较两者的误差，判断复杂模型是否值得使用。

<a id="ch13"></a>

### 13 AI 产品的分析

#### 13.1 AI 功能的度量

AI 功能的效果需要多个维度一起看：

| 维度 | 示例指标 |
| --- | --- |
| 采用 | 使用 AI 功能的用户比例 |
| 质量 | 评测集得分、人工抽检结果、用户反馈 |
| 采纳 | 用户接受、修改或拒绝结果的比例 |
| 结果 | 使用后的任务完成情况，例如修改后投递的比例 |
| 信任 | 重复使用率、反馈中的信任问题 |
| 成本与延迟 | 单次使用的成本、等待时间 |
| 风险 | 错误、投诉与安全事件 |

#### 13.2 分析中的特殊问题

- 模型、提示词与检索数据的版本都会影响结果，分析时需要按版本拆分。
- 用户反馈（点赞、点踩）样本有偏差，只有少数用户会主动反馈。
- 离线评测与线上效果可能不一致，需要两者结合。
- AI 功能的实验同样需要护栏：质量提高可能伴随成本或延迟的上升。

#### 13.3 用 AI 辅助分析

AI 工具可以帮助编写查询、解释数据和起草报告，但需要注意：生成的查询可能口径不对或逻辑错误；对数据的“解释”可能是编造的；不要把敏感数据发送给未经评估的外部服务。所有结论都要回到数据核对。

**本章练习**：为一个 AI 功能建立包含上表七个维度的指标看板，按模型版本拆分，并说明每个指标的数据来源与局限。

<a id="ch14"></a>

### 14 隐私、伦理与数据治理

#### 14.1 数据最小化与访问控制

只采集与保留分析所需的数据；分析时尽量使用聚合或去标识的数据；对包含个人信息的数据集设置访问控制与审计。个人信息处理的合法性基础与保留期限由法务确认。

#### 14.2 去标识与差分隐私

删除姓名、手机号等直接标识，并不一定能防止重新识别：多个看似无害的字段组合起来可能定位到个人。差分隐私通过在统计结果中加入经过设计的噪声，提供可量化的隐私保护。美国国家标准与技术研究院在 2025 年发布的 SP 800-226 指南，帮助评估差分隐私方案实际提供了什么保证。[B07](#ref-b07)

#### 14.3 分析的伦理

- 不利用分析操纵用户做出违背其利益的选择。
- 关注分析与模型对不同群体的影响，避免强化不公平。
- 实验涉及对用户有重大影响的内容时，评估潜在的伤害。

**本章练习**：审查一个数据集中的字段，识别直接标识与可能的间接标识，设计去标识方案并评估重新识别的风险。

## 第四篇：协作、实战与成长

<a id="ch15"></a>

### 15 与开发者的协作接口

#### 15.1 分析师应提供给开发者的内容

| 内容 | 最低要求 | 常见缺失 |
| --- | --- | --- |
| 埋点方案 | 事件、触发时机、属性与取值 | 只说“统计一下点击” |
| 指标口径 | 清楚的定义 | 开发者自行理解，与报表不一致 |
| 验证方法 | 怎样确认埋点正确 | 上线后才发现数据有误 |
| 实验需求 | 分组方式、开关、记录的分组信息 | 分组信息没有记录在事件中 |

#### 15.2 开发者应提供给分析师的内容

业务数据的结构与含义、系统中的权威数据来源、埋点实现的限制、版本发布与配置变更的记录（便于解释指标变化）。

#### 15.3 一起保证数据可信

把埋点当作功能的一部分：写在需求中，在测试中验证，在代码评审中检查。重要的业务事件优先从服务端记录。发布可能影响数据的变更时，提前通知分析师。

<a id="ch16"></a>

### 16 开发者怎样用数据做决定

#### 16.1 独立开发者的最小数据实践

- 定义一个北极星指标和三个输入指标，写下口径。
- 为核心流程的每一步记录服务端事件。
- 每周查看一次核心漏斗与留存。
- 新功能上线前写下预期，上线后对照。
- 流量不足以做实验时，用前后对比加用户访谈，并承认因果证据较弱。

#### 16.2 外包项目中的数据

在需求阶段与客户约定：要回答哪些业务问题、需要哪些报表、指标怎样定义。很多客户在系统上线后才发现“没有想要的数据”，而补采历史数据通常是不可能的。

#### 16.3 技术背景的常见偏差

- 记录大量事件，却没有明确要回答的问题。
- 只看平均值和总数。
- 把相关关系当作因果关系。
- 不检查数据质量就相信图表。

### 17 贯穿实战：简历分析功能的指标与实验

本章展示一次完整的指标与实验工作。数字均为示意。

#### 17.1 指标树

| 层次 | 指标 |
| --- | --- |
| 北极星 | 每周完成简历修改并投递的学生数 |
| 输入 | 分析完成率、建议采纳率、修改后重新分析率 |
| 护栏 | 错误建议反馈率、单次分析成本、分析耗时的第 95 百分位 |
| 诊断 | 上传成功率、解析失败率、各类建议的采纳率 |

#### 17.2 实验：建议的呈现方式

- **假设**：用“问题＋原因＋修改示例”呈现建议，比只列出问题能提高建议采纳率。
- **主要指标**：建议采纳率（被标记为有用或被实际修改的建议比例）。
- **护栏指标**：分析完成率、页面加载时间、错误建议反馈率。
- **随机单位**：用户，保证同一用户始终看到同一版本。
- **样本量**：基线采纳率约 20%，希望发现 2 个百分点的提升，按经验公式每组约需 16 × 0.16 ÷ 0.0004 = 6400 名用户；按当前流量约需三周，并覆盖完整的周期。

#### 17.3 结果

1. **有效性检查**：两组用户数之比接近设计的 1:1，样本比例检查通过。
2. **主要指标**：实验组采纳率比对照组高约 4 个百分点，95% 置信区间不包含 0。
3. **护栏**：分析完成率无明显差异；页面加载时间略有增加但在可接受范围内；错误建议反馈率无明显差异。
4. **分群探索**：提升在首次使用的学生中更明显。由于这是事后的分群发现，作为下一次实验的假设，而不作为确定结论。

#### 17.4 决定与跟进

产品经理决定全量上线新的呈现方式。分析师在报告中说明：结论针对建议采纳率，对最终投递与面试结果的影响需要更长时间观察；上线后继续监控北极星指标与护栏指标。

- [ ] 结论先行，表达不确定性与局限。

## 附录 C：常见误读、内容边界与修订记录

### C.1 常见误读与准确表述

| 容易误读的说法 | 更准确的表述 |
| --- | --- |
| 数据越多越好 | 没有明确问题的数据难以产生价值，还带来隐私与成本风险 |
| 指标上升说明改动有效 | 可能来自季节、渠道或其他改动，需要实验或因果分析 |
| 统计显著就说明效果重要 | 显著不等于有业务意义，也需要看效果大小 |
| 不显著说明没有效果 | 可能只是样本不足 |
| 平均值能代表整体 | 需要看分布、中位数与分群 |
| 看板可以代替分析 | 看板监控已知指标，分析回答具体问题 |
| 实验中途显著就可以停止 | 反复查看并提前停止会增加误报 |
| 去掉姓名就是匿名数据 | 多个字段组合仍可能重新识别个人 |
| AI 能自动完成分析 | AI 可以辅助，口径与结论需要人核对 |
